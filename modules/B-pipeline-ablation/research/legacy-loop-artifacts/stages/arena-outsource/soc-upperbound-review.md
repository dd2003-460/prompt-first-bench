## §1 任务一：审「46/10 拍法」的系统性偏差

原估算：pending 77 中「约 46 个 knowledge/given 可翻」+ degraded 31 中「约 10 个可救」→ 174+46+10=230 → 0.813。

**偏差 1：混淆「未核验」与「可核验」（最严重，conf 0.9）**
pending 77 全部 evidence/retrieval_sources 为空 = 尚未跑核验，不是核验失败。「46 可翻」把"还没核"当成"能核"。节点 pending 可能只因状态机没轮到它、或当时通道挂，与它本身可不可核无关。用"未核验"集合直接拍"可翻"数，逻辑前提就错了。

**偏差 2：场景混用（内部矛盾，conf 0.9）**
- 「46 个 knowledge/given 可翻」隐含前提 = **search 通道挂**（所以只数 knowledge/given）。
- 「10 个 degraded 可救」：degraded 共 31 = knowledge 3 + search 28。knowledge degraded 最多 3 个，所以「10 可救」**必然包含 ≥7 个 search degraded**，这又隐含前提 = **search 通道修好**。
- 同一个 0.813 里，46 假设通道挂、10 假设通道通 → **两个场景被混在一个点估计里**。这是 0.813 的根本逻辑缺陷。

**偏差 3：乐观偏差（模糊算进可翻，conf 0.8）**
人拍"可翻"数时倾向把模糊的算进可翻。degraded 31 抽查（按 evidence 文本模式，非逐条终判）：约 2 条"检索失败 all 5 failed"（通道类，可救）、约 27 条"逻辑自洽但无来源支持/经验事实"（平台内部参数，**通道修好也无公开来源**）、2 条其他（含 N250 evidence 为空的可推导计算类）。真正"可救"远少于 10——"无来源支持"类即使通道全修也翻不了。

**偏差 4：source 字段 ≠ 可核性（conf 0.85）**
「knowledge/given 类可翻」假设 source=knowledge 就可核。但 N10（source=knowledge）的 claim 是"阈值 0.85 经验参数"，knowledge 通道也核不了——**source 标的是期望来源类型，不是可核性**。可核性取决于 claim 本身（定义/计算类可核，经验参数类不可核），与 source 字段无必然关系。

**偏差 5：点估计而非区间 + 隐含 100% 翻成功率（conf 0.85）**
拍法给点估计 0.813，无不确定区间；且隐含"可翻节点 100% 翻成功"。实际 knowledge 通道通过率 98.3%（非 100%），翻本身有失败率。

**偏差 6：failed 1 未交代（conf 0.7）**
N195（search）evidence = 量纲错误/概念混淆 = claim 本身逻辑错，不可翻。0.813 没数它（对），但没说明"为什么排除"，属口径不透明。

> **小结**：0.813 不是"偏乐观"那么简单，它是**场景混用 + 前提错误**的产物。conf 0.9

## §2 任务二：更严谨的估算框架（公式 + 字段名 + 区间）

### 2.1 记号（字段名直接对应 checkpoint）

| 记号 | 含义 | 取值 |
|---|---|---|
| `T` | 总节点数 | 283 |
| `V` | 当前 verified 数（`status=verified`） | 174 |
| `P_s` / `D_s` / `F_s` | source=s 的 pending/degraded/failed 数 | 见 §0 交叉表 |
| `H_s` | source=s 历史通过率 = `V_s/(V_s+D_s+F_s)` | knowledge 0.983 / given 1.0 / search 0 |
| `H_s^L, H_s^U` | `H_s` 的 Wilson 95% CI 下/上界 | 见 §0 |
| `R_s` | **source=s 节点中"有公开来源或可推导"的比例**（可核率） | **需 arena/core 提供**，见 §4 |
| `flip_s` / `recov_s` | pending/degraded 的翻/救概率 | 见下 |

### 2.2 上限公式

```
cov_max = ( V + U_P + U_D ) / T
U_P = Σ_s P_s × flip_s        # pending 最多可翻
U_D = Σ_s D_s × recov_s        # degraded 最多可救
```

**flip_s / recov_s 的取值规则（按通道场景）：**

- **knowledge / given（通道可用）**：`flip_s = recov_s = H_s`，区间用 `[H_s^L, H_s^U]`。
- **search（关键分叉）**：
  - **场景 A（search 通道仍挂）**：`flip_search = recov_search = 0`（拿不到来源）。
  - **场景 B（search 通道修好）**：`flip_search = recov_search = R_search`（= 可核率，由 claim 是否有公开来源决定，**不是** H_search，因为 H_search=0 是通道故障的假象）。

### 2.3 区间推导（代入 §0 数值）

**场景 A（search 通道仍挂）：**
```
U_P^L = 45×0.9505 + 5×0.4385 + 27×0 = 44.96
U_P^U = 45×0.9941 + 5×1.0    + 27×0 = 49.73
U_D^L = 3×0.9505  + 0        + 28×0 = 2.85
U_D^U = 3×0.9941  + 0        + 28×0 = 2.98
cov_max^A = [ (174+44.96+2.85)/283 , (174+49.73+2.98)/283 ]
          = [ 221.8/283 , 226.7/283 ] = [ 0.784 , 0.801 ]
```
> **场景 A 上限 ≈ [0.784, 0.801]，上界 0.801 < 0.813。** conf 0.85
> 即：即使 knowledge/given 的 pending+degraded 全部 100% 翻/救，也只得 227（0.802），**到不了 0.813**。0.813 必然数了 search 节点 → 印证 §1 偏差 2（场景混用）。

**场景 B（search 通道修好，R_search 为变量）：**
```
cov_max^B = [ (221.8 + 55×R_search^L)/283 , (226.7 + 55×R_search^U)/283 ]
```
（55 = P_search 27 + D_search 28）

| R_search（可核率） | cov_max^B 下界 | cov_max^B 上界 | 上界节点数 | 下界节点数 | 过 0.898?（V≥255） |
|---|---|---|---|---|---|
| 0.0（全不可核） | 0.784 | 0.801 | 226.7 | 221.8 | 否 |
| 0.3 | 0.842 | 0.859 | 243.2 | 238.3 | 否 |
| 0.5 | 0.881 | 0.898 | 254.2 | 249.3 | 否（上界差 0.8） |
| 0.6 | 0.900 | 0.918 | 259.7 | 254.8 | 上界口径是 / 下界口径差 0.2 |
| 0.8 | 0.939 | 0.957 | 270.7 | 265.8 | 是 |

> **过 gate 0.898（V≥255）需 R_search ≥ 0.514（上界口径）/ ≥ 0.603（下界口径，稳健）。** conf 0.85
> 注：254/283=0.8975<0.898，255/283=0.9011≥0.898，故 gate 实际要求整数 V≥255；节点数列是连续期望值，保留一位小数以示非整数。

### 2.4 框架要点

1. **上限是区间不是点**：[下界, 上界] 来自 H_s 的 CI 与 R_s 的估计误差，点估计只作中位参考。
2. **两个场景分开报**：场景 A（不修通道）与场景 B（修通道）必须分开，禁止混算。
3. **H_search 禁用**：search 的 H=0 是通道故障假象，修通道后必须改用 R_search（claim 可核率），不得沿用 H。
4. **R_s 是唯一外生输入**：框架内所有量（V/P/D/F/H）都从 checkpoint 直接算出，唯一需要外部提供的是 R_s——这正是对接 arena/core 产出的接口（§4）。
5. **failed 单列**：F_s 不进 U_P/U_D（不可翻），只作口径说明。
6. **区间仅含参数不确定性**：[下界, 上界] 来自 H_s 的 CI 与 R_s 的估计误差，**不含分布漂移风险**——把 H_s（verified+degraded+failed 的历史通过率）外推到 pending 节点，隐含「pending 与 verified 同分布」假设。若状态机先核易的、留难的是 pending，则 pending 实际翻率 < H_s，场景 A 上界 0.801 仍偏乐观。conf 0.8

## §3 任务三：gate 0.898 可达性判断

**gate 要求**：cov = verified/total ≥ 0.898，即 V ≥ 0.898×283 = 254.1 → **整数 V ≥ 255**。当前 V=174，缺口 81 个节点。conf 0.95

**可达性分场景判断：**

| 场景 | 上限（§2 区间） | 过 0.898? | 判断 |
|---|---|---|---|
| A：search 通道不修 | [0.784, 0.801] | **否**（差约 28 节点） | 不可达，且差距大 |
| B：修通道 + R_search≤0.5 | ≤0.898 | **否**（上界刚好触线） | 不可达 |
| B：修通道 + R_search≥0.6 | [0.900, 0.918] | **是**（上界口径） | 可达，但依赖 R_search 真 ≥0.6 |
| B：修通道 + R_search≥0.8 | [0.939, 0.957] | **是**（下界也过） | 稳健可达 |

**关键判断：**

1. **不修通道，0.898 绝对不可达**（上限 0.801，差约 28 节点）。任何"只重跑 verify、不动通道"的方案都到不了 gate。conf 0.9
2. **修通道后是否可达，完全取决于 R_search（search 节点可核率）**，而 R_search 目前**没有任何实测数据**——这正是 arena/core 两路要补的。conf 0.9
3. **arena 已产出的交叉验证**（`soc-gap-20261116.md`）估计 search 类节点中"参数估计类 35 + 设计类 9 = 44 个基本无公开来源"，"公式/定义类 30 个有来源但不可核本题取值"，"其他 3 个少数有"。若采信，按 arena 类型占比折算 search 55（pending 27 + degraded 28）构成，R_search ≈ (17.8×0.5 + 4.1×0.5)/55 ≈ 0.20（公式定义类只能核定义不能核参数、其他类少数有，均按 0.5 折；参数估计/设计类无公开来源按 0）→ **落在"不可达"区间**。conf 0.6（arena 估计本身 conf 0.78，且是粗分类 + 占比折算假设）
4. **0.813 这个数在场景 A 下连上界都到不了**（0.801），所以"0.813 是现实上限"这句话本身不成立——它只在"修通道 + R_search∈[0.06, 0.15]（上/下界口径）"的混合场景下才成立，而那个场景没被明确声明。conf 0.85

**gate 本身是否设错？建议：**

- **gate 口径没错，错的是把"通道故障"当成"claim 不可核"来算 cov**。cov = verified/total 的口径本身合理（全量核验率），问题在于 search 通道的 56 个节点 0 通过是**基础设施故障**，不是这些 claim 真的不可核。用全量 cov 衡量"核验能力"会被单通道故障绑架。conf 0.85
- **建议一（推荐）：cov 分通道报 + 主 gate 用"可核子集"**。把 cov 拆成 `cov_knowledge`、`cov_search`、`cov_given` 三个子指标，主 gate 改为"可核子集 cov ≥ 0.898"，其中"可核子集" = 排除掉 arena 判定"基本无公开来源"的节点（参数估计类 + 设计类）。这样 gate 衡量的是"在能核的节点上核了多少"，而不是"通道挂了拖垮了多少"。注：子集定义现基于 arena 粗分类（conf 0.78），正式定义需 core 逐条分类复核。conf 0.8
- **建议二（保守）：保留全量 cov，但加"通道可用"前置条件**。gate 通过的前提是 search 通道实测可用（curl 200 且返回有效结果），通道不可用时 gate 自动挂起（不判失败），等通道修好再重跑。避免在通道故障期间反复重跑 verify 刷 cov。conf 0.75
- **建议三（不推荐）：降 gate 阈值**。把 0.898 降到 0.80 能过，但这是用"降标准"掩盖"通道故障"，会丢失"search 类节点必须核验"的要求，不推荐。conf 0.6

> **结论：gate 0.898 在"不修通道"下不可达；修通道后是否可达取决于 R_search（当前无实测，arena 粗估偏"不可达"）；gate 口径本身合理，但建议改成"可核子集 cov"或加"通道可用"前置条件，避免被单通道故障绑架。** conf 0.8

## §4 任务四：与 core / arena 两路产出的对接接口

**核心原则**：本框架（§2）内所有量（V/P/D/F/H_s/CI）都从 checkpoint `sm-soc-r1.json` 直接算出，**唯一外生输入是 R_s（可核率）**。R_s 不是拍出来的，必须来自 core/arena 的逐条分类产出。下面写清"等他们的文件 X 出现后，把 Y 字段代入公式 Z"。

### 4.1 对接 core team（pending 77 逐条分类）

**等文件**：`experiments/stage-ablation/loop-artifacts/stages/arena-outsource/soc-pending77-final.md`
（core 任务书要求 method-reviewer + logic-reviewer 双人独立分类后，lead 裁决出 final，含最终 A/B/C/D/E 计数 + 分歧表）

**core 的分类口径**（来自其任务书）：
- `A-可翻`：source=given 且 claim 可直接核验（有明确数值/日期/定义，evidence 缺失但可补）
- `B-需检索`：需外部来源（search_query 非空或 retrieval_sources 为空的事实断言），来源存在但通道挂
- `C-难核`：claim 模糊/复合/依赖主观判断，公开来源基本不存在
- `D-可救`：degraded，evidence 部分存在、只差补强
- `E-弃`：degraded，claim 本身站不住

**代入公式**（等 final 文件出现后执行）：

```
# 从 soc-pending77-final.md 读：A/B/C/D/E 计数 + 「分类 × source」交叉表
# core 的 B 类定义不限 source（pending 77 中有 12 个 knowledge 节点 search_query 非空，可落入 B 类）
# 故分子只数 B 类中 source=search 的部分：
R_search = (B∩search + D_search) / (P_search + D_search)
         = (B∩search + D_search) / (27 + 28)
# B∩search = 交叉表中 B 类且 source=search 的节点数
# D_search = D 类（可救）中 source=search 的节点数
# C 类（无公开来源）与 A 类（source=given）不进 R_search

# 代入 §2 场景 B 公式
cov_max^B = [ (221.8 + 55×R_search^L)/283 , (226.7 + 55×R_search^U)/283 ]
```

**具体步骤**：
1. 读 `soc-pending77-final.md` 的「最终 A/B/C/D/E 计数」表**和「分类 × source」交叉表**。
   - **若缺交叉表，接口不可执行**：需向 core 补要——core 的 B 类定义不限 source，仅 A/B/C/D/E 总数无法拆出 B∩search。
2. 取 B∩search（B 类且 source=search）→ R_search 分子核心。
3. 取 D_search（D 类且 source=search）→ 加进 R_search 分子（degraded 可救 = 通道修好后可翻）。
4. 计算 R_search = (B∩search + D_search) / 55，代入 §2 场景 B 公式，得出 cov_max^B 区间。
5. 对比 0.898：若 cov_max^B 上界 < 0.898 → 修通道也不可达，gate 需改口径（§3 建议一）；若 ≥ 0.898 → 可达，但需确认 R_search 估计的置信度。

**注意**：core 的 A 类（source=given 可翻）不进 R_search，它进 §2 场景 A/B 的 given 项（flip_given = H_given = 1.0）。C 类（无公开来源）不进分子。B/C 类**不一定**全是 source=search（B 类定义不限 source，pending 77 中有 12 个 knowledge 节点 search_query 非空可落入 B 类），只有交叉表中的 search 部分才进 R_search。conf 0.85

### 4.2 对接 arena team（来源可达性 + 上限交叉验证）

**等文件**：`experiments/stage-ablation/loop-artifacts/stages/arena-outsource/soc-gap-20261116.md`（**已产出**）

**arena 已提供的可代入字段**：

- §3 上限交叉验证：arena 已按节点类型给出"有无公开来源"粗分类（参数估计 35+18 无 / 公式定义 30+5 有但不可核参数 / 设计 9+3 无 / 其他 3+5 少数有）→ **这是 R_search 的第一版估计**。


5. **arena 估计的局限**：arena 是粗分类（按 claim 主题猜类型，非逐条核来源可达性），conf 0.78。其 R_search≈0.20 是**下界估计**（实际"公式/定义类"中可能有部分能核到参数值，R_search 可能更高）。需 core 的逐条分类（4.1）来校准。

### 4.3 两路产出的合并（最终 R_search）

core 和 arena 给的是 R_search 的两个独立估计：
- **arena**：粗分类，R_search ≈ 0.20（conf 0.78，偏下界）
