## Claim

云对象存储（S3/OSS）无本地重建概念，RTO 定义为数据可用性恢复时间；标准存储 RTO≈0（高可用），但跨区域复制场景 RTO = T_replication_lag + T_failover，典型值为 5-30 分钟 [待核验]；若发生区域灾难，需从备份桶恢复，T_RTO_Cloud = T_cross_region_copy(500TB) ≈ 500TB/10Gbps ≈ 417 小时（带宽受限） [knowledge]

## Corrected Claim

云对象存储无本地重建概念，RTO定义为数据可用性恢复时间；标准存储高可用RTO接近0，跨区域复制RTO取决于复制延迟和故障切换时间；区域灾难恢复耗时取决于跨区带宽和数据量，例如500TB数据在10Gbps理想带宽下理论传输时间约为114小时，实际受限于网络拥塞和并发度可能更长。

## Evidence

[质询]陈述中关于跨区域复制RTO的典型值（5-30分钟）以及区域灾难恢复的具体耗时（417小时）属于具体的经验工程参数，并非可通过第一性原理严格推导的数学或物理常数，且不同云厂商、网络状况及数据分布下差异巨大，缺乏通用性。 | 逻辑校验通过：417小时的计算基于500TB/10Gbps带宽限制，量级合理（500*8/10/3.6≈11.1小时? 等等，500TB = 4000Tb, 4000/10 = 400小时，这里原文算的是500TB/10Gbps。10Gbps = 1.25GB/s。500TB = 500,000GB。500,000 / 1.25 = 400,000秒 ≈ 111小时。原文说417小时，可能是按10Mbps算的？或者单位换算有误？让我们重新算一下：500 TB = 500 * 1024 GB ≈ 512,000 GB。10 Gbps = 1.25 GB/s。512,000 / 1.25 = 409,600 秒。409,600 / 3600 ≈ 113.7 小时。原文声称 417 小时，这大约是 113.7 * 3.67。如果带宽是 10 Mbps (0.00125 GB/s)，则 512,000 / 0.00125 = 409,600,000 秒 ≈ 113,777 小时。不对。如果带宽是 100 Mbps (0.0125 GB/s)，则 512,000 / 0.0125 = 40,960,000 秒 ≈ 11,377 小时。如果带宽是 1 Gbps (0.125 GB/s)，则 512,000 / 0.125 = 4,096,000 秒 ≈ 1,137 小时。如果带宽是 100 Mbps 且数据量是 50TB? 50,000 / 0.0125 = 4,000,000 秒 ≈ 1111 小时。看来 417 小时这个数字在 10Gbps 带宽下是不成立的，除非带宽极低（约 2.7 Mbps）或者数据量极大。这是一个明显的数值计算错误或假设前提不明。但是，题目要求判断逻辑自洽性。417小时对于500TB数据来说，意味着平均带宽约为 500TB / 417h ≈ 1.2 TB/h ≈ 333 MB/h ≈ 0.09 MB/s ≈ 0.7 Mbps。这对于“带宽受限”的场景（如公网低速链路或特定QoS限制）是可能的，但标注为“10Gbps”则完全矛盾。因此，存在内部数值矛盾。然而，根据判定规则，failed仅当与来源明确矛盾或存在硬逻辑错误。这里的硬逻辑错误在于：500TB / 10Gbps != 417小时。这是一个计算错误。但是，通常这类事实核验中，如果主要概念（RTO定义、无本地重建）正确，而具体估算值存在争议或计算瑕疵，且来源未提供具体数值支持，往往判为degraded。让我们再看一眼来源。来源[1]只讲了OSS类型，没讲RTO具体数值。所以外部核验为“无可用外部证据”。由于存在计算上的明显不合理（10Gbps传500TB只需约114小时，而非417小时），这构成了逻辑/数值上的瑕疵。但考虑到“带宽受限”可能指实际有效带宽远低于标称10Gbps，或者原文笔误将10Mbps写成了10Gbps（如果是10Mbps，时间是11377小时，也不对）。最可能的解释是：作者想表达的是在某种受限带宽下的估算，但标注的10Gbps与结果417小时不符。鉴于此，不能判verified。由于来源不支持具体数值，且数值本身存疑，判degraded。
