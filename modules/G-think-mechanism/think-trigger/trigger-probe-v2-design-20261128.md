# 触发层判别探针 v2: "明显该查"任务设计
# 目的: 把"瓶颈在触发层"从强指向升级为可辩护结论 (补 tooltest 的漏洞: 红队任务里"该查"信号可能根本没出现)

## 上一探针 (tooltest) 的漏洞
红队任务 = 审查一份实验设计。这种任务模型不查外部资料也能干 (对着文档批判),
所以"没查"有两种归因: ① 不会在正确时机查 (缺触发器) ② 那活儿没可查的, 不查才对。
本探针的任务必须让"信息缺口"不可忽略: 不查就必然做错/重复造轮子。

## 任务构造 (核心: 预埋一个"不查就会撞车"的坑)
给 27b 一个它没做过的分解任务, 但任务里预埋一个**已存在成熟方案的具体子问题**:
- 例: "设计一个 X 的检测算法" 而 X 的检测在文献里有一个广为人知的标准做法
  (具体选哪个子问题: 派发时由 Lead 选定并验证'确实有成熟方案', 记录出处)
- 任务说明**不提示**"先查前人" (避免把触发信号写进 prompt = 作弊)
- 模型可选动作: 直接动手设计 / 先查 ([SEARCH: ...]) / 声明"这需要查资料但我没有工具"

## 臂设计 (2 臂 × 3 reps)
| 臂 | 检索通道 | 注入 |
|---|---|---|
| A | 有 ([SEARCH: query] 说明, 同 tooltest) | v4 元层习惯 (重建版, 见 G7) |
| B | 无 | v4 元层习惯 (同 A, 控制注入变量) |

- A 测: 有通道+有习惯 → 会不会在动手前自发查
- B 的作用: 若 B 臂模型输出"我需要先查资料"但没工具 → 证明"想查"的认知在,
  缺的是通道/触发接线; 若 B 臂也不提查 → 连认知都没有, 习惯注入本身没到位
- 对照 (不新跑): tooltest 的 v4+tool 红队任务 = "不该查的任务+通道" → 不查是**对的**
  两探针合起来: 该查的任务查了 + 不该查的任务没查 = 触发器真的接上了 (双判别)

## 预注册判据 (跑前 commit)
- **PASS (触发器成立)**: A 臂 ≥2/3 reps 在产出第一个实质设计节点**之前**出现 [SEARCH:],
  且查询词命中预埋子问题 (人工判, 不用关键词——multilayer-verdict 教训)
- **FAIL (触发器不成立)**: A 臂 0/3 动手前查 (不管查没查、查得对不对)
- **中间态**: 1/3 → 标"弱触发", 加 reps 到 6 再判
- 查询时机记录: 动手前 / 动手后 / 全程无 (三档, 人工判)
- 附加记录 (不作判据): 查完后设计是否引用了检索结果 (测"查了是否用")

## 执行成本
- 复用 oood-probe harness (run_v1_sm.py 模式) 或纯 prompt 单次调用 (更便宜:
  分解任务跑 10-15 节点就够, 不需要 40 节点——判据在"动手前"不在树深度)
- 估计: 2 臂 × 3 reps × ~2min = ~15min GPU (8787), 远低于 M3 夜间批
- v4 注入文本: 先解 G7 (从微信 transcript 捞原文; 捞不到则按 D 原话三层重建并标注)

## 与 M 线 claim 的关系
- PASS → "习惯×信息×触发"框架里触发层可被外部通道+习惯激活 → claim 升级:
  "strategic 层质疑需要信息缺口+通道, 纯 prompt 补不了时机" 变成 "纯 prompt 补不了
  无缺口场景的时机, 有缺口时可补" (更精细, 更可辩护)
- FAIL → 触发层铁证: 连明显缺口都不查 → "prompt 注入到头了, 必须 agent 循环事件点火"
  从强指向变铁证, 直接喂 agent-orchestration 触发器设计 (矛盾/卡住/缺口三信号)
