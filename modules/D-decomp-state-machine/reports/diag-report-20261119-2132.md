## 二、根因分析

### 2.1 502 burst：上游 ECONNRESET + 退避窗口不足（主因）

- 8787 代理（proxy.mjs）唯一活跃上游是局域网直连 `10.20.33.188:8000`（ninfer qwen3.8-27b）。
  proxy.log 显示两波 `UPSTREAM_ATTEMPT_FAIL ... ECONNRESET -> failover` → `PROXY_ERROR fetch failed`：
  **19:41–19:47** 与 **21:00–21:13**，实测持续 6–12 分钟。
- SM 侧 `call_llm` 旧退避是 5·2^n（5+10+20+40=75s），retries=3–4 的总窗口盖不住 6–12min 的 burst
  → 重试耗尽 → 异常上抛 → 整 run FATAL。7 个 run 全部死在这个模式上。
- 21:13 之后上游恢复（proxy.log HEALTH 全 OK，15–49ms），r06 已正常开跑。
- **风险**：无备用上游（8010 relay 与 Tailscale 通路已注释），burst 再来一次仍会丢 run，
  只是丢得少了（退避窗口加长后 6min 内的 burst 可扛住，12min 的仍扛不住）。

### 2.2 driver resume 路径双重前缀 bug（次因，放大损失）

- SM FATAL 时 E12 落盘 `runs-s5-sm-{qid}-checkpoint.json`，driver 拿到后应 resume 续跑。
- 但 driver 传的是相对路径 `experiments/stage-ablation/...`，而 s5_state_machine.py 入口
  `os.chdir` 到 stage-ablation/（1708 行）→ 解析成 `stage-ablation/experiments/stage-ablation/...`
  → FileNotFoundError。r04/r05 各浪费 3 次 resume 全失败（/tmp/t53b/gpu_text_r04.sm.log 铁证）。
- 后果：r04 已跑 36min 树 38 节点、r09 跑 42min 树 30 节点，进度全部作废。

### 2.3 设计冲突（未修，需 Lead 裁决）

- **batch 失败标记 done=true**：t53b-batch.sh 第 48–61 行，driver 失败后 batch 把该 run
  标 done=true + note「标记跳过」。但 driver 自身设计是「不记账，保持 done=false，下轮重试」。
  502 期间失败的 run 被 batch 永久跳过 → 这 7 个 run 的数据**已丢失**（done=true，不会再跑）。
  与 driver 的重试语义直接矛盾。
- **_verify_batch 并发 502 脆弱点**：s5_state_machine.py 640–685 行，ThreadPoolExecutor
  4 并发调 verify_node（默认 retries=2），无 try/except——任一节点 502 耗尽重试 → 异常上抛
  → 整 run FATAL。其余 LLM 调用点（classify_edge / judge_necessary_batch / _rework /
  _scan_contradictions / _verify_parent_nodes）均有 try/except 降级，唯独 verify 主路径没有。
  修它属于实验语义变更（节点降级 vs run 失败），监控员不擅动。
