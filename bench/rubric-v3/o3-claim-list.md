## 1. 背景与问题定义

### 1.1 现行判据为何不可执行（AUDIT finding #13）

DRAFT v1 L58 / v2 L71（修订前）的命中判据为：

> judge 拿产出逐节点对照 gold tree.md，**节点 ID 对得上**且通过正确性/相关性/必要关系核验才算 h_v=1

该判据预设「run 产出使用与 gold-tree 相同的节点编号体系」。冻结数据证明这个预设不成立——run 各自构建自己的分解树并使用**自家的层级编号**（N-x.y 格式巧合相似但语义无关）。三个具体失败模式，每条带 run 原文 evidence：

| # | 失败模式 | 实例（冻结数据 evidence） | 后果 |
|---|----------|---------------------------|------|
| FM-1 | **假命中（ID 幻觉匹配）**：run 自家树的 N-2.1 与 gold N-2.1 同号不同义 | run1 的 "N-2.1" = 权重占用（weight bytes）；gold N-2.1 = 业务需求占空比 duty_demand。按 ID 判据，run1 在 N-2.1 上「命中」，实质内容完全不对应 | 分数虚高，构念效度数字失真 |
| FM-2 | **假漏判（同 ID 不同义的反向）**：run 写了 gold 某节点的实质内容，但没用 gold 的 ID 表述 | hit-matrix 全部 h=1 evidence 中**无一条**以 gold 节点 ID 字样表述（如 N-3.2.2 的 evidence 是「KV cache 64K≈8GB」「~200-400MB/流」，从不含 "N-3.2.2"）→ 严格按 ID 判据，这些真实覆盖全部记 0 | 分数虚低，好产出被误杀 |
| FM-3 | **方向错误也算/不算命中的歧义**：run 把自家 N-1.3 写成「通过率倒数 1/P」（实为 gold N-4 的内容），gold N-1.3（故障损耗）被整体漏掉 | run1/run6/run7 的 "N-1.3" = 通过率放大支；gold N-1.3 = 故障损耗（三年故障概率×卡价/H）。ID 判据下这三个 run 在 N-1.3「命中」、在 N-4 的对应内容归属混乱 | 同一份数据两种读法，judge 间无法收敛 |

**双向失效**：FM-1/FM-3 产生假命中，FM-2 产生假漏判——「节点 ID 对得上才算命中」既不是充分条件也不是必要条件。这正是 AUDIT §2-O3 判定其「不可执行」的实证基础。

### 1.2 修复方案（AUDIT §2-O3 L79 处置原文）

> 「节点 ID 对得上才算命中」不可执行 → gold 节点转原子 claim 清单，judge 判实质内容包含（≥2/3 独立判者一致），映射一致性本身作为可报效度指标

落地为本文三件：§2 原子 claim 清单（判什么）+ §4 多判者协议（怎么聚合）+ §3 映射一致性指标（新旧判据的一致性可报告、可机算）。

## 2. 原子 claim 清单（31 节点全覆盖）

### 2.1 claim 设计原则（三属性，逐条可查）

每条 claim 必须满足：
- **(a) 自含**：不读 gold-tree.md 全文也能理解在说什么（SHARED 引用节点禁交叉引用，展开为完整陈述）
- **(b) 可二值判**：yes/no 无中间态（「有/无该实质内容」，非「深浅程度」）
- **(c) 方向内嵌**：错误方向的覆盖不算命中（沿用 TASK-ablation Step 1「实质性覆盖 = 有对应内容且方向正确」；判据从严——提到名词但无数值/区间/机制 = no）

**防答案泄漏约束（R1）**：claim 只写**结构/机制/方向**，不写 gold-tree 专有数值。自检由 `ablation/scripts/assert-o3-claim-list.py` 机判（claim 文本中的数字 token 不得出现在该节点 gold-tree 行的数值集合中）。已知例外登记：无——31 条 claim 定稿措辞零数值（结构性小数如「三项之和」用汉字不用阿拉伯数字，避免误触发）。

### 2.2 逐节点 claim（h_v 判定对象）

判定操作：judge 盲读 run 产出全文，对该节点 claim 回答 yes/no + 引一句产出原文作依据（evidence 规则沿用 TASK-ablation Step 1：必须是产出中真实存在的句子）。

| node | claim（judge 判「产出是否包含以下实质内容」） | 方向内嵌说明（no 的典型情形） |
|------|----------------------------------------------|------------------------------|
| N-0 | 产出以**每（验收通过的）任务成本**为目标量，并给出「小时持有成本 × 单任务耗时 ÷ 有效利用率 ÷ 任务通过率」这类乘除分解结构（而非只报一个总账数字或只报每小时成本） | 只给 $/hr 不给每任务口径 = no；给了每任务数但无任何分解因子 = no |
| N-1 | 小时持有成本被拆为**购置摊销 + 电费 + 故障损耗**三项之和（故障项缺失但显式声明忽略理由，判者裁量，见 §4 tie 规则） | 只有摊销+电费两项且未提及故障维度 = no |
| N-1.1 | 硬件购置成本被**按使用寿命摊销**进小时成本（一次性支出折成每小时金额，出现 $/hr 或等价单位） | 只列采购总价不折算 = no |
| N-1.1.1 | 给出候选卡的**购置价格**（具体数值，或显式标为待取数的黑盒 + 获取路径） | 通篇不提卡价 = no |
| N-1.1.2 | **主机/机箱价格从卡价中单独列出**（而非合并为整机价一笔带过） | 「整机 X 元」不拆卡/主机 = no |
| N-1.1.3 | 显式引入**残值率**（设备报废时的剩余价值比例）修正摊销基数 | 直线折旧到零、不提残值 = no |
| N-1.1.4 | 给出**摊销年限或等效小时数**的具体取值（如「按 N 年」或「约 M 小时」），而非只写「折旧」一词 | 有折旧概念无寿命参数 = no |
| N-1.2 | **电费作为独立成本支**建模，呈「功耗 × 时长 × 电价」乘积结构 | 电费隐含在总账里不可分离 = no |
| N-1.2.1 | 给出**整机/满载功耗**的数值或区间（W 或 kW 单位） | 提「功耗高」无数值 = no |
| N-1.2.2 | **显式设定电价取值**（含货币/单位，如 $/kWh），而非把电价隐含在最终数字里 | 直接给电费总额、电价不可追溯 = no |
| N-1.3 | **硬件故障导致的损失被纳入小时成本**（可靠性/故障率/MTBF 类项，使持有成本 > 摊销+电费） | 完全不考虑故障维度 = no |
| N-1.3.1 | 给出（或显式标为待测的）**多周期硬件故障概率估计**（如「N 年内故障率约 p」） | 定性说「会坏」无概率量 = no |
| N-1.3.2 | 故障损耗项引用的**卡价与摊销项的卡价为同一参数**（显式复用同一取值，而非两处独立取数或矛盾取值） | 两处卡价不一致且未说明 = no；只有一处卡价无法构成「同一参数」判断时，按 §4 判者裁量 |
| N-2 | **有效利用率作为吞吐的独立因子**进入成本公式（c ∝ 1/u 或等价位置），而非隐含在实测吞吐里 | 直接用实测 tokens/hr、u 不出现在任何公式 = no |
| N-2.1 | 利用率进一步拆出**业务需求占空比**（需求侧因子：业务实际请求时间占比，需日志/流量测量），且识别其为高敏感度因子 | 只有供给侧调度效率、无需求侧占空比 = no |
| N-2.2 | 利用率拆出**调度效率子因子**（供给侧：排队/批处理/抢占损耗，区别于需求占空比） | 两个子因子混为一谈 = no |
| N-3 | **原始产出速率按单任务耗时的倒数**建模，且单任务耗时拆 **prefill + decode 两段**（λ = f(t_prefill, t_decode) 结构） | 只给端到端吞吐不分阶段 = no |
| N-3.1 | **prefill 阶段时间被单独建模**，呈「计算量 / 算力」结构（FLOPs 或 token 数除以峰值/MFU 折扣后的算力） | prefill 与 decode 混在一个时间项里 = no |
| N-3.1.1 | prefill 计算量以 **FLOPs 形式量化**（出现 FLOP 数量级估算，而非只给时间或 token 数） | 只说「prefill 要 X 秒」无计算量 = no |
| N-3.1.2 | 引入候选卡的**峰值算力规格**（TFLOPS 级数值）参与 prefill 时间估算 | 算力只用模糊描述（「很快」）= no |
| N-3.1.3 | 引入 **MFU（模型算力利用率）**或等价折扣系数对峰值算力打折，而非直接用峰值算力当有效算力 | 峰值算力直接代入、无折扣 = no |
| N-3.2 | **decode 阶段时间被单独建模为带宽受限过程**，呈「输出字节数 / 有效带宽」结构 | decode 按算力建模（混淆 compute-bound）= no |
| N-3.2.1 | 按**精度位宽给出权重字节数**（量化位数 → GB 的换算关系，如各档位宽各多少 GB） | 只说「量化后更小」无字节数 = no |
| N-3.2.2 | 给出**每并发流的 KV cache 字节数**估算（每流口径；总量口径需能折算回每流才算覆盖，见 §4 边界态示例 B-1） | 只给 KV 总量不区分每流 = 边界态（判者裁量）；完全无 KV 容量分析 = no |
| N-3.2.3 | 引入候选卡**峰值显存带宽规格**（GB/s 级数值）参与 decode 时间估算 | 带宽只作定性描述 = no |
| N-3.2.4 | **区分峰值带宽与有效带宽**（引入 TP/实现/协议损耗系数对峰值带宽打折，如「实际约为峰值的 x 成」） | 峰值带宽直接当有效带宽 = no |
| N-4 | **任务通过率作为成本放大因子**进入公式（有效成本 ÷ 通过率，或等价地计入重试成本），而非假设全部任务一次通过 | 默认 G=1、通过率不出现在任何计算 = no |
| N-5 | 产出中存在**可行性淘汰动作或硬约束筛选**：不满足某硬约束的候选被显式排除、不进入成本优化（无论是否命名为「过滤层」） | 所有候选都进成本比较、无淘汰 = no |
| N-5.1 | **显存容量门槛被用作并发数上限**（权重 + KV 总和 ≤ 可用显存的判定决定 n_cap 或等价量） | 显存只用于「放不放得下权重」、不约束并发 = no |
| N-5.2 | **按精度推导最低带宽准入阈值**并据此显式淘汰候选（如「低于某 GB/s 的卡在 Wx 下出局」） | 带宽只做时间估算输入、不做准入淘汰 = no |
| N-5.3 | **前缀缓存命中率被单列为影响速率的参数**（含敏感性讨论或 nuisance 标注，如「命中率每变化 δ 对成本的影响」） | 提缓存但不分析命中率变量 = no |

**NA 档检查结果**：31 节点全部写出可二值 claim，**零 NA**（最接近 NA 的 N-1.3.2 SHARED 引用节点已按 R4 展开为完整陈述）。若未来新增节点落入 NA，分母处理见 §3.2。

## 3. 映射一致性指标（新旧判据一致性，可报效度指标）

### 3.1 定义

设旧判据（节点 ID 级）判定函数 h_id(run, node) ∈ {0,1}（hit-matrix.json 现值），新判据（claim 级）判定函数 h_claim(run, node) ∈ {0,1}（按 §2 + §4 执行）。

**主口径 M1（cell 级一致率）**：

```
consistency_M1 = |{ (r, v) : h_claim(r,v) == h_id(r,v) }| / |{(r, v) : v ∈ V_judgeable}|
```

- 分子：两判据判定相同的 (run, node) cell 数
- 分母：V_judgeable = 可二值判节点集（当前 = 全部 31 节点，零 NA）；NA 节点（若未来出现）从分母剔除并在报告中显式列出
- 切片报告义务：M1 必须同时报全量（248 cell）与 gold strict 子集（5 节点 × 8 run = 40 cell）两个切片

**辅助口径 M2（run 级聚合一致率）**：

```
agreement_M2 = |{ r : ∀v, h_claim(r,v) == h_id(r,v) }| / |runs|
```

per-run hit 向量完全一致的 run 比例（比 M1 严：一个 cell 翻转即整 run 失配）。

### 3.2 冻结数据基线值（机算，脚本可复现）

**identity-baseline（degenerate, pre-execution）标签强制随值报出**：

| 口径 | 当前值 | 计算 | 标签 |
|------|--------|------|------|
| M1 全量 | 248/248 = 1.000 | h_claim := h_id（claim 判据尚未独立执行，两函数恒等） | identity-baseline (degenerate, pre-execution) |
| M1 gold strict 切片 | 40/40 = 1.000 | 同上 | 同上 |
| M2 | 8/8 = 1.000 | 同上 | 同上 |

**数据分布注记（机算，供重判采样参考）**：hit-matrix 冻结数据 h=1 cell = 98/248（39.5%）；gold strict 切片 h=1 = 10/40（N-3.2.2×6 + N-4×4，N-2.1/N-2/N-1.3 零命中）。

**口径声明（强制随指标一起报出，缺一即指标无效）**：
1. M1/M2 在 claim 判据首次独立执行（fresh-context judge 盲读 run 原文）之前**恒等于 1.0**——当前值不是有效性证据，只是分母定义与未来偏离锚点。
2. M1 对 h=0 方向**无判别力**：两判据同判 0 可能都是漏判（FM-2 方向），召回检验依赖独立重判补数（queue: RV3G6-o3-claim-rejudge，arena 通道，样本 = 31×8 全 cell，优先 h=0 的 150 cell）。
3. 未来独立重判落盘后，M1/M2 的实际读数 = 与 1.0 锚点的偏离量；偏离集中在哪些 (node, 方向) 切片须逐格报告。
4. **evidence 文本本身含 gold 数值不构成泄漏通道**（已核：98 个 h=1 cell 中 13 个 evidence 含 gold-tree 数值 token，如「27B」「3 年」——这些是 run 自产文本被冻结进 hit-matrix，属 #13 假命中的证据而非答案注入；§2 claim 文本的防泄漏由 assert 脚本检查②独立保证，两者不混用）。（V1 口径，assert-hitmatrix-evidence.py 机判；原值 27 见 r142 勘误）

复算脚本：`ablation/scripts/assert-o3-claim-list.py`（检查③：从 hit-matrix.json 独立复算上述基线值并与本表比对）。

## 4. 多判者协议（≥2/3 文字化）

### 4.1 判者构成

- **N = 3 独立判者**（AUDIT 原文「≥2/3」的最小整数解；N=5 会引入 3/5 平票态需额外 tie 规则，超出上游授权范围）
- 独立性定义：上下文独立（各自盲读 run 原文，不见他判者结论、不见 hit-matrix 现值、不见 gold-tree 全文——只见 §2 对应行 claim 文本）
- 家族独立性：**当前不可达**（工具纪律禁 subagent；现有判者均为同族底座）→ 本协议产出同样受 S2 同源偏置限定（§5.1），不构成对外宣称证据

### 4.2 聚合规则（tie 处理）

| 3 判者投票 | 结果 | 说明 |
|-----------|------|------|
| 3/3 yes | h_v = 1 | — |
| 2/3 yes | h_v = 1 | 「≥2/3 一致」达标；第 3 判者的 no 理由必须记录在案（分歧日志） |
| 1/3 yes | h_v = 0 | 未达标 |
| 0/3 yes | h_v = 0 | — |

N=3 下**无平票态**（不存在 1.5/3），规则封闭。

### 4.3 与 κ 条目层门禁的关系（不重复不矛盾）

- **κ（R-02，条目层）**：衡量判者间**二值判定的一致程度**（inter-rater agreement），是质量门禁——κ 低于预注册下限则本轮判定作废重判
- **本协议（聚合层）**：在 κ 门禁**通过之后**，把 3 个二值判定**聚合为单个 h_v** 的规则
- 顺序固定：先算 κ（条目层质检）→ 过门禁 → 再按 4.2 聚合。两者作用在不同环节，无循环依赖

### 4.4 执行降级（当前状态）

独立重判需 fresh-context judge（arena 会话通道）→ 工具纪律禁 subagent，**当前 unverified**。降级替代：claim 措辞用 hit-matrix h=1 evidence 做正例校准（已完成，见 o3-claim-list 起草过程工件 loop-artifacts/stages/02/），h=0 方向漏判检查导出 queue（RV3G6-o3-claim-rejudge）。**在独立重判完成前，本清单只定义判据、不产生任何新的 h 值。**
