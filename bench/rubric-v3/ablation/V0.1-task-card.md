# V0.1 重跑任务书（arena agent mode · 固定会话续发）

## 背景
prompt-V0.txt 已删除任务画像里的缓存比「90:9:1」（commit 8bbee92）——原题面把 N-5.3 cache_hit_rate 的答案直接写进题里，导致 8 run 全 hit 但实际只是抄题面。本任务用新题面重跑 8 个独立 run，验证模型能否**自发**拆出 N-5.3（命中率决定 decode 占比 → 必须量化）。

## 待读材料（都在本分支）
- `bench/rubric-v3/ablation/prompt-V0.txt` — 新题面（无缓存比，只保留"有长期不变的可缓存前缀"事实）
- `bench/rubric-v3/ablation/gold-tree.md` — **仅供你了解节点命名空间，禁止用其内容指导拆解**（防答案泄露；你的产出会被对照它评分，但你拆解时只能靠题面+自行调研）

## 执行要求
1. 按 prompt-V0.txt 的完整指令做拆解，共 **8 个独立 run**（run1-run8），每个 run 从零开始、互不参考。
2. 每个 run 产出格式与旧版一致：一棵拆解树 + 每节点标注（是什么/能调还是只能测/怎么量/占父份额）+ 黑盒声明 + 瓶颈判定 + 矛盾清单。参考旧 run 的**格式**（`runs-C0-run1.md` 等 8 份，只看结构不看内容结论）。
3. 每个 run 落盘为 `bench/rubric-v3/ablation/runs-V0.1-run{N}.md`（N=1..8），文件头加 sha256 自注（该文件除头部外内容的 sha256 前 16 位）。
4. 候选硬件列表和权重精度由你自行调研（题面已注明不指定）。
5. 分批交付：每次 2 个 run（run1+run2 → run3+run4 → ...），单批回复 ≤200 行。全部 8 个落盘后输出 `{"status":"done","files":["runs-V0.1-run1.md",...,"runs-V0.1-run8.md"]}`。

## 约束
- 不许引入 gold-tree 的节点定义来"凑"拆解——拆不出来的节点就不存在，这是本实验的测量对象。
- 中文回答。
- 落盘硬约束：8 个文件不存在 = 任务未完成。
