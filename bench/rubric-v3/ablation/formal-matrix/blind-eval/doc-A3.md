## 0. 根节点

**C = 每验收任务的成本（USD/任务）**

```
C = c_hour / (3600/T × S × p)

c_hour = capex/H + P_kW × 0.270
T      = 3500/prefill + 500/per_stream_decode
S      = 可同时驻留的流数（显存/内存可容纳的 KV 数 与 每流 ≥20 t/s 取小）
```

口径：W(Q4_K_M)=17.1 GB，单流 64K KV=4.0 GiB，开销 1.5 GiB，H=26,280 h，p=0.90，电价 0.270 USD/kWh。

**本 run 的第一条结论先摆出来**：统一内存机的「内存够大」是假优势。它们的显存闸动辄 19–27 条流，但**每流速度只有 6.5–38.6 t/s**，20 t/s 这条硬约束直接把一半候选打死，另一半锁在 S=1。

## 1. 分解树

```
C 每验收任务成本 [$/任务]                          SHARE 1.00  BOUND 3.9x（2.56m / 0.66m）
├── N-1 c_hour [$/h]                              SHARE 0.34  BOUND 2.7x（0.234–0.687）
│   ├── N-1.1 资本摊销 capex/H                     SHARE 0.64  BOUND 5.6x（2880–14000）
│   │   ├── 整机价格                              leaf 可查
│   │   └── H = 26,280 h                          leaf 可定
│   └── N-1.2 电费 P_kW × 0.270                    SHARE 0.36  BOUND 12x（0.20–2.90 kW）
│       └── 整机功率                              leaf 可测（统一内存机 0.20–0.30 kW 极低）
├── N-2 task/h                                    SHARE 0.56  BOUND 13x（103–1,343）
│   ├── N-2.1 T 单任务耗时 [s]                     SHARE 0.22  BOUND 1.7x（18.6–31.5 s）
│   │   ├── prefill 3500 tok（400–900 t/s）        ← 统一内存机的 prefill 是弱项
│   │   └── decode 500 tok（per-stream）
│   └── N-2.2 S 并发流数                           SHARE 0.78  BOUND 8x（1–8）
│       ├── 容量闸（内存/显存 ÷ 4.0 GiB）           区间 1–27
│       └── 速度闸 per-stream ≥ 20                 区间 0–1
└── N-3 p 通过率                                   SHARE 0.10  BOUND 1.18x
```

份额校验：0.34+0.56+0.10 = 1.00 ✅；0.64+0.36 = 1.00 ✅；0.22+0.78 = 1.00 ✅。

## 3. 瓶颈

**BOTTLENECK: N-2.2 S 并发流数**（0.56 × 0.78 × 8.0 = **3.49**，远高于 N-1.1 的 0.34×0.64×5.6 = 1.22）。

三条理由：

1. **S 在这一族候选上是 0 或 1，没有中间态**。DGX Spark（10.83）与 Strix Halo（6.5–10.9）连 1 条流都达不到 20 t/s，直接出局；M5 Ultra（38.6）与 M5 Max（22.0）能达到 1 条，但都到不了 40。**这一族机器的问题是「每条流都不够快」，不是「装不下」。**
2. **容量闸在这里是纯浪费**。M5 Max 的容量闸是 27 条流（128−18.6)/4.0），实际只能用 1 条——**买了 96% 的空闲内存**。DGX Spark 的容量闸是 27，实际是 0。
3. **多机扩展不会改变 S 的每流口径**。2×DGX Spark 把容量翻到 256 GB，但每流速度仍是 10.83，S 仍是 0——**容量能池化，带宽不能**。

瓶颈的下一层：per-stream ≈ 带宽 ÷ 22.1 GiB。跨 20 需 **442 GB/s**，跨 40 需 **884 GB/s**。DGX Spark（273）与 Strix Halo（215）都在 442 以下，M5 Max（614）过了 20 却没到 40，M5 Ultra（1,200）过了 40 却因为 prefill 与实现效率只跑出 38.6——**距离第 2 档差 1.4 t/s**。

**排序**：2×3090 TP2 0.727m < 8×3090 0.980m < 2×3090 复制 1.010m < 4×3090 1.022m < M5U 1.857m < M5 Max 2.561m。

**四条要点**

1. **多卡复制几乎不降成本**（2×1.010m → 4×1.022m → 8×0.980m）。因为 capex 与功耗都随卡数线性涨，S 也线性涨，**分子分母同时乘以 N，成本不动**。真正的收益必须来自「同一个模型跑得更快」（TP），而不是「多开几个模型副本」。
2. **TP2 是唯一有非线性的配置**：同一模型的单流从 34.0 提到 50.0，S 从 1 跳到 2，成本从 1.010m 降到 0.727m（−28%）。
3. **M5 Ultra 差 1.4 t/s 就换档**：38.6 → 40 会让 S 从 1 变 2、成本腰斩到 0.93m 左右，直接进前三。**这是全表最脆的一个数**。
4. **DGX Spark 与 Strix Halo 的容量是纯负债**：128 GB 能装下 27 条流，但一条都跑不到 20 t/s。按 $/GB 买它们是「便宜」，按 $/任务买它们是「出局」。

## 6. 矛盾清单

**X1 · DGX Spark 的 27B 解码：34 t/s vs 10.83 t/s vs 4.3 t/s（差 8 倍）**
- 源 A：pyshine（2026-10-01）引 llamaperf「Qwen3.8-27B dense: 34 tok/s under SGLang with NVFP4 weights」。
- 源 B：harrisoldroyd（2026-07-11）实测表「Gemma 3 27B Q4_K_M: prefill 834 / decode 10.83」。
- 源 C：canitrun.dev（2026-10-28）「Qwen 3.6 27B BF16 ~4.3 t/s」。
- **三个数不冲突，是三种口径**：C 是 BF16（每 token 读 54 GB ÷ 273 GB/s ≈ 5 t/s，与 4.3 自洽）；B 是 Q4_K_M（读 ~18 GB ÷ 273 = 15 t/s 上限，10.83 是 72% 效率，合理）；A 是 NVFP4 + SGLang（权重 ~14 GB，理论上限 19.5 t/s，**34 t/s 超过了 roofline**）。
- **采信 B**（Q4 口径与本任务最接近，且与带宽上限自洽）。**A 的 34 t/s 判为口径错误或含投机解码**——它在数学上是不可能单独由 273 GB/s 支撑的。这条是本 run 最重要的一处辨伪。

**X2 · Strix Halo 的 27B 解码：6.5–10.9 vs 30.6–36.0 t/s**
- 源 A：huppiflupp 实测集「dense models from 27B upwards stay below 15 tok/s」，Qwen3.8-27B 6 次测量 10.9–28.3。
- 源 B：julianmb/q38rocm（2026-09-04）「30.56–36.04 tok/s via MTP Speculation + TurboQuant KV + RADV Wave64」。
- **两者都成立但含义不同**：B 的 36 t/s 依赖三层外挂（投机解码、KV 量化、专用内核），**本任务无 drafter、且要求标准 64K 上下文**，因此 B 的口径不可直接搬用；A 的 baseline 才是可比的。
- **采信 A 的 10.9 t/s**（乐观取上沿）。注意：若 MTP 可用，36 t/s 会让它变成全表第一（0.39m）——**这条值得实测，但不应写进主口径**。

**X3 · Strix Halo 的价格：$3,499 vs $3,999**
- 源 A：compute-market（2026-07-16）「AMD Ryzen AI Halo Developer Platform … for $3,999」。
- 源 B：同一生态的裸机/整机报价常见 $3,499（128 GB 版本）。
- **采信 $3,999**（含开发者平台套件，是能直接买到的形态）。差 14%，对结论无影响（两种价都出局）。

**X4 · 「统一内存机的内存大 = 能跑大模型 = 划算」**
- 源 A：compute-market（2026-07-16）「the Halo owns the 27B–120B MoE sweet spot」，$3,999 128 GB。
- 源 B：本 run 的 roofline：dense 27B 每 token 必须读 ~18 GB（Q4），215 GB/s 给出 **12 t/s 的硬上限**。
- **A 说的是 MoE**（每 token 只激活 3B），B 说的是 dense。**本题是 dense 27B**，所以 A 的结论不适用。这是一处**「模型形态被偷换」的典型来源冲突**——它也是本题里最容易被厂商话术带走的地方。

## 8. 交付

- **最优：2×RTX 3090 TP2（48 GB，$2,880），0.727×10⁻³ $/验收任务**；次优 8×3090 复制（0.980m）与 2×3090 复制（1.010m）。
- **本 run 的核心判据**：统一内存机的问题不是「装不下」，而是「**每条流都跑不到 20**」。DGX Spark 10.83、Strix Halo 10.9 直接出局；M5 Ultra 38.6、M5 Max 22.0 能跑但锁在 S=1。**它们的 128 GB 里有 96% 是买来闲置的。**
- **两个反直觉**：①多卡复制不降成本（capex、功耗、S 同时线性涨，分子分母对消）；②最便宜的机器（Strix Halo $3,999）与最贵的多卡方案（8×3090 $14,000）差 3.5 倍价格，但都进不了前三。
- **该先测的三件事**：①各统一内存机在 64K 深度的真实单流（唯一能翻转排序的量）；②M5 Ultra 能否到 40；③2×3090 的 TP2 per-stream 衰减。
- **一句话**：这道题的胜负手是**每流 20 t/s 这道门槛**——它把「内存很大但带宽只有 200–600 GB/s」的一整族机器挡在门外，而 2×3090 用两块便宜卡把单流从 34 推到 50，跨过了第二个门槛。
