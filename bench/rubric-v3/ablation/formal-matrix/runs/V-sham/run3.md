## 1. 本 run 的问题重述

题面里只有一句话不是硬件参数：「**上下文里有一段长期不变的前缀，可以被缓存**」。

「可以被缓存」这四个字，决定了 `T` 里有多大的比例真的发生在 GPU 上。而它**不在任何规格书里**，也不在价格里。所以本 run 把**命中率 h** 当成主变量：

- **h = 0**（缓存失效，每次都重算 3,500 token 前缀）→ 硬件选型的重点是 **prefill 吞吐**（compute-bound）；
- **h → 1**（前缀常驻，只有 500 token 新内容 + 500 token 解码）→ 重点只剩 **decode 带宽**与 **capex**。

**这两件事在硬件上不是同一张卡擅长的**——这正是本 run 要检验的。

## 3. 成本公式（把 h 显式化）

```
T(h) = 3500 × (1 − h) / prefill + 500 / decode
C(h) = c_hour ÷ (3600 ÷ T(h) × S × p)
```

W=17.1 GB；KV 64K=5.0 GiB；开销 1.5 GiB；H=26,280 h；p=0.90；电价 0.270 USD/kWh。

**注意 S 不随 h 变**——因为前缀 KV 常驻不减少「每 token 要读多少」，只减少「每 token 之前要不要重算一遍」。

## 4. 分解树

```
C(h) 每验收任务成本 [$/任务]                        SHARE 1.00  BOUND 6.4x
├── A c_hour [$/h]                                SHARE 0.40  BOUND 2.6x
│   ├── A1 capex / H                              SHARE 0.63  BOUND 5.3x
│   └── A2 电费                                    SHARE 0.37  BOUND 2.8x
├── B task/h                                      SHARE 0.50  BOUND 7.9x
│   ├── B1 T(h) [s]                               SHARE 0.16  BOUND 3.0x（8.3–22.3）
│   │   ├── B1.1 prefill 段 = 3500(1−h)/prefill     **随 h 缩放**（0–4.6 s）
│   │   └── B1.2 decode 段 = 500/decode             **与 h 无关**（7.7–18.5 s）
│   └── B2 S                                      SHARE 0.84  BOUND 4.0x（0–3）
└── C p = 0.90                                    SHARE 0.10  BOUND 1.18x
```

份额：0.40+0.50+0.10 = 1.00 ✅；A1 0.63+A2 0.37 = 1.00 ✅；B1 0.16+B2 0.84 = 1.00 ✅。

**B1.1 与 B1.2 的耦合声明**：两者都进 `T(h)` 的加法，**不会相互抵消**——它们是串行的两段。**h 只作用于 B1.1**，所以「提高命中率」这个优化对 B1.1 慢的卡收益更大、对 B1.1 快的卡几乎无感。

## 6. 瓶颈：随 h 迁移

**h = 0（缓存完全失效）时的瓶颈：B1.1「prefill 段」**
- 此时 T 里 prefill 占 3.8–7.8 s（3090 4.56 s、M5U 7.78 s），**占 T 的 20–35%**。
- 打分：B1.1（此时）= 0.50 × 0.16 ×（7.8/3.8 = 2.05）= **0.16**；B2 = 0.50 × 0.84 × 4.0 = **1.68**。**B2 仍更大。**

**h = 0.99（前缀全命中）时的瓶颈：B2「并发流 S」，且 B1.1 完全消失**
- B1.1 → 0.021–0.078 s，**占 T 的 0.2–0.9%，可以忽略**。打分：B1.1 = **0.002**；B2 不变 **1.68**。

**BOTTLENECK: B2「并发流 S」——它在整个 h 区间上都是瓶颈，而 h 只改变 B1.1 这一支。**

**但 h 会改变「第二名之争」，这是本 run 真正的发现：**

| 对比 | h=0 | h=0.99 | 变化 |
|---|---|---|---|
| 3090 vs 4090 | 1.119 vs 1.134（**3090 赢 1.3%**） | 0.856 vs 0.996（**3090 赢 16.3%**） | **3090 的优势被放大 12 倍** |
| 4090 vs PRO 6000 | 1.134 vs 0.830（PRO 赢） | 0.996 vs 0.710（PRO 赢） | 不变 |
| M5 Ultra vs A6000 | 1.857 vs 1.621（A6000 赢） | **1.167 vs 1.342（M5U 反超）** | **名次翻转** |

**为什么**：4090 的全部优势在 prefill（1,918 vs 767，快 2.5 倍），而这个优势**只作用于 B1.1**；h→1 时 B1.1 归零，**4090 就只剩「比 3090 贵 $850」这一个特征**。M5 Ultra 反过来——它的 prefill 是全表最差（450），但 decode 不弱（38.6），**命中率一高，它最烂的那一项就不计分了**。

**一句话**：**命中率高的负载，会把「prefill 快的卡」的溢价抹掉，把「prefill 慢但 decode 不弱」的卡的缺陷藏起来。**

## 7. 矛盾清单

**X1 · 前缀缓存的命中率到底是 50% 还是 99.6%**
- 源 A：gigagpu（2026-05-06）「典型 chatbot 共享系统提示的命中率 **70–90%**，聚合吞吐提升 30–50%」；并给了一张表：1.5K 系统提示 720→1,180 tok/s（+64%）、3K RAG 480→720（+50%）。
- 源 B：jarvislabs（2026-02-06）「实测命中率约 **50%**，输出吞吐 +254%（427→1,513 tok/s），TTFT −78%」。
- 源 C：dev.to/runcrate（2026-10-27）「4,000 token 共享前缀、64 并发、**99.6% 命中率**；1,000 token 前缀 88%；单并发时 1,000 token 前缀只有 85%」。并指出「**第一个请求总要付全款**」。
- **三者不冲突，是三个不同画像**：A 是「chatbot 级」共享提示，B 是「混合请求」，C 是「所有请求共享同一个长前缀」。
- **本题属于 C 的画像**（题面明说「长期不变的前缀」），**采信 h ≈ 0.9–0.99**；但**取 h=0.9 作为保守基准**（C 的 99.6% 需要前缀完全一致且并发足够高）。
- **边界类型：③ 信息边界** —— `research_required: 本题画像下的真实命中率；路径 = 跑一周真实流水线统计 prefix cache hit rate`。

**X2 · prefill 是 compute-bound 还是 memory-bound**
- 源 A：outcomeschool（2026-07-05）「prefill 是 compute-bound（算术单元可到 90% 利用率），decode 是 memory-bound（20–40%）」。
- 源 B：aivineet（2026-02-10）「KV cache 极大加速 decode，但**不消除 prefill 的成本**——每个 prompt token 至少要处理一遍」。
- **两者互补，无冲突**：A 说瓶颈在哪，B 说为什么缓存帮不上 prefill 的忙。**合起来就是本 run 的 B1.1/B1.2 拆分依据。**
- **边界类型：① 数学/理论边界** —— `T = t_prefill + t_decode` 是串行加法，两段各自受不同资源约束（算力 / 带宽），到此为止。

**X3 · L40S 的 2.3 倍 FP16 算力为什么没用**
- 源 A：flopper.io（规格对照）「L40S FP16 dense 362 TFLOPS vs RTX A6000 155，2.3 倍」。
- 源 B：本 run 的实测表：**L40S 的 prefill 只有 1,200 t/s，排在 A100-40（1,800）、4090（1,918）之后**；而它的 $/任务在 h 全区间都是**最后一名（2.44–2.86m）**。
- **判为非矛盾但结论明确**：L40S 的算力优势没有转化成 prefill 吞吐优势（可能受显存带宽与 kernel 限制），**而它贵 2.8 倍**。
- **边界类型：① 数学/理论边界** —— prefill 的有效吞吐 = `min(算力, 带宽)` 的合成；当带宽只有 864 GB/s 时，算力再高也被带宽卡住。到此为止。

**X4 · 「缓存命中后就不花钱了」这句话对不对**
- 源 A：dev.to/runcrate「第一请求总要付全款」，且 85% 的命中率「接近共享部分占比（1,000/1,200）」。
- 源 B：本 run 的 `T(h)` 公式：h=0.99 时 prefill 段仍有 0.035–0.078 s（不是 0）。
- **两者一致**：**缓存省的是「重复计算」，不省「冷启动」与「唯一部分」**。本题 500 token 的新内容仍要全量 prefill（已计入 decode 段的假设里）。
- **边界类型：① 数学/理论边界** —— `T(h) = 3500(1−h)/prefill + 500/decode`，h→1 时第一项趋 0 但不为负，到此为止。

| B5 | 缓存的内存占用 | B2（容量闸） | 已在 5.0 GiB 内计 | ② 实操 | 到此为止因为前缀 KV 已计入每流 5.0 GiB |

**OPEN**
- **O1「能不能把前缀 KV 一直钉在显存里，让它不受并发影响」** → **① 数学/理论边界**：若多个流共享同一前缀，KV 可以共享（省显存），但 `S` 仍受 `⌊decode/20⌋` 限制。到此为止因为 `min` 的整数闸不因共享而变。
- **O2「命中率能不能靠工程手段推到 99%」** → **② 实操边界**：需要「前缀完全一致 + 高并发 + 足够长的缓存 TTL」。到此为止因为**缓存 TTL 与显存容量冲突**（缓存的 KV 会挤占并发槽位）。
- **O3「M5 Ultra 的 prefill 只有 450，能不能优化」** → **② 实操边界**：MLX 的 prompt processing 在长上下文上受 Metal kernel 限制。到此为止因为**这需要重写 kernel**（Z = 工程人力）。
- **O4「h=0 与 h=1 的答案不同吗」** → **① 数学/理论边界**：**冠军不变（A100-80），但第 3 名会变**（h=0 时 5090 0.546 稳居第 3；h=1 时 5090 0.435 仍第 3）。**名次变化发生在 3090/4090 与 M5U/A6000 这两对之间。** 到此为止。

## 9. 交付

- **最优：1×A100 80GB，h=0 时 0.403m、h=0.99 时 0.342m**；次优 A100 40GB（0.454m → 0.375m）。
- **本 run 的判据**：**命中率 h 只作用于 prefill 段（T 的 0–35%），所以它不改冠军，但改「谁排第二梯队」。**
- **最反直觉的一条**：**h=0 时 3090（1.119m）只比 4090（1.134m）便宜 1.3%；h=0.99 时差距放大到 16.3%**。因为 4090 的全部优势都在 prefill（快 2.5 倍），**而题面说前缀「可以被缓存」——这句话直接把 4090 的溢价抹掉了**。**如果你买卡是为了「prefill 快」，先确认你的前缀到底缓存不缓存。**
- **第二反直觉**：**M5 Ultra 是全表对 h 最敏感的机器（−37%）**——它 prefill 最慢（450 t/s），命中率一高，「最烂的那一项」就不计分了，于是它以 1.167m 反超 A6000（1.342m）。**一台「全面平庸」的机器，在高缓存命中率下会比一台「prefill 强但带宽弱」的机器更划算。**
- **最该记住的一条**：**L40S 在全 h 区间都垫底（2.44–2.86m）**。它的卖点是 2.3 倍 FP16 算力，而 prefill 实测只有 1,200 t/s —— **算力没有转化为吞吐，价格却是 A100-40 的 2.3 倍**。
- **该先测的三件事**：①读者自己画像的命中率 h（跑一周日志）；②各机 64K 的 prefill 与 decode（两段要分开测，别只测 decode）；③5090 的 64K decode（26 与 62 的差别能改两个名次）。
