## 4. 瓶颈

**BOTTLENECK: B2「并发流数 S」——具体是 B2b「每条 ≥20 t/s 时最多几条」。**

打分：B = 0.53 × 0.82 × 3.0 = **1.30**；A = 0.37 × 0.63 × 4.2 = **0.98**。B 更高。

为什么是 B2b 而不是 B2a：

1. **B2a 的区间（1–12）比 B2b（1–3）宽，但它对结论几乎不起作用**——9 个候选里有 6 个的 S 由 B2b 卡住（A6000 槽 5 但速度闸 1、RTX 6000 Ada 槽 5 闸 1、MI210 槽 9 闸 1、M5U 槽 15 闸 1、5090 槽 2 闸 1）。**容量买多了全在空转。**
2. **它是「贵卡为什么输」的唯一解释**：A6000 与 RTX 6000 Ada 的显存都是 48 GB（够装 5 条），capex 是 3090 的 1.8–2.7 倍，但因为 decode 只到 27.1 / 34.8 t/s，S 停在 1，**$/任务反而比 3090 更贵**（1.621m / 1.583m vs 1.119m）。
3. **它也是 DGX Spark 出局的唯一原因**：128 GB 能装 21 条，10.8 t/s 一条都跑不满。

**关键数值**：27B@64K 的每 token 读量 ≈ 22.1 GiB，**20 t/s 需要 442 GB/s 带宽**。这条线以下（DGX Spark 273）硬性出局；这条线的 1–3 倍（442–1,326）对应 S=1–3；再往上（MI210 1,638）带宽有了但**实现效率不到 0.5**，S 还是 1。

**瓶颈的下一层：实现效率比带宽更决定 S。** MI210 的标称带宽是 3090 的 1.75 倍，实测 decode 只高 6%（36.0 vs 34.0）——**ROCm 在 Q4_K_M + 64K 上把 1,638 GB/s 兑现成了 36 t/s（效率 0.49），而 CUDA 把 936 兑现成 34（效率 0.80）**。所以「换更快的卡」在中低端不成立，**换掉 kernel 才成立**。

## 6. 矛盾清单

**X1 · MI210 的 1.6 TB/s 到底能兑现多少**
- 源 A：UBB 商品页（2026-07-29）规格：64 GB HBM2e、4096-bit、**1.6 TB/s**、PCIe 4.0 x16。
- 源 B：ROCm 生态的通行评价——vLLM 在 CDNA2 上对 GGUF/Q4_K_M 的 kernel 支持不完整，社区普遍报「AMD 的 decode 只有同带宽 NVIDIA 的 60–75%」（本轮检索的两处二手报价页均只报价格、不报吞吐，故此项按区间处理）。
- **更可信：B 的方向，但 A 的规格。** 采信 36.0 t/s（效率 0.49），这个值可能偏低也可能偏高，**它是本 run 最大的单点不确定**。
- **边界类型：③ 信息边界** —— `research_required: MI210 上 vLLM/llama.cpp 跑 Qwen 级 27B Q4 在 64K 深度的实测 tok/s；路径 = ROCm 机器实测一次 llama-bench -d 60000`。

**X2 · RTX 6000 Ada 二手价差 2 倍**
- 源 A：gpuvet（2026-09）最低 $3,700 / 中位 $7,450 / 最高 $12,445（52 条在售）。
- 源 B：clustermelt（2026-09-01）$4,750–7,359；alibaba（2026-08-15）$4,700–6,500。
- **两者不冲突，是分布不同**：A 的 $3,700 是极值报价，B 的 $4,750 起是「可成交」区间。**采信 $4,700** 作为保守值，并在敏感性里给 $3,700。
- **边界类型：③ 信息边界** —— `research_required: 实际成交价（不是挂牌价）；路径 = eBay Sold 近 30 天`。

**X3 · 48 GB 显存的真实价值**
- 源 A：gpuvet 对 RTX 6000 Ada 的定位「Single-card home for 70B models」——暗示大显存是核心卖点。
- 源 B：本 run 的算式：48 GB 给 5 个槽位，但速度闸只放 1 条，**5 个槽位里 4 个是死的**。
- **判为口径冲突，不是事实冲突**：70B 场景下「装得下」确实是全部价值；**27B@64K 且要求 20 t/s 的场景下，容量超过速度闸的部分价值为零**。采信 B 对本题。
- **边界类型：① 数学/理论边界** —— `S = min(槽位, 速度档)`，第二项一旦更小，第一项的增量价值严格为 0。

**X4 · DGX Spark 的 128 GB 是不是「能跑 27B 长上下文」**
- 源 A：pyshine（2026-10-01）128 GB 统一内存 + 273 GB/s。
- 源 B：同页报 BF16 4.3 t/s、NVFP4 34 t/s（引 llamaperf）；harrisoldroyd（2026-07-11）Gemma3-27B Q4 10.83 t/s。
- **两者冲突**：34 t/s 与 10.83 t/s 差 3.1 倍。**采信 10.83**（Q4、dense 27B、非 NVFP4 小模型口径）——NVFP4 的 34 t/s 大概率是更小的模型或投机解码。
- **边界类型：③ 信息边界** —— `research_required: Spark 上 Qwen 级 27B Q4、64K 深度、无投机解码的单流；路径 = 官方 DGX Spark playbook 复现`。

**OPEN**
- **O1「S 能不能靠批处理而不是多流提高？」** → **① 数学/理论边界**：题面约束是「每个并发流 ≥20 t/s」，批处理提高的是总吞吐、降低的是单流速度；**批大小 b 与单流速度是反向的**，到此为止因为 `tok/s_batch = 带宽 ÷ (22.1 GiB)` 是总量约束，分到 b 条流上每条 ≤ 总量 ÷ b。
- **O2「能不能用投机解码把 decode 拉到 20 t/s 以上？」** → **② 实操边界**：投机解码要 draft 模型，额外占 1–2 GB 显存 + 额外内存带宽；在 64K 深度上接受率下降明显。到此为止因为**需要先有 draft 模型的实测接受率**（Z = 一次对照实验）。
- **O3「27B 换成 MoE 是否绕开带宽墙？」** → **② 实操边界**：换模型改变的是每 token 读量（MoE 只读激活专家），但 64K KV 仍在；到此为止因为超出「选硬件」的范围（Z = 质量评估）。

## 8. 交付

- **最优：1×A100 80GB（$7,400 二手），0.403×10⁻³ $/验收任务**；其余 8 个候选全部 ≥ 1.11m，**差 2.8 倍**。
- **本 run 的判据**：`S = min(⌊(VRAM−18.6)/5.0⌋, ⌊decode/20⌋)`，9 个候选里 6 个被第二项钉死在 1。
- **最反直觉的一条**：**MI210 的标称带宽是 3090 的 1.75 倍，实测只快 6%**。所以「按 GB/s 排序」在这个价位段完全无效，**实现效率（CUDA vs ROCm）才是第二把刀**。
- **候选集本身的限制**：本 run 的 9 个候选是按「市面上常见的一体机/单卡」自然列出来的，**没有系统性地去找「非默认先验但可能更便宜」的方案**（例如双卡拼装、改装卡、退役数据中心卡、上一代同容量卡）。这一点会系统性影响结论：**若存在一个 $2,000–4,000、S=2 的组合，它会直接顶掉 3090 的第 2 名位置**。我把这条作为本 run 最大的方法论缺口记在这里，而不是假装 9 个候选已经穷尽。
- **一句话**：在默认思路下，答案就是 A100 80GB 一台独走——因为只有它同时有「够快的带宽」和「够装的显存」。
