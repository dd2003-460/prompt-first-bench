## 0. 根节点

**C = 每完成一个验收通过任务的成本 [USD/任务]**

题面**没有指定权重精度**。这不是一个可以随手设定的常数——**它同时改了分母（速度）、改了容量门槛（哪张卡装得下）、还改了分子（不同精度的任务通过率）**。所以本 run 把「精度」当成第一个决策变量，而不是背景假设。

```
C(q) = c_hour ÷ (3600 ÷ T(q) × S(q) × p(q))
每 token 读量 R(q) = W(q) + 1.5 + 5.0      （权重 + 开销 + 64K KV）
S(q) = min( ⌊(VRAM − W(q) − 1.5)/5.0⌋ , ⌊decode(q)/20⌋ )
```

**权重体积（三个源交叉）**

| 精度 | 权重体积 | 来源 |
|---|---|---|
| Q4_K_M | **15.2 / 16 / 16.5 GB** | runyard 2026-09-01「15.2 GB」；llamabuilds 2026-10-14「16 GB」；取 **16.5**（含 embedding 与输出头） |
| Q5_K_M | **18.8 GB** | 按 5.5 bits/param 推算（Q4 与 Q8 之间线性） |
| Q8_0 | **28.7 / 30 GB** | runyard「28.7 GB」；llamabuilds「30 GB」；取 **29.3** |
| F16 | 54 GB | 27B × 2 bytes |

**一个关键的实测交叉**：acecloud（2026-10-29）实测「Qwen3.8-27B 在 64K 上下文下 Q4 占用约 **22 GB**」。按本 run 的模型反推：16.5 + 1.5 + 5.0 = **23.0 GB**，与实测差 4%。**这个 4% 的吻合给了 `R(q)` 这条公式一个独立校验**——也是本 run 敢把「每 token 读量」当硬约束用的底气。

## 2. 分解树

```
C 每验收任务成本 [$/任务]                          SHARE 1.00  BOUND 6.3x
├── A 精度档位 q（第一决策变量）                    ← 不在成本项里，它改所有项
│   └── A1 W(q) = 16.5 / 18.8 / 29.3 / 54 GB      leaf 可查+可算
├── B c_hour [$/h]                               SHARE 0.35  BOUND 2.4x
│   ├── B1 capex / H                             SHARE 0.62  BOUND 4.4x
│   └── B2 电费 P × 0.270                        SHARE 0.38  BOUND 3.4x
├── C task/h                                     SHARE 0.55  BOUND 6.0x
│   ├── C1 T(q, 卡) = 3500/prefill + 500/decode    SHARE 0.16  BOUND 3.9x
│   └── C2 S(q, 卡) = min(容量闸, 速度闸)           SHARE 0.84  BOUND 3.0x
│       ├── C2.1 容量闸 ⌊(VRAM − W(q) − 1.5)/5.0⌋   随 q 单调下降
│       └── C2.2 速度闸 ⌊decode(q)/20⌋               随 q 单调下降
└── D p(q) 通过率                                SHARE 0.10  BOUND 1.18x
```

份额：0.35+0.55+0.10 = 1.00 ✅；B1 0.62+B2 0.38 = 1.00 ✅；C1 0.16+C2 0.84 = 1.00 ✅。

**A 支的地位**：它不进份额（它是**外生选择**，不是成本的组成部分），但它是唯一一支**同时把两个闸都往下拉**的东西——这在树里是异常结构，所以单独标出来。

## 4. 瓶颈

**BOTTLENECK: C2.1「容量闸」在 Q4 下是真正的约束，C2.2「速度闸」在 Q5/Q8 下接管——而把两者一起往下拉的，是 A1「权重体积 W(q)」。**

打分：C2 = 0.55 × 0.84 × 3.0 = **1.39**；B1 = 0.35 × 0.62 × 4.4 = **0.95**；C1 = 0.55 × 0.16 × 3.9 = **0.34**；D = 0.10 × 1.18 = 0.12。**C2 最高。**

**为什么是「容量闸先动、速度闸后动」**：

- **W(q) 每加 1 GB，容量闸掉 0.2 槽、速度闸掉 0.9 t/s**（以 24 GB 卡为例）。**容量的边际惩罚是速度的 4.4 倍**——因为 KV 的 5.0 GiB 是台阶式的（1 槽 = 5 GiB），而速度是连续的。
- **24 GB 卡的可用余量只有 1.0 GiB（24 − 23.0）**，也就是**只剩下 1/5 个槽的余量**。任何精度上浮都会把它清零。**这是「24 GB 卡在 2026 年已到天花板」的定量表述。**
- **40 GB 卡的余量是 17.0 GiB（3.4 槽）**，**48 GB 卡是 25.0 GiB（5 槽）**，**80 GB 卡是 57.0 GiB（11.4 槽）**——**容量闸从 40 GB 开始就不再是约束**，速度闸接管。

**瓶颈的下一层**：**KV 是「台阶」而权重是「斜坡」**。KV 每槽固定 5.0 GiB，所以容量闸的变化是阶跃的（装得下/装不下），而权重体积是连续增长的。**这意味着「精度」这个旋钮在 24 GB 卡上是开关（0 或 1），在 48 GB 以上是滑轨（3→2→1）。同一张表里两种函数形态，这是本 run 最想指出的一件事。**

## 5. 「Q8 到底值不值」——一个可以算死的问题

困惑度数据（presenc.ai 2026-05-07，Wikitext-2）：

| 精度 | Qwen 3 32B 困惑度 | 相对 Q8 的劣化 |
|---|---|---|
| Q8_0 | 4.79 | —（+0.2%） |
| Q4_K_M | 4.87 | **+1.7%** |

vucense（2026-10-02）在 Llama 3 8B 上给的差是 +0.1754（Q4_K_M）对 +0.0026（Q8_0），**量级一致**。

**Q8 要通过成本这一关，需要多少通过率提升？**

$$\frac{p_{Q8}}{p_{Q4}} \ge \frac{C_{Q8}}{C_{Q4}}$$

| 卡 | C(Q4) | C(Q8) | **需要的 p 比值** |
|---|---|---|---|
| A100 80G | 0.403m | 0.942m | **2.34×** |
| A100 40G | 0.454m | 1.413m | **3.11×** |
| PRO 6000 | 0.830m | 2.582m | **3.11×** |

**而 `p ≤ 1`，`p_Q4 = 0.90`，所以 p 比值最大只能到 `1/0.90 = 1.11`。** 需要 2.34–3.11 是不可能的。

**结论：在本题的成本口径下，Q8 永远不可能靠「更准」把钱赚回来。** 不是因为 Q8 不好，而是因为它把每个任务的时间翻了 2.4–3.1 倍，而通过率的上限只有 1.11 倍。**这是一条硬边界，不是经验判断。**

**唯一能翻盘的情形**：如果 Q4 的通过率低到 `p_Q4 < 0.90/2.34 = 0.385`，Q8 才会赢。**而本题说「通过率不是 100%」，显然不是 38.5% 那么惨。**

## 7. 矛盾清单

**X1 · Q4_K_M 的权重到底多大：15.2 / 16 / 16.5 / 17.1 GB**
- 源 A：runyard（2026-09-01）「Q4_K_M：权重 **15.2 GB**，8K 上下文总占用 18.7 GB」。
- 源 B：llamabuilds（2026-10-14）「Q4_K_M：**16 GB** 权重，8K 总 18 GB，32K 总 20 GB，每 1K token 加 0.07 GB（16-bit KV）」。
- 源 C：acecloud（2026-10-29）「**64K 上下文实测约 22 GB**」。
- **交叉校验**：B 的「每 1K 加 0.07 GB」× 64 = 4.48 GB，+ 18 GB = 22.5 GB —— **与 C 的 22 GB 吻合**。这个一致性非常强，说明 B 与 C 是同一口径。
- **采信：权重 16.5 GB（介于 A 与 B 之间，含 embedding），64K 总占用 23.0 GB。** A 的 15.2 是纯权重、不含输出头与 compute buffer。
- **怎么终止**：三个源在 4% 内自洽（22.0 vs 22.5），**再往下需要自己去 `llama-gguf` 里读 tensor 表**，对结论无影响（全体平移 1%）。停止。

**X2 · Q4_K_M 的质量损失：+1.7% 还是 +3–5%**
- 源 A：presenc.ai（2026-05-07）「Qwen 3 32B：Q4_K_M 4.87 vs Q8_0 4.79 = **+1.7%**」。
- 源 B：llmhardware.io（2026-05-03）「Q4_K_M 相对 F16 **+3–5%**」，注意**基線是 F16 而不是 Q8_0**。
- **两者不冲突**：A 比的是 Q4 对 Q8，B 比的是 Q4 对 F16。**而 Q8 本身距 F16 只有 +0.1–0.5%**，所以 Q4 对 F16 应该在 +2–5% 区间，与两条源都对得上。
- **采信：Q4 相对 Q8 劣化约 2%。**
- **怎么终止**：这 2% 的量级在 §5 的 2.34× 面前完全不够看，**精度论证的结论对它不敏感**。停止。

**X3 · 「每 token 读量 23 GB」这个模型对不对**
- 源 A：acecloud 的 22 GB（64K、Q4）是本 run 唯一一个**直接测出来的总占用**。
- 源 B：本 run 从带宽反推的 4090 = 38.4 t/s（1,008 × 0.84 ÷ 23.0 = 36.8，与 38.4 差 4%）。
- **两者互相印证**：用 23.0 这个读量，实测 decode 与带宽推算吻合到 4% 以内。**这说明「decode 是带宽受限、每 token 读一遍权重+KV」这个模型在本画像下是对的。**
- **怎么终止**：4% 的残差大概率来自 KV 的实际压缩（llama.cpp 的 Q8 KV 缓存），**我没有直接证据，只能记在这里**。停止。

## 9. 交付

- **最优：1×A100 80GB + Q4_K_M，0.403×10⁻³ $/验收任务**；次优 A100 40GB（0.454m）。**两者都在 Q4 档，且 Q5 就让 80G 从 3 档掉到 2 档（0.403m → 0.666m）。**
- **本 run 的判据**：**精度不是一个可以随手选的参数，它是本题最强的单点杠杆**——它同时改容量门槛、改速度、还该改通过率。
- **最硬的一条结论**：**Q8 在本题的成本口径下永远不可能赢**。它需要 p 提升 2.34–3.11 倍，而 `p ≤ 1` 给出上限只有 1.11 倍。**这不是「Q8 不划算」的经验判断，是「分母翻了 2.4–3.1 倍而分子最多只能翻 1.11 倍」的不等式。**
- **最实用的一条**：**24 GB 卡（3090/4090）在 2026 年已经到天花板**——Q4 下只剩 1.0 GiB 余量（1/5 个槽），**Q5 就装不下了**。如果你的任务必须用 Q5 以上，24 GB 卡直接出局，起点变成 A100-40。
- **第二实用**：**A6000 的 Q8 是「装得下 3 条、跑不动 1 条」的标本**——24.0 t/s 离 20 只差 4，但整数闸让它与「19 t/s」同命运。**速度门槛附近的方案，实际价值是断崖式的。**
- **该先测的三件事**：①各精度下 64K 单流实测（决定速度闸）；②KV 的实际字节/token（决定容量闸）；③Q5 下 q8_0 KV 缓存能否把 24 GB 卡救回来。
- **一句话**：**先定精度，再选卡**——反过来的话，你会买一张 Q5 就装不下的卡。
