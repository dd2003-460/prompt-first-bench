## 0. 任务定义（本 run 的切入点）

从零起。题面给的是「每完成一个任务多少钱」，但**这个数在网络上的所有参照值都是以「每百万 token 多少钱」给出的**。本 run 顺着这个习惯切：先把机器折算成**两个 token 单价**（输入侧、输出侧），再拿任务的 token 账本去乘。这样做的好处是：任何一步都能与公开的 $/M 数字对上账，错在哪一步立刻看得出来。

- **根**：C_task = [ n_out × u_out + n_in_new × u_in + n_prefix × u_prefix ] ÷ p
- u_out / u_in / u_prefix = 输出、新增输入、缓存前缀三类 token 的单价 [$/M tok]
- u = S_hourly ÷ (3600 × 该类的 tok/s) × 1e6
- 候选（自行调研）：3090 24G×1、4090 24G×1、L40S 48G×1、A100 40G×1。

## 1. 拆解树

```
C_task 每通过任务成本
├─ 单价支 u_x = S_hourly ÷ 该类 token 吞吐        ← 本 run 的重心
│  ├─ u_out  输出 token 单价
│  │  └─ 单流 decode tok/s（64K 深度）             〔只能测〕
│  ├─ u_in  新增输入 token 单价（预填）
│  │  └─ 预填 tok/s                                〔只能测〕← 实测 1503
│  └─ u_prefix 缓存前缀 token 单价
│     ├─ 预填计算被省掉的部分  ≈ 0                 〔只能测：开了前缀缓存后实测〕
│     └─ 但仍要在每个 decode 步里被 attention 读 → 已含在 u_out 里（不重复计）
├─ 账本支 每任务的 token 量
│  ├─ n_out 输出 token 数                          〔只能测；题面未给〕
│  ├─ n_in_new = 64K×(1−rho_pre)                   〔只能测；rho_pre 题面留白〕
│  └─ n_prefix = 64K×rho_pre
├─ 分母 p 通过率                                  〔只能测〕
└─ 共享的分子 S_hourly = capex_h + power_h        〔只能查/只能测〕
```

**关键结构差异**：单价支里的三个 u 共用一个 S_hourly，所以它们不是相加关系而是「同一笔钱分摊到三条 token 流上」；本 run 用**分别计算、按量加权**的方式处理，不做份额加和（份额加和只适用于拆父节点的同一笔钱）。

## 2. 单卡 3090 的三个 token 单价（24×7 满负荷口径）

S_hourly = capex_h 0.060 + power_h 0.054 = **$0.114/h**

| token 类 | 吞吐 | tok/h | 单价 u |
|---|---|---|---|
| 输出（decode，64K 深度） | 22 tok/s | 79,200 | **$1.44 /M tok** |
| 新增输入（prefill） | 1,503 tok/s | 5,410,800 | **$0.0211 /M tok** |
| 缓存前缀（开前缀缓存后） | — | — | **≈ $0**（预填计算被省） |

**输出 token 比新增输入 token 贵 68 倍。** 这个倍数就是整棵树的骨架：一个任务里只要输出 token 数量不可忽略，成本就几乎全由 decode 决定。

## 3. 一个任务的 token 账本与成本

题面：64K 上下文（含长期不变可缓存前缀）、输出长度未给。取 n_out=1000、rho_pre=0.9（即新增输入 6,400、前缀 57,600）。

| 项 | 量 | 单价 | 钱 | 占比 |
|---|---|---|---|---|
| 输出 | 1,000 tok | $1.44/M | $0.001440 | **91.0%** |
| 新增输入 | 6,400 tok | $0.0211/M | $0.000135 | 8.5% |
| 缓存前缀 | 57,600 tok | ≈$0 | $0.000000 | 0% |
| 小计 | | | $0.001575 | |
| ÷ p=0.9 | | | **$0.00175 /task** | |

**自校验**：换一条完全不同的路算——按时间算：T_task = 6400/1503 + 1000/22 = 4.3 + 45.5 = 49.8 s = 0.01383 h；0.01383 × $0.114 = $0.001577；÷0.9 = **$0.00175**。两条路差 0.1%（四舍五入）。**这是本树唯一的内部一致性检验，它通过了。**

## 4. 三种常见算错法，以及它们各错多少

| 错法 | 结果 | 相对正确值 |
|---|---|---|
| ① 把 64K 全部当输入 token 计费 | 65,000×$0.0211/M=0.00137 + 输出 0.00144 = 0.00281 | **+78%** |
| ② 只用「每百万 token 混合单价」不看构成 | 用公开值 $0.01/M（27B INT4 单卡）→ 0.000065 | **−96%** |
| ③ 用集群级吞吐（vLLM 26,200 prefill / 10,100 decode tok/s） | 单价 ×0.002 | **−99%** |

错法①是最容易犯的：**把缓存前缀当成「省了预填计算但还要花钱的东西」**——实际上它在预填侧确实 ≈ 免费，只在 decode 的 attention 里留下成本，而那部分已经含在 22 tok/s 里了。重复计一次就多算 78%。
错法②③则相反：把「机器能力」当成「你的产出」。公开的 $0.01/M 是在**满批处理、满利用率**下的数字，与本 run 的单流、单机、24×7 差三个数量级。

**同一台机器、同一个任务，「每百万 token 多少钱」可以报出 $0.024 到 $0.213 之间的任意值**，取决于分母算哪些 token：
- 分母只算输出 token：$0.001575 ÷ 0.001 M = **$1.58/M**
- 分母算 74,000 个「新增」token：**$0.0213/M**
- 分母算 65,000 个上下文 token：**$0.0242/M**
- 分母算 66,000（上下文+输出）：**$0.0239/M**
**跨度 74 倍，全部「正确」。** 所以任何跨来源的 $/M 比较，只要没写分母口径，就没有意义（见矛盾 2）。

## 5. 真正的杠杆：批处理，而不是换卡

上表的 22 tok/s 是**单流**数字。同一台机器开连续批处理（continuous batching）后，GPU 同时处理多个请求，decode 的总 token 吞吐可以成倍上升，而 S_hourly 一分不涨——这就是 $/M 的分子不动、分母变大。

| 场景 | 单流 tok/s | 批处理 tok/s（估） | u_out | 每任务成本 |
|---|---|---|---|---|
| 单流（本 run 基准） | 22 | — | $1.44/M | $0.00175 |
| 批 4 | 22 | 4×0.75×22 = 66 | $0.48/M | $0.00062 |
| 批 8 | 22 | 8×0.6×22 = 106 | $0.30/M | $0.00042 |

（0.75/0.6 是「批越大每流越慢」的经验折减，属黑盒。）
**批 8 把每任务成本降到 1/4，而换一张贵 4 倍的 A100 只在单流上快 2.9 倍（63/22），且 S_hourly 涨 4 倍。** 换句话说：**在同一台机器上提高批大小，比升级硬件便宜得多**——前提是题面的 20 tok/s 是**每并发流**的下限（题面原文如此），批处理会压低每流速度，所以批到 8 时每流可能掉到 13 tok/s 而破约束；这就是约束真正咬人的位置（见 §7）。

## 6. 黑盒声明

1. **n_out 输出长度**（题面未给）：区间 **[300, 2000]** tok。**它是本树最敏感的量**——输出 token 占成本 91%，n_out 翻倍成本几乎翻倍。测法：跑 100 个真实任务记输出长度分布，取 P90，半天。
2. **rho_pre 可缓存前缀占比**（题面留白）：区间 **[0.5, 0.95]**。**注意：它对本树的成本影响极小**——因为缓存前缀单价≈0、新增输入只占 8.5%，rho_pre 从 0.9 掉到 0.5 只让成本涨 5.7%。这与「先测前缀占比」的直觉相反，是本 run 的一个反直觉结论。
3. **单流 decode 在 64K 深度的真值**：区间 **[12, 30] tok/s**（社区实测 35–50 是浅上下文；同机 95K 深度实测塌到 4.03）。**这是唯一能翻排序的量**：若真值 12，u_out 涨到 $2.64/M，每任务 $0.0031，会被 A100 档追上。
4. **批处理后的每流速度折减**：区间 **[0.5, 0.9]** per stream，决定批大小能不能在 20 tok/s 约束下开大。
5. **p 通过率**：区间 [0.5,0.95]，只平移不改排序。

## 7. 瓶颈判定

**瓶颈 = 输出 token 的单价 u_out，也就是「64K 深度下的单流 decode tok/s」这一个数。**

- 结构证据：它一个人占成本的 91%；另外两个 token 类（新增输入 8.5%、缓存前缀 0%）加起来不到一成。
- 杠杆证据：能改 u_out 的只有三件事——换更快的卡（最多 2.9 倍）、开更大批（最多 4–8 倍）、把深度降下来（题面固定 64K，不可动）。**批大小是最大的杠杆，而它受 20 tok/s/流 这个约束限制**——所以本题的核心张力是：**批得越大越便宜，但每流速度会跌破 20，约束挡在中间。** 最优批大小是「每流刚好 20 tok/s」那一点，而不是越大越好。
- 反例检查：如果 n_out 实际只有 100 token（而不是 1000），输出占比会从 91% 掉到 51%，预填与新增输入的地位上升，瓶颈会转到 prefill 支——**所以 n_out 是决定「这棵树长成什么样」的上游量，必须先测它。** 这是本 run 与「先测硬件」的默认顺序相反的判断。
- 落点：**先测 n_out 与 64K 深度下的单流 tok/s（各半天），再谈买卡；批大小按「每流 20 tok/s」反解。**

## 8. 矛盾清单

**矛盾 1 · 27B 自建的每百万 token 成本：$0.01 vs $0.66 vs $1.83（差 180 倍）**
- 源 A：27B INT4 单卡 3090「$0.01/M」；同一篇文章另一处又说 1×3090 租赁 $0.25/hr、700K tok/hr → 按此应为 **$0.357/M**。**同一张表里自身的算术就差了 1000 倍**（$0.25 ÷ 0.7M tok = $0.357/M，表里写 $0.00036/M）。
- 源 B：Flowstate 测算「自有节点满负荷 ≈ **$0.66/M**」；另一份把自建 3,000 tok/s 的机器算成 **$1.83/M 输出 token**。
- 同一个量（27B 级本地部署的每百万 token 成本），不同来源给 $0.01 / $0.357 / $0.66 / $1.83。**差 180 倍，判为真矛盾。**
- **更可信：按各自吞吐复算，而不是直接采信任何一方**。理由：这四个数分别对应 700K、3,000、约 1,000 tok/s 量级的吞吐假设，**它们争论的不是成本，是吞吐口径**。本 run 用自己可复算的单卡 22 tok/s 得到 $1.44/M 输出 token，与源 B 的 $1.83/M 同量级（差异来自利用率假设），与源 A 的 $0.01/M 差 144 倍（差异来自「把满批处理的集群吞吐套到单机」）。
- 后果：**任何「自建只要 $0.01/M」的说法在单流单机场景下不成立，会低估 100 倍以上。**

**矛盾 2 · 同一任务的 $/M 可以差 74 倍（分母口径之争）**
- 源 A：把上下文 token 计入分母 → 本 run 的 $0.024/M。
- 源 B：只把输出 token 计入分母 → 本 run 的 $1.58/M。
- 两者用的是同一台机器、同一个任务的同一笔钱，仅分母不同。题面定义的「每完成一个任务多少钱」不涉及这个选择，但**所有对外比较都会撞上它**。
- **更可信：题面的口径（每任务）优先；若必须报 $/M，一律注明分母。** 理由：不注明分母的 $/M 不可复算，也就不可比较。
- 后果：这不是数值矛盾，是**定义矛盾**；它解释了为什么矛盾 1 里那四个数能同时「正确」。

**矛盾 3 · 缓存前缀的价格：0×（省掉）还是 0.1×（照收）**
- 源 A：自建 vLLM「自动前缀缓存」，命中部分的预填计算被省掉，5–10 倍加速（≈免费）。
- 源 B：商业 API 上缓存读按标准输入价的 **10%** 计费（另有一家报到 2.5%）。
- **更可信：源 A 对本 run**。理由：定价折扣是商业策略，不是物理成本；自建时省钱 = 真的少算 FLOPs。
- 后果：本 run 取 ≈0；若按 0.1× 计，缓存前缀要加 $0.00012，成本涨 7.6%，**不改变排序**。

**未判为矛盾的**：vLLM 集群 26,200/10,100 tok/s 与单流 1,503/22 tok/s 的差异（不是同一量，是批处理前后的两个量）、电价口径差异。

## 9. 自检

- **完整**：三类 token × 各自单价 + ÷p 还原 C_task，且与「时间×小时成本」这条独立路径互验通过（差 0.1%）。单价支的三项共用一个 S_hourly，已按量加权而非加和，未重复计钱。✓
- **不重叠**：三个 u 抢的是**同一台机器的不同时间片**（预填与解码在时间上互斥），所以按「每小时能产出多少该类 token」分配 S_hourly 是干净的；账本支只提供量，不提供钱。**已知耦合**：批处理同时抬高 u_out 的分母（好）和压低每流速度（坏，撞 20 tok/s 约束），一个旋钮两个方向，本 run 在 §5 用折减系数表达但未精确建模。**已知遗漏**：KV 显存限制批大小上限（显存是批大小的硬顶），本 run 完全没建这一支——若显存只能支持批 2，§5 的 4–8 倍杠杆就吃不到，这一条必须补。
- **未做**：n_out、64K 深度单流 tok/s、批后每流折减、p。按本 run 的判断，前两项优先。
