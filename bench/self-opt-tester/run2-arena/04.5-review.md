## Q2：链路总消耗 −30% 的最小改动（只改 prompt/SOP，1-2 个）

**改动 1｜规则负载瘦身 + 示例按需加载（打步骤 4 的 F1×F2）**
- 内容：loop/prompt-first/*.md 的示例/案例段（实测 3,535 o200k = 38%，M2）抽到 `loop/prompt-first/examples/`；主文件留 ≤40 行规则卡（操作流程+判定标准）；00-common 与 sop/arena-loop-pipeline 重复的降级/门禁段去重（SOP 为唯一入口）；goal 模板加一句"示例仅在阶段判定不确定或 revise 时读"。
- 依据：pilot 实况已证明 **~1.1k o200k 规则卡（M5）能驱动全流程达 91/91/98（M8）**——全量 12,086 并非质量必需；外部 E4 同向（规则文件 +20% 成本、收益甚微）。目标 L：12.6k → 6-7k o200k（−45-50%）。
- 机制：L 每 turn 重发，T≈45 时省 ≈ 5.6k×40 ≈ **−0.22M/会话**（固定部分 −45%）。

**改动 2｜迭代协议改增量任务书 + 轮数上限（打步骤 6 的 F4）**
- 内容：goal-template §3.0 步骤 6 与 arena-loop-pipeline.md 把"一轮迭代 = 任务书全量重发"改为"一轮迭代 = **delta-brief**：漏洞清单 + 仅涉事阶段规则卡 + 上轮工件 git hash 清单 + 变更范围"；加硬上限"≤2 轮，未达 conf 0.7 转 Lead 裁决"。
- 机制：第二轮 L 12.6k→3-4k、T 45→20 → 第二轮会话 −60-70%。

**合并估算（conf 0.5-0.6，模型假设 T/U 未实测）**：情景 a ≈ **−31%**（贴线达标）；情景 b ≈ −50-57%。两情景均 ≥30% 或贴线 → 建议两项同上（单项改动 1 约 −25-30%，不足以在保守情景保证 30%）。
**排除项（如实记录）**：prompt caching/KV cache（harness/API 层，越权）；模型分层 orchestrator-worker（harness）；砍阶段数（与 M8 的 V4 +10/+15/+19 质量实证冲突）。

# 04.5 反方检查
- **薄弱点 1**：T=30-60 与 U=25-50k 是假设（repo 无 turn 记录）。反制：结论只用数量级（大头排序对 T 在 20-100 内不敏感：步骤 4/6 是仅有的两个"整会话级"成本，与 T 具体值无关）；度量方案强制下轮实测。
- **薄弱点 2**：arena compaction 可能已削减重发放大（round1 笔记）→ 模型或高估。反制：情景 a 给出 −31% 贴线值而非取中位；若 compaction 已生效，实际基线更低，但瘦身仍同比例有效（L 变小对任何重发机制都省）。
- **薄弱点 3**：o200k tokenizer 是 OpenAI 口径，非各实际模型 tokenizer。反制：字节数（wc -c）同表给出，比例结论（6.44×、38%、12,086 全量 vs 1.1k 卡片）对 tokenizer 选择不敏感。
- **薄弱点 4**：外部来源多为二手（Anthropic 原文经转引）。已标 conf ≤0.7；关键主张均有内部实测双源（C1-C3）。
- **未完成项**：Q3 度量未执行（属下一 run 的工作，本 run 只交付度量设计）；T/compaction 实测空缺移交 run3 或下轮。
- **残余风险**：示例抽走后 agent 在 revise 场景可能不读附录（遵从性）→ 度量 1 的 ③ 质量门即为该风险的检测器。
- **最有价值的下一步**：按度量 1 先跑瘦身 A/B（最小成本、最大杠杆），把 M1′ 输入代理固化进 bench.md。
