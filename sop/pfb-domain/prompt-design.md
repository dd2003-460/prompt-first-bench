# Prompt 臂设计规范

> origin: ai · 2026-11-07 · pfb 领域 SOP
> 为什么需要这份文件：prompt 是 pfb 的核心变量。臂设计错了，后面所有评分都是噪音。这份文件记录"什么样的 prompt 结构有效、为什么有效"，不是"必须用这个模板"——模板会过时，原则不会。

## 版本线（不要跨版本比较）

| 版本 | 名称 | 核心特征 | 状态 |
|------|------|---------|------|
| v0 | 朴素空间 | 无结构，直接问 | baseline |
| v1 | 数学/代数 | 代数化分解（因素枚举→公式推导） | 已淘汰 |
| v2 | 混合引导式 | 引导式思考 + 机械检查 | 主力（S5 基于此） |
| v3 | 先查后拆 | 调研→矛盾→按证据分解→递归 | 开发中 |

**为什么不能跨版本比分数**：v1 的"代数分解"和 v3 的"先查后拆"解决的是不同层次的问题。v1 假设答案可以从已知条件推导出来，v3 假设答案需要先找到证据才能正确分解。把 v1 的 0.55 和 v3 的 0.79 放在一起说"v3 比 v1 好 0.24"是有意义的；但把 v1 和 v0 比就只是"有结构比没结构好"，信息量低。

## S5 当前结构（v2 主力臂）

```
阶段 01 — 目标分解
  引导语："在动手之前，先花几分钟想清楚这个问题到底在问什么。
          列出你知道的、能推出来的、还缺的。为什么要先做这一步——
          如果直接扎进搜索，注意力会被'找到了什么'牵着走，
          很容易在错误的方向上花掉大部分时间。"
  产出：因素列表 / 已知条件 / 可推导条件 / 缺口清单

阶段 02 — 信息搜集
  引导语："现在带着缺口清单去查。每条缺口对应一个具体的搜索方向，
          不是泛泛地'了解更多'。"
  工具：arXiv API + KNOWN_SITES 直访（见 research-hook.md）

阶段 03 — 综合验证
  引导语："把找到的东西拼回去，看有没有漏。两条线索互相矛盾时，
          哪个更可靠？为什么？不确定的地方标出来，不要硬填。"
  产出：最终答案 + 不确定性标注 + 引用来源
```

**关键设计决策**：每个阶段的引导语都包含"为什么做这一步"（因果句），不只是"做什么"（指令句）。这不是修辞——S10 实验证明 reviewer 讲原因（C臂 0.704）比不讲原因（A臂 0.426）让模型多覆盖 3.5 倍的缺口。

## S10 Tone Finding（@4ecb5ee · 自判 conf cap 0.7）

**一句话：reviewer 怎么说比说什么重要。**

| 臂 | 策略 | Total | vs A |
|---|---|---|---|
| A | 机械清单式反馈 | 0.426 | — |
| B | 人话 reviewer | 0.746 | +0.320 |
| C | 讲原因 | 0.704 | +0.278 |
| D | soothe（安抚情绪向量） | 0.751 | +0.325 |
| E | 组合(B+C+D) | 0.748 | +0.322 |

维度拆解：
- **M4 缺口覆盖**是最大差距源：A=0.189 vs 其他≈0.55-0.71。机械反馈让模型只修表面问题。
- **M6 URL 存活**：A=0.000，其他全部 1.000。机械反馈把模型逼进了"不查资料只列要点"模式。
- **M3 不确定性标注**：A=1.000 反而最高——因为输出短、hedge 多但内容空。M3 高分≠质量好。

**对 prompt 设计的启示**：
1. 面向模型的反馈（reviewer/judge/critic）用目标+原因结构，不用打勾清单
2. 被拒后的安抚（soothe）有实际效果——它降低了模型的"防御性收缩"倾向
3. 具体指认缺口 > 泛泛说"不够好"。"第 3 条缺少数值支撑"比"质量需提升"有效得多
4. 这些原则适用于所有 AI↔AI 交互场景，不限于 pfb

## 新臂设计检查清单

设计新臂时过一遍（不是打勾，是问自己）：
- [ ] 每个阶段有"为什么"吗？（没有 → 模型不知道为什么做，容易跳过或敷衍）
- [ ] 引导语是启发式的还是命令式的？（"试试从 X 角度想" > "必须列出 X"）
- [ ] 执行/检查环节可以机械化吗？（是的——URL 验证、格式检查这类不需要判断力的步骤用机械规则就行）
- [ ] 跟现有臂正交吗？（两个臂测同一个变量 = 浪费 run 预算）
- [ ] 失败模式是什么？（提前想好"如果模型在这个臂下卡住，会卡在哪儿"）

## 反模式（踩过的坑）

1. **全机械检查**：v1 的代数分解就是反面教材——把"理解问题"变成"套公式"，模型失去了判断力
2. **过度结构化**：阶段太多（>5）会让模型在早期阶段耗尽注意力，后面敷衍
3. **模糊指令**："深入分析"、"全面考虑"——模型不知道"深入"到什么程度算够，要么过度要么不足
4. **跨版本混跑**：v2 和 v3 的 prompt 结构差异太大，混在同一批 run 里会让统计检验失效
