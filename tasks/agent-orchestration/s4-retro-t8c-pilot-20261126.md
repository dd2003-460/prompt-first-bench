## 补充故障模式（2026-11-27 凌晨，S4-1 交付时观察到）

6. **sub 汇报层复读循环 ≠ 执行失败**（deleg_3e9281bb）
   → 现象：sub 执行层全落盘（commit 9309abbaf 完好、逻辑 5 处在位、worktree 无半成品），
   但写最终汇报行时掉进复读循环被掐 → 系统报 failed。
   → 处置规则：收到 sub failed 先核磁盘（commit 链 + 逻辑在位 + worktree 干净），
   三件全过 = 误报，不重派（重派 = 重复劳动 + 烧 token）。
   → 与既有"信磁盘不信 sub 最后一句话"规则同构，本案例是其在 failed 通知上的应用。
7. **monitor 静默停摆（状态列精确匹配）**
   → 现象：任务行状态写「就绪（2026-11-27 00:07 立项）」（带括号注释），
   queue_monitor 的 `st in ("就绪","执行中")` 精确匹配 → 整行跳过 → 队列假 IDLE，
   任务永不被认领（比 STALE 盲区更隐蔽：STALE 还有 45min 翻转，这个是永久停摆）。
   → 修复：解析器 re.sub 剥括号后缀再判（已修，commit 见下）；
   → 教训：monitor 的信号完整性 = 架构的感知层，解析器对状态列的容错必须
   覆盖"人会在状态列加注释"这个高频行为。
8. **Lead 直接起重复进程（跨会话协调盲区，2026-11-27 00:37）**
   → 现象：CapFix-Verify 已由微信执行者 00:29 完成（回执 DONE），Lead 00:37 未查
   receipts/ 直接起重复进程 25725，跑完 stage 01 后覆盖执行者的 sidecar B1_01/B1_02
   （固定文件名），靠 git 从执行者 commit 67d0582fb 恢复。
   → 根因：monitor 的 WORKING 状态只挡执行者之间互抢，不挡 Lead 直接起进程——
   两个独立会话（QQ Lead + cron 执行者）盯同一张任务表，锁的覆盖面缺了 Lead 这一侧。
   → 处置：executor-protocol 硬边界加「起长任务前查 receipts/ 当锁」（commit 5c419fe55）：
   任何会话起长任务前 `ls receipts/<短ID>.json`，status∈{claimed,working,done} → 不重复起。
   判别信号：sidecar/产物 mtime 早于自己启动时刻 = 别人先跑过，立即停手核回执。
   → 与 #3 同族：都是"感知层覆盖不全"——#3 是执行者对完成事件无感，#8 是 Lead 对
   执行者已认领无感。架构可靠性结论需修订：可防御范围 = 执行者↔执行者互抢；
   Lead↔执行者跨会话协调目前靠 receipts 锁 + 人工纪律，未形成架构内闸门。

## 补充故障模式（2026-11-27 N9 周期，T8c n=9 正式跑放行→完成→判决）

9. **monitor 状态列嵌套括号破坏正则（#7 同族复发，2026-11-27 01:45）**
   → 现象：T8c-N9 行状态写「就绪（…；命令钉死 `cmd`（内置备份…）；验收：…）」，
   括号内又嵌了第二层括号。queue_monitor 的 `re.sub(r"[（(].*?[)）]", "", st)` 是非贪婪，
   只剥第一个括号组，嵌套括号导致剥离后剩余 ≠「就绪」→ 整行跳过 → READY 信号丢失，
   队列假 IDLE（与 #7 同型，但 #7 是单层括号注释，本条是嵌套括号）。
   → 根因：状态列自由文本 + 正则剥离，对"括号里再带括号"无容错。
   → 处置（commit 61952d51c）：状态列详情全收进**单层**括号，禁嵌套；任务卡正文承载
   细节，状态列只留「就绪（一句话理由）」。
   → 教训（与 #7 合并）：状态列是机器解析的信号位，不是给人读的注释位。凡是要进
   monitor 的状态列，格式约束应**写进任务表表头**（"状态列禁嵌套括号/禁多句"），
   靠人自觉 = 迟早复发。当前靠事后修，未做表头硬约束（遗留）。

10. **执行者任务卡映射行缺失（认领后找不到任务卡，2026-11-27 01:45 放行时补）**
    → 现象：T8c-N9 转就绪后，executor-protocol 的「任务卡映射」表里没有 T8c-N9 行。
    执行者按协议 step3「读任务卡（路径见映射表）」会找不到路径 → 认领后卡死或乱找。
    → 根因：派发流程只更新了 decomposition 任务表的状态列（转就绪），漏了同步
    executor-protocol 的映射表——两张表是同一队列的两个视图，改一忘一。
    → 处置（commit 288f58561）：补映射行 `T8c-N9 → n9-taskcard.md`。
    → 教训：「转就绪」是个复合动作 = ①任务表状态列 ②executor-protocol 映射行 ③任务卡文件存在。
    三者缺一执行者就会卡。应在协议里把"转就绪"定义为 checklist（三项全过才算就绪），
    而非隐式约定。当前靠 Lead 记得，未制度化（遗留）。

11. **长任务脚本非幂等（进程中途死 → 接力重跑产生重复 run，2026-11-27 01:45 补）**
    → 现象：run_exp_t8c_n9.py 原设计是"从头跑 run4-9 追加"，无"跳过磁盘已有 run"逻辑。
    若 A 臂跑完 3 个后进程死，执行者接力重跑会**重复跑已完成的 run**（浪费 + 可能重复 append）。
    → 根因：脚本假设"一次跑完"，没考虑 setsid 长任务中途死亡后的接力场景（#4 已证 Hermes
    跟踪进程会被回收，setsid 长任务死亡是常态非常态）。
    → 处置（commit 288f58561）：run_arm_a/b 各加 `existing = {s.get("run") for s in ...}`，
    循环开头 `if i in existing: continue`。幂等单测：run1-9 全在盘 → 0 HTTP 调用、无重复。
    → 教训：**长任务脚本必须幂等**（跳过已完成单元），这是 setsid 长任务 + 接力模式的
    硬前提，不是可选项。任务卡的"接力=重跑"规则只有在脚本幂等时才安全。
    应在 executor-protocol 硬边界加一条："长任务脚本必须幂等（跳过磁盘已完成单元），
    任务卡验收含幂等单测"。当前靠逐脚本手工加，未制度化（遗留）。
