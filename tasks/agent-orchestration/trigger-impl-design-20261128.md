## 0. 一句话
把 S2 的五条 T-条件从"写在任务卡里的软提醒"变成执行者循环里**机械检测 + 强制中断**的硬触发器: 检测到信号 → 停下当前动作 → 跑固定的思考轮 (反思+查证) → 带 thinking_log 继续。M 线实验已证软提醒无效, 这是硬触发的实现层。

## 1. 信号 → 检测器映射 (S2 五条件归并为三信号)
| 信号 | S2 原条件 | 机械检测 (执行者每拍自查, 全可脚本化) | 检测成本 |
|---|---|---|---|
| 矛盾 | T-矛盾 + T-失配 | ① 本拍要写的数字/事实, grep 任务卡真值节+上一拍回执, 不一致=触发 ② 回执 status 与磁盘事实不符 (evidence 路径不存在) | 低 (grep/ls) |
| 卡住 | T-卡死 | 同一操作 (同命令/同文件同区域) 连续 2 拍无新落盘产出 (diff 为空) | 低 (git diff) |
| 缺口 | T-数字 + T-单源 | ① 本拍产出含具体值但无出处标注 (正则: 数字后无 路径/commit/运行号) ② 结论句引用的来源计数=1 | 中 (正则+来源计数) |

归并理由: 五条是同一件事的五个症状——"执行者要往下走了, 但脚下没有验证过的事实"。三信号是症状的最小完备划分 (矛盾=事实冲突, 卡住=无进展, 缺口=无依据), 再加第五条就是过拟合 S2 的措辞。

## 2. 触发后的动作 (固定思考轮, 非自由发挥)
触发 → 执行者停当前动作 → 跑一个固定模板的反思轮 (写进执行者 prompt, ~10 行):
1. 复述触发的信号和证据 (哪个数字/哪个 diff/哪个无出处值)
2. 回答: 我的下一步动作依赖这个未验证事实吗? 依赖=先验证再动; 不依赖=标 [待核验] 继续
3. 验证动作 (按信号类型): 矛盾→核磁盘一手; 卡住→换路 (换工具/拆小步/降级, 按 flexible-execution); 缺口→跑出来或找第二来源
4. 写 thinking_log 进本拍回执: {signal, evidence, action, result}
**边界**: 思考轮本身限 1 轮 (防思考轮里再卡住); 同信号同证据 2 次触发 = 升级回执 (报监督者, 不自己硬磨)。

## 3. 挂载点 (用现成的, 不新造)
- 检测器: 执行者 cron 每拍开头的固定脚本步骤 (读上拍回执+本拍计划 → 跑三个检测 → 输出 trigger/no-trigger JSON)。载体=脚本 (机械), 不占模型 token。
- 思考轮: 执行者 prompt 里的固定段 (触发时读 trigger JSON 注入本拍上下文)。
- thinking_log: 回执 JSON 加字段 (schema 变更走 L4 验收层, receipts schema 冻结需同步更新)。
- 监督者侧: 验收时机械检查 thinking_log 存在性 (触发过就必须有, 无=打回), 不读内容 (内容判断留给抽检)。

## 4. 缺口信号的 prompt 侧 (探针依赖, 待定)
trigger-probe-v2 判 PASS (模型在有通道+缺口时自发查) → 缺口信号可降级为"给通道+提示, 不硬触发";
判 FAIL → 缺口信号必须硬触发 (检测器发现无出处值 → 强制思考轮, 不指望模型自觉)。
两种结果都保留矛盾/卡住的硬触发 (探针不覆盖这两信号)。

## 5. 验收 (本设计的完成标准)
1. 三检测器脚本落盘 + selftest (构造 3 个触发 case + 3 个不触发 case, 全对)
2. 执行者 cron 接入: 连续 2 拍, 其中 1 拍人为制造触发 (任务卡埋一个与磁盘矛盾的假数字) → thinking_log 出现且处置正确
3. 回执 schema 更新 + L4 验收命令加 thinking_log 检查
4. 与 S2 试点 (T8c) 的 thinking_log 格式兼容 (s4-retro 已有触发记录, 不另立格式)
