# 监督者-执行者架构（supervisor-executor）

## 一句话核心
**工作以「任务卡 → 执行者 → 回执」三件套流经队列；监督者只看回执和任务表，执行者只看任务卡和磁盘，思考机制=执行者的矛盾触发器（不是软提醒）。**

其余全是这条的推论。

## 为什么是这个形状（推导链）
1. 监督者（QQ/微信入口）亲自下场 → 上下文被执行细节灌满 → 品味下降 → 方向错（今日 J3b 反例实证）。⇒ 执行必须离开聊天入口。
2. 执行者瞬态（delegate_task sub）→ 27b 输出上限，输入>300行/输出>100行必死（今日 7 死 6 实证）。⇒ 执行者要持久、要有落盘接力（任务书/回执都是磁盘态，不依赖会话内存）。
3. 思考软提醒（stop_hook 常驻提示）→ 实证无效（D 11-26 指正"有 hook 为什么没看到你认真思考"）。⇒ 思考必须由**可证伪的矛盾**触发，触发器=一组具体异常条件，不是"请认真思考"。
4. sub 汇报"成功"≠成功（今日 T6-XCHECK：sub"死"了但工作其实完成了；反向也有：汇报成功但数字错）。⇒ 验收=回执+磁盘核验+数字复算（Selective Verification：查最便宜的决定性点）。
5. sub 会越权（Show-Up Attack，前沿模型 ASR 最高 0.93）。⇒ 任务书锁死范围（文件清单+边界节），验收核 scope。
6. 执行者共享同一份坏任务书会集体错（Selective Verification 的 shared failure）。⇒ 任务书里的关键数字必须带出处（oracle 实跑/文件路径），监督者在派发前核验过。

## 四层结构

### L1 监督者层（QQ/微信/CLI 入口 = 你和我的聊天会话）
只做四件事：
- **方向判断**：goal 对不对、优先级、品味（claim 可防御性）
- **任务表**：编辑 decomposition.md 任务表（唯一工作队列）
- **派发**：写任务卡（自包含：goal/验收/边界/关键数字带出处）
- **验收**：读回执 → 核磁盘/commit/复算关键数字 → 放行或打回
不做：读长文件、写代码、跑实验、改多文件。
上下文检验标准：被问"更大方向"时，上下文里主要是方向判断，不是执行细节。

### L2 队列层（磁盘，单一事实源）
```
tasks/<goal>/decomposition.md   # 任务表（强制列：任务|依赖|读|写|commits|载体）
tasks/<goal>/cards/TASK-<id>.md # 任务卡（自包含指令，执行者唯一指令来源）
tasks/<goal>/receipts/<id>.json # 回执（执行者写，监督者读）
```
任务卡格式（今日 reanchor-taskcard.md 已验证可行）：背景（执行者不需理解）+ 真值（带出处）+ 执行方式 + 逐点替换/步骤 + 验收命令 + 边界（不许动什么）。
**派发前门禁**：任务卡关键数字已核验（①类来源）；I/O 过阈值（读>300行/写>100行）→ 先拆或换载体。

### L3 执行者层（Hermes cron job，持久，每 10-15 分钟一拍）
执行者 = 一个 cron session，固定 prompt，每拍：
1. 读任务表 → 找就绪任务（依赖全 done，无 in-progress 冲突）
2. 认领（回执文件先写 status=claimed，防多执行者抢同一任务）
3. 按载体规则执行：
   - 机械提取/检查 → 脚本（执行者写小脚本跑，不手打内容）
   - 纯执行+散文<100行 → 自己干（cron session 内）
   - 判断/综合 → 写判断回执，标 conf，留给监督者
   - 需要更强推理 → 派 delegate_task sub（任务卡已按阈值拆过）
4. **思考触发器（内置，矛盾驱动，非软提醒）**——执行中遇到以下任一条必须停下处理：
   - T-数字：要写的数字没有出处（文件路径/运行记录）→ 先跑出来或标 [待核验]
   - T-单源：结论只有一个来源 → 找第二个独立源，找不到降 conf
   - T-矛盾：与已有 checkpoint/日志/任务书真值矛盾 → 停下，核磁盘，不猜
   - T-失配：任务书描述与实际数据不一致（数量/格式/路径）→ 停下，回执报失配，不模糊匹配
   - T-卡死：同一操作 2 轮无新事实 → 换路（换工具/拆小步/降级），不硬磨
   每次触发写进回执 thinking_log（触发条件+处置+结果）——这就是"完整思考加入机制"的可观测形式。
5. 写回执 JSON + git commit（回执和产出同 commit，留痕）

### L4 验收层（监督者执行，机械化）
每个任务卡自带验收命令，监督者验收=跑三条检查：
1. **回执检查**：status=done + evidence 路径存在
2. **scope 检查**：`git diff --name-only <base>..HEAD` ⊆ 任务卡声明的文件（防 Show-Up 越权）
3. **数字复算**：关键数字独立重跑一次（oracle/selfcheck），对得上才放行
全过 → 任务表标 done；不过 → 打回（回执标失败原因，执行者下拍看到后换路重试，2 次同死法=换载体）。

## 分配系统（载体判定，今日实证规则制度化）
```
任务 → 读(行)/写(行) 估计 →
  机械（替换/提取/检查）        → 脚本（执行者写脚本跑）
  判断/综合/设计                → 判断-监督者 或 arena（外部交叉）
  纯执行+散文产出 <100 行       → 执行者直接干
  读>300 行 或 写>100 行        → 必须再拆（S1 纯提取→JSON + S2 综合）
  同一任务同一死法 2 次         → 换路（禁止第 3 次原样重派）
```
多执行者：任务表加 lane 列；认领机制（claimed 回执）保证互斥；并行上限=2（共享 worktree 冻结规则：执行者不 stash/checkout）。

## 验收标准（本 goal）
1. 执行者 cron 上线：连续 3 拍空转正常（无任务时静默退出，不刷屏）
2. 试点跑通：T8c 重锚定经 L1→L2→L3→L4 全流程，监督者会话零执行细节（只读回执+跑验收命令）
3. 思考留痕：试点回执 thinking_log ≥1 条真实触发（T8c 任务书已知有 6f 洞，执行者应触发 T-失配）
4. 回执格式冻结：receipts/*.json schema 落盘 + 示例
5. SOP 写回：本文件精华进 sop/，decomposition.md 任务表加 lane 列

## 风险与边界
- **cron 执行者上下文同样有限**：每拍是新 session，任务必须自包含（任务卡已保证）；长任务（>1 拍）用 background terminal + notify_on_complete，回执记 PID
- **执行者判断力 < 监督者**：27b 执行者只做机械+浅判断；判断类任务它只收集事实（S1 模式），判断留给监督者
- **cron 频率成本**：10-15 分钟一拍，空转一拍=几次读文件，成本可忽略；有任务时一拍内干完一个任务（任务卡已按粒度拆过）
- **不接的**：Agent Teams AI / arena 通道本期不接（MVP 先验证闭环，再接第二执行者池——D"一个或更多执行者"的"更多"=二期）

## 交叉验证（缺口 ④ 收口, 2026-11-28, ego-browser 双源）
**S2 关键判断 ≥2 独立来源交叉**: ChatGPT + Gemini (同题, 英文, 已登录 ego-browser)。
- **一致性**: 两源独立给出相同结论——(a) 监督者/执行者分离健全 (保护监督者上下文/战略带宽); (b) 机械触发 > 软提醒 (1/3 vs 端到端 PASS 是直接证据, 两源都认)。
- **共同指出的最弱假设 (false negative)**: 机械触发只覆盖"可检测的矛盾" (数字不匹配/卡住/缺口), 覆盖不了**内部一致但语义错误**的结果——回执看着合法但推导有洞/边缘 bug/误读。两源措辞不同但指向同一缺口。
- **落地的缓解 (已在本架构内, 非新增实体)**:
  1. 验收层 L4 本就是"数字复算+磁盘核验" (S2 第 4 条推导), 抽检语义 = L4 的职责, 不是执行者的——两源建议的"risk-based verification / 抽检"已由 L4 承担。
  2. Gemini 建议"bound retries" (卡住的机械重跑设上限, 超限升级监督者) → 已入 S4 SOP (DEAD 探活+故障模式 1-7), 采纳。
  3. 残留 [真缺口]: 语义错误的抽检目前靠监督者人工 (L4), 未机械化。这是 S2 架构的已知边界, 不阻塞 MVP, 二期考虑 (自动语义 tripwire: 异常残差/跳过的断言/测试失败触发升级)。
- **结论**: 架构判断经双源交叉确认健全; 最弱假设 (false negative) 已识别且部分缓解 (L4 抽检+retries 上限), 残留语义抽检机械化列为二期。缺口 ④ 收口。
