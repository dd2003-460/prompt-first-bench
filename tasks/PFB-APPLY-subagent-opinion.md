# Subagent 意见：PFB-APPLY 中期目标挑毛病

> origin: ai · subagent 讨论轮 · 2026-11-07
> 依据：tasks/PFB-APPLY-midterm-plan.md + scoring.md + d1-score-draft.md + competitor-survey.md（全部本轮读过的仓库文件）

## Q1. 伪需求子项

**结论：B2（换第二个模型家族跑同题）是伪需求，对四个验收面都没实质贡献。**

A 可应用不需要它——CLI 用户默认就用本地这一个模型，产品不承诺"多模型都能用"。C 打赢开源更不需要——对手 GPT Researcher 也是跑在同一个 27b 上，比的是流水线不是模型，换模型反而把变量搅浑。D gold 复现也不需要——gold 门禁量的是流程在新题上能不能达到阈值，跟用哪个模型无关。唯一沾边的是 B 泛化，但"真实泛化"的核心是题目域泛化（没见过的题也行），不是模型泛化——用户原话锚定的是"真实泛化也能打赢开源"，没说换模型。砍掉后省下的精力投到 B1（加新领域题目）上，才是真泛化。

## Q2. 执行顺序哪里错了

**结论：C3 配对检验排在 C1 后面、C2 检索对齐拖到最后，这两个位置都反了。**

第一，C3 依赖 C1 的 D1 扩 rep 数据没错，但 Q1（battle 异族打分 S10）排在第 3 位却只服务 S10 一个旧臂，而主 claim 的统计硬化（C1→C3）应该和 D 门禁并行推进——C1 纯本地跑 ~2h，D 的 arena 建树可以外包出去等结果，两条线互不阻塞，现在写成串行浪费时间。第二，C2 放最后是最危险的：D1 现在用 duckduckgo 无 key 检索是下限配置，C1 扩 15 runs 再跑配对检验，测的还是这个下限。如果第二轮才换检索器，C1/C3 白跑一遍，整个 C 面要重来。正确顺序应该是 C2 的可行性判断（免费额度够不够）先于 C1 开跑，哪怕先用现有配置跑一版做方向确认，也得把"要不要重跑"的决策点提前。

## Q3. 不可机器检查的验收标准

**结论：D3「达到 gold 级阈值」不可机器检查，因为"gold 级"本身没有定义成数字。**

gold tree 有 31 个节点，但"对照 gold 标准打分：达到 gold 级阈值？"这句话里，阈值是多少分、按哪几个维度算、judge 间分歧超过多少算仲裁，全都没写死。改成可查的版本：S5 盲跑输出与 gold tree 做节点级比对（Jaccard/覆盖率），总分 ≥ X（X 从已有 gold 对比数据里取一个具体数，比如 pfb 历史 run 对 gold 的分位数），且 M4/M5/M6 三个维度各自 ≥ Y，双 judge 分差 ≤ Z 才算过；超了走仲裁。Q1 的 κ≥0.6 倒是可查的（有 assert-kappa-receipt.py 消费 schema），但前提是 battle 回执落盘且成功家族数 ≥3——这条计划里写了，没问题。真正缺数字的只有 D3。

## Q4. 最大单点风险

**结论：评分器本身是单点风险——所有分数都是同一个 27b 自判的，它一偏，四个验收面全塌。**

scoring.md 自己承认 self-judge bias，conf cap 0.7，S5 的 0.7907 和 D1 的 0.602 都出自同一把尺子。如果这把尺子系统性偏好某类输出风格（比如偏爱长报告或特定结构），那 S5 vs D1 的 Δ+0.189 可能是尺子的幻觉而不是流水线的功劳——C 面的主 claim 直接建立在上面，塌了就全塌。对冲办法计划里其实已经埋了（Q1 battle 异族 judge κ≥0.6），但排在了第 3 位，太晚。应该把异族 judge 校准提到最前面：先用 battle 通道对现有 S5/D1 的 35 个已打分 run 做一次异族复评，κ 达标了才信后续所有分数，不达标就先修 rubric 再跑任何新实验。这是花钱买保险，但保险对象是整个项目。

## Q5. 只能砍一个保进度

**结论：砍 B2（模型泛化），理由同 Q1。**

五个候选里 A 是用户点名的"最终可应用"不能动，C 是主 claim 不能动，D 是用户点名的前置不能动，Q 是质量红线不能动。B1/B3 是 B 面的核心（题目域扩展 + 评分器泛化），B2 是唯一可降级的——缺口标注里自己也写了"没有就降级为单模型+声明"，说明它本来就是备胎。砍掉后在报告里诚实声明"模型泛化未验证，结论限定在 27b 家族内"，不影响其他任何验收面。
