# 质疑机制状态机（落地与驱动）
# origin: human (D 2026-11-28 "状态机停止条件什么的能写吗") + ai (设计)

## 设计原则

1. **不靠模型自觉触发**（S5 实证：27b 自发质疑率低）。结构转移由 harness 强制，语义判断由模型负责。
2. **分工**：harness 拥有"何时启动/何时停止/去哪检索"（结构）；模型拥有"质疑什么/反驳得了吗/证据是否解决缺口"（语义）。对应 D 既定架构：检索层可纯 hook，写入裁决需模型。
3. **载体 = 分解树**。质疑的结构化版本 = 带缺口的分解（D 2026-11-28）。缺口挂在分解节点上，缺口注册表按 (task, node, gap-statement) 键控。
4. **每个状态有预算**，防止无限循环。预算耗尽 = 合法停止，不是失败。

## 状态定义

| 状态 | 干什么 | 谁驱动转移 | 预算 |
|------|--------|-----------|------|
| S0 WORKING | 执行当前任务（推理/代码/实验） | — | — |
| S1 QUESTIONING | 对当前工作的**前提**（不是细节）列质疑：方向/前人/更快/性价比四刀 | 进入：harness（结构触发）；离开：模型 | 每工作节点 ≤1 次 |
| S2 REFUTING | 逐条尝试反驳自己的质疑 | 模型 | 每条质疑 ≤1 轮反驳 |
| S3 GAP | 质疑存活 → 形式化缺口：{陈述, 为何反驳不了, 什么证据能定案}，查重后写入缺口注册表 | 进入：模型判定存活；离开：harness（查重+路由） | 每任务 ≤5 个活跃缺口 |
| S4 RETRIEVING | 按通道序填缺口：本地文件 → GitHub → arXiv → 网页 LLM(ego-browser) → arena | harness 路由 | 每缺口 ≤3 通道 |
| S5 INTEGRATING | 裁决证据是否解决缺口（模型）→ 更新记忆/先验/注册表 | 裁决：模型；写入：harness | — |

终态（从 S5 出发）：
- **RESOLVED**：证据定案（能反驳或确认）→ 回 S0，新先验注入
- **PERMANENT**：通道耗尽仍未决 → 注册表标"永久未知"+置信上限，回 S0 继续（带着天花板工作）
- **FRONTIER**：定案需要新实验（不是检索能解决的）→ 转为实验任务入队，回 S0

## 转移条件

```
S0→S1  结构触发：工作节点命中（规划完/派发前/验收时/不可逆决策前/汇报前）
       语义触发：模型自由推理中声明缺口（防御性语言）——best-effort，logprob 探针只排序不触发
S1→S2  质疑清单非空；空 → 直接回 S0（无缺口，正常）
S2→S3  质疑存活（反驳不了）；被反驳 → 丢弃，继续 S2 下一条
S3→S4  缺口形式化且查重通过（注册表已有同键 → 合并，不新开检索）
S4→S5  三选一：找到定案证据 / 通道耗尽 / 预算耗尽
S5→S0  RESOLVED 或 PERMANENT
S5→S3  检索暴露子缺口（缺口可再分解）——深度 ≤2，防递归
S5→FRONTIER  定案条件 = 新实验 → 不检索，转实验队列
```

## 停止条件（汇总）

| 层面 | 条件 | 动作 |
|------|------|------|
| 推理线程 | 到达 S3（反驳不了） | **停该线程推理**，不再空转——这是"停止条件"的本义 |
| 检索 | 找到定案证据 | 关缺口，RESOLVED |
| 检索 | 通道耗尽（3 通道）无果 | PERMANENT，标置信上限 |
| 检索 | 预算耗尽（时间/token） | 同上，标"预算止" |
| 缺口循环 | 同缺口 ID 两轮检索仍未决 | 停止自动检索，升级：换分解角度 / 标 FRONTIER |
| 全局 | 任务验收标准达成 | 未决缺口全部留在注册表（不阻塞交付，但随交付物一起标出） |

## 缺口注册表（持久状态 = "知道自己不知道"的存储）

```yaml
# tasks/<task>/gap-registry.yaml
gaps:
  - id: G-001
    node: "分解树节点路径"
    statement: "瓶颈可能是检索而非质疑"
    why_unrefutable: "没做过给检索工具的对照实验"
    settles_with: "A1+检索臂 vs A1 无检索臂的 D2 分差"
    status: open | resolved | permanent | frontier
    retrieval_attempts: [channel, result, ts]
    resolution: ""          # resolved 时填
    confidence_ceiling: 0.6 # permanent 时填
```

注册表的消费方：
- **任务卡注入**：派 sub 时，把与该任务相关的 open/permanent 缺口写进任务卡（sub 继承已知未知，不重复踩）
- **记忆更新**：resolved → memory 条目；permanent → memory 条目带置信上限
- **下一轮先验**：S0 启动时注入相关缺口 = 新先验

## 与现有基础设施的对接

| 现有组件 | 对接方式 |
|----------|----------|
| stage-gate | 每阶段 advance 增加门禁字段：本阶段前提的缺口已查（S1 跑过）且未决缺口已注册（S3 落盘） |
| T1 stop_hook | 注入内容从"通用反思清单"改为"缺口定位 prompt"：你反驳不了的具体点是什么？输出 {陈述, 为何, 何证据定案} |
| subagent 任务卡 | 增加"已知缺口"节（来自注册表），sub 的任务边界包含这些缺口 |
| logprob 探针 | 维持既定角色：只对模型声明的缺口做优先级排序（先检索哪个），不做触发 |
| arena 外包 | S4 的第 5 通道；FRONTIER 类缺口的实验设计外包 arena |

## 验证（怎么知道状态机在工作）

1. **注册表增长曲线**：open 缺口随时间增多 = 系统在识别更多未知（好）；resolved 率上升 = 检索在填坑（好）；permanent 占比过高 = 通道弱或问题太难（需分流）。
2. **反事实检查**：resolved 的缺口，其证据是否改变了后续决策？没改变 = 检索了但没进先验，S5 环节失效。
3. **最便宜探针**：跑一个任务，看 gap-registry.yaml 是否被真实写入且条目可追溯（statement 能回溯到某轮推理）。

## 已知边界

- S1/S2 的质量 = 模型认知上限（S5 测的就是这个），状态机只保证**发生**，不保证**质量**。
- 27b 跑 S1-S3 时输出格式可能不稳 → 缺口形式化用固定 JSON schema + 脚本校验落盘（结构化产出走脚本，不走模型输出流）。
- 每任务 5 缺口 × 3 通道 = 最多 15 次检索，这是硬上限；超出 = 任务本身太大，先拆任务。
