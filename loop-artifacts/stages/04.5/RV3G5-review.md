## 反方检查（对交付物 g5-optimization-list.md）

1. **"机判化候选 C1-C5 都能写成 assert 脚本"是否过于乐观——C1/C2 的 schema 不存在，断言逻辑是空中楼阁？** —— 部分成立。C1/C2 的断言逻辑确实依赖尚不存在的 schema（p̃ source 字段 / κ 回执文件），本 goal 只给了最小 schema 提案而非定稿。但交付物已显式标注"含 schema 提案"前置依赖，且成本估算中包含了 schema 定义的工作量。这不是"空中楼阁"而是"有明确前置条件的可行路径"。G6 或 RV3G4-* 落地时需先完成 schema 定稿。

2. **"12 blocker 合计 ~32 回合"的成本估算是否有依据——逐条 L1/L2 分类是否经得起推敲？** —— 部分成立。L1/L2 分类基于修复动作的性质（文本修订 vs 协议重设计），不是精确工时。例如 B1（O1/O3 正交性）标 L2 ~4 回合，但如果最终决定"废弃 O1"而非"重新论证正交性"，成本可能降到 L1 ~1 回合。交付物 3b 节已标注"B2 完整修复路径为信息边界"，但未对每条都加"若走替代路径则成本不同"的注记。建议 G6 在处置表中逐条确认修复路径后再锁定成本。

3. **"P4 BLOCKED by finding #17"是否过度保守——变体矩阵未冻结只是说归因不成立，不代表不能先跑起来再补冻结？** —— 不成立。S3 教训的核心是"执行保真度"：如果变体定义不清就开跑，结果无法归因，等于白跑。先修 DRAFT（~2 回合 L1 文本修订）再跑是正确顺序。

4. **负面结果声明第 5/6 条（语义级重判不可机判 / κ 值计算不可机判）是否应该放在"机判化候选表"里作为"不可机判"行，而非放在负面结果声明？** —— 部分成立。这两条确实与机判化直接相关，放在负面结果声明中容易被读者忽略。但当前结构也有合理性：候选表只放"可机判"的项，负面结果声明放"看起来能但实际不能"的项，两者互补。维持现状。

5. **"给 G6 的导出"中"建议 G6 前落地 5 项"是否越权——定稿权在 G6？** —— 措辞检查：写的是"建议"而非"必须"，且每项都附了理由（前置条件/消除矛盾/固化验证链）。没有替 G6 选 O1/O2/O3 方案，只是指出哪些低成本高收益项值得优先处理。符合边界。

6. **成本估算用"runner 回合数"作为单位是否合理——不同 runner 配置下同一任务耗时差异大？** —— 部分成立。runner 回合数是本 loop 的实际资源单位，比人时更贴近实际约束。但确实存在配置差异（模型能力、上下文窗口等）。交付物 04 未完成项已标注"非人时，不同 runner 配置下实际耗时可能不同"。
