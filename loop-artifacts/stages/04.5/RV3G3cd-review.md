## 攻击 1 · DP 枚举器是否仍有未暴露的过计数/漏计数？

**攻击**：M0 fuzz 只有 50 seeds、n≤16、权重池 ≤8——覆盖不了多跨 cut 组 + 大组的组合空间；Bug #2 就是 fuzz 才抓出来的，会不会还有 Bug #3？
**核查**：(i) 补跑双跨 cut 组手构样例（w=60×2 @pos8-9 + w=55×3 @pos10-12，gold 随机 5）→ DP=[3] == BF=[3] ✓；(ii) 预算过滤的正确性论证：不同权重组间不可交错是排序语义的硬约束（组序即名次区间序），故 Σk_j == 10 − above_members 是**必要且充分**的终态条件——必要性显然（top-10 恰好 10 席），充分性由「跨 cut 组内部任意排列 + 上方组全进下方组全出」可构造达成 ✓。(iii) 残余风险：fuzz 分布偏小 n——但算法复杂度 O(m·10²) 与 n 无关，n 只影响分组形态，而分组形态已由权重池碰撞率控制。**判定：驳回**（双实现互验 + 不变量论证双重覆盖；若未来 batch2 数据触发 DP≠BF 不可能发生，因 BF 只在测试路径调用）。

## 攻击 2 · (a) 判定 D3 三分支是否过严/过松？

**攻击**：S2==S1∩域 才 PASS——第二域新增一个也过线的方案（如 W1 在第二域也 ≥4）会直接 FAIL，但「过线集合变大」未必是坏信号（可能是第二域题目区分度更高）。
**核查**：D3 预注册时已标注为「成璐可推翻项」（01/02.5 X3 均登记）。当前语义 = 「跨域稳定」的字面读法（集合不变）；「变大」归入 SIGNAL/FAIL 边界确实有解释空间——但本 goal 交付物是**骨架**，判定语义的价值在于 byte-stable 预注册 + 数据到来后可一处修改，而非此刻选到唯一正解。exit code 契约（SIGNAL → 0，FAIL → 1）保证误判方向安全：宁可人工裁决（SIGNAL exit 0 显式打印）不静默通过。**判定：驳回**（设计决策已透明登记，非隐藏假设）。

## 攻击 3 · (b) 只审计过线方案，漏了「未过线方案 tie 到过线」的假阳性方向？

**攻击**：tie-sensitivity 威胁是双向的——W2-new 第一域基准序 2 不过线，但若某合法 tie-break 下可达 4，则「t=4 判据把 W2-new 排除」这一结论本身 tie-sensitive。
**核查**：04 N4 已登记此边界。但复核发现**第一域事实恰好证明该方向重要**：proof L57 记载 W2-new 可达 [2,3]——上限 3 < 4，所以第一域无假阳性威胁；然而第二域数据未知，该方向**可能**被触发。当前脚本对未过线方案不做可达性检查 → 若第二域出现「基准序 3、可达 4」的方案，(b) 会漏报。**处置**：这是真实覆盖缺口，但属**语义扩展**（L4.2 原文 (b)「过线集合在全部合法 tie-break 下不变」严格读法其实包含双向——见攻击 4），不在本轮修（修 = 改判定语义，须成璐裁定 D3 后统一做），已在 04 N4 + 本攻击记录中显式登记，queue 闭环候选条目将引用此缺口。**判定：成立（降级登记，不阻塞收口）**。

## 攻击 4 · L4.2 原文 (b) 的严格读法 vs 骨架实现语义是否漂移？

**攻击**：原文「过线集合不变」= 集合层面双向稳定（进的不掉、出的不进）。骨架实现 = 仅「过的不掉」（单向 robustness check on s2 members）。
**核查**：与攻击 3 同根。X3（02.5）当时核对的是「集合成员排名不变 ≠ 哪些方案过线」——排除了过度解读，但**没有核对方向完整性**。诚实结论：骨架实现 ⊂ 原文严格语义。因 D3 本就预注册为可推翻解释，且骨架常态是 blocked-on-external（语义从未在真实数据上生效过），不构成「错误结论落盘」——构成的是「预注册解释偏窄」，随 batch2 数据到来的闭环 goal 一并裁定。**判定：成立（与攻击 3 合并登记）**。

## 攻击 5 · 冻结数据零修改声明是否可信？

**核查**：分支自 main r139 切出，切出前 `git status` clean（会话起始快照）；A5 实测 `git diff --name-only HEAD` 为空 + 四文件逐一 UNTOUCHED + runs-C0/stats 无 diff；变异 fixture 写入 `batch2/` 后已 `shutil.rmtree` 删除（最终 `git status --porcelain` 仅新脚本一行）。**判定：驳回**。

## 攻击 6 · schema 预注册的字段集是否最小且自洽？

**攻击**：hit-matrix-batch2.json 被 (a)/(b) 复算协议消费为零（N2 已承认），为何仍设为必需文件（缺失 → ERROR exit 2）？半套数据拒收的理由够硬吗？

## 攻击 8 · 「常态 SIGNAL exit 0」会不会被轮询系统误判为「已验证通过」？

**攻击**：X4 预判过此攻击，缓解措施是「SIGNAL 行显式打印 + queue 不划掉」。但 exit 0 机器语义就是 success——任何 `if exit==0: mark_verified` 的自动化都会踩坑。
**核查**：缓解措施有效性的边界：本仓库当前**不存在**消费该脚本 exit code 的 CI/轮询（grep 零命中，脚本是新文件）。风险是前瞻性的。更强缓解（SIGNAL 也用独立 exit code 如 3）会破坏 r136 kappa-receipt 建立的「0 = 无 FAIL」家族约定，且 docstring 已把 exit 语义写成契约（0 = 无 FAIL **含 SIGNAL**）。维持 D4，但在此明示：若未来接入自动化门禁，须按 stdout 的 `[SIGNAL]` 前缀分流，不能只看 exit code——该义务写入 queue 闭环候选条目。**判定：驳回（附前瞻义务登记）**。
