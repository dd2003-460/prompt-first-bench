## 1. 目标与交付物

**任务**：为 30 人研发团队选一套会议室预约系统；预算 ≤¥20,000/年；需支持 macOS/Windows/Web 三端；日历集成 Google Calendar + Outlook；门禁联动可选。

**必须交付（缺一即半成品）**：

| # | 交付件 | 验收形态 |
|---|--------|----------|
| D1 | 推荐方案 ×1 | 产品/方案名 + 计价模型 + 年度成本 + 满足约束的逐条证据 |
| D2 | 备选方案 ≥2 | 分层（不同取舍：成本优先 / 能力优先 / 自主可控优先） |
| D3 | 淘汰理由 | 对**冻结候选集内每一类/每一个被考察对象**给出淘汰或保留理由，可追溯到硬约束 |
| D4 | 成本明细 | 年度 TCO（人民币），含计价单位、档位、年付/月付、隐藏费用（onboarding/平台费/硬件/运维工时）、汇率处理说明 |
| D5 | 证据链 | 每条关键主张带来源 URL/路径 + 快照时间戳，或显式「存在性断言-未核验」 |

**不交付（出域，见阶段 00 §3）**：视频会议软件选型、办公套件整体迁移方案、访客管理专项、工位管理专项。

## 4. 正交顶层因素分解（F1–F8）

分解原则：两两正交（可独立取值、互不包含），合起来完整覆盖"选型报告"目标。

| 因素 | 定义与边界条件 | 优先级 | 当前状态 |
|------|----------------|--------|----------|
| **F1 规模与需求参数** | 用户数=30（已知）；会议室数量 n（未知）；日均预约量；地点数（假设 1，待确认） | 高（成本/档位的自变量） | 部分已知 |
| **F2 终端覆盖** | macOS / Windows / Web 三端的**实现形态**：原生桌面客户端 / PWA / 浏览器 / 套件内嵌（Teams、飞书）/ 移动端 | 高（硬约束） | 定义待澄清（G3a） |
| **F3 日历集成深度** | Google Calendar 与 Outlook/Microsoft 365 的对接：单向 vs 双向；资源日历/房间邮箱映射；忙闲同步；所需管理员授权与档位 | 高（硬约束） | 未知 |
| **F4 预约与治理能力** | 预约规则、冲突检测、重复会议、审批、no-show 自动释放、签到、门牌显示、统计报表 | 中（决定"系统"价值） | 未知 |
| **F5 门禁联动** | 原生集成（门禁厂商列表）/ API-Webhook 自建 / 无；联动粒度（预约人临时权限、刷卡签到） | 低（可选项，加分） | 未知 |
| **F6 成本与计价模型** | 计价单位（用户/房间/资源/实例）、最低档、年付折扣、一次性费用（onboarding/实施）、平台费、硬件、自托管服务器与运维工时；货币与汇率 | 高（硬约束） | 未知 |
| **F7 部署与运维** | SaaS vs 自托管；SSO/目录同步；数据驻留与合规；备份；升级与运维工时（折算成本进 F6，但能力本身独立） | 中 | 未知 |
| **F8 风险与可持续性** | 厂商/项目存续与活跃度（最近发布/维护）、定价变动风险、数据导出与锁定、支持响应、单点故障 | 中 | 未知 |

**正交性自检**：F1（量）× F2（端）× F3（日历）× F4（功能）× F5（门禁）× F6（钱）× F7（怎么跑）× F8（风险）可分别独立取值。易混淆处已划边界：
- F6 与 F7 重叠风险 → **划界**：F7 只谈"能力与形态"，其产生的费用一律折进 F6 的 TCO，避免双计。
- F2 与 F4 重叠风险 → **划界**：F2 只问"在哪个终端能用"，F4 只问"能做什么"。
- F3 与 F4 重叠风险 → **划界**：F3 只问"与外部日历的数据流"，F4 只问"系统内部的预约治理"。

**覆盖性自检**：选型结论 = 在 F2/F3 硬门禁下，从 F1 规模出发，按 F4 能力排序，受 F6 预算硬约束截断，经 F7 可行性过滤，用 F8 修正风险，F5 作为加分项打破平局 → 无落空维度。

## 5. 递归分解（每个因素 → 子因素，展开到叶子；叶子标 已知 / 可推导 / 待研究）

### F1 规模与需求参数
- F1.1 用户数 = 30 — **已知**
- F1.2 会议室/可预约空间数量 n — **待研究（G1，需用户确认）**
  - F1.2.1 大会议室数 / F1.2.2 小会议室（电话间）数 — 待研究（影响"是否把电话间算作计费空间"）
- F1.3 地点数（单办公室 or 多地点）— **待研究（G1b）**，默认假设 1（显式标注为假设）
- F1.4 日均预约量级 — **可推导上界**：30 人 × 日均 ≤3 场 ≈ ≤90 预约/日，远低于任何商用系统容量上限 → **非瓶颈，不作为筛选因素**（叶子，最小）
- F1.5 需管理员账号数 — 待研究（部分产品额外收费）

### F2 终端覆盖
- F2.1 Web 端（浏览器可用）— **待研究各候选**（预期普遍满足）
- F2.2 macOS 端 — 子问题：a) 原生 .app 客户端 b) PWA/浏览器 c) 经 Teams/飞书/Slack 桌面端内嵌 — **待研究（G3a 定义 + G6 各候选能力）**
- F2.3 Windows 端 — 同 F2.2 三形态
- F2.4 移动端（iOS/Android）— 任务未要求 → **不作为硬门禁**，仅作加分记录（叶子）
- F2.5 门牌/显示屏端（房间门口设备）— 属 F4.7/F5 交叉，归入 F4.7，避免与 F2 重叠（边界声明）

### F3 日历集成深度
- F3.1 Google Calendar：a) 双向同步 b) 资源日历（Calendar Resources）映射 c) 需要 Workspace 管理员授权与档位 — **待研究（G6）**
- F3.2 Outlook / Microsoft 365：a) 双向同步 b) 房间邮箱（room mailbox）映射 c) Exchange Online vs 本地 Exchange — **待研究（G6）**
- F3.3 两套日历并存时的冲突处理（同一房间被两侧各自占用）— **待研究**，是本任务最容易被忽略的技术难点
- F3.4 Teams/Google Meet 会议链接自动生成 — 加分项（叶子）

### F4 预约与治理能力
- F4.1 冲突检测与防双重预约 — 待研究（基线能力，预期普遍满足）
- F4.2 预约规则（时长上限、提前天数、权限分组）— 待研究
- F4.3 重复会议 — 待研究
- F4.4 审批流 — 加分项
- F4.5 no-show 自动释放 / 签到 — 待研究（研发团队"占了不用"的典型痛点）
- F4.6 统计报表（利用率）— 加分项
- F4.7 门牌显示屏支持（硬件可选）— 待研究，**成本归 F6**

### F5 门禁联动（可选）
- F5.1 原生门禁集成清单（哪些门禁品牌）— 待研究（G7）
- F5.2 开放 API / Webhook 可自建联动 — 待研究（G7）
- F5.3 联动语义（预约时段临时开门权限 / 刷卡即签到）— 待研究
- F5.4 国内门禁生态（与海外产品的兼容性）— 待研究，**预期为弱项，需显式标注不确定**

### F6 成本与计价模型
- F6.1 计价单位：a) 按用户 b) 按房间/空间 c) 按资源 d) 平台整包 e) 自托管（服务器）— **待研究（G5）**
- F6.2 最低档价格与所含额度（如"$99/月含 15 空间"）— 待研究（G5）
- F6.3 年付 vs 月付差价 — 待研究
- F6.4 一次性费用：onboarding/实施费、平台费（部分厂商不公开）— 待研究，**不公开 = 风险项，必须显式记录**
- F6.5 硬件 CAPEX（门牌设备单价 × 房间数）— 待研究
- F6.6 自托管成本：服务器年费 + 域名/证书 + 运维工时折算 — 待研究（G8）
- F6.7 汇率（USD/EUR → CNY）— **易变事实，必须用近 7 天来源，否则标未解决（G9）**
- F6.8 既有套件的沉没成本 vs 增量成本口径 — 待研究（G2 + G4）

### F7 部署与运维
- F7.1 SaaS vs 自托管 — 候选属性，待研究
- F7.2 SSO / 目录同步（Google / Entra ID）— 待研究，部分产品锁在高档位
- F7.3 数据驻留与合规（境内/境外）— 待研究，国内团队可能有要求（未由用户给出 → 不假定）
- F7.4 运维负担（自托管升级/备份/安全补丁）— 待研究（G8）

### F8 风险与可持续性
- F8.1 项目/厂商活跃度（最近版本发布时间）— 待研究（尤其开源候选）
- F8.2 定价变动与涨价风险 — 待研究
- F8.3 数据导出与锁定 — 待研究
- F8.4 单点故障（自托管无 SLA）— 可推导：自托管无厂商 SLA → 风险由内部承担（叶子）

**停止条件判定**：上述叶子均为"可单独核验的最小问题"（某个字段、某个价格、某个集成是否存在），不可再分；非原子因素均已展开；全部未验证条件已进入 §7 空缺清单；阶段 02 可据 §8 研究入口直接开工 → **分解完成**。

## 7. 空缺清单（未知条件，不伪装成默认值）

**约定**：复合空缺必须拆出可分别核验的子问题（01 规则「复合空缺处理」）。

| # | 空缺 | 子问题（可分别核验） | 阻塞哪个后续判断 | 优先级 | 归属 |
|---|------|----------------------|------------------|--------|------|
