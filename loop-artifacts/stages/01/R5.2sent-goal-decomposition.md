# 阶段 01：目标拆解 — R5.2hard-EXEMPT-sentinel

> origin: ai · 2026-10-30 · 输入 = `tasks/current-goal.md` + `r5/assert-packet-symmetry.py` L76-78 EXEMPT 定义处

## 1. 现状

`assert-packet-symmetry.py` L78 `EXEMPT = []`——r104 预留的显式豁免清单，设计预期永不为空。当前唯一保护是"命中条目 stdout 明示 `[EXEMPT]`"（逐 token 可见），但**清单本身非空这一事实没有独立警告**：若未来某 run 注入 1 条豁免且该前缀恰好无 token 命中，stdout 将零痕迹——严格模式被静默稀释且无人察觉。这正是 r104 04.5 W1 登记的风险面。

## 2. 哨兵设计（F 因素分解）

- **F1 触发条件**：脚本启动早期（EXEMPT 定义后、任何 check 之前）检查 `len(EXEMPT) > 0`。
- **F2 输出格式**：
  ```
  WARNING [EXEMPT-NONEMPTY] N 条豁免生效中——严格模式已被部分放宽，请人工确认每条 reason 合理性：
    - <prefix> → <reason>
  ```
  逐条列出 (prefix, reason)，与现有 `[EXEMPT]` 逐 token 行互补（一个管"清单存在性"，一个管"实际命中"）。
- **F3 exit 语义不变论证**：WARNING 只 print，不 append failures/passes，不 sys.exit；豁免命中判定逻辑（file_reachable 内查表）零改动。EXEMPT=[] 时 F1 条件为假 → **零新增 stdout 行** → 基线逐字一致由构造保证（不是靠测试碰运气）。
- **F4 自测方案**：临时把 `EXEMPT = []` 改为含一条假条目（如 `("definitely-not-a-real-path-prefix", "SELF-TEST 假豁免")`）跑一次 → 预期 WARNING 出现且计数=1、其余输出与基线一致（假前缀无任何 token 命中，不影响 PASS/FAIL）→ 恢复 `EXEMPT = []` 再跑一次确认回到基线。两次运行输出留痕于 04 日志。
- **F5 落点选择**：哨兵放 EXEMPT 定义紧下方（而非 main 汇总段）——保证在任何 file_reachable 调用前打印，且与清单定义同屏可审。

## 3. 验收映射

current-goal 验收 6 = 基线重跑逐字一致 + 假豁免自测留痕 → F3（构造性保证）+ F4（实证）直接满足。
