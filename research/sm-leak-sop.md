## 什么算泄漏

| 类型 | 例子 | 判定 |
|------|------|------|
| 题目原文片段 | "2024年NVIDIA H200 GPU的TDP是多少" | **泄漏** — 整句/长片段原样出现 |
| 题目结构回声 | "X比Y高多少百分比"（X/Y 是题目实体） | **泄漏** — 把"问什么"的关系带进了 prompt |
| 给定参数引用 | "qwen3-27b"、"bf16"、"H200" | **不算泄漏** — 题目给定的约束条件，回答时正常需要引用 |
| 通用术语 | "GPU"、"参数量"、"MoE" | **不算泄漏** — 领域常识，不是题目特有信息 |

## 实体提取策略（当前实现）

```python
def extract_entities(question):
    # 1. 只从问号部分提取（"？"/"?" 之后的子句）
    # 2. 跳过纯英文/数字实体（[a-z0-9.\-]+）— 这些是给定的技术参数
    # 3. 只拦 ≥8 字中文连续串 — 这是"问题结构回声"的特征长度
```

**为什么这样设计**（3 次 smoke 迭代得出）：
- v1: 所有 ≥4 字实体都拦 → 误报 "qwen3-27b"/"bf16"（给定参数被当泄漏）
- v2: 只从问号部分提取 → 还是拦住 "qwen3-27b"（9 字英文命中 min_len=7）
- v3 (FINAL): 跳过所有 `[a-z0-9\.\-]+`，只拦中文 ≥8 字 → 通过

## 审计执行时机

每轮 DECOMPOSE / REWORK 的 LLM 输出后、入库前执行 `leak_check()`。命中 → raise `LeakError` → 整轮中止 + 记录到 `runs/sm-leak-audit.log`。

## 误报处理

如果 bench 中出现 LeakError 但人工判断是误报（比如模型输出了一个恰好 ≥8 字的中文通用短语）：
1. 记录到 `runs/sm-leak-audit.log`（原始文本 + 命中的实体 + 人工判定）
2. 将该实体加入白名单 `LEAK_WHITELIST`（代码内常量）
3. 重跑该题

**禁止**：为了绕过 leak_check 而降低阈值或注释掉检查。

## 已知局限

- 不检测语义级泄漏（模型用完全不同的措辞复述了题目的核心关系）→ 需要 judge 层面补检（bench 时让 judge 额外判"答案是否直接引用了题目未公开的信息"）
- 不检测跨题泄漏（A 题的实体出现在 B 题的 prompt 中）→ bench 每题独立进程，物理隔离
