三测定义（对每条核验主张逐条判定）：
①具体性：是否指向具体来源编号 + 字段/数据点（泛泛而谈=fail）

判定规则：三条全过才 pass；任一 fail 则该条 fail。特别地：若发现「处置标记与证据不符」（例如把未解释/不可解释的矛盾标成"已解释"且没有新证据支撑），该条必须 fail 并在 note 中点名指出。

## 2. 对抗核验（r29 补丁：主动攻击核验结论本身）

### 攻击轮 1：定价数据的时效性与口径

**质疑**：S1-S6 的官方定价页均"页面未标注日期"——这些价格是否可能是 2024/2025 的旧价？

**反驳**：

- **残余风险**：飞书/坚果云/语雀的定价可能近期调整但未反映在缓存中。置信度从 🟢 降为 🟡（时效性不可证伪）。**处置：在 04 成本表中标注"价格观察时间 2026-10-30，有效期未知"**

### 攻击轮 2：Syncthing "无版本管理"是否过于绝对？

**质疑**：Syncthing 有 "File Versioning" 选项（保留旧版本文件），是否算"版本管理"？

**反驳**：
- Syncthing 的 versioning 是**被动保留**（删除/覆盖时留副本），不是**主动版本树**（无版本号、无 diff、无分支、无恢复 UI）
- 任务书 I1 要求"文档版本管理"——研发团队的文档协作场景需要的是可追溯的版本历史+回滚，不是删除保护
- S38 README Goals 节明确列出 7 个目标，无一涉及版本管理/协作/权限
- **判定**：Syncthing 的 versioning ≠ 任务书要求的"版本管理"。淘汰判定成立，但措辞修正为"无主动版本管理（仅有被动文件保留）"，避免过度声称。

### 攻击轮 3：自托管 TCO 估算是否低估了运维负担？

**质疑**：0.5 人天/月 的运维假设是否乐观？Nextcloud 升级（大版本）通常需 1-2 天停机+测试。

**反驳**：
- 0.5 人天/月 是**稳态均值**（含小补丁+备份验证+磁盘监控）；大版本升级（约 2 次/年 × 1.5 天 = 3 天/年 ≈ 0.25 天/月）已包含在内
- 更保守估计：1 人天/月 = ¥6,000/年（翻倍）
- **处置**：04 成本表给两档：乐观 ¥3,000/年 / 保守 ¥6,000/年。TCO 区间相应扩大。
- **停止理由**：运维工时折算率是**个人信息搜集瓶颈**——没有公开的"研发团队自托管 Nextcloud 运维工时基准"数据，穷尽可查渠道（GitHub issues/discussions 有零散报告但无系统统计）后只能给区间。

### 攻击轮 4：飞书标准版 1500GB 总存储是否够用？

**质疑**：30 人研发团队，{50,200}GB/人 区间 → 需求 {1.5TB, 6TB}。飞书标准版 1500GB 恰在下沿——如果实际用量偏上，直接不够。

**反驳**：

- 任务书原文："细粒度权限控制"——未定义具体粒度（文件夹级？文件级？角色级？）
- 坚果云 Standard 有：文件夹共享 + 权限数量限制 + IP 白名单 + 两步验证 + 远程擦除
- Seafile Pro 有：Fine-grained folder permission（明确写了 fine-grained）
- **诚实评估**：坚果云的权限粒度**可能不如** Seafile Pro 细，但任务书未要求"文件级 ACL"，文件夹级+IP 限制对 30 人研发团队通常够用
- **处置**：在推荐方案中加一条注："若'细粒度'指文件级 ACL，则 Seafile Pro（备选 3）更匹配"
- **判定**：不改变推荐（任务书措辞模糊，按最合理解释处理），但显式标注歧义

### 挑战 3：国内可达性 U7 是否应该淘汰所有海外 SaaS？

**质疑**：Google Drive / Box / Dropbox 被标"国内可达性差"而淘汰——但很多国内公司用 VPN 访问 Google Workspace，这不算"不可用"。

**反驳**：
- 本 run 的实验参数设定是"30 人研发团队"（默认国内，因预算单位为 CNY）
- 如果团队已有 VPN 基础设施，Google Workspace BS（¥18,037）是合理选项
- **但**：U7 是 lead-unverifiable（本环境非国内出口），不能确认"可用"还是"需代理"
- **处置**：淘汰理由修正为"国内可达性未验证（U7），若团队有稳定代理则 Google WS BS 为可行备选"——从"淘汰"降为"conditional 淘汰"
- **判定**：不影响推荐方案（坚果云不受此影响），备选池微调

### 挑战 4：M365 超预算仅 ¥62（+0.2%）是否应该保留？

**质疑**：¥30,062 vs ¥30,000 只差 ¥62——汇率波动 ±0.05 就能翻过来。这是"超预算"还是"贴线"？

**反驳**：
- 预算约束是硬约束（≤¥30,000），不是软目标
- ¥62 超出 = 违反约束，无论幅度多小
- 且 M365 的 OneDrive 1TB/user（30TB 总量）对 30 人研发团队严重过剩——溢价买的是不需要的容量
- **判定**：淘汰维持不变。但备注"若预算上调至 ¥30,100 则 M365 进入备选池"

### 挑战 5：自托管 TCO 区间（¥5,400-9,000）是否过宽？

**质疑**：Nextcloud TCO 给了 ¥5,400-9,000 区间（跨度 67%）——这个精度够做决策吗？

**反驳**：
- 区间宽度反映的是**真实不确定性**（服务器配置 ×2 + 运维工时 ×2 = 4 种组合）
- 收窄区间需要更多假设（如固定 4C8G 服务器 + 0.5 人天/月），但这些假设本身也是推导
- 对决策的影响：即使取上沿 ¥9,000，仍低于推荐方案 ¥10,800 → 排序不变
- **判定**：区间合理，不修改。决策稳健性已验证（上下沿不改变排序）
