# 阶段 03：具体行动分解

## 操作流程

1. 只使用已经通过 Reviewer 的证据，不把猜测写成行动前提。
2. 将目标拆成可执行步骤，每步写输入、动作、依赖、预期产出和验收方式。
3. 标注哪些步骤可以并行，哪些步骤必须等待前一步结果。
4. 为关键失败情况写替代路径和停止条件。

## Reviewer 质检标准

- 行动步骤是否覆盖目标，而不是只生成漂亮计划；
- 每步是否有明确产出和验收方式；
- 依赖关系是否完整且没有循环；
- 关键未知是否被错误地当成已知前提；
- 另一个执行者能否直接依据本工件行动。

如果行动计划依赖尚未核验的事实，repair_stage 写 02 或 02.5；否则写 03。

## 通用原则

### 步骤设计原则

1. **原子性**：每步只做一个明确的事情
2. **可验证**：每步都有明确的验收方式
3. **可并行**：能并行的步骤明确标注
4. **有退路**：关键步骤有替代方案
5. **owner 类型标注（防粒度混排）**：每步必须标 owner = `user`（需用户交互/确认/登录态）或 `agent`（可离线执行）。Reviewer 发现未标 owner 的步骤，或 user/agent 步骤混排导致执行顺序歧义 = revise，repair_stage 写 03。依赖关系图必须显式体现 user 步骤是同步阻塞点还是异步等待点。

### 依赖关系处理

1. **无依赖**：可以立即执行
2. **单依赖**：等待前一步完成后执行
3. **多依赖**：等待所有依赖完成后执行
4. **循环依赖**：重新分解步骤，消除循环

### 失败处理

1. **记录失败**：如实记录失败原因
2. **评估影响**：判断失败对后续步骤的影响
3. **执行替代**：使用替代方案或标记为未解决
4. **不掩盖问题**：不要把失败包装成成功
