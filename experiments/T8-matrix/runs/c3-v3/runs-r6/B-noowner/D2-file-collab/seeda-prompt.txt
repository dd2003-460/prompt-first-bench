# 阶段 01：目标分解、已知与空缺条件

## 操作流程

1. 将任务拆成互相区分但合起来覆盖目标的影响因素。
2. 区分人类已经提供的条件、可以从项目推导的条件和仍需研究的条件。
3. 把无法假定的条件写入空缺清单，避免把未知内容伪装成默认值。
4. 然后递归：把每个因素本身视为子目标，再分解它的子因素；重复 2–4 对每个子因素。
5. 停止条件：当且仅当每个叶子因素已最小则停止（最小，不能再分解）。

## 递归分解方法（强制）

按以下循环，直到分解完成：

1. 先分解目标 → 因素：把目标拆成互相正交、合起来完整覆盖的顶层影响因素（例如有理数和无理数，互相正交，并且加起来等于实数集合）。
2. 对每个因素，区分三种条件：人类已提供的条件、从项目可推导的已确定条件、仍需研究的条件。
3. 把无法假定的条件写入空缺清单，避免把未知内容伪装成默认值。
4. 然后递归：把每个因素本身视为子目标，再分解它的子因素；重复 2–4 对每个子因素。
5. 停止条件：当每个叶子因素不能再分解。
6. 判定"分解完成"：所有叶子原子、所有非原子因素已递归展开（类似文件夹和子文件夹还有更小文件夹的关系）、所有未验证条件在空缺清单、阶段 02 研究入口可据此直接开始。
7. 若判定"分解未完成"：在本阶段判定中，用 Ego Lite 浏览器把（本阶段 prompt + 当前分解 + 未覆盖/未原子缺口）到网页 LLM 求补分解，把其输出作为待验证假设并入，再回到 5。

## 阶段边界

- 本阶段是因素分解，不是资料搜集；尚未核验的型号、日期、价格、性能或兼容性只能作为"待研究假设"出现，必须明确标注为未验证，并写入空缺条件。
- 不要求在本阶段给出阶段 02 才能取得的价格、性能或网页 AI 证据；但必须给出阶段 02 的具体研究路径、来源类型和失败备用路径。
- Reviewer 不应因为阶段 02 的事实证据尚未出现而拒绝阶段 01，只要这些事实没有被伪装成已知，且对应空缺、优先级和研究动作完整。

### 启动下一阶段的门槛

- 阶段 01 的目的，是把任务变成可以立刻执行的研究入口，不是把研究对象抽象到无法行动，也不是穷举全部候选对象。
- 可以写出具体对象类别、候选对象、目标来源、搜索词、字段和研究动作；它们必须标成"待验证的研究目标/假设"，不能写成已经核验的事实。
- 只要目标交付物、主要因素、已知条件、关键空缺、阻塞影响和阶段 02 的第一批行动已经清楚，Reviewer 应判定 `pass`，允许直接进入阶段 02。未解决的价格、性能、时效性和来源问题本来就是阶段 02 的工作。
- 不得因为术语具体、空缺之间有轻微重叠、研究路径较详细或措辞不够抽象而 revise；只有遗漏关键因素、把未验证内容写成确定事实，或下一阶段无法据此开始行动时才 revise。

### 本阶段的判定原则（通用框架）

- **因素正交**：每个因素应独立影响目标，不重叠。若因素 A 和 B 有重叠，合并或重新定义边界。
- **覆盖目标**：所有关键目标必须有至少一个因素覆盖。若目标未被覆盖，添加新因素。
- **边界清晰**：每个因素的边界条件应明确（如"n ≥ 2"、"误差 < 10⁻⁶"），避免模糊。
- **优先级合理**：高优先级因素应直接影响目标达成，中优先级影响体验，低优先级仅参考。
- **空缺完整**：所有未验证条件必须列入空缺清单，不得伪装成已知。
- **研究路径具体**：阶段 02 的研究路径应写明目标网站、搜索词、字段和备用来源，但不要求实际执行。
- **候选对象处理**：若工件主动列出候选对象，必须标明其属性/数值仍待验证（例如：候选 X — 待验证属性 a）。排除理由应明确（例如：排除满足 ¬P 的候选 — 违反约束 C）。
- **候选集冻结（防漂移）**：阶段 01 产出的候选类别清单即为本任务的冻结集合。后续阶段不得悄悄增删候选类别；任何新增或排除必须在阶段 02 逐一核验后显式记录（含理由与时间戳），或在阶段 01 工件中显式标注"排除 — 理由 C"。Reviewer 发现候选集相对 01 发生未声明的漂移 = revise，repair_stage 写 01。
- **复合空缺处理**：若使用复合空缺名，必须在其条目中列出可分别核验的子问题（例如："[待研究] 各候选对象属性 — 子问题：1) 属性 a 2) 属性 b 3) 属性 c"）。
- **术语具体性**：术语具体、空缺之间有轻微重叠、研究路径较详细或措辞不够抽象，不构成 revise 理由。只有遗漏关键因素、把未验证内容写成确定事实，或下一阶段无法据此开始行动时才 revise。

## 当前工件必须回答

- 目标到底要交付什么；
- 目标受哪些因素影响；
- 哪些条件已经确定；
- 哪些条件仍然缺失；
- 缺失条件会阻塞哪个后续判断；
- 下一阶段应该优先研究什么。

## Reviewer 质检标准

- 是否覆盖了任务目标的主要影响因素；
- 是否区分已知、可推导和未知；
- 是否存在把关键未知条件直接假定掉的情况；
- 每个后续研究问题是否能追溯到一个具体空缺；
- 阶段 02 能否直接依据本工件开始搜集资料。
- 未验证事实是否都明确标注为假设/空缺，而不是无来源的确定性断言。
- 阶段 02 的研究路径是否足够具体，但没有把阶段 02 的实际证据伪装成阶段 01 结果。
- 预算/资源约束应以用户给出的总预算为约束；若讨论子预算视角，必须明确它只是待验证的下游分配问题，不得把未经阶段 02 成本核验的子预算写成阶段 01 结论。

如果上述内容已经足够让阶段 02 立即开始研究，即使仍有待验证空缺，也应判定 `pass`，并把这些空缺交给阶段 02，而不是继续要求阶段 01 细化。

如果因素分解不完整，repair_stage 写 01。

# 阶段 02：资料搜集与网页 AI 交叉询问

## 操作流程

1. 读取阶段 01 的空缺条件，只围绕这些空缺搜集资料。
2. 必须先运行 `ralph prompt-first web-llm . "围绕阶段 01 空缺条件的具体核验问题" --context "阶段 02；只要求可复核来源线索"`，把真实回执写入阶段工件；网页 LLM 只提供线索，不是事实来源。必须直接调用已安装的 `ralph` 可执行文件；不要使用 `npx`、`npm`、管道或 `head` 包装它。若命令以未授权/未配置状态快速失败，记录完整失败原因后继续公开网页资料搜集，不得等待或循环重试。
3. 为每个关键主张记录来源标题、URL、发布或更新时间、实际观察时间、具体观察和不确定性。
4. 关键主张至少寻找两个相互独立的来源。厂商规格、独立评测、实际价格或用户实测应明确区分。
5. 对价格、库存、版本、政策、软件支持等易变事实，优先使用最近 7 天内的资料；若没有足够新资料，明确标为未解决。
6. 对稳定事实可以使用较早的一手资料，但必须说明它为什么仍然适用。
7. 记录搜索失败、登录限制、网页 LLM 不可用和零结果；这些不是证据，不能伪装成来源。对同一主张的 WebSearch 若返回 0 结果或失败，最多更换一次关键词；仍失败就记录失败原因和未解决状态，停止重复搜索并写入阶段工件。
8. WebFetch 只对最多 4 个已知、具体 URL 各尝试一次；单个 URL 无结果、403、404 或明显长时间无响应时立即记录状态，不要重复抓取或等待。至少拿到一个可读的一手页面后就停止抓取并写阶段工件。
9. 不要在本阶段写最终推荐，只收集证据、暂定结论和仍未解决的空缺。

### ego-browser 用法（单通道，驱动用户已登录的 ego-lite）

网页 LLM 交叉验证、登录态页面、动态渲染页面**一律走 ego-browser**，不用任何无头/非持久浏览器。全局规则与站点清单见 `AGENTS.md` §网页 LLM 交叉验证流程。

```bash
ego-browser nodejs <<'EOF'
const task = await taskSpace('my-task')        // 同名 space 可复用
const p1 = task.page('p1')
await p1.goto('https://example.com')
const s = await p1.snapshot()                  // 定位: @N ref / loc=css: / loc=role: / text= / xpath=
// await p1.fill('text=输入框', '内容')
// await p1.click('@3')
// await p1.waitForFunction(() => document.body.innerText.includes('完成'), { timeout: 60000 })
const reply = await p1.snapshot()
console.log(reply)
await task.finish({ keep: [] })                // 结束前必须 finish，否则留僵尸进程
EOF
```

**关键注意事项：**
- 选择器：快照 ref `@N`、`loc=css:`、`loc=role:`、`text=`、`xpath=`
- 等待：`waitForURL` / `waitForSelector` / `waitForFunction` / `waitForTimeout`
- 每次 heredoc 是独立 Node 运行时，跨次状态不保留；靠同名 `taskSpace` 复用浏览器会话
- 结束前必须 `task.finish({ keep: [] })`
- 不要用 Playwright 方法，不要另开浏览器实例

## Reviewer 质检标准

- 阶段 01 的关键空缺是否逐项有证据或明确保留为未解决；
- **证据来源完备（防"名不副实"）**：每条关键主张必须附来源 URL/本地路径 + 快照时间戳，三者缺一即降级为"存在性断言-未核验"，不得计入已核验证据。Reviewer 抽查发现无来源主张被当事实使用 = revise，repair_stage 写 02。
- 关键主张是否有足够独立来源；
- 易变事实是否接近当前日期，实际观察时间是否明确；
- 是否把网页 LLM 线索误写成事实来源；
- 是否记录并处理来源矛盾；
- 是否仍存在会改变下一阶段方案的关键证据缺口。

只要关键主张缺少独立来源、关键时效信息过期或存在未解释矛盾，必须 revise，repair_stage 写 02。
