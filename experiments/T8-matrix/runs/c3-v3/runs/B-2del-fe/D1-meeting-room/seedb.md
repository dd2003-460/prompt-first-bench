# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

本阶段旨在将“为 30 人研发团队设计会议室预约系统”这一任务分解为可执行的研究入口。最终交付物（将在后续阶段完成）应包含：
1.  **选型推荐**：明确推荐的 SaaS 服务或自建方案架构。
2.  **成本表**：基于验证数据的年度总拥有成本（TCO），严格控制在 ≤¥20,000/年。
3.  **风险清单**：涵盖技术兼容性、数据隐私、供应商锁定及实施风险。

**当前状态声明**：本阶段仅进行因素分解和条件梳理，**不包含**任何未经验证的具体价格、软件功能细节或兼容性断言。所有具体数值和功能特性均标记为“待研究假设”，需由阶段 02 通过公开网络资料核验。

## 2. 顶层影响因素分解（正交性检查）

我们将系统需求拆解为五个互相正交且覆盖完整的影响因素：

| 因素 ID | 因素名称 | 定义与边界 | 优先级 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| F1 | **核心功能与用户体验** | 预约流程、冲突检测、多端同步体验、UI 易用性。 | High | 直接影响 30 人团队的日常使用效率。 |
| F2 | **日历集成能力** | Google Calendar (GCal) 与 Outlook (M365) 的双向同步机制、OAuth 支持、延迟容忍度。 | Critical | 用户明确要求双日历集成，这是硬性约束。 |
| F3 | **客户端兼容性** | macOS、Windows 桌面端支持情况，以及 Web 端的浏览器兼容性与 PWA 能力。 | High | 必须覆盖指定三端，排除仅支持单一平台的方案。 |
| F4 | **成本结构** | 订阅费用、隐藏费用（如门禁硬件接口费）、按人头计费 vs 按房间计费模式。 | Critical | 硬约束：≤¥20,000/年。需区分 SaaS 订阅与自建运维成本。 |
| F5 | **扩展性与安全合规** | 门禁联动接口可用性（可选）、数据主权、GDPR/等保合规性、单点登录 (SSO) 支持。 | Medium | 门禁为可选，但需评估未来扩展的 API 开放性；安全是底线。 |

**正交性说明**：
- F1 关注“好不好用”，F2/F3 关注“能不能连上/打开”，F4 关注“买不买得起”，F5 关注“安不安全/能否扩展”。
- 若某方案 F2 优秀但 F4 超标，则直接淘汰，无需深入 F1 细节。

## 3. 递归分解与条件分类

### 3.1 因素 F2：日历集成能力（Critical）

#### 子因素分解
- **F2.1 双向同步机制**：是实时推送（Webhook）还是轮询（Polling）？冲突解决策略是什么？
- **F2.2 OAuth 认证范围**：是否支持标准的 GCal/M365 OAuth 2.0？是否需要管理员全局授权？
- **F2.3 混合团队支持**：同一房间内，GCal 用户和 Outlook 用户能否看到彼此的忙碌状态？

#### 条件分类
- **人类已提供条件**：
    - 必须支持 Google Calendar。
    - 必须支持 Microsoft Outlook。
- **从项目推导的条件**：
    - 由于团队规模仅 30 人，无需企业级复杂权限管理，标准 OAuth 即可满足。
    - “双向同步”隐含要求：在 A 日历修改会议，B 日历必须更新，反之亦然。
- **仍需研究的条件（空缺）**：
    - **[待研究] R2.1**：主流候选方案（如 Roomster, Booked, 钉钉/飞书会议室模块, 自研 Next.js+Fullcalendar）对 GCal/Outlook 的双向同步延迟实测数据。
    - **[待研究] R2.2**：各方案对 M365 的集成深度（是仅读取忙闲，还是完全事件同步？）。
    - **[待研究] R2.3**：是否存在需要额外付费才能解锁高级日历集成的条款。

### 3.2 因素 F3：客户端兼容性（High）

#### 子因素分解
- **F3.1 Web 端性能**：移动端浏览器适配、PWA 安装支持、加载速度。
- **F3.2 桌面端形态**：是否有原生 macOS/Windows 应用，还是仅依赖 Electron 包装或 WebView？
- **F3.3 离线/弱网表现**：在无网环境下能否查看本地缓存的日程？

#### 条件分类
- **人类已提供条件**：
    - 必须支持 macOS。
    - 必须支持 Windows。
    - 必须支持 Web 端。
- **从项目推导的条件**：
    - 30 人团队通常配备较新的办公电脑，因此对老旧操作系统（如 Win7）的支持非必需，主要关注 Win10/11 和 macOS 12+。
    - Web 端应是主要交互界面，桌面端主要用于快捷访问或通知。
- **仍需研究的条件（空缺）**：
    - **[待研究] R3.1**：候选方案是否提供原生桌面客户端，还是仅提供 Web App？若为 Web App，其 PWA 在 Mac/Win 上的稳定性如何？
    - **[待研究] R3.2**：各主流浏览器（Chrome, Edge, Safari）下的 UI 渲染一致性。

### 3.3 因素 F4：成本结构（Critical）

#### 子因素分解
- **F4.1 基础订阅费**：按用户数、按房间数还是固定套餐？
- **F4.2 汇率与支付**：国际 SaaS 的人民币结算方式、发票开具能力。
- **F4.3 隐性成本**：实施费、培训费、API 调用超限费、数据存储超额费。
- **F4.4 自建替代成本**：若选择开源方案，服务器、域名、SSL 证书及维护人力成本估算。

#### 条件分类
- **人类已提供条件**：
    - 总预算上限：¥20,000 / 年。
- **从项目推导的条件**：
    - 30 人团队，假设会议室数量为 3-5 间（典型研发团队配置，需确认实际数量，见 R4.1）。
    - 若采用 SaaS，人均成本上限约为 ¥666/人/年（20000/30），这远高于大多数轻量级会议室软件的定价，因此预算非常宽松，重点在于寻找“性价比最高”而非“最便宜”。
- **仍需研究的条件（空缺）**：
    - **[待研究] R4.1**：团队实际拥有的物理会议室数量（影响按房间计费的方案成本）。*注：此信息缺失可能导致按房间计费方案的预估偏差，需向用户确认或假设 3-5 间作为基准。*
    - **[待研究] R4.2**：候选 SaaS 方案在中国大陆的可访问性及支付方式（微信/支付宝/对公转账）。
    - **[待研究] R4.3**：开源方案（如 OpenRoom, Cal.com）的部署和维护所需的技术人力小时成本估算。

### 3.4 因素 F5：扩展性与安全合规（Medium）

#### 子因素分解
- **F5.1 门禁联动接口**：是否提供 RESTful API 或 Webhook 用于对接门禁系统（如 HID, ZKTeco, 海康威视）？
- **F5.2 数据安全**：数据存储位置（境内/境外）、加密标准、备份策略。
- **F5.3 SSO 集成**：是否支持 OIDC/SAML 以接入公司现有的身份认证系统？

#### 条件分类
- **人类已提供条件**：
    - 门禁联动为“可选”，非强制一期交付。
- **从项目推导的条件**：
    - 研发团队通常对代码和数据安全敏感，优先选择有明确 SLA 和安全白皮书的厂商。
    - 若选择境外 SaaS，需评估数据出境合规风险。
- **仍需研究的条件（空缺）**：
    - **[待研究] R5.1**：候选方案的门禁 API 文档公开程度及社区案例。
    - **[待研究] R5.2**：候选方案的数据存储地理位置及是否符合中国《个人信息保护法》要求。

### 3.5 因素 F1：核心功能与用户体验（High）

#### 子因素分解
- **F1.1 预约流程简化**：是否支持一键预约、拖拽调整、重复会议设置？
- **F1.2 设备资源管理**：能否关联投影仪、白板等设备？
- **F1.3 通知机制**：邮件、IM（Slack/Teams/钉钉）提醒能力。

#### 条件分类
- **人类已提供条件**：无特定 UI 偏好。
- **从项目推导的条件**：
    - 研发人员习惯高效工具，UI 需简洁，避免冗余字段。
    - 通知需集成到常用 IM 工具中，减少邮件打扰。
- **仍需研究的条件（空缺）**：
    - **[待研究] R1.1**：候选方案对 Slack/Teams/钉钉的官方集成插件成熟度。
    - **[待研究] R1.2**：用户评价中关于“易用性”和“Bug 率”的反馈汇总。

基于上述分解，阶段 02 应执行以下具体研究动作：

### 5.1 候选对象筛选（待验证假设）

根据初步市场认知，构建候选池（**注意：以下属性均为假设，需阶段 02 逐一核验**）：

1.  **SaaS 商业软件类**：
    *   *候选 A*: **Roomster** (假设：支持 GCal/Outlook，按房间收费，可能有免费版)
    *   *候选 B*: **Booked Scheduler** (假设：开源核心+商业版，功能强，需自建或托管)
    *   *候选 C*: **钉钉/飞书/企业微信 内置会议室模块** (假设：国内访问快，集成好，但可能绑定生态，定制性差)
    *   *候选 D*: **Zoom Rooms / Teams Rooms** (假设：视频协作强，但纯预约功能可能冗余，成本高)
2.  **开源/自建类**：
    *   *候选 E*: **Cal.com** (假设：开源，支持多种日历，需自行部署和维护)
    *   *候选 F*: **Next.js + FullCalendar + Supabase/Firebase** (假设：完全定制，开发成本低但长期维护成本高)

### 5.3 失败备用路径

- 若官网价格模糊或需登录才能查看：记录“需联系销售”，并转向查找该厂商在 G2/Capterra 上的用户提及的价格区间。
- 若开源方案部署过于复杂（超过 4 小时）：降低其优先级，标记为“高维护成本风险”，转而聚焦 SaaS 方案。
- 若所有境外 SaaS 在国内访问不稳定：将“国内 IM 平台内置模块”提升为首选，即使其定制化较差。
