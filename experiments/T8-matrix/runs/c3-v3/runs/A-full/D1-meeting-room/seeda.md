# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

**最终交付物**：一份包含以下三部分的可执行选型报告：
1. **选型推荐**：针对 30 人研发团队会议室预约系统的具体产品/方案组合（含核心功能匹配度分析）。
2. **成本表**：年度总成本 ≤ ¥20,000 的详细预算拆解（含软件订阅、硬件门禁、实施费等），需区分一次性与经常性成本。
3. **风险清单**：技术集成风险、数据安全风险、供应商锁定风险及缓解措施。

**约束边界**：
- **规模**：30 人研发团队（非全公司，可能涉及跨部门共享会议室或独立空间）。
- **平台**：必须支持 macOS、Windows 客户端/Web 端访问；日历双向同步 Google Calendar + Outlook。
- **预算硬顶**：¥20,000/年（含税，假设人民币结算）。
- **可选模块**：门禁联动（非强制，若加入需评估额外成本是否导致超支）。

## 2. 顶层影响因素正交分解

为确保覆盖完整且互不重叠，将任务分解为以下五个正交因素：

| 因素 ID | 因素名称 | 定义与边界 | 优先级 |
| :--- | :--- | :--- | :--- |
| **F1** | **软件功能匹配度** | 核心预约流程、多端支持、日历集成能力、冲突检测、资源管理。这是系统存在的根本价值。 | P0 (高) |
| **F2** | **成本结构与控制** | 订阅费、用户数计费模式、隐藏费用（如 API 调用、SSO）、汇率波动、预算合规性。直接决定方案可行性。 | P0 (高) |
| **F3** | **技术集成与兼容性** | GCal/Outlook 双向同步稳定性、macOS/Win/Web 客户端体验、API 开放性、SSO/LDAP 支持。影响落地难度。 | P1 (中) |
| **F4** | **门禁联动可行性** | 硬件接口协议、软件插件支持、安全认证机制、额外硬件成本。属于“可选”但需评估对总预算的影响。 | P2 (低/可选) |
| **F5** | **运维与风险** | 数据隐私合规、供应商 SLA、单点故障、退出成本（数据迁移）、本地化支持。影响长期维护。 | P1 (中) |

> **正交性检查**：
> - F1 关注“能不能用”，F2 关注“买得起吗”，F3 关注“好不好接”，F4 关注“加不加门”，F5 关注“稳不稳”。
> - 无重叠：例如“日历集成”在 F1 中作为功能需求，在 F3 中作为技术实现细节，在 F2 中不涉及（除非特定集成收费，但这归入 F2 的隐藏费用）。

## 3. 递归分解与条件分类

### 3.1 F1: 软件功能匹配度

#### 子因素分解
- **F1.1 核心预约流程**：创建会议、选择房间、设置时长、邀请参会者。
- **F1.2 多端访问**：Web 响应式设计、macOS/Windows 原生或 Electron 客户端、移动端 App（虽未明确要求，但研发人员常需移动查看）。
- **F1.3 日历集成深度**：单向写入 vs 双向同步；GCal 与 Outlook 同时支持；时区处理。
- **F1.4 资源管理**：会议室设备显示（投影、白板）、容量限制、清洁状态标记。

#### 条件分类
| 类型 | 内容 |
| :--- | :--- |
| **人类已提供** | 必须支持 GCal + Outlook 双向同步；必须支持 Mac/Win/Web。 |
| **可推导** | 30 人团队意味着并发不高，无需企业级高可用集群；需要简单的权限管理（管理员 vs 普通用户）。 |
| **仍需研究 (空缺)** | [待研究] 主流 SaaS 会议室系统（如 Roomle, Frontify, Calendly Rooms, 国内如飞书/钉钉自带功能、第三方如 MeetBook）是否真正支持**同时**双向同步 GCal 和 Outlook？多数产品侧重其一。<br>[待研究] 是否有免费或低价版本支持 30 用户且包含双日历集成？ |

### 3.2 F2: 成本结构与控制

#### 子因素分解
- **F2.1 订阅模式**：按席位（Per User）vs 按房间（Per Room）vs 固定套餐。
- **F2.2 价格币种与汇率**：国际产品多为 USD/EUR，需换算 CNY 并考虑支付通道费。
- **F2.3 隐藏成本**：API 超额费、SSO 附加费、高级报表费、取消政策。
- **F2.4 门禁硬件成本**：若启用 F4，需估算读卡器/屏幕/控制器成本。

#### 条件分类
| 类型 | 内容 |
| :--- | :--- |
| **人类已提供** | 总预算 ≤ ¥20,000/年。 |
| **可推导** | 若纯软件方案，平均每人每月成本上限约为 ¥55 (20000/30/12)。若含门禁，软件预算需压缩至 ¥10k-15k，硬件 ¥5k-10k（一次性或分摊）。 |
| **仍需研究 (空缺)** | [待研究] 候选产品在 30 用户规模下的实际年费（CNY）。<br>[待研究] 是否存在“按房间计费”且房间数少于人数从而更便宜的方案？<br>[待研究] 门禁硬件（如 ZKTeco, HID 等）的最小可行套件成本。 |

### 3.3 F3: 技术集成与兼容性

#### 子因素分解
- **F3.1 日历 API 稳定性**：Google Workspace / Microsoft 365 的 OAuth 2.0 授权流程、Token 刷新、冲突解决逻辑。
- **F3.2 客户端性能**：Mac/Win 客户端是否为原生开发还是 Web Wrapper？启动速度、离线缓存能力。
- **F3.3 身份认证**：是否支持 SAML/OIDC 以对接公司现有 AD/Azure AD？（30 人团队可能无复杂 IdP，但需确认）。

#### 条件分类
| 类型 | 内容 |
| :--- | :--- |
| **人类已提供** | 三端支持。 |
| **可推导** | 研发团队通常技术能力强，能容忍轻度配置复杂度；但要求日历同步不能出现“幽灵会议”或重复预订。 |
| **仍需研究 (空缺)** | [待研究] 候选产品的 GCal/Outlook 双向同步在实测中的延迟和冲突处理机制。<br>[待研究] 是否支持自定义域名或私有部署（若数据敏感）？ |

### 3.4 F4: 门禁联动可行性 (可选)

#### 子因素分解
- **F4.1 软件插件**：预约成功后自动下发门禁权限的时间窗口（提前 15 分钟？）。
- **F4.2 硬件生态**：支持的读卡器品牌、通信协议（TCP/IP, RS485, Wi-Fi）。
- **F4.3 安全策略**：如何防止尾随进入？是否需要人脸/指纹辅助？

#### 条件分类
| 类型 | 内容 |
| :--- | :--- |
| **人类已提供** | 门禁联动是“可选”。 |
| **可推导** | 若预算紧张，优先保证软件核心功能，门禁可作为二期或简化方案（如仅显示“使用中”灯效，不开锁）。 |
| **仍需研究 (空缺)** | [待研究] 哪些低成本会议室系统原生支持门禁 API？<br>[待研究] 最小门禁套件（1 个门口屏 + 1 个控制器 + 卡片）的成本范围。 |

### 3.5 F5: 运维与风险

#### 子因素分解
- **F5.1 数据主权**：数据存储位置（中国境内 vs 海外）？是否符合《个人信息保护法》？
- **F5.2 供应商连续性**：公司规模、融资状况、历史停运案例。
- **F5.3 退出策略**：数据导出格式（ICS, CSV）、账号注销流程。

#### 条件分类
| 类型 | 内容 |
| :--- | :--- |
| **人类已提供** | 无明确合规要求，但隐含企业级基本安全期待。 |
| **可推导** | 30 人团队数据量小，但代码/会议内容可能涉密，需评估云服务商等级。 |
| **仍需研究 (空缺)** | [待研究] 候选产品的数据中心位置及合规声明。<br>[待研究] 客户流失率或负面评价（特别是关于日历同步 Bug 的反馈）。 |

## 5. 阶段 02 研究入口与行动指南

### 5.1 候选对象类别 (冻结集合)

基于行业常识，初步划定三类候选对象，供阶段 02 逐一核验。**注意：此列表仅为研究范围，不代表推荐。**

1.  **国际专业会议室 SaaS**：
    *   *示例候选*：Roomle, Frontify (Rooms), Calendly (Rooms feature), Doodle (Spaces), Booked.ai.
    *   *特点*：功能成熟，国际化好，但价格可能较高，且需验证双日历支持。
2.  **协作套件内置功能**：
    *   *示例候选*：Microsoft Teams Rooms (需 M365 许可), Zoom Rooms (需 Zoom Business), Slack Huddle (非专门预约).
    *   *特点*：若公司已购 M365/Zoom，边际成本低；但功能可能受限，且通常绑定单一生态（难同时完美支持 GCal+Outlook 双向）。
3.  **国内轻量级/开源方案**：
    *   *示例候选*：飞书会议室 (若已用飞书), 钉钉会议室, 自托管开源项目 (如 Meetingroom, Cal.com).
    *   *特点*：成本低，合规性好，但需验证是否满足 Mac/Win 原生体验及双日历集成。

### 5.2 第一批研究动作 (阶段 02 立即执行)

1.  **筛选候选**：
    *   访问上述候选对象官网，查找 "Integrations" 或 "Calendar Sync" 页面。
    *   **关键过滤条件**：必须明确列出支持 "Google Calendar" AND "Microsoft Outlook/Exchange" 的**双向**同步。
    *   输出：通过初筛的产品列表（预计 3-5 个）。

2.  **成本核算**：
    *   对通过初筛的产品，查找 30 用户的年费。
    *   计算：`Annual_Cost_CNY = (Price_Per_User_USD * 30 * Exchange_Rate) + Hidden_Fees`.
    *   标记：超过 ¥20,000 的方案直接排除或标注为“需谈判”。

3.  **门禁成本探查**：
    *   搜索电商平台上“会议室门禁一体机”或“门禁控制器+读卡器”套装的价格区间。
    *   确定一个基准值（如 ¥3,000 - ¥5,000/套），用于后续判断是否可在剩余预算内实现。

4.  **交叉询问 (Web LLM)**：
    *   使用 `ralph prompt-first web-llm` 询问：“Which meeting room booking software supports bidirectional sync with both Google Calendar and Outlook for small teams under $200/month?”
    *   目的：发现被遗漏的长尾产品或验证主流产品的真实口碑。

### 5.3 失败备用路径

*   **若所有国际 SaaS 均不支持双日历双向同步**：
    *   转向研究“中间件”方案：使用 Zapier/Make.com 连接日历与一个简单的内部网页表单，或使用开源库自行开发轻量前端。
    *   此时 F3 权重上升，F2 可能降低（自建成本低），但 F5（运维风险）大幅上升。
*   **若预算严重不足**：
    *   降级需求：放弃“双向同步”，改为“单向推送”（从预约系统推送到日历，但不允许在日历直接修改预约状态），或使用共享 Outlook 邮箱模拟会议室。
    *   此时需在风险清单中注明“用户体验下降”和“手动冲突风险”。
