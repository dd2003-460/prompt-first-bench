# 阶段 01：目标分解、已知与空缺条件

## 1. 任务目标交付物定义

本任务旨在为一家 30 人规模的研发团队设计一套会议室预约系统。最终交付物必须包含以下三个核心部分，且所有结论必须基于可验证的事实或明确标注的假设：
1.  **选型推荐**：针对 macOS/Windows/Web 三端、日历集成（GCal+Outlook）及可选门禁联动的具体技术方案或 SaaS 产品组合。
2.  **成本表**：年度总预算 ≤ ¥20,000 的详细拆解，包括软件许可、硬件（如需）、实施费用及潜在隐性成本。
3.  **风险清单**：识别技术兼容性、数据隐私、供应商锁定及预算超支等关键风险及其缓解措施。

## 2. 顶层影响因素分解（正交覆盖）

为确保覆盖所有关键维度，将目标分解为以下五个互相正交的影响因素：

| 因素 ID | 因素名称 | 描述与边界 | 优先级 |
| :--- | :--- | :--- | :--- |
| F1 | **功能匹配度** | 系统是否原生支持 macOS/Windows/Web 客户端；是否支持 Google Calendar 和 Outlook 的双向同步；是否具备会议室资源管理核心功能（冲突检测、预订界面）。 | High |
| F2 | **成本合规性** | 年度总拥有成本 (TCO) 是否严格控制在 ¥20,000 以内；需区分订阅费、一次性授权费、硬件采购费及实施服务费。 | High |
| F3 | **集成扩展性** | “门禁联动”作为可选功能，其实现难度、额外成本及对主系统的侵入性。若无法低成本实现，需有降级方案。 | Medium |
| F4 | **部署与维护复杂度** | 自建 (Self-hosted) vs SaaS 的选择对 IT 维护负担的影响；数据迁移、用户培训及后续版本升级的工作量。 | Medium |
| F5 | **数据安全与合规** | 会议数据（可能含敏感研发信息）的存储位置、加密标准、访问控制粒度及符合公司安全策略的能力。 | High |

## 3. 递归分解与条件状态分析

### 3.1 因素 F1：功能匹配度

*   **子因素 F1.1：多端支持**
    *   *人类已提供条件*：必须支持 macOS, Windows, Web。
    *   *可推导条件*：Web 端通常意味着响应式设计或独立 Web App；桌面端可能是 Electron 应用、原生应用或仅通过浏览器访问。
    *   *待研究条件（空缺）*：主流候选方案中，哪些同时提供原生桌面体验（而非仅 PWA）？PWA 在 macOS/Windows 上的安装体验是否满足“三端”要求？
*   **子因素 F1.2：日历双向同步**
    *   *人类已提供条件*：集成 Google Calendar + Outlook。
    *   *可推导条件*：需使用 CalDAV 协议或厂商提供的 API（GCal API, Microsoft Graph API）。单向同步（只读）不满足“预约”场景下的状态回写需求。
    *   *待研究条件（空缺）*：候选方案是否原生支持双日历提供商的同时绑定？还是需要通过中间件（如 ICS 文件交换、Zapier 或自研 Bridge）？同步延迟是多少？
*   **子因素 F1.3：核心预约逻辑**
    *   *人类已提供条件*：30 人团队，会议室预约。
    *   *可推导条件*：并发量低（<50 QPS），数据量小。无需复杂的高可用架构。
    *   *待研究条件（空缺）*：候选方案是否支持“会议室设备”作为资源（Resource）进行预订？是否支持临时取消/修改？

### 3.2 因素 F2：成本合规性

*   **子因素 F2.1：软件许可/订阅费**
    *   *人类已提供条件*：年预算 ≤ ¥20,000。
    *   *可推导条件*：平均每人每年 ≤ ¥666。若按席位收费，需评估实际活跃用户数（30 人全员 or 部分人）。
    *   *待研究条件（空缺）*：
        1.  候选 SaaS 产品的最新定价（Per user/month 或 Flat rate）。
        2.  是否存在教育版/初创版折扣？
        3.  自建开源方案的服务器托管成本（Cloud VPS 价格）。
*   **子因素 F2.2：硬件与实施费**
    *   *人类已提供条件*：门禁联动可选。
    *   *可推导条件*：若选择纯软件方案，硬件成本为 0。若涉及门禁，需考虑传感器/控制器成本。
    *   *待研究条件（空缺）*：
        1.  主流门禁联动方案（如 RFID 读卡器、蓝牙信标）的单价。
        2.  是否有现成的“会议室预约+门禁”一体化硬件套件？
        3.  实施集成的人工时薪估算（若需外包或内部投入）。

### 3.3 因素 F3：集成扩展性（门禁联动）

*   **子因素 F3.1：联动机制**
    *   *人类已提供条件*：可选功能。
    *   *可推导条件*：联动方式通常为：预约成功 -> 发送信号给门禁 -> 开门。
    *   *待研究条件（空缺）*：
        1.  候选软件是否提供 Webhook 或 API 用于触发外部硬件？
        2.  常见的低成本门禁控制方案（如 ESP32 + 继电器、商用智能门锁 API）的技术可行性。
        3.  失败处理机制（如预约被取消，门禁权限如何自动撤销？）。

### 3.4 因素 F4：部署与维护复杂度

*   **子因素 F4.1：部署模式**
    *   *人类已提供条件*：无明确指定，但受预算限制。
    *   *可推导条件*：SaaS 零运维但依赖网络；自建需维护服务器、数据库、备份。
    *   *待研究条件（空缺）*：
        1.  主流开源会议室预约系统（如 Resource Guru OSS, Unify, 或特定 GitHub 项目）的部署难度（Docker Compose 一键部署？）。
        2.  SaaS 服务商的数据导出能力（防止锁定）。
*   **子因素 F4.2：用户采纳率**
    *   *人类已提供条件*：研发团队，技术人员多。
    *   *可推导条件*：对 CLI 或简单 Web 接受度高，对复杂移动端 APP 接受度低。
    *   *待研究条件（空缺）*：候选方案的 UI/UX 评价，尤其是 Web 端的操作流畅度。

### 3.5 因素 F5：数据安全与合规

*   **子因素 F5.1：数据存储与控制**
    *   *人类已提供条件*：研发团队（可能涉及代码、架构讨论）。
    *   *可推导条件*：SaaS 数据存储在第三方云端；自建数据在内网。
    *   *待研究条件（空缺）*：
        1.  候选 SaaS 是否符合 GDPR/PIPL（个人信息保护法）？
        2.  自建方案中，如何配置 HTTPS 证书和内网访问控制？
        3.  审计日志功能是否默认开启？

## 5. 阶段 02 研究入口与行动路径

基于上述空缺，阶段 02 应优先执行以下研究动作：

### 5.1 第一批研究行动（针对 P0 空缺）

1.  **搜索词建议**：
    *   "meeting room booking software pricing per user 2024"
    *   "open source meeting room booking system github docker"
    *   "Google Calendar Outlook two-way sync meeting room app"
    *   "smart door lock api webhook integration meeting booking"
2.  **目标来源类型**：
    *   官方定价页面（Price Page）。
    *   G2/Capterra 等 B2B 评测网站的用户评论（关注同步问题和稳定性）。
    *   GitHub Repository README 和 Issues 区（关注部署问题和 Bug）。
    *   智能家居/物联网论坛（如 Home Assistant Community）的门禁联动帖子。
3.  **具体核验字段**：
    *   价格：币种、计费周期（月/年）、最低起购人数。
    *   功能：Checklist 打钩（Multi-platform? Dual Calendar Sync? API Access?）。
    *   时间戳：记录网页抓取的具体日期和时间。

### 5.2 第二批研究行动（针对 P1/P2 空缺）

1.  **门禁联动深度调研**：
    *   查找支持 MQTT 或 HTTP API 的智能锁品牌（如 Aqara, Yale, 或通用继电器模块）。
    *   验证预约软件是否暴露 Webhook 事件（Booking Created, Booking Cancelled）。
2.  **自建方案 PoC 评估**：
    *   选取一个最活跃的开源项目，尝试阅读其 Deployment Guide，评估从 Clone 到 Run 的步骤数量。
    *   检查其文档中是否提及 CalDAV 或 OAuth 2.0 配置。

### 5.3 失败备用路径

*   若所有 SaaS 均不支持原生双日历同步：
    *   *备用路径*：采用“单向同步 + 手动确认”或开发一个简单的 Node.js/Python 中间件，监听两个日历的变化并写入统一数据库，前端展示该数据库。此路径需计入 F4 维护复杂度增加的风险。
*   若门禁联动成本超过预算剩余空间：
    *   *备用路径*：放弃物理门禁联动，改为“虚拟门禁”（如生成动态二维码，员工扫码后由人工或简易脚本开门），或仅保留屏幕显示当前预订人信息。
