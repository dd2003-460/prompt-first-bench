# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

**核心交付物**：一份针对 30 人研发团队的会议室预约系统选型推荐报告，包含：
1. **选型推荐**：明确推荐 1 个首选方案 + 1-2 个备选方案，并说明理由。
2. **成本表**：基于预算 ≤¥20,000/年 的详细年度成本拆解（含软件许可、硬件、集成费用等）。
3. **风险清单**：技术兼容性、数据隐私、供应商锁定、维护成本等关键风险及缓解措施。
4. **来源索引**：所有事实性主张的来源编号（S1, S2...），矛盾处置记录，不确定性标注。

**非目标（Out of Scope）**：
- 不开发定制代码（假设使用现成 SaaS 或开源部署）。
- 不涉及会议室物理装修或网络布线施工细节（仅涉及门禁联动接口可行性）。
- 不处理跨时区复杂调度逻辑（假设团队在同一办公地点）。

## 2. 顶层影响因素分解（正交且覆盖完整）

| ID | 因素名称 | 边界定义 | 优先级 | 说明 |
|----|----------|----------|--------|------|
| F1 | **功能完备性** | 是否满足“预约、日历同步、多端访问”三大核心需求 | P0 | 缺失任一即不可用 |
| F2 | **平台兼容性** | macOS / Windows / Web 三端体验一致性；Google Calendar & Outlook 双向同步支持 | P0 | 用户指定硬性约束 |
| F3 | **总拥有成本 (TCO)** | 年度总花费 ≤ ¥20,000，含软件订阅、可选硬件、实施费 | P0 | 预算硬约束 |
| F4 | **门禁联动能力** | 是否支持 API/Webhook 对接主流门禁系统（如海康、大华、ZKTeco） | P1 | “可选”但需评估实现难度与额外成本 |
| F5 | **数据安全与合规** | 数据存储位置、GDPR/中国《个人信息保护法》合规性、SSO 支持 | P1 | 研发团队敏感信息保护 |
| F6 | **运维与维护成本** | IT 管理员日常配置、故障排查、版本升级负担 | P2 | 影响长期可持续性 |
| F7 | **可扩展性与稳定性** | 30 人规模下的并发性能、未来扩容至 50+ 人的能力 | P2 | 当前规模小，但需避免过早瓶颈 |

> **正交性检查**：F1-F7 相互独立。例如，功能完备（F1）不等于成本低（F3）；兼容性好（F2）不等于安全合规（F5）。无重叠。

## 3. 递归分解与条件分类

### F1: 功能完备性
- **子因素 F1.1**: 会议室资源管理（创建、删除、属性设置）
- **子因素 F1.2**: 预约流程（搜索空闲时段、冲突检测、取消/修改）
- **子因素 F1.3**: 通知机制（邮件、IM 推送、短信）

#### 条件分类：
- **人类已提供**：无具体功能细节要求，仅隐含“标准预约功能”。
- **可推导**：30 人团队通常有 3-8 间会议室，需支持多人同时预约不同房间。
- **仍需研究**：各候选系统是否原生支持“设备绑定”（如预约后自动开启投影）、“访客预约”权限控制。→ **[空缺 O1]**

### F2: 平台兼容性
- **子因素 F2.1**: 客户端形态（Native App vs PWA vs Desktop Client）
- **子因素 F2.2**: 日历集成深度（单向 vs 双向同步、事件字段映射完整性）
- **子因素 F2.3**: 移动端体验（iOS/Android 虽未明确要求，但 Web 端应适配移动浏览器）

#### 条件分类：
- **人类已提供**：macOS/Windows/Web 三端；Google Calendar + Outlook 集成。
- **可推导**：Web 端应为响应式设计，无需单独安装插件。
- **仍需研究**：
  - 各候选系统对 Google Calendar 和 Outlook 的**双向同步**支持情况（部分系统仅支持单向导入）。→ **[空缺 O2]**
  - macOS/Windows 是否有专属桌面客户端，还是仅依赖浏览器？→ **[空缺 O3]**

### F3: 总拥有成本 (TCO)
- **子因素 F3.1**: 软件订阅费（按用户数 or 按会议室数计费？）
- **子因素 F3.2**: 初始实施费（配置、迁移、培训）
- **子因素 F3.3**: 硬件成本（若需专用终端、门禁控制器）
- **子因素 F3.4**: 集成开发费（若需定制 API 对接门禁）

#### 条件分类：
- **人类已提供**：总预算 ≤ ¥20,000/年。
- **可推导**：30 人团队，若按人头收费，人均 ≤ ¥666/年（约 $92/年）；若按会议室收费（假设 5 间），单间 ≤ ¥4,000/年（约 $553/年）。
- **仍需研究**：
  - 主流 SaaS（如 RoomGuru, Cudo, Zoom Rooms, Microsoft Teams Rooms）的**最新定价模型**（2024-2025 价格）。→ **[空缺 O4]**
  - 开源方案（如 Cal.com, Nextcloud Meeting）的**自托管成本**（服务器、域名、SSL、人力维护时间折算）。→ **[空缺 O5]**
  - 门禁联动是否需要额外付费模块或第三方中间件（如 IFTTT, Zapier, n8n）的费用。→ **[空缺 O6]**

### F4: 门禁联动能力
- **子因素 F4.1**: 开放 API 可用性（RESTful, Webhook）
- **子因素 F4.2**: 主流门禁厂商兼容性（海康威视、大华、中控智慧等）
- **子因素 F4.3**: 联动逻辑复杂度（预约成功→开门权限下发；会议结束→权限回收）

#### 条件分类：
- **人类已提供**：“门禁联动可选”，未指定具体门禁品牌。
- **可推导**：若选择微软生态（Teams Rooms），可能与 Azure AD 或现有 Windows 域环境有潜在集成优势；若选择 Google 生态，可能需通过 Workspace API。
- **仍需研究**：
  - 候选系统是否提供**预置的门禁集成模板**或官方文档支持的对接方式。→ **[空缺 O7]**
  - 若无原生支持，通过 Webhook + 自建轻量服务（Node.js/Python）对接门禁 API 的**技术可行性与工作量**。→ **[空缺 O8]**

### F5: 数据安全与合规
- **子因素 F5.1**: 数据存储地理位置（中国大陆节点 vs 海外）
- **子因素 F5.2**: 身份认证（SSO/SAML/OIDC 支持）
- **子因素 F5.3**: 数据导出与所有权

#### 条件分类：
- **人类已提供**：无明确合规要求，但“研发团队”暗示可能有代码/项目信息泄露风险。
- **可推导**：若使用境外 SaaS（如美国公司），需考虑数据出境合规性及访问延迟。
- **仍需研究**：
  - 各候选 SaaS 在中国大陆的**服务器节点分布**及访问速度。→ **[空缺 O9]**
  - 是否支持与企业现有 IdP（如 Okta, Authing, 或本地 AD）进行 SSO 集成。→ **[空缺 O10]**

### F6: 运维与维护成本
- **子因素 F6.1**: 系统更新频率与破坏性变更
- **子因素 F6.2**: 技术支持响应速度（中文支持？）
- **子因素 F6.3**: 管理员界面易用性

#### 条件分类：
- **人类已提供**：无。
- **可推导**：30 人团队通常无专职 IT 管理员，需低维护方案。
- **仍需研究**：
  - 候选系统的**中文客服/文档**支持程度。→ **[空缺 O11]**
  - 开源方案的社区活跃度与 Issue 响应时间。→ **[空缺 O12]**

### F7: 可扩展性与稳定性
- **子因素 F7.1**: 并发处理能力（30 人峰值）
- **子因素 F7.2**: 架构弹性（云原生 vs 单体）

#### 条件分类：
- **人类已提供**：无。
- **可推导**：30 人规模下，任何现代 SaaS 均能轻松承载，此因素主要作为排除极端低端产品的依据。
- **仍需研究**：无明显空缺，除非发现某免费方案有严格并发限制。→ **[空缺 O13]**（待验证是否存在此类限制）

## 5. 阶段 02 研究路径与行动入口

### 5.1 候选对象类别（冻结集合）

为避免漂移，阶段 01 冻结以下三类候选对象，阶段 02 不得随意增删类别，只能在此框架内筛选具体产品：

1. **商业 SaaS（Cloud-based）**：
   - *典型代表*：RoomGuru, Cudo, Zoom Rooms, Microsoft Teams Rooms, Slack Connect (if applicable), 钉钉/飞书会议室模块（若适用）。
   - *特点*：开箱即用，免运维，按用户/会议室收费。
   - *待验证属性*：价格（O4）、双向日历同步（O2）、门禁集成（O7）、国内访问速度（O9）。

2. **开源自托管（Self-hosted Open Source）**：
   - *典型代表*：Cal.com, Nextcloud Meeting, Mattermost (with plugins), Jitsi Meet (with booking plugin).
   - *特点*：无许可费，数据私有，需自行维护服务器。
   - *待验证属性*：服务器成本（O5）、维护人力（O12）、功能完整性（O1）。

3. **混合/轻量级方案（Hybrid/Lightweight）**：
   - *典型代表*：基于 Airtable/Notion + Zapier/n8n 构建的简易预约系统；或使用 Office 365/Google Workspace 内置共享日历功能。
   - *特点*：低成本，灵活，但功能有限，依赖人工或简单自动化。
   - *待验证属性*：能否满足双向同步（O2）、门禁联动可行性（O6, O8）。

> **排除原则**：若某候选系统在阶段 02 中被证实**不支持双向日历同步**（违反 F2 P0 约束）或**年度成本远超 ¥20,000**（违反 F3 P0 约束），则显式排除并记录理由。
