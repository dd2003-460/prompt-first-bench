# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

**核心交付物**：一份针对 30 人研发团队的会议室预约系统选型报告，包含：
1. **选型推荐**：明确推荐的具体产品/方案（或自建组合），并说明理由。
2. **成本表**：年度总成本 ≤ ¥20,000 的详细拆解（软件订阅、硬件、实施费、维护费等）。
3. **风险清单**：技术兼容性、数据隐私、供应商锁定、扩展性等方面的主要风险及缓解措施。

**非目标（Out of Scope）**：
- 不设计具体的 UI/UX 原型。
- 不进行代码级架构设计（除非是自建方案的核心逻辑验证）。
- 不涉及办公空间物理布局改造建议。

## 2. 顶层影响因素分解（正交且覆盖完整）

为确保覆盖所有关键维度，将任务分解为以下 5 个互相正交的顶层因素：

| 编号 | 因素名称 | 描述 | 优先级 |
|------|----------|------|--------|
| F1 | **功能匹配度** | 是否满足多端支持、日历集成、门禁联动等核心需求 | P0 |
| F2 | **成本结构** | 总拥有成本（TCO）是否在预算内，成本构成是否透明 | P0 |
| F3 | **技术兼容性与集成能力** | macOS/Windows/Web 三端体验，Google Calendar + Outlook 双向同步稳定性 | P0 |
| F4 | **部署模式与数据主权** | SaaS vs 自托管，数据安全性，合规性（如国内法规） | P1 |
| F5 | **运维与扩展性** | 管理复杂度，未来人员增长或会议室增加的适应性 | P2 |

### 递归分解

#### F1: 功能匹配度
- **F1.1 多端支持**
    - 子因素：Web 端可用性（浏览器兼容）、移动端 App（iOS/Android）、桌面端体验（macOS/Windows 是否有原生客户端或优秀 Web 封装）。
    - *已知*：用户要求 macOS/Windows/Web 三端。
    - *空缺*：各候选产品在 macOS/Windows 上的具体交互体验差异；是否存在原生桌面应用。
- **F1.2 日历集成深度**
    - 子因素：单向同步 vs 双向同步；冲突检测机制；会议邀请自动发送能力。
    - *已知*：必须集成 Google Calendar (GC) 和 Microsoft Outlook (M365)。
    - *空缺*：主流 SaaS 对 GC/M365 的双向同步稳定性评测；自建方案的 OAuth 集成难度。
- **F1.3 门禁联动（可选）**
    - 子因素：硬件接口标准（API/SDK）；主流门禁品牌兼容性（如海康、大华、中控）；延迟容忍度。
    - *已知*：作为“可选”功能，意味着如果成本过高或集成复杂，可降级为人工确认或独立门禁。
    - *空缺*：哪些 SaaS 提供现成的门禁 API？自建方案对接国内主流门禁品牌的开发工作量评估。

#### F2: 成本结构
- **F2.1 软件许可费**
    - 子因素：按席位计费 vs 按会议室计费 vs 一次性买断；免费额度限制。
    - *空缺*：各候选产品针对 30 人团队（假设全员需访问，但仅部分人常预订）的准确报价。
- **F2.2 硬件成本（若含门禁）**
    - 子因素：门禁控制器、读卡器、屏幕显示器（用于显示会议室状态）的成本。
    - *空缺*：若选择 SaaS 自带硬件套件的价格；若自建，国产门禁设备的市场价区间。
- **F2.3 实施与维护费**
    - 子因素：初始配置费、年维护费、技术支持等级。
    - *空缺*：SaaS 厂商是否收取实施费；自建方案的人力投入折算成本。

#### F3: 技术兼容性与集成能力
- **F3.1 日历协议支持**
    - 子因素：CalDAV 支持情况；OAuth 2.0 授权流程的顺畅度；时区处理准确性。
    - *空缺*：GC 和 M365 在不同平台上的同步延迟实测数据。
- **F3.2 跨平台一致性**
    - 子因素：Web 端在 Safari/Chrome/Edge 下的表现；移动端推送通知可靠性。
    - *空缺*：用户对“Web 端”的定义是否包含响应式设计还是必须有独立 App。

#### F4: 部署模式与数据主权
- **F4.1 数据存储位置**
    - 子因素：服务器地理位置（境内/境外）；是否符合《数据安全法》/《个人信息保护法》。
    - *空缺*：海外 SaaS（如 Roomle, Zoom Rooms）的数据存储地；国内 SaaS（如飞书会议室、钉钉智能会议室）的合规性优势。
- **F4.2 账号体系集成**
    - 子因素：SSO（单点登录）支持；AD/LDAP 集成；SCIM 用户同步。
    - *空缺*：各候选产品对企业级身份认证的支持程度。

#### F5: 运维与扩展性
- **F5.1 管理后台易用性**
    - 子因素：管理员设置会议室属性、权限、报表的难度。
    - *空缺*：实际管理 30 人规模下，不同系统的操作效率对比。
- **F5.2 扩展性**
    - 子因素：增加新会议室的流程；人员离职/入职的处理自动化。
    - *空缺*：API 开放程度，便于未来对接其他 IoT 设备（如空调、灯光）。

## 3. 已知条件 vs 可推导条件 vs 空缺条件

### A. 人类已提供的条件（Confirmed Constraints）
1. 团队规模：30 人研发团队。
2. 预算上限：¥20,000 / 年。
3. 终端要求：macOS, Windows, Web 三端可用。
4. 日历集成：必须支持 Google Calendar 和 Outlook (Microsoft 365)。
5. 附加功能：门禁联动为可选（Optional），非强制。
6. 交付物：选型推荐 + 成本表 + 风险清单。

### B. 从项目可推导的条件（Derived Assumptions - 需标注为假设）
1. **会议室数量假设**：30 人研发团队通常拥有 3-8 间会议室。*假设*：按 5 间会议室计算硬件和软件费用。（*注：此为待验证假设，若实际数量偏差大，成本模型需调整*）。
2. **用户活跃度假设**：并非所有 30 人都需要高频预订，但所有人都可能需要查看空闲状态。*假设*：软件许可按“全量用户”或“活跃预订者”计费，需分别测算。
3. **“Web 端”定义**：*假设*：指通过现代浏览器（Chrome/Safari/Edge）访问的响应式 Web 应用，无需安装额外插件。
4. **门禁联动范围**：*假设*：若启用，仅需实现“预订成功自动开门”或“会议结束自动关门”，无需复杂的生物识别或访客管理。
5. **数据合规基线**：*假设*：作为中国境内企业，优先考虑数据存储于中国境内的服务，以降低合规风险和数据传输延迟。

## 4. 候选对象类别（冻结集合）

为避免阶段 02 漂移，现将潜在解决方案分为以下三类进行并行研究：

1. **国际通用 SaaS 平台**
   - *代表候选（待验证）*：Zoom Rooms, Microsoft Teams Rooms (若已有 M365), Slack Connect (若使用 Slack), Roomle, Doodle Rooms.
   - *特点*：功能成熟，生态好，但可能有数据出境问题或价格较高。
2. **国内协同办公平台内置模块**
   - *代表候选（待验证）*：飞书会议室, 钉钉智能会议室, 企业微信会议室.
   - *特点*：成本低（可能免费或含在套餐内），本土化好，但功能定制性可能受限，门禁联动支持不明。
3. **垂直领域专业 SaaS / 轻量级工具**
   - *代表候选（待验证）*：Meet.io, Calendly (会议室插件), Acuity Scheduling, 或国内初创公司开发的专用会议室系统.
   - *特点*：专注预约场景，性价比高，但需仔细验证日历集成深度。
4. **自建开源方案**
   - *代表候选（待验证）*：基于 React/Vue + Node.js/Python + CalDAV 库自行开发; 或使用现有开源项目二次开发.
   - *特点*：完全可控，无年费，但有人力开发和运维成本。

> **注意**：以上均为“待验证的研究目标”，具体产品名称、版本、价格均需阶段 02 核验。

## 6. 风险初步识别（供阶段 03 细化）

1. **日历同步冲突风险**：GC 和 M365 同时使用时，可能出现事件重复创建或时间偏移。*缓解*：选择支持“主日历源”策略的系统，或仅允许单向写入。
2. **预算超支风险**：SaaS 按席位计费时，30 人可能超出预期；或门禁硬件一次性投入高。*缓解*：区分“必要席位”与“只读席位”；门禁作为二期选项。
3. **供应商锁定风险**：数据格式私有，迁移困难。*缓解*：确保支持 CalDAV/iCal 导出；避免使用专有数据库格式。
4. **合规风险**：海外 SaaS 数据出境可能违反国内法规。*缓解*：优先选择国内部署的服务，或在合同中明确数据本地化条款。
