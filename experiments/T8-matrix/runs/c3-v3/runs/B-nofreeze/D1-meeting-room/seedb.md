# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**核心交付物**：一份包含以下内容的完整选型推荐报告：
1. **选型推荐**：针对 30 人团队，在 macOS/Windows/Web 三端支持、Google Calendar + Outlook 双日历集成、可选门禁联动约束下，推荐的会议室预约系统架构或 SaaS 产品。
2. **成本表**：年度总成本 ≤ ¥20,000 的详细预算拆解（含软件许可、潜在硬件、实施费用）。
3. **风险清单**：技术兼容性、数据隐私、供应商锁定、运维成本等关键风险及缓解措施。
4. **工件要求**：必须包含来源编号索引、矛盾处置记录、不确定性标注，不能仅给结论。

## 2. 顶层影响因素分解（正交且覆盖完整）

### 因素 A：软件功能与平台兼容性
*   **子因素 A1：多端支持能力**
    *   是否原生支持 macOS 和 Windows 客户端？
    *   Web 端是否响应式适配移动端浏览器？
    *   *边界*：必须同时满足桌面端（Mac/Win）和 Web 端，排除仅支持单一平台的方案。
*   **子因素 A2：日历双向同步集成**
    *   Google Calendar 集成深度（API 稳定性、冲突检测机制）。
    *   Outlook (M365) 集成深度（Exchange Online 或本地 Outlook 支持情况）。
    *   *边界*：必须实现“双向同步”而非单向读取，确保会议室占用状态实时反映到个人日历。
*   **子因素 A3：门禁联动扩展性**
    *   是否提供开放 API 或 Webhook 用于对接门禁系统？
    *   是否内置常见门禁品牌插件？
    *   *边界*：此为“可选”功能，不强制要求，但需评估未来扩展的技术债务和额外成本。

### 因素 B：成本结构与预算约束
*   **子因素 B1：软件订阅费用**
    *   SaaS 按人头收费 vs 按会议室数量收费模式。
    *   30 人团队的席位成本估算。
    *   *边界*：年费总额 ≤ ¥20,000。若按人头算，人均 ≤ ¥666/年；若按房间算，需结合房间数量推导单价上限。
*   **子因素 B2：隐藏成本与实施费用**
    *   一次性部署/配置费用。
    *   高级功能解锁费用（如 SSO、审计日志）。
    *   货币汇率波动影响（多数 SaaS 为美元计价）。
*   **子因素 B3：硬件依赖成本**
    *   是否需要专用显示终端（如 iPad 支架、触摸屏）？
    *   门禁改造成本（若启用联动）。
    *   *边界*：题目未明确现有硬件状况，需区分“纯软件方案”和“软硬一体方案”的成本差异。

### 因素 C：技术架构与数据安全
*   **子因素 C1：部署模式**
    *   SaaS（公有云） vs 私有化部署（On-premise）。
    *   *边界*：预算 ¥20,000/年 极大概率指向 SaaS 模式，私有化部署通常涉及服务器采购和维护人力，超出预算范畴，但需验证是否存在轻量级开源自托管方案。
*   **子因素 C2：数据隐私与合规**
    *   数据存储位置（中国境内 vs 境外）。
    *   个人信息保护合规性（PIPL）。
    *   *边界*：30 人研发团队可能涉及敏感代码或项目信息，需评估云端存储的风险。
*   **子因素 C3：单点故障与可用性**
    *   SLA 承诺（99.9% vs 99.99%）。
    *   离线可用性（断网时能否查看日程？）。

### 因素 D：用户体验与运维负担
*   **子因素 D1：易用性与学习曲线**
    *   员工预约流程步骤数。
    *   管理员配置复杂度（会议室创建、权限设置）。
*   **子因素 D2：IT 运维投入**
    *   日常维护工作量（用户重置密码、设备故障排查）。
    *   技术支持响应速度。

## 3. 条件分类：已知、可推导、待研究

### 3.1 人类已提供的条件（Known Facts）
1.  **团队规模**：30 人研发团队成员。
2.  **预算上限**：≤ ¥20,000 / 年。
3.  **操作系统要求**：macOS, Windows, Web 三端必须支持。
4.  **日历集成要求**：必须集成 Google Calendar 和 Outlook。
5.  **门禁联动**：可选功能（Optional），非强制。
6.  **输出格式**：完整工件，含来源索引、矛盾处置、不确定性标注。

### 3.2 从项目可推导的条件（Derived Conditions）
1.  **人均预算限制**：¥20,000 / 30 人 ≈ ¥666.67 / 人 / 年。这意味着无法选择高端企业级 SaaS（如某些按 $10+/user/month 计费的产品，年费超 $3,600/user，远超预算）。
2.  **SaaS 倾向性**：由于预算极低且无专职 IT 基础设施描述，私有化部署（Self-hosted）的可能性较低，除非使用免费开源软件且团队具备 DevOps 能力。主要候选应为 SaaS 服务。
3.  **混合日历场景**：团队内部可能混用 Google Workspace 和 Microsoft 365，因此系统必须能处理跨提供商的冲突检测逻辑。
4.  **房间数量未知**：题目未给出会议室数量。这是一个关键变量。假设典型 30 人团队有 3-5 间会议室。成本模型需基于“按房间收费”或“按人头收费”两种假设进行敏感性分析。

### 3.3 仍需研究的条件（Open Questions / Gaps）
1.  **[GAP-1] 具体候选 SaaS 产品的当前定价**：
    *   Roomle, BookThatApp, Calendly (Team plan), Acuity Scheduling, 以及国内竞品（如钉钉/飞书自带的会议室模块、或独立第三方如“会小二”、“云会议”等）的最新价格。
    *   *子问题*：哪些产品支持“按房间收费”且单价低？哪些产品对 30 人以下团队有免费层或低价层？
2.  **[GAP-2] 日历集成的技术细节与限制**：
    *   候选产品是否真正支持“双向同步”？
    *   对于 Outlook，是支持 Exchange Online API 还是仅支持 ICS 文件导入导出（后者体验差且有延迟）？
    *   Google Calendar 集成是否支持 Service Account 以实现更稳定的后台同步？
3.  **[GAP-3] 门禁联动的实际可行性与成本**：
    *   主流 SaaS 是否有现成的门禁 API 文档？
    *   若需开发中间件，预估的开发成本和年维护成本是多少？
    *   常见的门禁品牌（如 HID, ZKTeco, 海康威视）是否有官方合作伙伴列表？
4.  **[GAP-4] 数据合规与服务器位置**：
    *   国际 SaaS（如 Roomle）的数据中心是否在海外？是否符合中国 PIPL 对出境数据的要求？
    *   国内 SaaS 是否提供 SLA 保障？
5.  **[GAP-5] 现有办公环境假设**：
    *   团队是否已有统一的身份认证系统（SSO/LDAP）？若有，候选产品是否支持 SAML/OIDC？
    *   会议室是否已配备智能面板或显示屏？若无，是否需要额外购买硬件（计入预算）？

## 4. 递归分解与叶子节点判定

### 递归层级 1：因素 A (软件功能)
*   **A1 多端支持** -> 叶子：各候选产品的 App Store/Microsoft Store 上架情况及 Web URL 可访问性。（待研究）
*   **A2 日历集成** -> 叶子：
    *   A2a: Google OAuth 2.0 授权流程支持情况。（待研究）
    *   A2b: Microsoft Graph API 或 Exchange Web Services 支持情况。（待研究）
    *   A2c: 冲突解决策略（先到先得 vs 优先级）。（待研究）
*   **A3 门禁联动** -> 叶子：API 文档公开程度、Webhook 事件类型（预约成功/取消/开始/结束）。（待研究）

### 递归层级 1：因素 B (成本)
*   **B1 订阅费** -> 叶子：
    *   B1a: 免费套餐功能限制（房间数、用户数、功能裁剪）。（待研究）
    *   B1b: 付费套餐阶梯价格（月付 vs 年付折扣）。（待研究）
*   **B2 隐藏成本** -> 叶子：
    *   B2a: 支付手续费（信用卡 vs 对公转账）。（待研究）
    *   B2b: 汇率换算后的人民币实际支出。（待研究，需查询实时汇率）
*   **B3 硬件成本** -> 叶子：
    *   B3a: 标准会议室显示终端市场价（iPad Mini / Android Tablet / 专用 Touch Panel）。（待研究）
    *   B3b: 门禁控制器升级费用（如需联网改造）。（待研究）

### 递归层级 1：因素 C (技术/安全)
*   **C1 部署模式** -> 叶子：
    *   C1a: 开源替代品（如 OpenProject, Nextcloud Rooms, Jitsi Meet 配套工具）的社区活跃度和 Docker 部署难度。（待研究）
*   **C2 数据合规** -> 叶子：
    *   C2a: 候选厂商的隐私政策中关于数据驻留地的声明。（待研究）
*   **C3 可用性** -> 叶子：
    *   C3a: 历史宕机记录或 Status Page 公开信息。（待研究）

### 递归层级 1：因素 D (体验/运维)
*   **D1 易用性** -> 叶子：
    *   D1a: 用户评价中关于“操作繁琐”的负面反馈频率。（待研究）
*   **D2 运维** -> 叶子：
    *   D2a: 客服支持渠道（邮件/在线聊天/电话）及响应时间 SLA。（待研究）

### 停止条件检查
所有叶子节点均为具体的、可通过网络搜索或厂商文档核验的事实性问题（价格、API 文档、SLA、地理位置等）。无需进一步抽象分解。分解完成。

## 6. 阶段 02 研究路径与入口

### 6.1 第一批优先研究行动（P0）
1.  **目标网站**：
    *   `roomle.com` (全球知名，功能全)
    *   `bookthatapp.com` (北美常用)
    *   `calendly.com` (团队版)
    *   `feishu.cn` / `dingtalk.com` (国内主流协作平台自带功能，需确认是否支持外部日历集成)
    *   `acuityscheduling.com`
2.  **搜索词**：
    *   "Roomle pricing 2024 per room cost"
    *   "BookThatApp pricing plans small team"
    *   "Calendly Team plan price per user"
    *   "飞书 会议室 预约 外部日历集成 Outlook"
    *   "Best room booking software under $100/month 2024"
3.  **关键字段提取**：
    *   最低起步价（Monthly/Yearly）。
    *   计费单位（Per User / Per Room / Flat Rate）。
    *   免费试用期限。
    *   是否支持 Google/Outlook 双向同步（Explicit mention in feature list）。
4.  **失败备用路径**：
    *   若上述国际 SaaS 均因汇率或最低消费门槛超出预算，转向研究国内垂直 SaaS（如“会小二”、“云会议”、“腾讯会议”企业版会议室模块）。
    *   若 SaaS 均不满足，转向研究开源方案（如 `nextcloud/rooms`, `openproject`）的 Docker 部署教程和社区支持活跃度。

### 6.2 第二批研究行动（P1）
1.  **技术集成验证**：
    *   针对初步筛选出的 2-3 个候选产品，深入阅读其 Developer Docs 或 Help Center。
    *   重点查找：`OAuth 2.0 scopes for Google Calendar`, `Microsoft Graph API permissions required`.
    *   确认是否支持 `ICS` 订阅作为降级方案。
2.  **门禁联动调研**：
    *   搜索关键词：`[Candidate Name] door access control integration`, `[Candidate Name] API webhook events`.
    *   若无直接支持，评估开发简单 HTTP Webhook 接收器的工作量（预计 < 1 人天）。

### 6.3 第三批研究行动（P2）
1.  **合规与风险**：
    *   下载候选产品的 DPA (Data Processing Agreement)。
    *   检查服务器地理位置声明。
2.  **用户口碑**：
    *   G2, Capterra, Trustpilot 上关于该产品的最近 6 个月评论，重点关注“Bug”、“Sync issues”、“Support response”标签。

## 7. 矛盾处置与不确定性标注原则

*   **矛盾处置**：若厂商官网宣传“支持 Outlook”，但 Help Center 显示仅支持“Ics Import”，则判定为“部分支持/弱支持”，并在最终报告中注明此差异，建议进行 PoC（概念验证）测试。
*   **不确定性标注**：
    *   所有价格必须标注 `[Price as of YYYY-MM-DD]`，因为 SaaS 价格变动频繁。
    *   所有 API 能力若未在官方文档明确写出，标注 `[Unverified - Requires PoC]`。
    *   门禁联动若仅为“理论可行”，标注 `[Theoretical Feasibility Only]`。
