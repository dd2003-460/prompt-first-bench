# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

本任务旨在为 30 人研发团队设计一套会议室预约系统方案，最终交付物包含以下三部分：
1. **选型推荐**：明确推荐具体的软件产品（SaaS 或自建/开源）及其版本。
2. **成本表**：基于年度预算 ≤¥20,000 的详细费用拆解（含软件许可、硬件、实施费等）。
3. **风险清单**：识别技术兼容性、数据隐私、预算超支及运维方面的潜在风险及缓解措施。

## 2. 顶层影响因素分解（正交性检查）

为了覆盖所有关键决策维度，将目标拆分为以下五个互相正交且完整覆盖的影响因素：

*   **F1: 核心功能满足度 (Core Functionality)**
    *   子因素 F1.1: 基础预约流程（创建、查看、取消、冲突检测）。
    *   子因素 F1.2: 日历集成能力（Google Calendar + Outlook 双向同步）。
    *   子因素 F1.3: 多端支持能力（macOS 客户端、Windows 客户端、Web 端响应式或独立应用）。
    *   子因素 F1.4: 门禁联动扩展性（是否提供 API/Webhook 以对接 IoT 门禁设备）。
*   **F2: 成本结构与预算合规性 (Cost & Budget Compliance)**
    *   子因素 F2.1: 软件许可费（SaaS 订阅费 vs 开源 License 费）。
    *   子因素 F2.2: 部署与维护成本（云服务费用、服务器维护、人力投入）。
    *   子因素 F2.3: 一次性实施/定制费用（如有）。
    *   约束条件：总年度成本 ≤ ¥20,000。
*   **F3: 技术兼容性与架构可行性 (Technical Compatibility)**
    *   子因素 F3.1: 操作系统兼容性（macOS/Windows 原生支持或跨平台框架稳定性）。
    *   子因素 F3.2: 日历协议兼容性（CalDAV/iCalendar 标准支持程度）。
    *   子因素 F3.3: 数据安全性与合规性（数据存储位置、加密标准、GDPR/等保要求）。
*   **F4: 用户体验与团队适配性 (UX & Team Fit)**
    *   子因素 F4.1: 界面易用性（学习曲线、移动端体验）。
    *   子因素 F4.2: 通知机制（邮件、即时通讯集成如 Slack/Teams/钉钉/飞书）。
    *   子因素 F4.3: 管理后台功能（权限控制、会议室信息管理、报表统计）。
*   **F5: 可扩展性与长期维护 (Scalability & Maintenance)**
    *   子因素 F5.1: 用户规模弹性（从 30 人扩展到 50-100 人的成本变化）。
    *   子因素 F5.2: 供应商锁定风险（数据导出难度、API 开放性）。
    *   子因素 F5.3: 社区活跃度与支持周期（针对开源方案）。

## 3. 条件区分：已知、可推导、待研究

### 3.1 人类已提供的条件（Known Conditions）
*   **K1**: 团队规模 = 30 人。
*   **K2**: 年度预算上限 = ¥20,000 CNY。
*   **K3**: 必须支持的终端 = macOS, Windows, Web。
*   **K4**: 必须集成的日历 = Google Calendar, Microsoft Outlook。
*   **K5**: 可选需求 = 门禁联动（非强制，但需评估可行性）。

### 3.2 从项目可推导的条件（Derivable Conditions）
*   **D1**: 人均年预算 ≈ ¥666.67/人。这意味着如果选择 SaaS 方案，单人年成本不能超过此值，或者需要寻找按会议室计费而非按用户计费的方案，或者选择低价开源方案。
*   **D2**: 由于涉及 Google 和 Outlook 双日历集成，所选系统必须同时支持 CalDAV 协议或拥有官方认证的第三方连接器（Connector），因为直接同时深度集成两大巨头私有 API 在小型系统中较少见，通常依赖标准协议或中间件。
*   **D3**: "门禁联动"通常意味着系统需要输出“会议状态”信号给硬件。这要求系统具备 Webhook 推送能力或 RESTful API。
*   **D4**: 30 人团队属于中小企业（SMB）场景，对定制化开发容忍度低，更倾向于开箱即用（Out-of-the-box）或低代码配置。

### 3.3 仍需研究的条件（Unknowns / Gaps）
*   **U1**: [待研究] 主流会议室预约 SaaS 在中国大陆的可访问性及支付便利性。
*   **U2**: [待研究] 具体候选产品的最新定价模型（按用户、按会议室、还是混合）。
*   **U3**: [待研究] 候选产品对 macOS/Windows 桌面客户端的支持情况（是 Electron 封装、原生 App 还是仅 PWA？）。
*   **U4**: [待研究] 候选产品与 Google/Outlook 集成的具体实现方式（自动同步还是手动导入？是否支持双向更新？）。
*   **U5**: [待研究] 开源方案（如 Roomle, OpenRoom 等类似项目）的部署复杂度及维护成本估算。
*   **U6**: [待研究] 门禁联动所需的 API 接口文档及常见门禁厂商（如海康威视、大华）的对接案例。

## 4. 递归分解与叶子节点判定

### F1: 核心功能满足度
*   **F1.1 基础预约流程**:
    *   *原子*: 冲突检测算法精度（秒级/分钟级）。
    *   *原子*: 临时借用/抢占机制。
*   **F1.2 日历集成**:
    *   *原子*: Google OAuth 授权流程稳定性。
    *   *原子*: Outlook/Microsoft Graph API 授权流程稳定性。
    *   *原子*: 时区处理正确性（中国标准时间 CST）。
*   **F1.3 多端支持**:
    *   *原子*: Web 端浏览器兼容性（Chrome, Edge, Safari）。
    *   *原子*: 桌面端安装包分发机制（DMG for Mac, EXE/MSI for Win）。
    *   *原子*: 离线模式支持（可选，非强制）。
*   **F1.4 门禁联动**:
    *   *原子*: Webhook 触发事件类型（开始、结束、取消）。
    *   *原子*: API 认证安全机制（Token/OAuth）。

### F2: 成本结构
*   **F2.1 软件许可费**:
    *   *原子*: SaaS 订阅单价（USD/CNY）。
    *   *原子*: 开源软件版权许可类型（MIT/Apache/GPL）。
*   **F2.2 部署与维护**:
    *   *原子*: 云服务器最低配置成本（CPU/RAM/Disk）。
    *   *原子*: 域名与 SSL 证书成本。
    *   *原子*: 内部 IT 人员维护工时折算（若选自建）。
*   **F2.3 实施费用**:
    *   *原子*: 初始配置时间预估。
    *   *原子*: 培训成本。

### F3: 技术兼容性
*   **F3.1 OS 兼容性**:
    *   *原子*: macOS 最低版本要求（如 Catalina+）。
    *   *原子*: Windows 最低版本要求（如 Win10+）。
*   **F3.2 日历协议**:
    *   *原子*: CalDAV 服务器地址格式支持。
    *   *原子*: ICS 文件生成与解析能力。
*   **F3.3 数据安全**:
    *   *原子*: 数据传输加密（HTTPS/TLS 1.2+）。
    *   *原子*: 数据存储加密（AES-256）。
    *   *原子*: 数据驻留地（中国大陆 vs 海外）。

### F4: 用户体验
*   **F4.1 易用性**:
    *   *原子*: 首次登录引导流程长度。
    *   *原子*: 搜索会议室的平均点击次数。
*   **F4.2 通知机制**:
    *   *原子*: 邮件模板自定义能力。
    *   *原子*: IM 机器人接入难度（Slack/Teams/Feishu/DingTalk）。
*   **F4.3 管理后台**:
    *   *原子*: 会议室属性编辑字段完整性（设备、容量、位置）。
    *   *原子*: 操作日志审计功能。

### F5: 可扩展性
*   **F5.1 规模弹性**:
    *   *原子*: 用户数增加时的边际成本曲线。
*   **F5.2 供应商锁定**:
    *   *原子*: 数据导出格式（CSV/JSON/ICS）。
    *   *原子*: API 速率限制策略。
*   **F5.3 社区/支持**:
    *   *原子*: GitHub Issues 平均响应时间（针对开源）。
    *   *原子*: 官方 SLA 等级（针对 SaaS）。

**停止条件判定**：上述所有叶子节点均为最小可执行研究单元，无法再进一步分解而不进入具体产品细节（属于阶段 02 工作）。

## 5. 空缺清单（Gap List）

| ID | 空缺描述 | 阻塞影响 | 优先级 | 备注 |
|----|----------|----------|--------|------|
| GAP-01 | 主流 SaaS 产品（如 Zoom Rooms, Teams Rooms, Calendly, Acuity, 国内云厂商套件）的具体定价及 30 人规模下的年费总额。 | 决定是否能通过预算筛选。 | High | 需验证是否有免费层或低价套餐。 |
| GAP-02 | 候选产品是否提供独立的 macOS 和 Windows 桌面客户端，还是仅依赖 Web/PWA。 | 直接影响 K3 条件的满足度。 | High | PWA 可能被视为不满足“三端”严格定义。 |
| GAP-03 | 候选产品对 Google Calendar 和 Outlook 的双向同步支持详情。 | 决定是否需要额外开发中间件。 | High | 单向同步可能导致数据不一致。 |
| GAP-04 | 开源方案（如 Next.js/React 全栈示例、Node.js 后端）的部署难度及所需服务器资源。 | 决定自建方案的隐性成本（人力/服务器）。 | Medium | 若人力成本高，则排除自建。 |
| GAP-05 | 门禁联动的具体 API 规范及是否有现成插件。 | 决定可选需求的实现成本。 | Low | 若无现成插件，需评估开发工作量。 |
| GAP-06 | 中国大陆网络环境下，海外 SaaS 服务的访问稳定性及数据合规风险。 | 影响用户体验和法律风险。 | High | 若不稳定，需考虑国内替代方案。 |

## 6. 阶段 02 研究路径与行动入口

### 6.1 第一批优先研究动作

1.  **市场扫描（SaaS）**：
    *   **目标网站**：Zoom, Microsoft, Google Workspace Marketplace, Calendly, Acuity Scheduling, 阿里云/腾讯云/华为云官网。
    *   **搜索词**：
        *   "meeting room booking software pricing 30 users"
        *   "会议室预约系统 SaaS 价格"
        *   "Zoom Rooms pricing per user"
        *   "Microsoft Teams Rooms license cost"
    *   **字段提取**：年费总额、计费单位（per user/per room）、是否包含桌面客户端、日历集成列表。
    *   **备用来源**：G2 Reviews, Capterra, 知乎专栏（搜索“会议室管理系统选型”）。

2.  **开源方案调研**：
    *   **目标网站**：GitHub, GitLab。
    *   **搜索词**：
        *   "open source meeting room booking system"
        *   "github meeting room scheduler caldav"
        *   "react meeting room app"
    *   **字段提取**：Star 数量、最后更新时间、License 类型、技术栈、Issue 活跃度、是否有 Docker Compose 一键部署脚本。

3.  **技术兼容性验证**：
    *   **目标**：查阅候选产品的官方文档（Documentation）。
    *   **关键字段**：
        *   "Supported platforms" (macOS/Windows versions)
        *   "Calendar Integration" (Google/Outlook sync direction)
        *   "API Reference" (Webhooks for door access)
    *   **失败备用路径**：若官方文档模糊，查找第三方评测博客或 Stack Overflow 相关问题。

### 6.2 具体研究问题映射到空缺

*   **针对 GAP-02**：确认每个候选产品是否有 `.dmg` 和 `.exe` 安装包下载链接。
*   **针对 GAP-03**：截图或引用文档中关于 “Two-way sync with Google/Outlook” 的描述。

## 7. 初步假设与候选对象（待验证）

*注意：以下内容仅为基于一般知识的初步假设，**未经验证**，必须作为阶段 02 的研究目标，不得视为事实。*

*   **候选 A: Microsoft Teams Rooms (MTR)**
    *   *假设属性*：强集成 Outlook，可能有专用硬件要求，成本较高。
    *   *待验证*：30 人许可证费用是否超预算？是否支持纯软件部署（无专用硬件）？
*   **候选 B: Zoom Rooms**
    *   *假设属性*：集成 Zoom 日历，可能有独立客户端，成本中等。
    *   *待验证*：是否支持 Google Calendar 同步？桌面客户端是否为原生？
*   **候选 C: 国内云厂商套件（如腾讯会议企业版/钉钉会议室）**
    *   *假设属性*：访问速度快，合规性好，可能包含在办公套件中。
    *   *待验证*：是否支持 Outlook 集成？是否有独立 macOS/Windows 客户端？
*   **候选 D: 开源方案（如 Roomle, OpenRoom, 或自研 React App）**
    *   *假设属性*：成本低（仅服务器费），高度可定制，支持 API。
    *   *待验证*：维护成本是否可控？日历集成模块是否成熟？

## 8. 矛盾处置与不确定性标注

*   **矛盾点 1**：预算极低（¥20,000/30人 ≈ ¥666/人/年）vs 国际主流 SaaS 通常按高价订阅收费。
    *   *处置*：阶段 02 需重点排查是否有“按会议室计费”而非“按用户计费”的模式，或寻找专门的 SMB 低价套餐。若所有主流 SaaS 均超预算，则需转向开源自建或国内低价替代品。
*   **矛盾点 2**：要求 macOS/Windows 原生客户端 vs 现代趋势多为 Web/PWA。
    *   *处置*：阶段 02 需严格区分“PWA 添加到主屏幕”与“独立桌面应用”。若用户严格要求 .dmg/.exe 安装，许多 Web-first 产品将被排除。
*   **不确定性**：门禁联动的具体硬件品牌未知。
    *   *处置*：阶段 02 仅研究系统的 API 输出能力，不深入特定门禁品牌的协议细节，除非用户提供具体品牌。
