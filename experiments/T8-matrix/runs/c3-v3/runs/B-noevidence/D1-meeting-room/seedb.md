# 阶段 01：目标分解、已知与空缺条件

## 1. 任务目标交付物定义

**核心交付物：**
1. **选型推荐清单**：针对会议室预约系统的各功能模块（核心预约引擎、日历集成层、门禁联动层、前端多端适配），给出具体产品/服务/开源方案候选，并标注其属性待验证状态。
2. **成本表**：基于年度预算 ≤¥20,000 的约束，列出各候选方案的预估年成本结构（许可费、服务器费、开发人力折算等），明确哪些是厂商标价、哪些是估算值。
3. **风险清单**：识别技术兼容性、数据隐私、供应商锁定、预算超支、维护成本等维度的风险，并评估其对项目成功的影响程度。

**非目标（Out of Scope）：**
- 不设计具体的 UI/UX 界面细节。
- 不提供完整的代码实现或架构拓扑图（属于阶段 03）。
- 不涉及硬件采购（如门禁控制器本身），仅关注软件层面的“联动”接口可行性。

## 2. 影响因素递归分解

### 顶层因素 (Level 1)

| 编号 | 因素名称 | 正交性说明 | 覆盖目标 |
| :--- | :--- | :--- | :--- |
| F1 | **核心预约引擎选型** | 负责会议创建、冲突检测、房间管理逻辑 | 选型推荐、成本表 |
| F2 | **多端前端适配策略** | macOS/Windows/Web 三端的访问方式与技术栈 | 选型推荐、风险清单 |
| F3 | **日历双向同步机制** | Google Calendar + Outlook 的集成深度与协议支持 | 选型推荐、风险清单 |
| F4 | **门禁联动扩展能力** | 可选功能的接口开放性与实施难度 | 选型推荐、风险清单 |
| F5 | **总拥有成本 (TCO) 构成** | 直接费用 vs 隐性费用（开发、运维、迁移） | 成本表、风险清单 |
| F6 | **数据合规与安全性** | 员工日程隐私、数据存储位置、权限控制 | 风险清单 |

#### Level 2 分解

##### F1: 核心预约引擎选型
*   **F1.1 SaaS 商业产品**: 现成云服务（如 Microsoft Bookings, Zoom Rooms, 国内企业微信/钉钉内置功能，或专业会议室系统如 RoomGuru, Calendly for Teams）。
    *   *子因素*: 许可证模式（按用户/按房间）、最低起订量、是否支持私有化部署。
*   **F1.2 开源/自研框架**: 基于开源项目二次开发（如 OpenProject, Odoo, 或轻量级 Node.js/Python 框架自建）。
    *   *子因素*: 社区活跃度、License 类型（MIT/Apache vs GPL）、二次开发工作量。
*   **F1.3 混合模式**: 使用通用日历 API 作为后端，前端自定义开发。
    *   *子因素*: API 限流、Webhook 可靠性、冲突处理算法复杂度。

##### F2: 多端前端适配策略
*   **F2.1 Web 优先 + PWA**: 所有端通过浏览器访问，macOS/Windows 通过 Electron/Tauri 封装或直接安装 PWA。
    *   *子因素*: 离线能力需求、推送通知在桌面端的可靠性。
*   **F2.2 原生客户端**: 为 Mac/Win 开发独立客户端（Electron/React Native Windows/macOS）。
    *   *子因素*: 打包体积、自动更新机制、跨平台一致性。
*   **F2.3 嵌入现有 IM/办公套件**: 若团队已用 Slack/Teams/企微，考虑插件形式。
    *   *子因素*: 平台依赖风险、功能限制。

##### F3: 日历双向同步机制
*   **F3.1 协议支持**: 必须同时支持 CalDAV (Google/Outlook 通用) 或 OAuth 2.0 (Google API / Microsoft Graph API)。
    *   *子因素*: 双向同步冲突解决策略（Last Write Wins vs Merge）、延迟容忍度。
*   **F3.2 认证与授权**: 
    *   Google: OAuth 2.0 + People API/Calendar API。
    *   Outlook: Microsoft Graph API (OAuth 2.0)。
    *   *子因素*: 应用注册审核流程、Token 刷新机制、Scope 最小化原则。
*   **F3.3 数据映射**: 会议室资源在日历中的表示方式（Resource Account vs Event Location Field）。

##### F4: 门禁联动扩展能力
*   **F4.1 接口开放性**: 系统是否提供 RESTful API/Webhook 用于触发门禁？
    *   *子因素*: 实时性要求（会议开始前 X 分钟开门）、失败重试机制。
*   **F4.2 硬件兼容性**: 主流门禁品牌（海康、大华、中控等）是否有标准 SDK 或中间件可对接？
    *   *子因素*: 是否需要额外购买网关设备、网络隔离问题。
*   **F4.3 安全边界**: 门禁指令的鉴权机制，防止未授权开门。

##### F5: 总拥有成本 (TCO) 构成
*   **F5.1 直接订阅费**: SaaS 产品的年费。
*   **F5.2 基础设施费**: 若自研/开源自托管，云服务器（ECS/CVM）+ 数据库 + CDN 费用。
*   **F5.3 开发与维护人力**: 
    *   初始开发工时估算。
    *   后续 Bug 修复、API 变更适配的人力投入。
    *   *注意*: 题目未给出人力单价，此为**关键空缺**。
*   **F5.4 第三方服务费**: 短信/邮件通知服务、域名证书、SSL 证书费用。

##### F6: 数据合规与安全性
*   **F6.1 数据存储地**: 数据是否出境？是否符合《个人信息保护法》？
*   **F6.2 权限粒度**: 谁能看谁的空闲？能否隐藏敏感会议标题？
*   **F6.3 审计日志**: 操作记录是否可追溯？

## 3. 条件区分：已知、可推导、未知

### A. 人类已提供的条件 (Known Constraints)
1.  **团队规模**: 30 人研发团队。
2.  **预算上限**: ¥20,000 / 年。
3.  **终端要求**: macOS, Windows, Web 三端可用。
4.  **日历集成**: 必须支持 Google Calendar 和 Outlook 的双向集成。
5.  **可选功能**: 门禁联动（非强制，但需评估可行性）。
6.  **交付物**: 选型推荐 + 成本表 + 风险清单。

### B. 从项目可推导的条件 (Derived Conditions)
1.  **并发量低**: 30 人团队，峰值并发极低，无需高可用集群架构，单节点即可满足性能需求。
2.  **数据量小**: 每日会议数量有限，存储成本几乎可忽略不计。
3.  **SaaS 偏好可能性高**: 鉴于预算有限且团队规模小，除非有强合规要求，否则自研全栈系统的人力成本极易超过 ¥20,000/年（假设中级开发月薪 15k，1 个月开发即 15k，加上运维很难控制在 2w 内）。因此，**SaaS 或轻量级开源部署**是主要候选路径。
4.  **Outlook 集成暗示**: 既然需要 Outlook，团队可能部分使用 Microsoft 365 生态，或者混合云环境。

### C. 仍需研究的条件 (Unknowns / Gaps) -> **写入空缺清单**

| 编号 | 空缺条件描述 | 阻塞影响 | 优先级 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **GAP-01** | **具体 SaaS 候选产品的当前定价** | 无法生成准确成本表 | 高 | 价格随促销、汇率、地区变化。需查询 Microsoft Bookings, Zoom, 飞书/钉钉会议室模块, 专业工具如 RoomGuru, Calendly 等最新报价。 |
| **GAP-02** | **各候选产品对 "Google + Outlook" 双日历同时集成的实际支持度** | 选型可行性判断 | 高 | 许多 SaaS 只支持单一生态。需确认是否支持 CalDAV 通用协议，或分别对接两个 OAuth。 |
| **GAP-03** | **各候选产品的 "门禁联动" API 开放程度** | 可选功能可行性 | 中 | 多数通用预约系统无此功能。需调研是否有 Webhook 或第三方中间件（如 IFTTT/Zapier）可桥接。 |
| **GAP-04** | **自研/开源自托管方案的真实 TCO** | 对比决策依据 | 高 | 需估算：云服务器最低配置成本 + 开发工时折算。若无人力预算，此项直接排除。 |
| **GAP-05** | **Microsoft 365 许可证现状** | 成本优化机会 | 中 | 若团队已有 M365 E3/E5，Bookings 可能免费包含在内，大幅降低预算压力。需确认 IT 部门现状。 |
| **GAP-06** | **门禁硬件品牌及接口标准** | 联动方案设计 | 低 | 若决定做联动，需知道现有门禁是什么牌子，是否有 TCP/IP 接口或 MQTT 支持。 |
| **GAP-07** | **公司对数据驻留的具体合规要求** | 选型否决项 | 中 | 若数据不能出中国大陆，则排除纯海外 SaaS（如 Zoom, Calendly），需选国内服务或私有化。 |

## 4. 候选对象初步筛选（待验证假设）

> **注意**：以下仅为基于常识的**候选类别**，具体型号、价格、功能均**未验证**，将在阶段 02 中核验。

### 类别 A: 国际主流 SaaS (待验证价格与合规性)
1.  **Microsoft Bookings**: 
    *   *假设*: 若团队有 M365 账号，可能免费或低成本。支持 Outlook 原生，Google 集成较弱（通常需 Zapier 或手动导入导出）。
    *   *待验证*: 是否包含在现有 License 中？Google Calendar 同步是否原生支持？
2.  **Zoom Rooms / Zoom Scheduler**:
    *   *假设*: 强大集成，但价格昂贵，可能超出 2w 预算。
    *   *待验证*: 30 人团队的最小订阅包价格。
3.  **Calendly (Pro/Business)**:
    *   *假设*: 用户体验好，支持 Web/Mobile。
    *   *待验证*: 是否支持会议室资源管理（Room Booking）？还是仅限人员预约？价格是否超标？

### 类别 B: 国内协同办公平台内置模块 (待验证功能完整性)
1.  **飞书 (Lark) 会议室预订**:
    *   *假设*: 若团队用飞书，功能完整，含门禁联动（飞书智能空间）。
    *   *待验证*: 是否支持外部 Google/Outlook 日历同步？通常封闭生态，**高风险点**。
2.  **钉钉 (DingTalk) 会议室**:
    *   *假设*: 类似飞书，生态封闭。
    *   *待验证*: 同上，跨生态日历同步极难实现。
3.  **企业微信**:
    *   *假设*: 同上。

### 类别 C: 专业会议室管理系统 (Niche SaaS)
1.  **RoomGuru / OfficeTime / Planview Space**:
    *   *假设*: 专为空间管理设计，功能强大，但通常按座位/房间收费，对小团队可能不友好或过于复杂。
    *   *待验证*: 最小起购门槛、是否支持 Web 端免费访问、API 开放性。

### 类别 D: 开源/自研轻量方案
1.  **OpenProject / Odoo (Community Edition)**:
    *   *假设*: 功能丰富，但配置复杂，需自行部署和维护。
    *   *待验证*: 会议室模块的易用性、日历同步插件的稳定性、自托管服务器成本。
2.  **GitHub 上的轻量级 Room Booking 项目** (如 `room-reservation-system` 类项目):
    *   *假设*: 代码量少，易于修改。
    *   *待验证*: 安全性、维护状态、是否有人接手维护。

## 5. 阶段 02 研究入口与行动路径

为了填补上述 GAP，阶段 02 应按以下顺序执行研究：

### 第一批行动（高优先级，决定选型方向）

1.  **核验 GAP-05 (M365 现状)**:
    *   *动作*: 询问 IT 管理员或检查邮箱域名后缀，确认是否已购买 Microsoft 365 Business Standard/Premium 或 Enterprise 套餐。
    *   *来源*: 内部 IT 资产台账、IT 经理访谈。
    *   *失败备用*: 若无 M365，则 Microsoft Bookings 需单独购买，成本上升。

2.  **核验 GAP-02 & GAP-01 (SaaS 功能与价格)**:
    *   *目标网站*: 
        *   Microsoft.com (Bookings 定价页)
        *   Calendly.com (Pricing)
        *   Zoom.us (Pricing)
        *   Feishu.cn / DingTalk.com (企业版定价)
    *   *搜索词*: 
        *   "Microsoft Bookings pricing per user 2024"
        *   "Calendly room booking feature availability"
        *   "飞书 会议室预订 外部日历同步"
    *   *字段*: 年费总额、是否支持 Resource Booking、是否支持 CalDAV/OAuth 双日历。
    *   *交叉询问*: 使用 `ralph prompt-first web-llm` 询问："Which meeting room booking SaaS supports both Google Calendar and Outlook two-way sync natively without third-party middleware?"

3.  **核验 GAP-07 (合规性)**:
    *   *动作*: 查阅公司信息安全政策，确认员工日程数据是否允许存储在境外服务器。
    *   *来源*: 公司合规手册、法务咨询。
    *   *影响*: 若不允许，直接排除 Zoom, Calendly, Microsoft (若数据中心在海外)。

### 第二批行动（中优先级，细化方案）

4.  **核验 GAP-03 (门禁联动)**:
    *   *动作*: 调研选定候选 SaaS 是否提供 Public API 文档。
    *   *搜索词*: "[Product Name] developer API documentation webhook"
    *   *备选*: 若 SaaS 无 API，调研 Zapier/IFTTT 是否有该产品的 Trigger 模板。

5.  **核验 GAP-04 (自研 TCO)**:
    *   *动作*: 估算 AWS Lightsail / 阿里云 ECS 最低配置（2核4G）年费。
    *   *计算*: 服务器年费 + (预计开发工时 × 人均时薪)。若结果 > ¥20,000，则标记自研方案为“不可行”。

### 第三批行动（低优先级，风险补充）

6.  **核验 GAP-06 (门禁硬件)**:
    *   *动作*: 查看机房门禁面板标签，确定品牌型号。
    *   *搜索词*: "[Brand Model] SDK integration guide"

## 7. 阶段 01 判定与 Reviewer 指引

*   **分解完整性**: 已覆盖核心引擎、前端、日历、门禁、成本、合规六大因素。
*   **空缺明确性**: 所有未验证的价格、功能支持度、合规政策均已列入 GAP 列表，未伪装成事实。
*   **行动可行性**: 阶段 02 可直接根据 GAP-01 至 GAP-07 开始搜集资料。
