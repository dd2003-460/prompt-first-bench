# 会议室预约系统选型最终报告

**项目名称**：30人研发团队会议室预约系统选型
**报告日期**：2024年5月
**预算约束**：≤ 20,000 CNY / 年
**核心需求**：macOS/Windows/Web 三端支持、Google Calendar + Outlook 双向集成、门禁联动（可选）

---

## 1. 推荐方案（单一最佳选择）

### **推荐产品：RoomGuru (或同类轻量级 SaaS，如 OfficeRnD 基础版)**

*注：鉴于国内直接可用的“原生支持双日历+三端+低门槛”的独立会议室软件较少，通常采用 **OfficeRnD** (开源/商业混合) 或 **RoomGuru** (纯SaaS) 作为此类场景的标准解。此处以 **RoomGuru** 为例进行具体化推荐，因其部署极简且完全符合预算。若团队偏好数据私有化，则推荐 **OfficeRnD Cloud** 托管版。*

#### **核心理由：**
1.  **成本极度可控**：RoomGuru 提供按房间计费而非按人头计费的模式，对于30人团队通常只需覆盖3-5间会议室，年费远低于2万元上限。
2.  **全平台无缝体验**：原生支持 Web、iOS/Android App，并完美适配 macOS/Windows 桌面环境（通过 Web 应用安装或 PWA）。无需强制安装笨重的客户端。
3.  **日历集成成熟稳定**：官方文档明确支持 Google Calendar 和 Microsoft Outlook (Exchange/Office 365) 的双向同步，解决“会议冲突”痛点，这是研发团队协作的核心。
4.  **零运维负担**：SaaS 模式免去了服务器维护、安全补丁更新等隐性人力成本，IT 部门仅需配置初始账户即可。

---

## 2. 备选方案

### **备选方案 A：OfficeRnD (自托管 Docker 部署)**

| 维度 | 对比优势 | 对比劣势 |
| :--- | :--- | :--- |
| **数据主权** | **绝对私有**：数据完全存储在内部服务器，满足严格的数据驻留合规要求（若公司禁止使用海外 SaaS）。 | **运维复杂**：需自行维护 Docker 容器、数据库备份及 HTTPS 证书更新，占用 IT 约 5-10% 工时。 |
| **功能扩展** | **高度可定制**：开源代码允许开发自定义插件，未来若需深度对接门禁硬件（API），灵活性远高于封闭 SaaS。 | **实施周期长**：从部署到调试日历同步可能需要 1-2 周时间，不如 SaaS 开箱即用。 |
| **成本结构** | **无订阅费**：软件本身免费（社区版），仅需支付服务器资源费（约 500-1000 CNY/年）。 | **隐性成本高**：若发生严重 Bug 或版本升级兼容性问题，缺乏 SLA 保障，风险由团队自担。 |

### **备选方案 B：Microsoft Teams Rooms (MTR) + 现有 Office 365 许可**

| 维度 | 对比优势 | 对比劣势 |
| :--- | :--- | :--- |
| **生态整合** | **极致融合**：如果团队已重度使用 Teams，预约界面直接嵌入 Teams 侧边栏，无需切换上下文。 | **依赖硬件**：通常需要购买 MTR 认证平板/显示器作为前台显示终端，硬件一次性投入可能超过预算。 |
| **管理效率** | **统一入口**：IT 管理员可通过 Azure AD 统一管理用户权限，无需单独维护一套账号体系。 | **功能局限**：对非 Microsoft 生态（如 Google Calendar 用户）的支持较弱，双向同步常存在延迟或单向限制。 |

## 3. 淘汰理由

以下候选产品在评估中被明确排除，依据如下：

1.  **Zoom Rooms / Cisco Webex Rooms**
    *   **排除依据**：**超预算且功能冗余**。这两款产品主要服务于视频会议终端，其会议室预约模块通常捆绑在昂贵的企业级视频许可证中。30人团队仅用于“物理空间预约”，无需支付高昂的视频带宽和处理费用。估算成本远超 2万/年。
2.  **自建通用 OA 系统模块 (如基于 Jira/Confluence 二次开发)**
    *   **排除依据**：**ROI 极低**。利用现有工具开发会议室模块需要消耗后端开发人员至少 2-4 人周的时间成本。按研发人员时薪计算，开发成本远超 2万元预算。且后续维护日历同步逻辑的技术债务极高。
3.  **传统本地客户端软件 (如早期版本的某些国产会议室软件)**
    *   **排除依据**：**多端支持差**。多数老旧软件仅支持 Windows 客户端，macOS 支持不佳或仅为网页套壳，无法实现任务要求的“三端一致体验”。且大多不支持现代 OAuth2.0 标准的 Google/Outlook 双向实时同步。

## 5. 风险与缓解措施

| 风险类别 | 风险描述 | 可能性 | 影响程度 | 缓解措施 |
| :--- | :--- | :--- | :--- | :--- |
| **技术风险** | **日历同步冲突**：Google 与 Outlook 同时操作同一时段导致数据不同步或重复预订。 | 中 | 高 | 1. 在 POC 阶段重点测试并发写入场景。<br>2. 制定团队规范：以“主日历”为准（例如规定研发人员以 Google 为主，行政以 Outlook 为主，系统设置优先级策略）。<br>3. 启用系统的“冲突检测”告警功能。 |
| **合规风险** | **数据出境**：SaaS 服务商服务器位于海外，可能不符合部分国企/外企的数据驻留要求。 | 低 | 中 | 1. 审查服务商 DPA (数据处理协议)，确认是否提供 EU/US 数据隔离选项。<br>2. 若合规红线不可突破，立即切换至 **备选方案 A (OfficeRnD 自托管)**，确保数据留在境内服务器。 |
| **运营风险** | **僵尸会议室**：用户忘记释放会议室，导致资源浪费。 | 高 | 低 | 1. 开启“自动释放”功能：会议结束后 15 分钟无人签到自动释放。<br>2. 引入“信用分”机制（若系统支持）或行政定期通报未按时释放的用户。 |
| **扩展风险** | **门禁联动失败**：未来接入门禁硬件时 API 不稳定。 | 中 | 低 | 1. 当前阶段不强行绑定门禁，保持预约系统独立性。<br>2. 预留 API Key 接口，待门禁供应商确定后，通过中间件 (Webhook) 异步调用，避免强耦合。 |

### **最终结论与建议行动**

1.  **决策**：批准采购 **RoomGuru** (或同等价位的轻量级 SaaS) 作为首选方案。
2.  **下一步行动 (Next Steps)**：
    *   **Week 1**：注册试用账号，邀请 5 名代表（含 Mac/Win 用户）进行为期一周的内部 Beta 测试，重点验证日历同步稳定性。
    *   **Week 2**：根据测试结果微调房间配置，正式开通付费订阅，并完成全员推广培训。
    *   **Contingency**：若测试中发现日历同步存在阻断性 Bug，立即启动备选方案 A (OfficeRnD) 的 Docker 环境搭建工作。
