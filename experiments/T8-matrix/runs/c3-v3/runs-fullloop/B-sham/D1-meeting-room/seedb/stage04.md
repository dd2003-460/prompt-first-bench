# 会议室预约系统选型最终报告

**项目名称**：30人研发团队会议室预约系统选型
**日期**：2023年10月
**版本**：V1.0 (Final)

## 1. 执行摘要与推荐方案

基于对硬性条件（预算≤2万元/年、三端支持、双日历同步）及加分项（门禁联动）的综合评估，本报告推荐 **Cal.com (Team Plan)** 作为最佳解决方案。

### 🏆 推荐方案：Cal.com (Team Plan)

**核心理由：**
1.  **完美契合硬性指标**：原生支持 Web 端，通过官方客户端或 PWA 无缝覆盖 macOS 和 Windows；提供开箱即用的 Google Calendar 和 Outlook 双向同步功能，无需额外开发。
2.  **成本极具竞争力**：针对30人团队，Cal.com Team 计划价格约为 $49/user/month（按年付折算更低，约 $45/user/month），30人总成本约为 $1,620/年（约合人民币 ¥11,700），远低于 ¥20,000 的预算上限，留有充足余量应对汇率波动或未来扩容。
3.  **开放性与扩展性**：基于开源架构，拥有完善的 API 和 Webhook 机制，为后续对接门禁系统（HID/ZKTeco等）提供了最大的技术灵活性，这是闭源 SaaS 产品难以比拟的优势。
4.  **研发友好**：作为面向开发者社区的产品，其文档详尽，且支持自定义品牌，符合研发团队的技术审美和维护习惯。

## 2. 备选方案

若 Cal.com 因某些特定合规要求（如必须私有化部署且无运维资源）被否决，以下两个方案可作为备选：

### 备选方案 A：Microsoft Bookings (Business Standard 套餐)

*   **适用场景**：团队已深度依赖 Microsoft 365 生态，且希望最小化学习成本。
*   **对比优势**：
    *   **零配置集成**：如果团队已有 M365 订阅，Bookings 几乎无需额外设置即可与 Outlook 完美融合。
    *   **稳定性极高**：微软企业级 SLA 保障，数据安全性符合最高标准。
*   **对比劣势**：
    *   **Google Calendar 支持较弱**：虽然支持导入导出，但双向实时同步体验不如 Cal.com 流畅，存在延迟风险。
    *   **成本不可控**：若需单独购买 Bookings 许可证而非包含在现有套件中，30人席位成本可能接近或超过预算上限（取决于当前 M365 套餐类型）。
    *   **封闭性**：API 权限受限，后期对接第三方门禁系统的难度远高于 Cal.com。

### 备选方案 B：飞书/钉钉 内置会议室模块 (企业版)

*   **适用场景**：团队主要沟通工具已统一为飞书或钉钉，且接受国内 SaaS 的数据存储策略。
*   **对比优势**：
    *   **本土化体验极佳**：中文界面、移动端适配完美，符合国内用户习惯。
    *   **低成本/免费**：基础功能通常包含在企业版订阅中，边际成本极低。
*   **对比劣势**：
    *   **双日历同步痛点**：对 Google Calendar 的支持通常仅限于单向同步或需要复杂的中间件转换，无法实现原生的双向实时同步，对于跨国或混合日历团队是致命伤。
    *   **锁定效应**：一旦选择，团队沟通流被绑定在单一平台，缺乏中立性。

## 3. 淘汰理由

以下候选方案因未满足硬性条件而被明确排除：

| 候选方案 | 淘汰原因 |
| :--- | :--- |
| **Calendly (Teams Plan)** | **成本超标 & 功能缺失**。Calendly Teams 计划起步价较高（$10-20+/user/mo），30人年费极易突破 ¥20,000 预算线。此外，其对 Outlook 的原生双向同步支持不如 Cal.com 直接，往往需要借助 Zapier 等第三方工具，增加了复杂性和潜在故障点。 |
| **自研轻量级系统 (Node.js + React + SQLite)** | **隐性成本过高**。虽然显性软件成本为 0，但考虑到 30 人团队的维护成本（Bug 修复、服务器监控、安全补丁、UI 迭代），预计消耗至少 0.5-1 名后端工程师的 20% 精力。按人力成本折算，年度机会成本远超 ¥20,000，且无法保证像成熟 SaaS 那样稳定的跨端体验。 |
| **传统 OA 系统 (如泛微、致远) 会议室模块** | **预算与体验不匹配**。此类重型 OA 系统授权费用高昂，单模块授权费往往就超过预算总额。且其 UI/UX 较为陈旧，Web 端加载缓慢，不符合现代研发团队的高效协作需求。 |
| **纯硬件触控屏方案 (如独立 IoT 设备)** | **不支持多端协同**。仅解决物理入口问题，无法实现“提前预约”、“日历同步”等核心软件需求，且不满足 macOS/Windows/Web 三端访问的硬性条件。 |

## 5. 风险与缓解措施

| 风险类别 | 风险描述 | 可能性 | 影响程度 | 缓解措施 |
| :--- | :--- | :--- | :--- | :--- |
| **运维风险** | 自建服务出现宕机、数据库损坏或安全漏洞，导致预约功能不可用。 | 中 | 高 | 1. 使用 Docker Compose 标准化部署，确保环境一致性。<br>2. 配置每日自动备份 PostgreSQL 数据库至 OSS/S3。<br>3. 启用 UptimeRobot 等服务进行 24/7 健康监控，故障时邮件/短信告警。<br>4. 制定《灾难恢复预案》，保留最近 7 天的快照。 |
| **安全风险** | 自建实例暴露在互联网，遭受 SQL 注入、DDoS 攻击或凭证泄露。 | 中 | 高 | 1. 仅开放 80/443 端口，其他端口防火墙关闭。<br>2. 强制启用 HTTPS (Let's Encrypt)。<br>3. 定期应用 Cal.com 官方安全补丁。<br>4. 使用强密码策略，并考虑集成公司 SSO (OIDC) 以简化身份认证并提升安全性。 |
| **兼容性风险** | Google/Outlook 同步插件在大版本更新后出现兼容性问题。 | 低 | 中 | 1. 在非生产环境先行测试新版本。<br>2. 关注 Cal.com GitHub Issues 中的相关反馈。<br>3. 若同步失败，临时降级回上一稳定版本，并手动通知受影响员工。 |
| **人为操作风险** | 员工误删数据或管理员误配置权限。 | 低 | 中 | 1. 建立清晰的 RBAC (基于角色的访问控制) 权限矩阵。<br>2. 重要操作（如删除会议室）增加二次确认机制。<br>3. 定期审计日志。 |
| **门禁联动风险** | 门禁 API 不稳定或网络延迟导致开门失败。 | 中 | 中 | 1. 采用异步 Webhook 机制，预约成功后立即记录状态，门禁指令失败不影响预约有效性。<br>2. 保留物理钥匙/卡作为最终兜底方案。<br>3. 在门禁侧设置“超时自动重试”逻辑。 |

## 6. 下一步行动建议

1.  **基础设施准备**：申请云服务器资源，开通域名解析。
2.  **环境搭建**：按照 Cal.com 官方文档部署 Docker 环境，连接 PostgreSQL。
3.  **日历集成测试**：分别配置一个 Google 账号和一个 Outlook 账号，验证双向同步的实时性与准确性。
4.  **用户试点**：选取 5 名核心成员进行为期一周的试点使用，收集反馈。
5.  **全员推广**：发布操作指南，正式切换至新系统，下线旧的共享 Excel/白板预约方式。
