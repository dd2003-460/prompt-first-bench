# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**最终交付物**：一份可执行的《30人研发团队文件协作/网盘选型报告》。
**核心内容要求**：
1. **推荐方案**：明确指定一个主要推荐产品。
2. **备选方案**：提供至少1-2个次优选项。
3. **淘汰理由**：解释为何其他潜在候选未入选（需基于约束）。
4. **成本明细**：详细列出推荐及备选方案的年度费用构成，证明符合预算。

## 2. 影响因素正交分解
为了覆盖“选型”这一复杂决策，我们将影响因素分解为以下四个正交维度（互不重叠，合起来完整覆盖选型逻辑）：

### 因素 A：硬性合规性（Hard Constraints）
*边界*：如果不满足其中任何一项，该候选直接淘汰，无需考虑其他因素。
*子因素*：
1.  **平台兼容性**：必须同时支持 Web、macOS、Windows 客户端。
2.  **功能完备性**：
    *   A2a: 文档版本管理（Version Control）能力。
    *   A2b: 细粒度权限控制（Granular Permission Control）能力。
3.  **预算上限**：30人团队年度总花费 ≤ 30,000 CNY。

### 因素 B：体验与效能增强（Soft Constraints / Bonuses）
*边界*：影响评分权重，但不直接导致淘汰（除非有严重缺陷抵消加分）。
*子因素*：
1.  **离线可用性**：是否支持离线编辑/同步（加分项）。
2.  **协作效率特性**：实时协同编辑、评论、任务集成等（虽非显式约束，但属于“团队协作”隐含需求，需作为次要评估点）。

### 因素 C：部署与运维模式（Deployment & Ops）
*边界*：决定成本结构和技术门槛，直接影响A中的预算和B中的体验。
*子因素*：
1.  **部署形态**：SaaS（公有云） vs Self-hosted（私有化/混合云）。
2.  **数据主权与安全**：数据存储位置、加密标准、合规认证（ISO/SOC2等），这对研发代码/文档安全至关重要。

### 因素 D：生态与集成（Ecosystem & Integration）
*边界*：影响长期使用成本和迁移难度。
*子因素*：
1.  **API/插件生态**：是否与现有研发工具链（Git, Jira, Slack/Teams等）集成。
2.  **迁移成本**：从现有工具迁移的数据格式兼容性。

## 3. 条件状态分类（已知 vs 推导 vs 空缺）

### 3.1 人类已提供的确定条件 (Known)
| 条件 | 值 | 来源 |
| :--- | :--- | :--- |
| 团队规模 | 30 人 | 用户输入 |
| 年度预算上限 | 30,000 CNY | 用户输入 |

| 核心功能2 | 细粒度权限控制 | 用户输入 |
| 加分项 | 离线使用 | 用户输入 |

### 3.2 从项目背景推导的条件 (Derived)
*(注：这些是基于“30人研发团队”这一上下文的合理推断，需在阶段02中验证其合理性)*
*   **D1: 数据类型敏感度**：研发团队通常涉及代码片段、架构图、技术文档，可能包含敏感信息。**推导**：需要较高的安全性，纯免费且无SLA保障的个人版网盘可能不适用，倾向于企业级SaaS或私有化部署。
*   **D2: 并发与性能**：30人规模属于小型团队，对高并发要求不高，但对同步延迟和稳定性有要求。
*   **D3: 预算人均分摊**：30,000 CNY / 30人 = 1,000 CNY/人/年 ≈ 83 CNY/人/月。这是一个相对宽松的企业级预算（主流SaaS如Notion, Confluence, Dropbox Business等通常在50-150 CNY/人/月区间），因此**预算不是最紧的约束，功能和体验更关键**。

### 3.3 仍需研究的空缺条件 (Unknowns / Gaps)
*(这些是阶段02必须解决的关键问题)*

#### Gap 1: 具体候选对象及其属性 (Candidate Attributes)
*   **子问题 1.1**: 哪些主流产品同时满足 Web/macOS/Windows + 版本管理 + 细粒度权限？
    *   *待验证假设*: Notion, Confluence, SharePoint Online, OneDrive for Business, Google Workspace, Feishu (Lark), Tencent Docs, Nextcloud (Self-hosted), GitLab Wiki, Obsidian (Sync).
*   **子问题 1.2**: 各候选的“细粒度权限”具体指什么？
    *   *定义模糊点*: “细粒度”是指文件夹级别？页面级别？还是字段级别？研发场景通常需要页面/文件夹级别的读写/评论权限区分。需确认各产品是否支持“仅查看”、“可评论”、“可编辑”的多级控制。
*   **子问题 1.3**: 各候选的“版本管理”深度？
    *   *定义模糊点*: 是简单的历史版本恢复（History），还是类似Git的分支/合并概念？对于文档协作，通常指历史版本回溯和对比。需确认各产品版本保留时长（如90天 vs 无限期）。

#### Gap 2: 精确成本模型 (Cost Modeling)
*   **子问题 2.1**: 各候选针对30人团队的准确报价。
    *   *难点*: SaaS价格常按“席位”或“存储量”计费。需确认是否有最低起购人数（如Confluence Cloud通常有最低席位限制，虽然30人可能刚好达标或略超）。
    *   *汇率波动*: 国际产品以USD计价，需按当前汇率估算并预留波动空间。
*   **子问题 2.2**: 隐藏成本。
    *   *例如*: 存储空间超出基础包的费用、高级安全功能（SSO, Audit Log）是否额外收费、离线功能是否仅在高级版可用。

#### Gap 3: 离线功能的实际表现 (Offline Capability Verification)
*   **子问题 3.1**: 哪些候选真正支持“离线编辑”而非仅“离线查看”？
    *   *待验证*: Notion (部分支持), OneDrive (支持), SharePoint (支持), Feishu (移动端支持较好，桌面端需确认), Nextcloud (原生支持)。
    *   *冲突解决*: 离线后的多设备同步冲突处理机制如何？

#### Gap 4: 部署模式的可行性 (Deployment Feasibility)
*   **子问题 4.1**: 如果选择 Self-hosted (如 Nextcloud, Wiki.js)，运维成本是否计入3万预算？
    *   *风险*: 3万预算若包含服务器租赁+运维人力分摊，可能会非常紧张。通常3万预算暗示倾向于免运维的SaaS。需确认用户是否接受自托管带来的隐性运维负担。
*   **子问题 4.2**: SaaS产品的数据出境合规性。
    *   *背景*: 中国研发团队可能受数据本地化法规影响。需确认所选SaaS是否有中国区节点或合规声明。

## 5. 阶段 02 研究路径规划

### 5.1 第一批行动（最高优先级）

**目标**：锁定 5-8 个强候选，并获取其核心功能矩阵和初步价格线索。

**步骤 1: 网页 LLM 交叉询问 (Ralph)**
*   **命令**: `ralph prompt-first web-llm . "列出5款适合30人研发团队的文件协作工具，要求支持Web/macOS/Windows，具备文档版本历史和细粒度权限控制。请列出它们的名称、大致每人每月价格(USD/CNY)、以及是否支持离线编辑。" --context "阶段 02；只要求可复核来源线索"`
*   **预期产出**：候选名单初筛，价格区间参考。
*   **注意**：LLM回答仅作线索，不可直接作为事实来源。

**步骤 2: 官方定价页核验 (WebFetch/Search)**
*   **目标网站**:
    *   Notion: `notion.so/pricing`
    *   Atlassian Confluence: `atlassian.com/software/confluence/pricing`
    *   Microsoft 365 Business/Enterprise: `microsoft.com/en-us/microsoft-365/business/compare-all-microsoft-365-service-plans-and-pricing`
    *   Feishu/Lark: `feishu.cn/hc/` 或官方销售咨询页面 (国内产品通常需联系销售获取精确报价，需记录此障碍)
    *   Nextcloud: `nextcloud.com/paid/` (若考虑自托管)
*   **搜索词示例**: `"Confluence Cloud pricing per user 2024"`, `"Microsoft 365 Business Standard price China"`, `"Feishu enterprise edition price 30 users"`
*   **字段提取**:
    *   单价 (Per User Per Month/Year)
    *   最低购买席位 (Minimum Seats)
    *   包含的存储容量
    *   功能差异表 (Feature Comparison Table) - 重点看 "Permissions", "Version History", "Offline Access"。

**步骤 3: 功能细节深挖 (Independent Sources)**
*   **针对“细粒度权限”**:
    *   搜索词: `"[Product Name] granular permission control documentation"`, `"[Product Name] page level access rights"`
    *   来源类型: 官方帮助文档 (Help Center), 独立评测博客 (G2, Capterra reviews mentioning permissions).
*   **针对“离线使用”**:
    *   搜索词: `"[Product Name] offline mode desktop app review"`
    *   关注点: 用户评论中关于断网后能否继续编辑的描述。

### 5.2 失败备用路径
*   **若官网价格不透明 (如 Feishu, WPS 365)**:
    *   动作: 记录“需人工询价”。在报告中将其标记为“预估成本区间”，并建议用户在最终决策前进行商务询价。
    *   替代来源: 查找第三方代理商报价、知乎/掘金上用户的实际采购分享（需标注为非官方数据）。
*   **若某产品无 macOS 客户端**:
    *   动作: 立即标记为“不满足硬约束”，移出候选池，不再深入研究其价格。
*   **若汇率波动大**:
    *   动作: 在成本明细中增加 10% 的汇率缓冲系数。

### 5.3 研究终止条件
当满足以下条件时，阶段02结束：
1.  至少有 3 个候选通过了所有 P0 硬约束（平台、功能、预算初估）。
2.  每个通过候选都有至少 2 个独立来源支持其价格和核心功能描述。
3.  所有未解决的空缺（如具体的折扣政策）已明确标注为“需商务确认”，并说明了其对最终选型的潜在影响。
