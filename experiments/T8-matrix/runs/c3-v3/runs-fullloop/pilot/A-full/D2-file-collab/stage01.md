# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**最终交付物**：一份可执行的选型报告，包含以下四个核心组件：
1.  **推荐方案（Primary Recommendation）**：唯一首选方案，需满足所有硬性约束。
2.  **备选方案（Alternative Options）**：1-3个次优方案，用于风险对冲或预算微调。
3.  **淘汰理由（Elimination Rationale）**：针对主要竞品被排除的具体技术或商务原因。
4.  **成本明细（Cost Breakdown）**：基于30人规模的详细年度费用计算表。

**成功标准**：
-   总年度成本 $\le$ ¥30,000。
-   支持 Web + macOS + Windows 客户端。
-   具备文档版本管理功能。
-   具备细粒度权限控制（如文件夹级、文件级、角色级）。
-   离线可用为加分项（非阻塞性，但影响评分权重）。

## 2. 影响因素递归分解

### Level 1: 顶层正交因素
将“选择最佳团队文件协作/网盘方案”分解为以下5个互相正交的顶层因素：

1.  **功能兼容性 (Functional Compatibility)**：是否满足核心需求（版本管理、权限）及平台支持。
2.  **成本经济性 (Cost Efficiency)**：在预算内的实际支出及性价比。
3.  **安全与合规 (Security & Compliance)**：数据加密、访问审计、私有化部署选项（若适用）。
4.  **用户体验与稳定性 (UX & Reliability)**：同步速度、冲突处理、客户端稳定性、离线能力。
5.  **生态集成与维护 (Ecosystem & Maintenance)**：与现有工作流（Slack/Teams/Jira等）的集成、API开放性、厂商长期维护承诺。

### Level 2: 子因素分解与条件分类

#### 2.1 功能兼容性
*   **2.1.1 核心功能验证**
    *   **版本管理**：
        *   [已确定] 必须支持历史版本回溯。
        *   [待研究] 不同方案对Office/PDF/代码文件的版本颗粒度差异（例如：Git式diff vs 快照式备份）。
    *   **细粒度权限控制**：
        *   [已确定] 需支持至少到“文件夹”级别的读写/只读/无权限区分。
        *   [待研究] 是否支持“仅查看不可下载”、“水印保护”、“外部协作者链接有效期”等高级权限。
*   **2.1.2 平台支持**
    *   [已确定] 必须提供原生 macOS (.app) 和 Windows (.exe/.msi) 客户端。
    *   [已确定] 必须提供响应式 Web 界面。
    *   [待研究] Linux 客户端是否存在（虽非强制，但作为研发团队的潜在需求，需记录其缺失情况作为扣分项）。

#### 2.2 成本经济性
*   **2.2.1 定价模型**
    *   [已确定] 预算上限 ¥30,000/年。
    *   [待研究] 各候选方案的计价单位（按人/月、按人/年、按存储量、按功能套餐）。
    *   [待研究] 是否有免费额度或试用期。
*   **2.2.2 隐性成本**
    *   [待研究] 超出基础存储后的扩容价格。
    *   [待研究] 是否包含技术支持费（SLA等级）。
    *   [待研究] 货币兑换汇率波动风险（若为美元计价）。

#### 2.3 安全与合规
*   **2.3.1 数据安全**
    *   [待研究] 传输加密标准 (TLS 1.2+) 和静态加密标准 (AES-256)。
    *   [待研究] 是否支持端到端加密 (E2EE)（注意：E2EE通常牺牲服务器端搜索和部分管理功能，需权衡）。
*   **2.3.2 访问控制与审计**
    *   [待研究] 是否支持 SSO (SAML/OIDC) 集成。
    *   [待研究] 操作日志审计功能的保留时长和导出能力。

#### 2.4 用户体验与稳定性
*   **2.4.1 同步性能**
    *   [待研究] 大文件上传/下载速度限制。
    *   [待研究] 增量同步机制（Delta sync）的实现方式。
*   **2.4.2 离线能力（加分项）**
    *   [待研究] 离线编辑时的冲突解决策略（Last-write-wins vs 合并提示）。
    *   [待研究] 离线状态下哪些功能不可用（如分享链接生成）。

#### 2.5 生态集成与维护
*   **2.5.1 第三方集成**
    *   [待研究] 与主流研发工具（Jira, GitLab, Slack, Teams）的原生集成程度。
*   **2.5.2 厂商稳定性**
    *   [待研究] 厂商融资状况、用户基数、近期重大安全事故记录。

## 3. 已知条件 vs 推导条件 vs 空缺条件

### 3.1 人类已提供的条件 (Given)
| 条件 | 值 | 备注 |
| :--- | :--- | :--- |
| 团队规模 | 30 人 | 固定人数，无显著增长预期假设 |
| 总预算 | ≤ ¥30,000 / 年 | 硬性约束 |
| 必需平台 | Web, macOS, Windows | 硬性约束 |
| 核心功能 1 | 文档版本管理 | 硬性约束 |
| 核心功能 2 | 细粒度权限控制 | 硬性约束 |
| 加分功能 | 离线可用 | 软性约束，用于排序 |

### 3.2 从项目推导的条件 (Derived)
| 条件 | 推导逻辑 | 状态 |
| :--- | :--- | :--- |
| 人均预算 | ¥30,000 / 30 = ¥1,000 / 人 / 年 | 用于快速筛选超支方案 |
| 月度人均预算 | ¥1,000 / 12 ≈ ¥83.3 / 人 / 月 | 用于对比国际大厂SaaS定价 |
| 存储容量估算 | 未知。研发团队通常涉及代码仓库（通常由Git托管）、设计稿、二进制包。假设平均每人每月产生 5GB 新数据，年增长 180GB。初始存量假设 500GB。总计需 ~700GB-1TB 起步。 | **待验证假设**：此容量估算仅为筛选参考，不作为硬性排除依据，除非方案单价极高导致容量不足。 |

### 3.3 仍需研究的条件 (Unknowns/Gaps) - **关键空缺清单**

> **注意**：以下所有条目均为 **[待研究]**，不得在后续阶段直接当作事实引用，除非经过阶段 02 核验。

#### G1: 候选对象集合冻结 (Candidate Set Freeze)
*   **问题**：当前市场上符合“Web+Mac+Win+版本+权限”的主流商业方案有哪些？
*   **初步候选类别（待验证属性）**：
    1.  **国际通用型 SaaS**: Dropbox Business, OneDrive for Business (Microsoft 365), Box, Egnyte.
    2.  **国内头部网盘/协作**: 阿里云盘企业版, 百度网盘企业版, 腾讯微云企业版, 坚果云 (Jianguoyun).
    3.  **专业协作/知识管理衍生**: Notion (侧重文档，弱文件存储), Confluence (需配合附件插件，可能不符合“网盘”定义，暂列为边缘候选).
    4.  **自托管开源方案**: Nextcloud, Seafile, OwnCloud. (注：虽然省钱，但需考虑运维人力成本是否计入“预算”，通常纯软件许可为0，但运维人力难以量化，需单独评估)。
*   **空缺动作**：阶段 02 需确认上述每个候选在当前时间点（2024-2025）是否仍活跃销售，以及是否完全覆盖硬性约束。

#### G2: 具体功能深度验证 (Feature Depth)
*   **G2.1 版本管理细节**：
    *   [待研究] 各候选是否提供“版本恢复”的一键操作？
    *   [待研究] 版本保留策略：是永久保留、保留N天、还是受存储空间限制自动清理？
    *   [待研究] 是否支持多人同时编辑同一文档的版本合并（Merge），还是仅支持最后保存者覆盖？
*   **G2.2 权限控制粒度**：
    *   [待研究] “细粒度”的定义边界：是否支持基于标签（Tag）的权限？是否支持继承权打破（Break Inheritance）？
    *   [待研究] 对外分享链接的安全控制：密码保护、有效期、IP白名单、禁止下载/打印。

#### G3: 精确成本结构 (Precise Cost Structure)
*   **G3.1 官方报价单获取**：
    *   [待研究] 30人规模的准确报价。许多SaaS对<50人用户提供特定小团队套餐，或对>50人提供折扣，需获取30人档位的精确价格。
    *   [待研究] 合同期限要求：是否强制年付？是否有月付选项（灵活性 vs 成本）？
    *   [待研究] 税费处理：国内厂商是否含税？国外厂商是否含VAT/GST？人民币结算渠道是什么？
*   **G3.2 存储成本敏感性分析**：
    *   [待研究] 基础套餐包含多少存储？（如：OneDrive 通常每人5GB，Dropbox 每人2TB，Box 每人100GB）。
    *   [待研究] 若存储不足，扩容单价是多少？

#### G4: 离线可用性与同步引擎 (Offline & Sync Engine)
*   **G4.1 离线功能范围**：
    *   [待研究] 离线时能否创建新文件？
    *   [待研究] 离线修改后重新上线的冲突检测灵敏度。
    *   [待研究] 移动端（iOS/Android）是否也支持离线（虽非硬性要求，但研发团队常移动办公，可作为加分项参考）。

#### G5: 部署模式与数据主权 (Deployment & Data Sovereignty)
*   **G5.1 数据存储位置**：
    *   [待研究] 数据存储在哪个数据中心？（中国大陆境内 vs 境外）。对于某些研发项目，数据出境合规可能是隐性硬约束，需确认团队是否有此顾虑。
*   **G5.2 私有化部署可行性**：
    *   [待研究] 若选择自托管（Nextcloud/Seafile），硬件成本估算（服务器+备份）是否超过¥30,000/年？运维人力成本如何折算？

## 4. 阻塞影响分析 (Blocking Impact)

| 空缺编号 | 描述 | 阻塞的后续判断 | 优先级 |
| :--- | :--- | :--- | :--- |
| **G1** | 候选集未最终确认 | 无法开始具体的功能对比和询价。若遗漏了某个新兴高性价比方案（如某国产新势力），会导致推荐偏差。 | **P0** |
| **G3** | 精确成本未知 | 无法判定是否超预算。若某方案看似便宜但存储极小，扩容后可能爆预算。 | **P0** |
| **G2** | 功能深度不明 | 无法判定是否满足“核心需求”。例如，若某方案只有快照没有版本Diff，可能不满足研发对文档变更追踪的需求。 | **P0** |
| **G4** | 离线能力不明 | 影响最终排名。若两个方案成本和功能相近，离线能力好的胜出。 | **P1** |
| **G5** | 数据主权/部署模式 | 若团队有严格的数据不出境要求，则直接淘汰所有纯海外SaaS。此为潜在一票否决项。 | **P1** |

## 5. 阶段 02 研究路径 (Research Path for Stage 02)

为了高效填充上述空缺，阶段 02 应按以下顺序执行研究任务：

### 批次 1：候选集筛选与硬性约束过滤 (Filtering)
*   **目标**：从 G1 初步候选中剔除明显不符合硬性约束的方案。
*   **动作**：
    1.  访问各官网，检查“Platform Support”页面，确认是否有 Mac/Win/Web 客户端。
    2.  检查“Pricing”页面，查找 30 人左右的入门档位，若最低档 > ¥30,000/年，标记为“疑似超预算”，进入深入核算；若明显低于，标记为“候选”。
    3.  检查“Features”页面，关键词搜索 "Version History", "Permissions", "Granular Access"。
*   **来源类型**：官方网站 (Official Websites)、G2/Capterra 等评测平台的概览页。
*   **失败备用路径**：若官网信息模糊，查阅最近一年的 TechCrunch/InfoQ 报道或知乎/Reddit 上的用户讨论帖。

### 批次 2：深度功能验证与成本精算 (Deep Dive & Costing)
*   **目标**：填充 G2 和 G3。
*   **动作**：
    1.  **注册试用账号**：对通过批次 1 筛选的前 3-5 名候选，注册团队试用版（如有）或使用个人版模拟团队场景。
    2.  **功能测试脚本**：
        *   创建文件夹 A -> 设置权限（用户B只读，用户C无权限）-> 验证生效。
        *   修改文档 D -> 保存 -> 再次修改 -> 验证版本列表是否显示 V1, V2 -> 尝试恢复 V1。
        *   断开网络 -> 修改本地文件 -> 重连 -> 观察冲突提示。
    3.  **获取报价单**：联系销售（Sales）获取 30 人正式报价单，询问存储包含量及扩容价格。
*   **来源类型**：产品试用环境、销售邮件/电话沟通记录、官方帮助文档 (Help Center/Knowledge Base)。
*   **失败备用路径**：若无法获得试用，查阅官方 API 文档以推断权限粒度的底层实现；查阅第三方审计报告（如 SOC2 Type II 报告摘要）以推断安全性。

### 批次 3：非功能性评估与决策矩阵构建 (Evaluation Matrix)
*   **目标**：填充 G4, G5，并生成最终排序。
*   **动作**：
    1.  收集用户反馈：在 Reddit (r/sysadmin, r/productivity), V2EX, 知乎 搜索 “[方案名] review", "[方案名] migration pain".
    2.  构建加权评分卡：
        *   成本 (30%)
        *   核心功能符合度 (30%)
        *   离线/同步体验 (15%)
        *   安全/合规 (15%)
        *   生态/集成 (10%)
    3.  计算总分，识别 Top 1 和 Top 2。
*   **来源类型**：社区论坛、社交媒体、行业分析报告。
*   **失败备用路径**：若缺乏最新口碑，参考该厂商过去两年的重大事故新闻或裁员新闻作为稳定性负面指标。

## 6. 自检与完整性声明

*   **因素正交性检查**：功能、成本、安全、体验、生态五个维度互不重叠，覆盖了“选型”的所有关键考量。
*   **覆盖目标检查**：
    *   30人规模 -> 体现在 G3 成本计算中。
    *   预算 <= 30k -> 体现在 G3 和 G1 筛选中。
    *   Web/Mac/Win -> 体现在 G1 和 G2.1 中。
    *   版本/权限 -> 体现在 G2.1, G2.2 中。
    *   离线加分 -> 体现在 G4 中。
    *   交付物格式 -> 已在第 1 节定义。
*   **已知/未知区分**：所有具体价格、版本号、功能细节均标记为 [待研究]，未伪装成事实。
*   **阶段 02 可操作性**：提供了具体的搜索词、网站类型、测试步骤和评分权重，阶段 02 可直接执行。

**结论**：本阶段分解已完成，所有叶子节点均为原子化研究任务，无进一步分解必要。可以进入阶段 02。
