# 阶段 01：目标分解、已知与空缺条件

## 1. 目标定义
**交付物**：一份针对 30 人研发团队的会议室预约系统选型报告。
**核心内容**：
1.  **推荐方案**（单一最佳选择，含理由）。
2.  **备选方案**（至少 1-2 个，含对比优势/劣势）。
3.  **淘汰理由**（对未入选主流候选的明确排除依据）。
4.  **成本明细**（年度总成本拆解，验证是否 ≤ 2 万元/年）。

## 2. 顶层影响因素分解（正交覆盖）

为了达成上述交付物，需分解为以下四个互相正交且合起来完整覆盖目标的影响因素：

*   **F1: 功能合规性 (Functional Compliance)**
    *   决定系统是否满足硬性需求（Must-have）。若不满足，直接淘汰。
*   **F2: 技术集成与兼容性 (Technical Integration & Compatibility)**
    *   决定系统与现有 IT 环境（日历、门禁、客户端）的融合度及实施难度。
*   **F3: 经济性与预算约束 (Economics & Budget Constraint)**
    *   决定方案是否在预算范围内，以及长期持有成本（TCO）的可预测性。
*   **F4: 运维与用户体验 (Operations & User Experience)**
    *   影响团队采纳率、IT 维护负担及日常使用流畅度。

---

## 3. 递归分解与条件分析

### F1: 功能合规性

#### 子因素 F1.1: 多端支持 (Multi-platform Support)
*   **定义**：必须同时支持 macOS, Windows, Web。
*   **已知条件**：用户明确要求三端支持。
*   **可推导条件**：Web 端通常是 SaaS 系统的标配；macOS/Windows 通常通过桌面客户端或 PWA 实现。
*   **待研究/空缺**：
    *   [待研究] 各候选系统的 macOS/Windows 客户端是否为原生应用？还是仅依赖浏览器插件/PWA？
    *   [待研究] 移动端（iOS/Android）虽非硬性要求，但作为“Web”的延伸，其可用性如何？（注：任务未强制要求手机 App，但 Web 在手机上访问体验是 UX 的一部分，归入 F4 考量，此处仅确认 PC/Web 端存在性）。
*   **阻塞影响**：若无原生或稳定 Web 端，无法部署。

#### 子因素 F1.2: 日历双向同步 (Calendar Two-way Sync)
*   **定义**：与 Google Calendar (GC) 和 Microsoft Outlook (M365) 进行**双向**集成。
*   **已知条件**：必须支持 GC + Outlook。
*   **可推导条件**：“双向”意味着在会议室系统中预订后，日历显示忙碌；在日历中创建会议时，能自动关联会议室资源。
*   **待研究/空缺**：
    *   [待研究] 候选系统对 GC 和 Outlook 的支持深度：是仅单向推送忙闲状态，还是支持资源对象（Resource Object）的双向同步？
    *   [待研究] 是否存在混合环境限制？例如：某些系统仅支持 M365 深度集成，GC 仅为基础 iCal 订阅（单向）。
    *   [待研究] 30 人规模下，混合使用 GC 和 Outlook 的用户比例是多少？（这决定了集成的关键路径优先级）。
*   **阻塞影响**：若仅支持单向或仅支持其中一种日历，将导致严重的工作流断裂，可能直接淘汰该方案。

#### 子因素 F1.3: 门禁联动可选性 (Access Control Integration - Optional)
*   **定义**：系统需具备对接门禁硬件的能力，作为可选模块。
*   **已知条件**：这是“可选”功能，不是 Must-have。
*   **可推导条件**：大多数专业会议室管理系统提供 API 或预置连接器（如 HID, Lenel, 国内海康/大华等）。
*   **待研究/空缺**：
    *   [待研究] 候选系统是否开放标准 API 供自定义门禁对接？
    *   [待研究] 是否有现成的第三方中间件支持？
    *   [待研究] 启用此功能是否产生额外的 License 费用或开发成本？
*   **阻塞影响**：若完全无 API 且无扩展机制，虽不直接淘汰（因为是可选），但会降低评分，并在未来扩展时构成阻碍。

---

### F2: 技术集成与兼容性

#### 子因素 F2.1: 部署模式 (Deployment Model)
*   **定义**：SaaS (公有云) vs Self-hosted (私有化/本地部署)。
*   **已知条件**：预算 ≤ 2 万/年，团队 30 人。
*   **可推导条件**：
    *   2 万/年的预算对于 30 人而言，人均约 667 元/年。
    *   私有化部署通常涉及服务器成本、运维人力、初始授权费，很难控制在 2 万/年以内（除非使用开源软件且无需商业支持，但开源软件的日历集成和门禁联动往往需要大量二次开发，隐性成本高）。
    *   因此，**SaaS 模式大概率是主要考察方向**，私有化仅作为极端低成本或特殊安全需求下的备选（需验证开源方案可行性）。
*   **待研究/空缺**：
    *   [待研究] 主流 SaaS 厂商在中国大陆的可用性（网络延迟、数据合规、支付通道）。
    *   [待研究] 是否存在符合预算的开源会议室系统（如 OpenSpace, RoomGuru OSS 等）及其集成能力评估。
*   **阻塞影响**：若所有 SaaS 均因网络/合规问题不可用，则必须转向私有化，这将彻底改变成本结构和实施周期。

#### 子因素 F2.2: 身份认证与目录同步 (SSO & Directory Sync)
*   **定义**：用户登录方式及组织架构同步。
*   **已知条件**：研发团队通常已有 AD/LDAP 或 Azure AD/Okta 等身份源。
*   **待研究/空缺**：
    *   [待研究] 候选系统是否支持 SSO (SAML/OAuth2)？
    *   [待研究] 是否支持从 LDAP/Azure AD 自动同步用户列表，避免手动维护账号？
*   **阻塞影响**：若不支持 SSO，每次入职离职都需手动管理账号，增加 IT 运维负担（影响 F4）。

---

### F3: 经济性与预算约束

#### 子因素 F3.1: 许可费用结构 (Licensing Structure)
*   **定义**：按人头收费 vs 按房间数收费 vs 固定平台费。
*   **已知条件**：总预算 ≤ 20,000 CNY / 年。
*   **可推导条件**：
    *   若按人头：$20,000 / 30 \approx 666$ CNY/user/year $\approx $93 USD/user/year。这是一个中等偏高的 SaaS 预算区间，应能覆盖主流企业级工具。
    *   若按房间数：假设 30 人团队有 5-8 间会议室。$20,000 / 8 = 2,500$ CNY/room/year。这也相对宽松。
*   **待研究/空缺**：
    *   [待研究] 各候选系统的计价模式（Per user vs Per room vs Flat fee）。
    *   [待研究] 是否有首年优惠、多年期折扣？
    *   [待研究] 价格是否包含所有必要功能（如日历集成），还是基础版不含高级集成？
*   **阻塞影响**：若基础版不含日历集成，需购买高级版，可能导致超预算。

#### 子因素 F3.2: 隐藏成本 (Hidden Costs)
*   **定义**：实施费、培训费、API 调用费、门禁硬件适配费等。
*   **待研究/空缺**：
    *   [待研究] 是否有一次性实施费（Onboarding Fee）？
    *   [待研究] 门禁联动是否被视为“高级功能”而单独收费？
    *   [待研究] 超出套餐的 API 调用是否有额外费用？
*   **阻塞影响**：隐藏成本可能导致实际 TCO 超过 2 万上限。

---

### F4: 运维与用户体验

#### 子因素 F4.1: 会议室面板展示 (Room Display)
*   **定义**：会议室门口显示屏实时显示预订信息。
*   **已知条件**：虽然任务未显式提及“屏幕”，但“会议室预约系统”的行业标准隐含此功能，否则预约意义减半（路人无法知道房间空闲）。
*   **待研究/空缺**：
    *   [待研究] 系统是否提供官方的 Room Display App（运行在 iPad/Mac Mini 上）？
    *   [待研究] 是否需要额外购买硬件（iPad 等）计入预算？（注：硬件通常由 IT 资产采购，不一定计入软件 SaaS 预算，但需在报告中说明）。
*   **阻塞影响**：若不提供显示界面，需自行开发网页嵌入，增加工作量。

#### 子因素 F4.2: 易用性与学习曲线 (Usability)
*   **定义**：员工预订会议的便捷程度。
*   **待研究/空缺**：
    *   [待研究] 移动端/Web 端的 UI 评价。
    *   [待研究] 是否支持“临时借用”、“取消释放”等高频操作的一键执行？
*   **阻塞影响**：低采纳率会导致系统闲置，选型失败。

基于上述分解，我们将市场划分为以下几类候选对象。**此为冻结集合，阶段 02 不得随意增删类别，仅在类别内筛选具体产品。**

| 类别 ID | 类别名称 | 典型代表 (待验证) | 纳入理由 | 排除理由 (若有) |
| :--- | :--- | :--- | :--- | :--- |
| **C1** | **国际主流 SaaS (Global Enterprise SaaS)** | Zoom Rooms, Slack Connect, Microsoft Teams Rooms (需配合其他预约工具), Calendly (Team版), Reclaim.ai | 功能成熟，集成能力强，全球标准。 | 需验证中国区可用性及价格。 |
| **C2** | **国内本土 SaaS (Local China SaaS)** | 飞书会议室, 钉钉会议室, 腾讯会议(企业版), 明道云/简道云定制, 专门的小型会议室系统(如 RoomGuru CN, 智慧空间类) | 网络速度快，中文支持好，符合数据合规，价格可能更优。 | 需验证日历集成的深度（特别是跨平台 GC+Outlook）。 |
| **C3** | **开源/自托管 (Open Source / Self-Hosted)** | OpenSpace, RoomGuru (OSS), Nextcloud (with plugins) | 无 License 费，数据完全自控。 | 实施成本高，日历/门禁集成需二次开发，可能超出 2 万预算（含人工）。 |
| **C4** | **通用项目管理/协作套件附带功能 (Suite Bundled)** | Jira/Confluence (Atlassian), Asana, Monday.com | 团队可能已在使用，边际成本低。 | 通常不具备专业的会议室物理资源和门禁联动能力，仅做逻辑预约。 |

**候选处理规则**：
*   C1-C4 中的所有具体产品均为 **[待验证假设]**。
*   阶段 02 需针对每个类别中的 Top 2-3 具体产品进行详细调研。

## 5. 已知条件汇总 (Confirmed Conditions)

1.  **团队规模**：30 人。
2.  **年度预算上限**：20,000 CNY (≈ $2,800 USD)。
3.  **终端支持**：macOS, Windows, Web 必须支持。
4.  **日历集成**：必须支持 Google Calendar **和** Microsoft Outlook (隐含双向同步需求，以解决资源冲突)。
5.  **门禁联动**：可选 (Nice-to-have)，不作为一票否决项，但需具备扩展能力。
6.  **交付物**：选型报告（推荐 + 备选 + 淘汰 + 成本）。

## 7. 阶段 02 研究路径与行动指南

### 7.1 优先研究顺序
1.  **P0 (最高优先级)**：确定 C1 和 C2 中具体的 3-5 个候选产品。
2.  **P1**：核验这些产品的 **日历集成能力** (G2) 和 **中国区可用性** (G1)。
3.  **P2**：获取 **报价** (G3) 并计算 TCO。
4.  **P3**：评估 **UX** (F4) 和 **门禁扩展性** (F1.3)。
5.  **P4**：评估开源方案 (C3) 的可行性（仅当 SaaS 全部超预算或不可用时深入）。

### 7.2 具体搜索策略与来源

#### A. 国际主流 SaaS (C1)
*   **目标对象**：Zoom, Slack, Calendly, Reclaim.ai, Acuity Scheduling, Booked Scheduler.
*   **搜索词**：
    *   `"[Product Name] meeting room booking integration"`
    *   `"[Product Name] Google Calendar Outlook two-way sync"`
    *   `"[Product Name] pricing per user annual"`
    *   `"[Product Name] China availability speed"`
*   **关键字段提取**：
    *   Pricing model (User vs Room).
    *   Calendar connectors (Native vs Zapier/Make).
    *   Hardware requirements (Do they need a dedicated tablet app?).
*   **备用路径**：若官网无明确中国区说明，搜索 Reddit/HackerNews 上关于 "Zoom in China" 或 "Slack latency China" 的最新讨论。

#### B. 国内本土 SaaS (C2)
*   **目标对象**：飞书 (Feishu/Lark), 钉钉 (DingTalk), 企业微信 (WeCom), 以及垂直领域的小众系统 (如 “易企秀会议室”, “智慧办公平台”).
*   **搜索词**：
    *   `"飞书 会议室 预约 集成 Outlook"`
    *   `"钉钉 会议室 门禁 联动"`
    *   `"国产 会议室预约系统 SaaS 价格"`
    *   `"会议室管理系统 源码 开源"` (针对 C3)
*   **关键字段提取**：
    *   是否支持导出/导入 ICS 文件以实现日历互通？
    *   是否有开放平台 API 供门禁对接？
    *   年费总价（通常国内 SaaS 价格较透明）。
*   **备用路径**：若小众系统信息少，直接联系其客服获取 Demo 和报价单。

#### C. 开源/自托管 (C3)
*   **目标对象**：OpenSpace, RoomGuru (Community Edition), Nextcloud (with Calendar/Meeting apps).
*   **搜索词**：
    *   `"OpenSpace github calendar sync outlook"`
    *   `"Self hosted meeting room system docker"`
    *   `"Open source room reservation software features"`
*   **关键字段提取**：
    *   GitHub Issues 中关于 "Outlook integration" 的状态。
    *   Docker 部署复杂度。
    *   社区活跃度 (Last commit date).
*   **备用路径**：若开源方案缺乏开箱即用的日历集成，判定为“高实施成本”，降级为备选中的“高风险选项”。

### 7.3 失败备用路径 (Fallback Strategies)
1.  **若所有 SaaS 均不支持 GC+Outlook 双向同步**：
