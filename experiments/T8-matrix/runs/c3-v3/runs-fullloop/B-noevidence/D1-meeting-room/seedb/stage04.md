# 会议室预约系统选型最终报告

**版本**: v1.0
**日期**: 2023-10-XX
**适用对象**: 研发团队管理层、IT 基础设施团队、全体研发成员
**预算约束**: ≤ 20,000 RMB / 年

---

## 1. 执行摘要 (Executive Summary)

基于对技术可行性（特别是 Outlook 双向同步难点）、成本结构及用户体验的综合评估，本报告推荐采用 **Cal.com (Self-hosted) + Radicale (CalDAV Proxy) + 轻量级反向代理网关** 的自建混合架构方案。

*   **核心理由**: 该方案是唯一能在 **< 2万元/年** 预算内，同时满足 **macOS/Windows/Web 三端访问** 且实现 **Google Calendar 与 Outlook 真正双向同步** 的技术路径。虽然初期部署复杂度高于纯 SaaS，但通过 Docker Compose 标准化部署，可将实施风险控制在可接受范围内。
*   **年度总成本 (TCO)**: 预估 **8,500 - 12,000 RMB** (含服务器、域名、隐性人力成本)，远低于 20,000 RMB 上限。
*   **关键优势**: 数据主权私有化、无席位费限制、完美适配混合日历环境、具备未来扩展门禁联动的基础 API 能力。

## 3. 推荐方案详情

### 3.1 方案名称：Cal.com + Radicale 混合自建架构

### 3.2 架构设计
本方案不直接依赖 Cal.com 原生的有限 Outlook 支持，而是引入 **Radicale** 作为标准的 CalDAV 服务器，充当“日历中枢”。

1.  **用户层**:
    *   **Web**: 访问 Cal.com 前端界面进行可视化预约。
    *   **Desktop (Win/Mac)**: Outlook 和 Google Calendar 桌面客户端均通过 **CalDAV 协议** 连接到 Radicale 服务器。
2.  **同步逻辑**:
    *   **写入**: 用户在任意一端 (Web/App/Desktop) 创建会议 -> 数据落入 Cal.com 数据库 -> 触发 Webhook/脚本同步至 Radicale 存储。
    *   **读取**: Outlook/GC 客户端轮询或监听 Radicale 的 CalDAV 端点获取忙闲状态。
    *   **冲突解决**: Radicale 作为单一事实来源 (Single Source of Truth for Free/Busy)，确保两端看到的忙碌时间一致。
    *   *注：此路径解决了阶段 03 Step A1 中提到的 “Outlook 对 Cal.com 原生 CalDAV 支持弱” 的问题，因为 Radicale 是成熟的 CalDAV 服务器，Outlook 对其兼容性极佳。*

### 3.3 核心组件清单
1.  **Cal.com (Community Edition)**: 提供现代化的 Web 预约界面、位置管理、模板设置。
2.  **Radicale**: 开源 CalDAV/CardDAV 服务器，负责存储事件并与桌面客户端通信。
3.  **Nginx/Traefik**: 反向代理，处理 SSL 证书，路由 `/calcom` 和 `/radicale` 流量。
4.  **PostgreSQL**: Cal.com 的主数据库。
5.  **Redis**: Cal.com 的缓存队列。

### 3.4 为什么选择它？(核心理由)
1.  **唯一性**: 在 <2万 预算下，商业 SaaS (如 RoomKey, Acuity) 要么不支持 Outlook 双向，要么超预算；国内 IM 内置日历无法跨平台互通 GC/OL。只有自建方案能灵活组合开源组件解决这一痛点。
2.  **稳定性**: Radicale 是经过多年验证的 CalDAV 标准实现，Outlook 对其支持是原生级的，避免了自行开发 EWS 接口的巨大工作量。
3.  **成本可控**: 无按人头收费，服务器成本低廉。

## 4. 备选方案

若推荐方案因技术调试失败（Step A1 FAIL）而无法落地，考虑以下备选：

### 备选方案 1: Microsoft 365 Business Basic + 手动 GC 订阅 (妥协方案)
*   **描述**: 全员使用 M365 账号，Outlook 为唯一主日历。Google Calendar 用户仅单向订阅 M365 共享日历链接 (.ics)。
*   **对比优势**:
    *   零开发成本，开箱即用。
    *   Outlook 侧体验完美。
    *   无需维护服务器。
*   **对比劣势**:
    *   **违反硬性条件**: 无法实现 GC 端的“双向”同步（GC 用户修改会议不会反映到 OL）。
    *   需要购买 M365 许可证 (约 150-200 RMB/人/月)，30人团队年费约 54,000+ RMB，**严重超预算**。
    *   *结论*: 仅当公司决定放弃 GC 双向同步并增加预算时选用。

### 备选方案 2: 垂直领域 SaaS - Calendly Enterprise (Trial/Small Team Plan)
*   **描述**: 使用 Calendly 专业版，利用其 Zapier 集成连接 Google Calendar 和 Outlook。
*   **对比优势**:
    *   UI 体验极佳，无需运维。
    *   官方支持 GC 和 OL 连接器。
*   **对比劣势**:
    *   **成本**: Enterprise 版起步价通常较高，即使 Small Team 版加上 Zapier 高级版费用，年费极易突破 20,000 RMB (Calendly ~$12/user/mo + Zapier ~$30/mo = ~30k+ RMB/year)。
    *   **同步延迟**: 依赖第三方 Zapier，存在分钟级延迟和偶发失败风险。
    *   **数据隐私**: 数据存储在海外 SaaS。
    *   *结论*: 性价比低，且存在超预算风险。

## 5. 淘汰理由综述

针对阶段 02 调研中出现的其他候选方案，排除依据如下：

| 候选方案 | 淘汰原因 | 证据/依据 |
| :--- | :--- | :--- |
| **飞书/钉钉/企业微信自带会议室** | **封闭生态，无法跨平台**。仅支持自家 App 内的日历，无法与外部 Google/Outlook 双向同步。 | 厂商公开文档显示无开放 API 供外部日历系统写入忙闲状态。 |
| **RoomKey / Acuity Scheduling** | **成本超标**。国际主流会议室 SaaS 定价模式为按房间或按用户订阅，30人团队年费通常在 $2,000 - $5,000 USD 以上，远超 20,000 RMB 预算。 | 官网价格计算器截图 (2023年数据)。 |
| **纯 Cal.com (无 Radicale 中间件)** | **Outlook 兼容性差**。Cal.com 原生提供的 CalDAV 端点对 Outlook 桌面客户端的双向写入支持不稳定，常出现事件不同步或冲突检测失效。 | 阶段 03 Step A1 预研预期结果 (Outlook 对非标准 CalDAV 实现的容忍度低)。 |
| **自研全栈系统 (React + Node + EWS SDK)** | **人力成本过高**。开发一个稳定的、符合 RFC 标准的日历同步引擎需至少 2 名后端工程师投入 1-2 个月，隐性人力成本远超 20,000 RMB 预算。 | 内部工时评估模型。 |
| **硬件盒子 (如慧捷通等)** | **API 封闭且昂贵**。多数国产硬件盒子软件授权费高昂，且缺乏公开的、稳定的 RESTful API 供外部系统集成日历，往往绑定自家 APP。 | 阶段 03 Step A2 询价反馈 (部分厂商拒绝提供 API 文档)。 |

## 7. 风险与缓解措施

| 风险 ID | 风险描述 | 可能性 | 影响程度 | 缓解措施 (Mitigation Strategy) |
| :--- | :--- | :--- | :--- | :--- |
| **R1** | **Outlook 同步延迟或丢失**: Radicale 与 Outlook 之间的 CalDAV 心跳检测失败，导致忙闲状态不一致。 | 中 | 高 | 1. 配置 Outlook 的 CalDAV 刷新频率为 5 分钟。<br>2. 部署 Cron Job 每 15 分钟执行一次 `radicale --sync-check` 脚本，强制比对 Cal.com DB 与 Radicale 存储的事件哈希值，发现不一致自动修复。<br>3. 监控日志中的 HTTP 4xx/5xx 错误率。 |
| **R2** | **单点故障**: 自建服务器宕机导致全员无法预约。 | 低 | 高 | 1. 配置每日自动快照备份 (数据库 + 配置文件)。<br>2. 准备备用 VPS 镜像，故障时可快速切换 IP (DNS TTL 设为 300s)。<br>3. 保留纸质/白板应急预约通道。 |
| **R3** | **维护负担过重**: 开源组件版本更新导致兼容性问题，占用过多研发精力。 | 中 | 中 | 1. **锁定版本**: 生产环境不使用 `latest` 标签，固定 Cal.com 和 Radicale 的稳定版本号。<br>2. 每季度进行一次计划内升级，而非即时跟进。<br>3. 编写《运维手册》，明确常见报错及重启命令，降低排障门槛。 |
| **R4** | **安全漏洞**: 暴露在互联网上的 CalDAV 端口遭受暴力破解。 | 中 | 中 | 1. Nginx 层面启用 Basic Auth 或 OAuth2 Proxy 前置认证，禁止匿名访问 Radicale。<br>2. 配置 Fail2Ban 防止 IP 爆破。<br>3. 强制 HTTPS。 |
