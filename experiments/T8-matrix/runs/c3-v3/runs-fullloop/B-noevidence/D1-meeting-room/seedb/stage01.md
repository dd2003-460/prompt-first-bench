# 阶段 01：目标分解、已知与空缺条件

## 1. 目标定义
为一家 30 人的研发团队交付一份**会议室预约系统选型报告**。
- **核心交付物**：包含推荐方案、备选方案、被淘汰方案及理由、完整成本明细的可交付文档。
- **硬性约束**：
  - 年度预算 ≤ 20,000 RMB。
  - 必须支持 macOS、Windows、Web 三端。
  - 必须对接 Google Calendar (GC) 和 Outlook (OL) 双日历。
- **加分项**：门禁联动（可选）。

## 2. 影响因素正交分解

我们将“选型决策”分解为以下五个互相正交的顶层因素，它们共同决定了最终方案的可行性与优劣：

### 因素 A：功能兼容性矩阵 (Functional Compatibility)
*决定方案是否满足硬性技术门槛。若任一子项不满足，直接淘汰。*

1.  **A1: 客户端覆盖度**
    *   A1.1: Web 端可用性（浏览器兼容性与体验）。
    *   A1.2: macOS 原生或 PWA 支持情况。
    *   A1.3: Windows 原生或 PWA 支持情况。
    *   *注：SaaS 通常以 Web+PWA 形式覆盖桌面，需验证其稳定性。*
2.  **A2: 日历集成深度**
    *   A2.1: Google Calendar 双向同步能力（创建/修改/删除会议室占用）。
    *   A2.2: Microsoft Outlook (Exchange/M365) 双向同步能力。
    *   A2.3: 冲突检测逻辑（当 GC 和 OL 同时存在时，系统如何处理资源锁）。
3.  **A3: 用户规模与权限管理**
    *   A3.1: 30 人团队的用户席位限制（是否按人头收费，是否有免费层上限）。
    *   A3.2: 管理员权限配置（会议室属性、时段规则设置）。
4.  **A4: 门禁联动能力 (Optional)**
    *   A4.1: 是否提供 API 或硬件插件支持主流门禁系统（如 HID, ZKTeco, 海康威视等）。
    *   A4.2: 联动延迟与安全性要求。

### 因素 B：商业成本结构 (Commercial Cost Structure)
*决定方案是否在预算内，以及隐性成本。*

1.  **B1: 显性订阅费用**
    *   B1.1: 基础版/专业版/企业版的年费单价。
    *   B1.2: 计费模式（按会议室数 vs 按用户数 vs 混合）。
    *   B1.3: 汇率波动风险（若为美元定价）及支付渠道手续费。
2.  **B2: 实施与维护成本**
    *   B2.1: 初始部署成本（SaaS 通常为 0，自建需服务器/开发人力）。
    *   B2.2: IT 运维工时成本（账号开通、日历映射调试、故障排查预估小时数 × 内部人力成本）。
    *   B2.3: 数据迁移成本（若有旧系统）。
3.  **B3: 合规与税务**
    *   B3.1: 发票类型（专票/普票/无票）对财务报销的影响。
    *   B3.2: 跨境服务的数据合规风险（GDPR/PIPL 考量，虽非硬性但影响选型偏好）。

### 因素 C：用户体验与效率 (UX & Efficiency)
*决定员工采纳率，间接影响项目成败。*

1.  **C1: 预约流程极简性**
    *   C1.1: 从打开应用到完成预约的点击次数。
    *   C1.2: 移动端支持情况（虽然任务未强制，但研发人员常用手机，属重要推导条件）。
2.  **C2: 信息透明度**
    *   C2.1: 实时空闲状态展示（地图视图 vs 列表视图）。
    *   C2.2: 设备/设施标签显示（投影仪、白板、视频摄像头等）。
3.  **C3: 通知与提醒机制**
    *   C3.1: 会议开始前提醒方式（邮件/IM/短信）。
    *   C3.2: 会议取消/改期的自动通知链路。

### 因素 D：技术架构与扩展性 (Architecture & Scalability)
*决定长期维护难度和未来扩展能力。*

1.  **D1: 部署模式**
    *   D1.1: SaaS (公有云) vs On-Premise (私有化) vs Hybrid。
    *   *推导：鉴于 2 万预算和 30 人规模，自建开源方案（如 OpenMeeting）的开发和维护成本极高，大概率排除，重点考察 SaaS 和轻量级托管。*
2.  **D2: API 开放性**
    *   D2.1: 是否提供公开 RESTful API 供未来集成其他内部工具（如 Slack/Teams 机器人）。
3.  **D3: 数据导出与所有权**
    *   D3.1: 能否方便地导出历史预约数据（CSV/JSON）。

### 因素 E：供应商可靠性与服务 (Vendor Reliability)
*决定服务连续性风险。*

1.  **E1: SLA 与服务等级**
    *   E1.1: 系统可用性承诺（99.9%?）。
    *   E1.2: 技术支持响应时间（工单 vs 实时聊天）。
2.  **E2: 市场口碑与案例**
    *   E2.1: 在类似规模（20-50人）研发团队中的使用反馈。
    *   E2.2: 中文本地化支持程度（界面、客服、文档）。

| D4 | **并发量极低** | 30 人团队，峰值并发预约请求远低于 100 QPS，因此无需考虑高性能集群架构，低成本 SaaS 即可满足性能要求。 |

### 3.3 仍需研究的条件 (Gaps / Unknowns)
*(这些是阶段 02 必须通过调研填补的空缺)*

| ID | 空缺问题 | 阻塞的判断 | 优先级 |
| :--- | :--- | :--- | :--- |
| G1 | **候选 SaaS 产品的具体价格表** | 无法判断哪些产品符合 <20k RMB/年 的预算。不同厂商对"会议室数量"和"用户数量"的计费差异巨大。 | High |
| G2 | **候选产品对 GC/OL 的双向同步实际效果** | 许多产品仅支持单向读取或需要复杂的 OAuth 配置。需确认是否存在"幽灵会议"（一边删了另一边还在）的问题。 | High |
| G3 | **候选产品在 macOS/Windows 上的具体呈现形式** | 是独立 Electron 应用？还是仅依赖浏览器书签？PWA 安装后的离线能力如何？ | Medium |
| G4 | **候选产品是否支持门禁硬件协议** | 大多数通用 SaaS 不直接连门禁，可能需要中间件（如 Home Assistant + 脚本），这会增加复杂度和成本。需确认是否有现成插件。 | Low (Optional) |
| G5 | **国内访问速度与稳定性** | 若 SaaS 服务器在海外（如美国/欧洲），国内用户访问延迟和丢包率是多少？是否需要代理？这直接影响可用性。 | High |
| G6 | **发票与支付方式** | 是否支持人民币对公转账？是否开具增值税发票？若无发票，财务报销流程将受阻，可能导致预算无法落地。 | High |
| G7 | **开源自建的真实 TCO (Total Cost of Ownership)** | 如果考虑自建（如基于 Next.js + CalDAV），需估算开发人员投入（人天×日薪）+ 云服务器费用。这有助于确定"购买 vs 自建"的分界线。 | Medium |

## 4. 空缺清单与研究路径 (Phase 02 Entry Points)

为了启动阶段 02，以下是具体的研究动作分解：

### 4.1 候选对象类别冻结 (Candidate Set Freeze)
基于 30 人规模和 2 万预算，我们将候选方案分为三类进行调研：
1.  **国际主流 SaaS (International SaaS)**: 全球知名，功能强，但可能有访问速度和发票问题。
    *   *代表候选（待验证）*: RoomKey, OfficeTime, Booked, Calendly (Room booking add-on), Acuity Scheduling.
2.  **国内本土 SaaS (Domestic SaaS)**: 访问快，发票方便，但功能可能较浅，GC/OL 集成能力存疑。
    *   *代表候选（待验证）*: 钉钉/飞书/企业微信自带的会议室模块（若团队已在用）、第三方专门做会议室预约的国内厂商（如：优办、简道云自定义表单等，需验证专业性）。
3.  **开源/自建方案 (Open Source / Self-hosted)**: 成本低（主要是人力），灵活度高，但维护成本高。
    *   *代表候选（待验证）*: 基于 CalDAV 协议的轻量级应用、GitHub 上 Star 数较高的 Meeting Room Booking 仓库。

### 4.2 阶段 02 具体研究动作

#### Action 1: 国际 SaaS 价格与功能核验
*   **目标**: 获取 RoomKey, OfficeTime 等 3-5 家头部厂商的最新定价。
*   **搜索词/来源**:
    *   官网 Pricing 页面。
    *   G2 Crowd / Capterra 上的对比评测（关注 "Calendar Integration" 和 "Mobile Support" 评价）。
*   **关键字段提取**:
    *   每间会议室月费/年费。
    *   用户数限制。
    *   是否提供 Free Trial (用于测试 GC/OL 同步)。
    *   服务器地理位置 (Data Center Location)。
*   **备用路径**: 若官网价格模糊，联系 Sales 获取针对 30 人规模的报价单 (Quote)。

#### Action 2: 国内 SaaS 与 IM 集成能力核验
*   **目标**: 确认钉钉/飞书/企微的会议室功能是否满足"独立于 IM 的 Web 端访问"和"GC/OL 外部同步"需求。
*   **注意**: 大多数国内 IM 的会议室功能是封闭生态，很难直接双向同步到外部的 Google/Outlook。此点极可能是**淘汰理由**。
*   **搜索词**: "钉钉 会议室预约 API 外部日历", "飞书 会议室 谷歌日历 同步".
*   **关键字段提取**:
    *   是否开放 API 给外部日历？
    *   是否支持非本 IM 用户的 Web 链接预约？

#### Action 3: 自建方案成本建模
*   **目标**: 计算一个最小可行产品 (MVP) 的自建成本。
*   **假设**: 使用 1 名中级前端/全栈工程师，投入 X 天。
*   **公式**: `TCO = (X days * Daily Rate) + Cloud Server Cost (Aliyun/Tencent ~200 RMB/month) + Domain/SSL`.
*   **研究**: 查找 GitHub 上成熟的 CalDAV 会议室预约模板，评估二次开发工作量。

#### Action 4: 门禁联动可行性预研
*   **目标**: 确认是否有低成本方案实现"SaaS -> 门禁"。
*   **路径**:
    *   搜索 "Meeting room booking system door lock integration API".
    *   考察 Home Assistant 社区是否有相关集成。
    *   若 SaaS 无 API，是否可通过 IFTTT/Zapier 中转？(Zapier 本身也有成本，需计入)。

### 4.3 失败备用路径 (Fallback Paths)

1.  **若所有国际 SaaS 均因访问速度或发票问题被否决**:
    *   *Backup*: 转向考察专注于亚太市场的 SaaS（如日本、新加坡服务商），或通过阿里云/腾讯云的市场place寻找经过认证的海外软件代理商（解决发票和加速问题）。
2.  **若所有现成 SaaS 均无法完美支持 GC+OL 双向同步**:
    *   *Backup*: 采用"单向同步 + 手动冲突解决"策略，或者选择支持 CalDAV 协议的自建方案，因为 CalDAV 是 GC 和 OL 都原生支持的底层协议，自建方案在此处可能比 SaaS 更稳定。
3.  **若预算不足以购买专业 SaaS 且自建人力成本过高**:
    *   *Backup*: 降级需求——放弃"双向同步"，改为"单向推送"（预约系统生成 .ics 文件，用户手动导入日历），或使用共享 Excel/Notion 表格 + 简单的网页前端（牺牲自动化，换取零软件成本）。
