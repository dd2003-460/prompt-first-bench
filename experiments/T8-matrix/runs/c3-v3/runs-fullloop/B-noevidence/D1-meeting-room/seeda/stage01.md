# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**核心交付物**：一份《30人研发团队会议室预约系统选型报告》。
**报告必须包含以下具体章节/内容**：
1.  **推荐方案**：单一最佳选择，需满足所有硬性约束。
2.  **备选方案**：至少1-2个次优但可行的选择，说明其与推荐方案的差异及适用场景。
3.  **淘汰理由**：针对市场上主流同类竞品（或不符合约束的候选），明确列出其被排除的具体原因（如超预算、不支持某端、缺乏日历集成等）。
4.  **成本明细**：推荐方案在“≤2万元/年”预算内的详细费用构成（软件许可费、实施费、硬件/门禁接口费、维护费等），需证明总和不超过预算上限。

### 递归分解 (Level 2 & Leaf Nodes)

#### F1: 功能合规性
*   **F1.1 基础预约功能**
    *   *叶子*: 会议室列表展示、时间段选择、冲突检测、预订确认通知。（已知需求）
*   **F1.2 规模适配性**
    *   *叶子*: 并发用户数支持 ≥ 30人；会议室数量支持范围（假设3-10间，需验证典型配置）。（可推导+待验证）
*   **F1.3 权限管理**
    *   *叶子*: 部门/个人视图隔离、管理员角色分配、黑名单/白名单机制。（待研究）

#### F2: 平台兼容性
*   **F2.1 操作系统支持**
    *   *叶子*: macOS 客户端存在性及版本要求。（已知需求）
    *   *叶子*: Windows 客户端存在性及版本要求。（已知需求）
*   **F2.2 Web 端支持**
    *   *叶子*: 浏览器兼容性（Chrome/Safari/Edge）、响应式设计（移动端Web访问能力，虽未强制但通常隐含）。（已知需求 + 待验证细节）

#### F3: 集成能力
*   **F3.1 日历集成 (硬约束)**
    *   *叶子*: Google Calendar 双向同步能力（创建/删除事件同步）。（已知需求）
    *   *叶子*: Microsoft Outlook (Exchange/Office 365) 双向同步能力。（已知需求）
    *   *子问题*: 是API级深度集成还是仅ICS文件订阅？（待研究，影响体验）
*   **F3.2 门禁联动 (可选约束)**
    *   *叶子*: 是否提供标准API/Webhook用于对接门禁系统？（已知需求：可选）
    *   *叶子*: 是否有现成的第三方网关或原生支持常见门禁品牌（如HID, ZKTeco）？（待研究）
    *   *注意*: 此功能为“可选”，若首选方案无此功能但有良好API，不直接淘汰，但需在报告中说明额外开发/集成成本风险。

#### F4: 成本结构
*   **F4.1 软件授权费**
    *   *叶子*: 按年订阅价格（Per user or Per room?）。（待研究）
    *   *叶子*: 最小起订量限制（MOQ）。（待研究）
*   **F4.2 一次性费用**
    *   *叶子*: 实施费、定制开发费（如有）。（待研究）
*   **F4.3 隐性/附加费用**
    *   *叶子*: 高级功能模块费（如门禁模块、报表模块）。（待研究）
    *   *叶子*: 数据存储超额费（如有）。（待研究）
    *   *约束检查*: Total Annual Cost ≤ 20,000 CNY。（已知约束）

#### F5: 部署与维护模式
*   **F5.1 部署方式**
    *   *叶子*: SaaS (云端) vs On-Premise (本地)。（待研究）
    *   *影响*: SaaS通常年费制，On-Premise可能涉及License买断+服务器成本。对于2万/年预算，SaaS可能性更大，但需验证。
*   **F5.2 数据安全与合规**
    *   *叶子*: 数据驻留地（国内节点 vs 海外节点）。（待研究，对中国团队至关重要）
    *   *叶子*: 隐私政策与SLA保障。（待研究）

#### F6: 用户体验与管理效率
*   **F6.1 前端体验**
    *   *叶子*: UI/UX 设计水平、多语言支持（中文界面必备）。（待研究）
*   **F6.2 后端管理**
    *   *叶子*: 会议室信息维护便捷性、使用率统计报表。（待研究）

## 3. 条件分类清单

### A. 人类已提供的条件 (Given Facts)
1.  **团队规模**: 30人研发团队。
2.  **预算上限**: ≤ 20,000 CNY / 年。
3.  **终端支持**: 必须支持 macOS, Windows, Web 三端。
4.  **日历集成**: 必须支持 Google Calendar 和 Outlook。
5.  **门禁联动**: 可选功能（Non-blocking requirement, but desirable if available within budget）。
6.  **交付物**: 选型报告（含推荐、备选、淘汰理由、成本明细）。

### B. 从项目可推导的条件 (Derived Conditions)
1.  **并发负载**: 系统需稳定支持至少30个活跃用户的日常操作（峰值可能在早晨9-10点集中预约）。
2.  **语言支持**: 鉴于团队为中文研发背景（隐含于任务语境），系统必须具备优秀的中文界面和本地化支持，否则无法落地。
3.  **网络环境**: 考虑到中国企业的网络特性，如果系统是SaaS，必须有稳定的中国大陆访问节点或服务，否则延迟将导致Web端和客户端体验极差。（这是一个强推导，但需验证具体厂商的CDN/节点策略）。
4.  **采购周期**: 2万元/年的预算属于中小企业SaaS订阅级别，排除了大型ERP套件中的会议模块（通常昂贵且复杂）和完全自研（开发成本远超2万/年摊销）。

### C. 仍需研究的条件 (Open Questions / Gaps) -> **写入空缺清单**

| Gap ID | 空缺描述 | 阻塞的判断 | 优先级 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| **G1** | **主流候选清单及其当前定价** | 无法确定哪些产品符合预算，无法进行横向对比。 | P0 | 需搜集 Zoom Rooms, Microsoft Teams Rooms, Slack Connect, 以及国内竞品（如钉钉/飞书自带功能、专业会议系统如RoomGo, MeetingPro等）的最新报价。 |
| **G2** | **各候选的日历集成深度与实现方式** | 判断是否真正满足“Google + Outlook 双集成”。有些产品只支持单向ICS，不支持双向同步。 | P0 | 需查阅技术文档或联系销售确认 API 能力。 |

## 4. 候选对象类别冻结 (Candidate Set Freeze)

为避免阶段02漂移，现将候选对象限定为以下三类。**阶段02不得引入此类之外的全新类别（如“自研开源方案”除非作为备选中的极端低成本选项进行简要评估，但不作为主要推荐方向，因为2万/年预算难以覆盖高质量自研维护）**：

1.  **国际主流协作平台附属功能** (International Collaboration Suite Features)
    *   *代表候选 (待验证)*: Microsoft Teams (Meeting Rooms), Zoom (Zoom Rooms), Slack (Slack Connect/Cal.com integration).
    *   *特点*: 生态强大，但可能捆绑其他昂贵组件，或对中国大陆访问不友好。
2.  **专用会议室预约SaaS (国际)** (Dedicated Room Booking SaaS - Global)
    *   *代表候选 (待验证)*: Envoy, Doodle Meet, Calendly (Business), Simply Book Me.
    *   *特点*: 功能专注，通常有免费版或低价版，需验证中文支持和国内访问速度。
3.  **国内垂直/通用办公会议系统** (Domestic Vertical/General Office Systems)
    *   *代表候选 (待验证)*: 钉钉 (智能会议室)、飞书 (妙记/会议室)、企业微信 (相关插件)、专业厂商如 RoomGo, 智会云, 易企秀(如有此业务) 等。
    *   *特点*: 国内访问快，中文好，通常集成在OA中，需验证独立计费模式和API开放度。

*注：以上列出的具体产品名称仅为“待验证的研究目标”，并非已确认的合格候选。阶段02需逐一核验其属性。*

### 5.2 第二批行动 (Priority 2: Deep Dive on Survivors)

**目标**: 对通过第一轮筛选的 2-3 个候选进行深度成本和功能核实。

| 步骤 | 动作 | 目标来源 | 需提取字段 | 失败备用路径 |
| :--- | :--- | :--- | :--- | :--- |
| **R2.1** | **获取详细报价单 (Quote)** | 渠道: 官网“联系我们”表单、电话销售、LinkedIn连接销售 | 1. 30用户/5房间的精确年费<br>2. 实施费/培训费明细<br>3. 门禁API是否额外收费<br>4. 合同期限灵活性 | 若销售响应慢 (>3天)，转向寻找代理商或合作伙伴报价，或在公开社区 (Reddit, V2EX, 知乎) 搜索近期用户分享的价格截图。 |

### 5.3 关键失败处理策略

*   **若所有国际SaaS因访问速度慢而不可行**: 立即切换重心至国内OA内置功能或国内垂直SaaS。即使其UI稍逊，只要满足功能和预算，应优先考虑可用性。
*   **若所有候选均超出2万/年预算**: 
    1. 检查是否有“Starter”或“Basic”套餐能满足基本需求（哪怕牺牲一些高级报表）。
    2. 考虑混合方案：使用免费的开源前端 (如 React-based booking widget) + 自建后端 (Serverless) + 现有日历API。但这超出了“选一套系统”的范畴，仅在商业产品全部失效时作为最后的“自研/半自研”备选提出，并明确指出其隐性人力成本极高。
*   **若门禁联动在所有候选中均需高额定制**: 在报告中明确将此列为“未来扩展项”，并在成本明细中将此部分标记为“未计入基础预算，如需启用需额外评估”，从而确保基础方案符合2万预算。
