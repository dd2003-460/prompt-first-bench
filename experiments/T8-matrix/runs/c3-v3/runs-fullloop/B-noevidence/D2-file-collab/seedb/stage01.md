# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**核心交付物**：一份可交付的《团队文件协作/网盘方案选型报告》。
**报告必须包含以下模块**：
1.  **推荐方案**：唯一首选，需满足所有硬性约束。
2.  **备选方案**：至少1个次优选项，说明其与推荐方案的差异及适用场景。
3.  **淘汰理由**：明确列出被排除的主要候选类别或具体产品，并给出违反约束的具体依据。
4.  **成本明细**：基于“每年总花费上限 3 万元人民币”的预算拆解，包含软件订阅费、潜在硬件/存储增量费（如有）、实施/培训隐性成本估算。
5.  **功能验证结论**：针对“文档版本管理”和“细粒度权限控制”两个核心功能的实现程度评估。
6.  **加分项评估**：离线使用支持情况的对比分析。

### L2/L3 递归分解

#### 1. 合规性约束 (Compliance Constraints)
*   **1.1 预算硬顶**
    *   1.1.1 [已知] 年度总预算 ≤ 30,000 RMB。
    *   1.1.2 [待研究] 各候选方案的实际年费结构（按人头 vs 按容量 vs 混合）。
    *   1.1.3 [待研究] 是否包含税费、汇率波动影响（若为海外服务）。
*   **1.2 平台覆盖强制要求**
    *   1.2.1 [已知] 必须支持 Web。
    *   1.2.2 [已知] 必须支持 macOS 客户端。
    *   1.2.3 [已知] 必须支持 Windows 客户端。
    *   1.2.4 [待研究] 各候选在上述三个平台的客户端成熟度（如：Web端功能是否阉割，桌面端同步稳定性）。

#### 2. 功能性匹配度 (Functional Fit)
*   **2.1 文档版本管理 (Core Feature A)**
    *   2.1.1 [待研究] 版本保留策略（无限历史 vs 有限天数 vs 手动快照）。
    *   2.1.2 [待研究] 版本恢复操作便捷性（一键回滚 vs 下载后替换）。
    *   2.1.3 [待研究] 并发编辑冲突处理机制（自动合并 vs 锁定文件）。
    *   2.1.4 [待研究] 是否支持非 Office 格式（代码、设计源文件等）的版本管理。
*   **2.2 细粒度权限控制 (Core Feature B)**
    *   2.2.1 [待研究] 权限层级深度（文件夹级 vs 文件级 vs 字段/行级——通常网盘仅到文件级，需确认）。
    *   2.2.2 [待研究] 用户组管理复杂度（是否支持嵌套组、动态组）。
    *   2.2.3 [待研究] 外部协作者权限隔离能力（Guest Access 安全性）。
    *   2.2.4 [待研究] 审计日志完整性（谁在何时修改了什么，能否导出）。
*   **2.3 离线使用 (Bonus Feature)**
    *   2.3.1 [待研究] 离线同步机制（全量下载 vs 按需缓存 vs 选择性同步）。
    *   2.3.2 [待研究] 离线状态下的编辑冲突解决策略。

#### 3. 经济性约束 (Economic Constraints) - *注：此处为子预算视角，最终数值依赖阶段02核验*
*   **3.1 直接订阅成本**
    *   3.1.1 [待研究] 30人规模下的阶梯定价。
    *   3.1.2 [待研究] 免费额度与付费额度的界限。
*   **3.2 隐性/间接成本**
    *   3.2.1 [待研究] 数据迁移成本（人力工时估算）。
    *   3.2.2 [待研究] 培训成本（是否需要专门培训，文档友好度）。
    *   3.2.3 [待研究] 网络带宽成本（若自建服务器则涉及，若SaaS则主要看出口带宽对同步速度的影响，通常不计入软件预算，但需记录风险）。

#### 4. 技术兼容性与体验 (Technical Compatibility & UX)
*   **4.1 客户端性能**
    *   4.1.1 [待研究] 大文件传输速度稳定性。
    *   4.1.2 [待研究] 多文件批量操作响应时间。
    *   4.1.3 [待研究] 资源占用率（CPU/Memory）。
*   **4.2 集成能力**
    *   4.2.1 [待研究] 与现有研发工具链（Git, Jira, Slack/Teams）的集成插件可用性。
    *   4.2.2 [待研究] API 开放程度（用于自动化脚本）。

#### 5. 运维与支持风险 (Operational & Support Risk)
*   **5.1 服务商可靠性**
    *   5.1.1 [待研究] SLA 承诺（99.9% vs 99.99%）。
    *   5.1.2 [待研究] 数据备份与灾难恢复策略。
    *   5.1.3 [待研究] 服务商地理位置与数据驻留要求（国内合规性 vs 海外服务访问速度/政策风险）。
*   **5.2 技术支持**
    *   5.2.1 [待研究] 中文支持质量。
    *   5.2.2 [待研究] 响应时效（工单 vs 在线聊天）。

## 3. 条件分类清单

### A. 人类已提供的确定条件 (Known Facts)
1.  团队规模：30人研发团队。
2.  年度总预算上限：30,000 CNY。
3.  必需平台：Web, macOS, Windows。
4.  核心功能1：文档版本管理。
5.  核心功能2：细粒度权限控制。
6.  加分项：支持离线使用。
7.  交付物形式：选型报告（含推荐、备选、淘汰理由、成本明细）。

### B. 从项目推导的确定条件 (Derived Conditions)
1.  **人均预算约束**：30,000 CNY / 30 人 = 1,000 CNY/人/年 ≈ $138 USD/人/年。
    *   *推导逻辑*：这排除了大部分高端企业级 SaaS（如 Box Enterprise, SharePoint Online E3 等通常远高于此人均单价），将范围缩小至中型团队版或国产高性价比 SaaS/PaaS。
2.  **数据类型推断**：作为“研发团队”，除常规文档外，可能涉及代码片段、配置文件、小型二进制文件。因此，“细粒度权限”不仅指Office文档，还需关注对非结构化文件的权限控制；“版本管理”需考虑非Office文件的兼容性。
3.  **部署模式倾向**：鉴于预算限制（<1万USD/年），自建私有云（On-Premise）的成本（服务器+维护人力）极大概率超出预算或导致运维负担过重，除非是极低成本的开源方案（如 Nextcloud + 廉价VPS），但这会引入高运维风险。因此，**SaaS 模式为主要研究对象，IaaS/PaaS 托管模式为次要研究对象**。

### C. 仍需研究的条件 (Open Questions / Gaps)
*(以下条目均标记为 **[待研究]**，严禁在阶段01中假定为事实)*

| ID | 空缺条件描述 | 阻塞的后续判断 | 优先级 |
|----|-------------|---------------|--------|
| G1 | **主流候选名单及其最新定价** | 无法生成成本明细表；无法进行初步筛选。 | P0 |
| G2 | **各候选“细粒度权限”的具体定义** | 无法判断是否满足核心功能B。例如：某些网盘只支持“共享链接权限”，不支持“内部文件夹继承权限”。 | P0 |
| G3 | **各候选“版本管理”的实现细节** | 无法判断是否满足核心功能A。例如：是否支持分支？保留多久？能否对比差异？ | P0 |
| G4 | **Web/macOS/Windows 三端功能一致性** | 无法判断是否存在平台短板。例如：某产品 Web 端无版本历史查看功能。 | P1 |
| G5 | **离线同步的具体机制与限制** | 无法准确评估加分项得分。 | P2 |

| G8 | **30人规模的最低起订量与折扣政策** | 精确计算年费。 | P0 |

## 4. 候选对象类别冻结 (Candidate Set Freeze)

基于推导条件 B1 (人均预算) 和 B3 (SaaS为主)，阶段 01 冻结以下**候选类别**供阶段 02 深入研究。任何新增类别需在阶段 02 显式记录理由。

1.  **国内主流企业协同办公套件 (Domestic Enterprise Collaboration Suites)**
    *   *代表假设*：飞书 (Feishu/Lark), 钉钉 (DingTalk), 企业微信 (WeCom)。
    *   *理由*：本土化好，价格通常较低，原生支持三端，权限体系相对完善。
2.  **国际通用文件协作 SaaS (International File Collaboration SaaS)**
    *   *代表假设*：Dropbox Business, Google Workspace (Drive), OneDrive for Business (Microsoft 365 Group Plan), Box, Miro (虽偏白板但有文件功能，暂列为边缘候选)。
    *   *理由*：全球标准，功能强大，但需重点考察价格换算后的可行性及国内访问速度。
3.  **轻量级/开源自托管方案 (Lightweight/Self-Hosted Solutions)**
    *   *代表假设*：Nextcloud, Seafile, OwnCloud (配合低成本 VPS/云服务器)。
    *   *理由*：软件免费或极低成本，可无限定制权限，但运维成本高，需评估是否计入“总花费”（人力成本难量化，通常此类方案因运维风险在30人团队中不推荐，除非有专职DevOps且预算允许额外服务器支出）。
4.  **垂直领域研发协作平台 (Vertical Dev-Collaboration Platforms)**
    *   *代表假设*：GitLab (自带Wiki/File storage), Confluence (Jira生态)。
    *   *理由*：研发团队专用，版本管理极强（Git基础），但通用文件存储能力较弱，需评估是否满足“网盘”属性。

**排除类别 (Excluded Categories)**：
*   *纯个人网盘* (百度网盘个人版等)：缺乏企业级权限管理和SLA，不符合B端需求。
*   *重型私有化部署 ERP/OA*：预算严重不足，实施周期过长。

## 5. 阶段 02 研究路径 (Research Path for Stage 02)

阶段 02 应基于上述冻结候选集执行以下动作：

### 第一步：构建候选短名单 (Shortlist Construction)
*   **动作**：针对上述4类中的具体产品，收集官方最新价格页（Price Page）。
*   **来源类型**：官方网站、G2/Capterra评测、知乎/掘金等技术社区真实用户反馈（侧重故障率和权限吐槽）。
*   **搜索词示例**：
    *   "Feishu enterprise plan price 30 users"
    *   "Dropbox business pricing per user annual"
    *   "Nextcloud self-hosted cost estimation 30 users"
    *   "Confluence cloud pricing small team"
*   **字段提取**：
    *   最低套餐名称
    *   单用户月/年费用 (CNY/USD)
    *   包含存储空间
    *   是否支持指定人数以下的优惠
*   **失败备用路径**：若官网价格模糊，寻找代理商报价单或联系销售获取 Quote。

### 第二步：功能矩阵验证 (Feature Matrix Validation)
*   **动作**：针对进入短名单的产品（预计3-5个），逐一验证核心功能。
*   **验证方法**：
    1.  **查阅官方文档**：搜索 "version history", "permission inheritance", "offline sync"。
    2.  **试用账号测试**：注册免费试用或申请 Demo，实际创建文件夹、设置不同权限、上传文件、模拟离线断开。
    3.  **社区挖掘**：在 Reddit, StackOverflow, V2EX 搜索特定痛点，如 "Dropbox permission bug", "Feishu drive version limit"。
*   **关键检查点**：
    *   [ ] 权限能否做到“只有张三能读，李四能写，王五不可见”？
    *   [ ] 版本历史保留多久？能否看到修改人？
    *   [ ] Mac/Win 客户端是否独立安装包，还是依赖浏览器？

### 第三步：成本模型细化 (Cost Modeling)
*   **动作**：计算 30 人规模的精确年费。
*   **公式**：`Total Annual Cost = (Per User Price × 30) + Storage Overage Fee (if any) + Implementation Cost Estimate`.
*   **注意**：对于自托管方案，需估算 `Server Cost + Maintenance Labor Hourly Rate × Estimated Hours`.

### 第四步：风险与合规评估 (Risk & Compliance Assessment)
*   **动作**：评估数据出境、访问速度、SLA。
*   **重点**：对于海外 SaaS，测试国内节点访问延迟；对于国内 SaaS，检查数据加密标准和隐私政策。

## 6. 阶段 01 判定自查

*   **覆盖目标**：所有任务书要求的输出（推荐、备选、淘汰、成本）均有对应因素支撑。
*   **边界清晰**：预算硬顶、平台要求明确。
*   **空缺完整**：所有未确定的价格、具体功能细节均已列入 Gap 列表，未伪装成已知。
*   **研究路径具体**：提供了具体的搜索词、来源类型和验证方法。
