# 阶段 02：资料搜集与事实核验报告

**任务目标：** 针对阶段 01 提出的选型方案（Nextcloud 自托管 vs 坚果云企业版等），基于公开知识对关键事实进行搜集、标注来源或标记为待核验假设，以支撑最终决策。

**核心原则：**
1. **开源软件特性**通常由官方文档和 GitHub 仓库确认，可信度高。
2. **SaaS 定价**具有高度动态性（促销、套餐变更、汇率波动），必须标记为“待核验”或提供区间估计。
3. **云服务成本**依据主流厂商（阿里云/腾讯云）当前公开目录价估算，需注明配置基准。

## 二、风险与不确定性分析

### 1. 运维人力成本隐性化
*   **事实：** Nextcloud 是开源软件，免费，但**维护是有成本的**。
*   **风险：** 阶段 01 低估了“运维复杂度”带来的隐性人力成本。如果 30 人团队中没有专人负责 Linux 服务器维护，每次升级、安全补丁、故障排查都需要占用开发人员工时。
*   **量化假设：** 假设每月花费 2 小时处理 Nextcloud 相关事务，开发人员时薪 ¥100，则年隐性成本为 `2h * 12m * ¥100 = ¥2,400`。
*   **对策：** 在成本明细中增加“隐性运维人力成本”项，使总成本更真实。调整后 Nextcloud 总显性+隐性成本 ≈ ¥1,310 + ¥2,400 = **¥3,710**，依然远低于 ¥30,000 预算。

### 2. 坚果云企业版的“存储陷阱”
*   **事实：** SaaS 网盘通常按“人头”收费，但存储容量往往有限制。
*   **风险：** 研发团队常处理大型设计源文件（PSD/Sketch/Xcode工程）或编译产物。若人均存储需求 > 100GB，坚果云可能需要购买额外的“存储包”，导致总成本激增。
*   **行动建议：** 在联系坚果云销售前，先统计团队现有文件总量及未来一年增长预估。若总量 > 3TB，需专门询问扩容价格。

### 3. 网络出口带宽瓶颈
*   **事实：** 轻量应用服务器的公网带宽通常较小（1-5 Mbps）。
*   **风险：** 30 人同时上传/下载大文件时，5 Mbps 带宽（约 600 KB/s）会被迅速占满，导致用户体验极差。
*   **解决方案：**
    1.  **升级带宽：** 将带宽提升至 10-20 Mbps，成本增加约 ¥1,000-¥3,000/年。
    2.  **使用 CDN/对象存储中转：** 对于超大文件，配置 Nextcloud 将大文件存储在 OSS，通过 CDN 加速分发，降低服务器带宽压力。
    3.  **内网优先：** 如果团队成员大多在公司内网，可配置 Nextcloud 走内网 IP 同步，仅对外部访问使用公网带宽。

## 四、阶段 02 结论与建议

1.  **事实确认：** Nextcloud 确实能免费满足所有核心技术需求（版本、权限、多端、离线）。其成本优势是绝对的（<10% of Budget）。
2.  **关键差异点：** 选择的核心矛盾不再是“功能是否具备”，而是**“运维投入 vs 金钱成本”**以及**“数据主权偏好”**。
    *   如果团队重视**数据安全、定制性、长期成本控制**，且有基本 Linux 能力 → **Nextcloud 是压倒性优势**。
    *   如果团队**极度厌恶运维**，且预算允许花掉大部分额度换取省心 → **坚果云企业版**是可行的 Plan B，但需警惕存储超额费用。
3.  **下一步行动 (Phase 03 准备):**
    *   撰写正式选型报告时，需明确列出 Nextcloud 的**运维 SLA**（例如：承诺每周一次备份，每月一次补丁更新）。
    *   向坚果云销售发送询价单，明确要求：“30人企业版，预计总存储 5TB，需要 API 接口，请提供三年期总报价”。
    *   在报告中加入“TCO (总拥有成本)”对比图表，展示 3 年期的累计成本差异（Nextcloud 几乎不变，SaaS 可能因涨价或扩容而上升）。

*(注：以上所有价格均为基于 2023-2024 年公开市场信息的估算，实际采购前请以供应商最新报价为准。)*
