# 阶段 03：具体行动分解（无 owner 组件）

**任务目标：** 基于阶段 02 的事实核验与成本模型，将“挑选团队文件协作/网盘方案并输出选型报告”这一宏观目标，拆解为可执行、可验证的具体步骤。

**核心策略：**
1.  **并行推进：** Nextcloud 技术验证（POC）与 SaaS 商务询价（RFP）同时进行，以获取真实数据支撑最终决策。
2.  **风险前置：** 重点解决 Nextcloud 的“带宽瓶颈”和“运维隐性成本”两个最大风险点。
3.  **交付导向：** 所有步骤的最终产出必须能直接拼入最终的《选型报告》中。

---

## 行动步骤分解表

### 步骤 1：Nextcloud 最小化可行性原型 (MVP POC) 搭建
*   **输入**: 
    *   一台符合配置基准的云服务器实例（2vCPU, 4GB RAM, 100GB ESSD）。
    *   Docker Compose 配置文件（包含 Nextcloud Server + OnlyOffice Document Server + PostgreSQL/MySQL）。
    *   测试用账号列表（模拟 5 个不同权限角色：Admin, Dev, Viewer, External Guest）。
*   **动作**: 
    1.  在云端服务器部署 Nextcloud 基础环境。
    2.  安装并配置 `onlyoffice` 集成插件，确保 Word/Excel/PPT 在线编辑功能正常。
    3.  配置版本管理策略：设置文本文件保留最近 10 个版本，二进制文件保留最近 5 个版本。
    4.  创建测试文件夹，分别授予 Admin、Dev、Viewer 不同级别的权限（读写、只读、评论）。
    5.  使用 macOS 和 Windows 客户端连接服务器，执行“断网编辑 -> 联网同步”流程，验证冲突解决机制。
*   **依赖**: 
    *   云服务器资源已开通。
    *   具备基本的 Linux/Docker 操作能力。
*   **预期产出**: 
    *   一个可访问的 Nextcloud 测试 URL。
    *   一份《POC 功能验证清单》，标记各项功能（版本回溯、细粒度权限、离线同步、协同编辑）是否通过。
*   **验收方式**: 
    *   非技术人员可通过 Web 端成功打开并编辑文档。
    *   删除当前文件后，能从版本历史中成功恢复上一版本。
    *   断开网络修改本地文件，恢复网络后，服务端正确合并或提示冲突，且数据不丢失。

### 步骤 2：Nextcloud 性能压测与带宽瓶颈评估
*   **输入**: 
    *   步骤 1 搭建的 Nextcloud 环境。
    *   一个大文件样本（如 500MB 的视频或 100MB 的代码包）。
    *   压力测试工具（如 JMeter 或简单的脚本模拟并发上传/下载）。
*   **动作**: 
    1.  模拟 5-10 个用户同时上传/下载大文件，记录平均响应时间和吞吐量。
    2.  监控服务器 CPU、内存及公网带宽利用率。
    3.  对比“5Mbps 带宽”与“10Mbps 带宽”下的体验差异（可通过临时升级带宽或限制速率模拟）。
    4.  评估是否需要引入 OSS + CDN 方案来卸载静态文件压力，并估算该架构的额外复杂度。
*   **依赖**: 
    *   步骤 1 完成。
*   **预期产出**: 
    *   《性能测试报告》，包含：
        *   单线程上传/下载速度实测值。
        *   并发场景下的带宽饱和阈值。
        *   针对 30 人团队的带宽推荐配置（例如：建议最低 10Mbps，最佳 20Mbps 或启用 CDN）。
*   **验收方式**: 
    *   明确回答：“在当前预算下，标准轻量服务器能否满足 30 人日常使用？”
    *   若不能，给出明确的硬件升级路径及对应成本增量。

### 步骤 3：SaaS 竞品（坚果云企业版）精确商务询价
*   **输入**: 
    *   团队现状数据：30 名用户，预计总存储需求 5TB（含增长冗余），主要文件类型为代码库和设计源文件。
    *   功能需求清单：需支持 API 集成、审计日志、细粒度权限控制。
*   **动作**: 
    1.  联系坚果云（Jianguoyun）官方销售或代理商。
    2.  发送标准化询价邮件/RFP，明确询问：
        *   30 人企业版年度授权费（License Fee）。
        *   5TB 存储空间的总费用（是包含在套餐内还是需额外购买？单价多少？）。
        *   是否提供三年期合同折扣？
        *   是否包含 API 调用配额及超额费用？
    3.  同步咨询阿里云盘企业版或百度网盘企业版的同等规模报价，作为交叉验证。
*   **依赖**: 
    *   内部确认好存储容量预估（步骤 2 中的假设需在此前由技术负责人粗略确认）。
*   **预期产出**: 
    *   供应商正式报价单（PDF/Excel）。
    *   《SaaS 方案成本对比表》，列出乐观价、保守价及潜在隐性费用（如扩容费、API 超量费）。
*   **验收方式**: 
    *   获得书面报价，且总价在 ¥30,000 以内的可能性被量化评估（例如：“若不加购存储，总价为 X，加购至 5TB 后总价为 Y”）。

### 步骤 4：运维成本量化与 SLA 制定
*   **输入**: 
    *   步骤 1 & 2 中发现的技术难点（如 OnlyOffice 更新繁琐、备份脚本维护）。
    *   团队成员当前的 Linux 技能水平调研结果。
*   **动作**: 
    1.  定义 Nextcloud 自托管的《运维服务级别协议 (SLA)》草案：
        *   数据备份频率：每日全量 + 每小时增量。
        *   安全补丁更新周期：每月第一个周二。
        *   故障响应时间：工作时间内 4 小时内响应。
    2.  根据 SLA，估算所需人力工时。例如：备份脚本调试初期需 8h，后续每月维护 2h。
    3.  计算“隐性人力成本” = 预估年工时 × 开发人员时薪（参考公司平均人力成本）。
*   **依赖**: 
    *   步骤 1 & 2 完成，了解实际运维痛点。
*   **预期产出**: 
    *   《Nextcloud 运维成本与风险评估书》，包含：
        *   显性基础设施成本（云主机+带宽+域名）。
        *   隐性人力成本（按小时折算的金额）。
        *   关键风险点及缓解措施（如：双人负责制防止单点故障）。
*   **验收方式**: 
    *   总 TCO（Total Cost of Ownership，含隐性成本）低于 ¥30,000 上限，且留有至少 20% 的安全边际。
    *   SLA 条款被团队技术负责人确认为“可执行”。

### 步骤 5：综合对比分析与决策矩阵构建
*   **输入**: 
    *   步骤 1-4 的所有产出物（POC 结果、性能数据、SaaS 报价、运维成本）。
    *   原始约束条件：预算 ≤ ¥30k/年，多平台支持，版本管理，细粒度权限，离线加分项。
*   **动作**: 
    1.  建立加权评分矩阵（Weighted Scoring Matrix）：
        *   维度：功能完整性 (30%)、TCO 成本 (30%)、运维复杂度/稳定性 (20%)、数据安全/合规 (10%)、扩展性 (10%)。
        *   对 Nextcloud 和 坚果云企业版进行打分（1-5 分）。
    2.  撰写《淘汰理由说明》：
        *   解释为何 Google Drive/OneDrive 被淘汰（预算超标、合规风险）。
        *   解释为何普通网盘（百度/阿里个人版）不被推荐（缺乏细粒度权限和企业级 API）。
    3.  确定最终推荐方案：
        *   **主选方案**：通常基于 TCO 和数据主权优势，Nextcloud 大概率胜出。
        *   **备选方案**：坚果云企业版（适用于无法承担运维风险的极端情况）。
*   **依赖**: 
    *   步骤 1-4 全部完成。
*   **预期产出**: 
    *   《方案对比评分表》。
    *   初稿形式的《选型决策建议书》核心章节。
*   **验收方式**: 
    *   评分逻辑清晰，权重分配合理。
    *   结论明确，没有模棱两可的表述。

### 步骤 6：撰写并评审最终《团队文件协作方案选型报告》
*   **输入**: 
    *   步骤 5 的分析结果。
    *   阶段 02 的事实核查报告（用于引用来源）。
    *   模板结构：背景、需求分析、候选方案介绍、详细对比、成本明细、风险分析、最终推荐、实施路线图。
*   **动作**: 
    1.  **整合内容**：
        *   **执行摘要**：一页纸概括推荐方案、核心理由、总成本。
        *   **需求回顾**：重申 30 人团队、预算、三大核心功能。
        *   **方案详情**：
            *   *Nextcloud*：展示架构图、POC 截图、性能测试数据、运维 SLA。
            *   *坚果云*：展示官方报价单截图、功能对比差异。
        *   **成本明细表**：列出 3 年期 TCO 对比（Nextcloud vs SaaS），突出长期节省金额。
        *   **风险与对策**：专门章节讨论带宽瓶颈、运维人力、数据备份安全性。
        *   **实施计划**：如果选择 Nextcloud，列出第一周、第一月、第一季度的实施里程碑。
    2.  **内部评审**：邀请 CTO/技术总监及财务代表审阅，重点审查成本数字和运维承诺的可行性。
    3.  **修订定稿**：根据反馈修改措辞，确保专业性。
*   **依赖**: 
    *   步骤 5 完成。
*   **预期产出**: 
    *   完整的《团队文件协作方案选型报告》(PDF/Word)。
    *   附录：原始测试数据、报价单扫描件、配置代码片段。
*   **验收方式**: 
    *   报告包含所有必需要素（推荐、备选、淘汰、成本）。
    *   所有数据均有出处（引用阶段 02 或步骤 3 的报价）。
    *   通过内部评审会议，获得管理层批准进入“采购/部署”阶段。

## 关键检查点 (Checkpoints)

| 检查点 | 时间点 | 关键问题 | 失败后果/应对 |
| :--- | :--- | :--- | :--- |
| **CP1: POC 功能达标** | 步骤 1 结束 | 版本管理和权限控制是否完全满足“细粒度”要求？ | 若不满足，需重新评估 Nextcloud 配置或考虑更换开源方案（如 Seafile），或直接转向 SaaS。 |
| **CP2: 性能可行** | 步骤 2 结束 | 在预算内的带宽配置下，30 人并发体验是否可接受？ | 若不可接受，需在报告中明确标注“需额外增加带宽成本”或“需引入 CDN 架构”，并更新 TCO。 |
| **CP3: 报价落地** | 步骤 3 结束 | 坚果云企业版含 5TB 存储的真实报价是否超过 ¥30,000？ | 若超过，则 SaaS 方案直接降级为“不推荐”，简化后续对比工作；若未超过，则保留为强力备选。 |
| **CP4: 运维共识** | 步骤 4 结束 | 团队是否有足够人力承接 Nextcloud 运维？ | 若无专人，需在报告中强烈建议外包运维或购买商业支持服务（虽可能增加成本，但仍在预算内），否则应倾向 SaaS。 |
