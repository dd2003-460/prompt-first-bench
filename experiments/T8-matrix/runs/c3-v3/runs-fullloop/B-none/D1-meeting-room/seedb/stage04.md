# 会议室预约系统选型最终报告

**项目名称**：30人研发团队会议室预约系统建设
**报告日期**：2023年10月
**适用对象**：IT部门、研发管理层、行政支持团队

---

## 1. 推荐方案（单一最佳选择）

### **核心推荐：Cal.com Self-Hosted (Docker Compose)**

#### **核心理由：**
1.  **完全满足硬性预算约束**：作为开源软件，License 费用为 ¥0。仅需承担云服务器基础设施成本，年度总显性成本可控制在 **¥2,500 - ¥3,000** 区间，远低于 ¥20,000 的预算上限，留有极大的缓冲空间用于应对云资源涨价或扩容。
2.  **完美契合三端与日历集成需求**：
    *   **Web/PWA 原生支持**：Cal.com 基于 Next.js 开发，天然支持 Web 访问，并可通过 PWA (Progressive Web App) 机制在 macOS 和 Windows 上实现“桌面应用”体验（无需开发独立客户端），完美覆盖三端要求。
    *   **双日历深度集成**：原生内置 Google Calendar 和 Microsoft 365/Outlook 的双向同步插件，无需额外开发即可实现忙闲状态实时同步和会议创建回写。
3.  **数据主权与安全**：自托管部署在公司内部服务器，用户数据和会议记录不出内网，符合研发团队对代码/会议敏感信息的安全合规要求。
4.  **高扩展性与门禁联动潜力**：提供标准的 Webhook API，便于后续通过轻量级中间件对接门禁系统（加分项），且无 SaaS 厂商的功能限制或席位费陷阱。

## 2. 备选方案

若 Cal.com 因技术栈复杂性（如 Node.js/Docker 运维门槛）被 IT 团队否决，以下两个方案可作为备选：

### **备选方案 A：Resource Guru (SaaS 版)**
*   **类型**：商业 SaaS 订阅服务
*   **优势**：
    *   **零运维**：无需维护服务器、SSL 证书或数据库备份，开箱即用。
    *   **界面友好**：UI 设计精美，拖拽式操作，员工学习成本极低。
    *   **集成成熟**：官方直接支持 GCal 和 Outlook 集成，稳定性经过大规模验证。
*   **劣势**：
    *   **成本较高**：按席位收费。30人团队通常需购买 Business 或 Enterprise 套餐，预估年费在 **¥8,000 - ¥15,000** 之间（取决于汇率和功能模块），虽在预算内但占比过高，且随人数增加成本线性上升。
    *   **数据出境风险**：数据存储于海外服务器，可能不符合某些企业对数据本地化的严格要求。
    *   **定制化受限**：门禁联动需依赖其高级 API 权限，且受限于第三方接口频率限制。

### **备选方案 B：飞书/钉钉 自带会议室功能 + 手动日历绑定**
*   **类型**：企业协作平台内置功能
*   **优势**：
    *   **零额外采购成本**：如果公司已全员使用飞书或钉钉，此功能免费。
    *   **无缝协作**：预约后可直接发起视频会议，消息通知直达 IM。
    *   **移动端体验极佳**：原生 App 体验优于 PWA。
*   **劣势**：
    *   **非专业资源管理**：其会议室功能更偏向于“日程备注”，缺乏专业的资源冲突锁定逻辑（例如无法严格防止两人同时预订同一物理房间，除非依赖人工协调）。
    *   **跨平台隔离**：仅适用于已接入该 IM 体系的用户。对于习惯使用 Outlook 且未深度绑定 IM 的研发人员，体验割裂。
    *   **门禁联动极难实现**：IM 平台的 Webhook 能力有限，难以精细控制硬件门禁指令。

## 3. 淘汰理由（未入选候选排除依据）

| 候选方案 | 淘汰理由 |
| :--- | :--- |
| **BookRoom / Acuity Scheduling** | **成本与功能不匹配**。Acuity 免费版功能受限，付费版价格昂贵；BookRoom 虽便宜但 UI 陈旧，且对 Outlook 集成的稳定性口碑较差，存在同步延迟风险。 |
| **自研 React/Vue 前端 + Node/Python 后端** | **ROI 极低，工期不可控**。开发一个具备日历双向同步、冲突检测、多端适配、用户权限管理的系统，预计需 2-3 名全栈工程师投入 2-3 个月（约 6-9 人月）。人力成本远超 ¥20,000 预算，且后续维护负担沉重，违背“快速交付”原则。 |
| **Microsoft Bookings (M365 内置)** | **生态锁定严重**。虽然能解决 Outlook 用户问题，但对 Google Calendar 用户的支持极弱（需复杂配置或单向同步）。此外，它主要服务于外部客户预约，内部会议室资源管理功能薄弱，无法有效区分不同会议室的设备属性。 |
| **传统 OA 系统（如泛微、致远）** | **架构过重，响应缓慢**。此类系统实施周期长，审批流程复杂，且移动端体验往往较差，不适合研发团队追求敏捷的工作风格。 |

## 5. 风险与缓解措施

| 风险类别 | 具体风险描述 | 发生概率 | 影响程度 | 缓解措施 |
| :--- | :--- | :--- | :--- | :--- |
| **技术兼容性** | 公司 Outlook 为本地 Exchange Server 而非 M365 Cloud，导致 OAuth 双向同步失败。 | 中 | 高 | **前置调研**：在项目启动前一周，必须由 IT 管理员确认邮件架构。<br>**降级方案**：若为本地 Exchange，启用 Cal.com 的 iCal 订阅功能实现“单向读取忙碌状态”，并通过脚本定期将 Cal.com 新创建的会议批量写入 Exchange（需开发简易脚本，耗时 < 4h）。 |
| **数据安全** | 服务器遭受 DDoS 攻击或黑客入侵，导致系统瘫痪或数据泄露。 | 低 | 高 | **网络层防护**：启用云厂商免费的 DDoS 基础防护；安全组仅开放 80/443/22，限制 SSH 源 IP。<br>**数据备份**：配置每日凌晨自动执行 `pg_dump` 导出 PostgreSQL 数据库至 OSS，保留最近 7 天备份。 |
| **用户体验** | 员工习惯旧流程，抵触使用新系统，导致会议室闲置或冲突频发。 | 中 | 中 | **强制切换期**：设定 2 周过渡期，期间旧 Excel/白板登记停止生效。<br>**激励措施**：前两周正确使用系统的团队可获得小额团建基金奖励。<br>**极简引导**：制作 1 分钟 GIF 动图教程嵌入登录页。 |
| **运维中断** | Docker 容器崩溃或服务器宕机，导致无法预约。 | 低 | 高 | **高可用策略**：配置 `systemd` 或 `docker restart policy: always` 确保容器自动重启。<br>**监控告警**：部署 UptimeRobot 或阿里云云监控，当 HTTP 状态码非 200 时立即发送短信/邮件给 IT 负责人。 |
| **门禁联动失败** | 门禁系统 API 不稳定或协议不兼容，导致开门指令丢失。 | 中 | 低 | **非阻塞设计**：门禁联动设为“尽力而为”模式。即使开门指令失败，会议仍可正常进行（员工可找前台协助）。<br>**重试机制**：中间件服务设置指数退避重试逻辑，并在 Cal.com 会议详情中标记“门禁状态：待确认”。 |
