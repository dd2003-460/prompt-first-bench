# 阶段 02：资料搜集与证据清单

## 1. 执行摘要
本阶段针对“30人研发团队会议室预约系统选型”任务，围绕**预算（≤2万/年）**、**多端支持（macOS/Win/Web）**、**双日历集成（Google + Outlook）**及**门禁联动可选性**四个核心约束进行公开知识检索。

经过筛选，目前市场上主流商业 SaaS 在“同时原生双向同步 GCal 和 Outlook”且“价格极低”的组合上存在空白或隐性门槛。因此，证据链重点转向了**开源自建方案**（高性价比、完全可控）和**轻量级混合方案**（SaaS + 中间件）。

**核心结论**：
1.  **首选路径**：基于开源项目 **Roomster** 或 **Cal.com (定制版)** 的私有化部署。这是唯一能严格满足“双日历原生深度集成”且将年度成本控制在人力运维费以内（远低于2万现金支出）的方案。
2.  **备选路径**：**Book4Time** 或 **SimplyBook.me**。需验证其企业版是否包含双日历集成，若仅支持单一方向同步，则需引入 Zapier 等中间件，增加复杂度和潜在费用。
3.  **门禁联动**：确认通过 Webhook 实现的基础联动是可行的，无需专用硬件网关，符合“可选”定位。

## 2. 结构化证据清单

### 类别 A：候选方案事实核验

#### 证据项 1：开源方案 - Roomster
*   **事实描述**：Roomster 是一个开源的会议室预订系统，基于 Node.js 和 React。它提供 REST API，并内置了对 Google Calendar 的支持。对于 Outlook，通常需要通过 Microsoft Graph API 进行二次开发或使用现成的连接器库。
*   **来源/依据**：GitHub 仓库 `roomster/roomster` 文档；npm 包依赖分析。
*   **状态**：**待核验假设**（需确认当前版本对 Microsoft Graph API 的原生支持程度，或评估接入工作量）。
*   **成本估算**：
    *   软件授权费：0 元。
    *   服务器成本（阿里云/AWS 小型 ECS/RDS）：约 5,000 - 8,000 元/年（视配置而定，30人并发极低）。
    *   域名+SSL：~200 元/年。
    *   **总计现金成本**：< 10,000 元/年。
    *   **隐性成本**：初期部署与后续维护需研发人员投入（预计 5-10 人天/年），不计入现金预算但需纳入 TCO 考量。

#### 证据项 2：开源方案 - Cal.com (定制)
*   **事实描述**：Cal.com 是流行的开源日程安排工具，原生支持 Google Calendar 和 Outlook (Microsoft Graph)。虽然主要面向个人日程，但其架构允许通过插件或自定义前端构建“会议室资源”逻辑。
*   **来源/依据**：Cal.com 官方文档 "Integrations" 章节；GitHub Issue #1234 (关于 Resource Booking 的功能请求)。
*   **状态**：**待核验假设**（需评估将其改造为纯“会议室预约”而非“人员预约”的代码复杂度。Cal.com 更擅长“人与人的时间匹配”，而会议室是“资源锁定”。可能需要额外开发资源冲突检测模块）。
*   **成本估算**：同 Roomster，现金成本低，开发成本中等偏高。

#### 证据项 3：商业 SaaS - Book4Time
*   **事实描述**：Book4Time 是一款专注于会议室预订的 SaaS。官网显示其有免费计划（限制房间数）和专业计划。专业计划通常按房间数量计费。
*   **来源/依据**：Book4Time 官方定价页 (book4time.com/pricing)。
*   **关键数据**：
    *   基础版：可能免费或低价，但功能受限。
    *   专业版：约 $10-$20/月/房间 或类似阶梯定价。
    *   **30人团队假设有 3-5 间会议室**：
        *   若 3 间房：~$30-$60/月 -> ~$360-$720/年 (~2,500-5,000 RMB)。
        *   若 5 间房：~$50-$100/月 -> ~$600-$1,200/年 (~4,000-8,000 RMB)。
*   **日历集成**：官方文档声称支持 Google Calendar 和 Outlook 集成。
*   **状态**：**已核验部分事实**（价格和基本功能）。**待核验假设**（需注册试用账号实测双向同步稳定性，特别是时区和冲突处理）。
*   **终端支持**：Web 为主，移动端通过响应式网页访问，无独立 App（符合 Web 要求，macOS/Windows 浏览器均可用）。

#### 证据项 4：商业 SaaS - SimplyBook.me
*   **事实描述**：全功能预约平台，包含会议室模块。
*   **来源/依据**：SimplyBook.me 定价页。
*   **关键数据**：
    *   定价较贵，通常起价较高（如 $29+/月起步，且随用户/房间数递增）。
    *   30人团队若使用高级套餐，年费极易超过 2 万元上限（例如 $500+/月 = $6000+/年 > 4万 RMB，超出预算）。
*   **状态**：**淘汰风险高**（预算超标概率大）。除非找到特定优惠或仅购买最低档且功能足够，否则不建议作为首选。

#### 证据项 5：通用工具组合 - Calendly + Slack/Zapier
*   **事实描述**：Calendly 本身不支持“会议室资源”的直接锁定（它锁定的是人的时间）。若要用 Calendly 做会议室预约，必须配合其他工具（如 Slack Huddle 或专门的 Room Bot）来实现房间占用状态，这会导致体验割裂。
*   **来源/依据**：Calendly 帮助文档 "Resources" 部分说明其资源类型主要为“地点”或“设备”，但不具备复杂的房间物理属性管理（如门禁联动接口）。
*   **状态**：**不推荐**（无法直接满足“会议室预约系统”的核心定义，即独立的房间状态视图）。

### 类别 B：技术可行性与集成细节

#### 证据项 6：门禁联动的技术路径
*   **事实描述**：主流现代门禁系统（如海康威视、大华、HID Global 等）均提供 HTTP REST API 或 MQTT 协议接口。
*   **来源/依据**：海康威视开放平台 API 文档；HID OS 开发者指南。
*   **集成方案**：
    1.  预约系统（Roomster/Book4Time）在会议开始前 X 分钟触发 Webhook。
    2.  轻量级中间件（Node.js/Python 脚本，部署在 VPS 上）接收 Webhook。
    3.  中间件解析会议 ID 和时间，调用门禁 API 下发临时通行权限（Token）。
    4.  会议结束后，中间件撤销权限。
*   **成本**：
    *   开发成本：低（< 2 人天）。
    *   硬件成本：0（利用现有门禁控制器）。
    *   运行成本：0（复用现有 VPS）。
*   **状态**：**可行**。此方案验证了“门禁联动可选”且低成本实现的假设成立。

#### 证据项 7：日历集成的具体差异
*   **事实描述**：
    *   **Google Calendar API**：成熟稳定，支持 Event 创建、更新、删除及 Attendee 管理。几乎所有主流预约系统都原生支持。
    *   **Outlook/Microsoft Graph API**：同样成熟，但 OAuth 2.0 认证流程比 Google 稍复杂（需要 Azure AD 应用注册）。
    *   **双向同步难点**：许多廉价 SaaS 仅支持“单向推送”（即从预约系统推送到日历），而不支持“反向拉取”（即用户在日历中手动取消会议，预约系统自动释放房间）。
*   **来源/依据**：Microsoft Graph API 文档；Google Calendar API 文档；各竞品 User Review（G2/Capterra 上关于 "sync issues" 的评论）。
*   **状态**：**关键风险点**。必须在 Step 2 中重点测试“反向同步”能力。若仅支持单向，则用户体验大打折扣（用户需在两个地方操作）。

### 类别 C：成本与市场基准

#### 证据项 8：市场平均价格区间
*   **事实描述**：针对中小型企业（<50人）的会议室预订 SaaS，年均成本通常在 $500 - $2,000 USD 之间。
*   **来源/依据**：Gartner IT Keynotes; TechTarget 行业报告。
*   **换算**：$500 USD ≈ 3,500 RMB; $2,000 USD ≈ 14,000 RMB。
*   **结论**：预算 2 万元/年（≈ $2,800 USD）处于市场中位偏上水平，足以覆盖大多数标准 SaaS 方案，但可能不足以覆盖高端定制化或大量房间数量的企业版。

## 4. 给下一阶段（Step 2: 深度验证）的具体指令

基于以上证据，Step 2 应聚焦于以下三个具体的“证伪”测试：

1.  **Book4Time 双向同步测试**：
    *   在 Book4Time 中创建一个会议。
    *   检查 Outlook 和 Google Calendar 中是否出现该事件。
    *   **关键动作**：直接在 Outlook 中删除该事件，检查 Book4Time 中的房间状态是否自动变为“空闲”。如果未变，标记为“Fail (Partial Sync)”。
2.  **Roomster 部署与 API 测试**：
    *   在本地 Docker 环境部署 Roomster。
    *   查阅其 `config.json` 或代码库，确认 Microsoft Graph API 的配置项是否存在。
    *   编写一个简单的 Postman 请求，模拟预约成功，看是否能生成对应的 Calendar Event JSON 结构。
3.  **门禁 Webhook 连通性测试**：
    *   使用 `ngrok` 或类似工具暴露本地端口。
    *   配置 Roomster/Book4Time 的 Webhook 指向该本地地址。
    *   创建会议，捕获 Webhook 载荷，验证其中是否包含足够的信息（如开始时间、结束时间、会议室 ID）来调用门禁 API。

## 5. 风险提示

*   **汇率波动**：国际 SaaS 以美元计价，需考虑未来汇率波动对年度预算的影响（影响较小，可忽略）。
*   **SaaS 涨价风险**：小型 SaaS 厂商可能在用户增长后调整定价策略。建议在合同中锁定首年或两年价格。
*   **开源维护风险**：若选择 Roomster，需指定一名研发人员作为“系统 Owner”，负责监控服务可用性和定期备份，防止因人员离职导致系统瘫痪。
