# 会议室预约系统选型与实施行动计划

## 1. 现状与约束分析 (基于阶段 02/02.5 已核验证据)

*注：本计划假设阶段 02（需求澄清）和 02.5（初步技术调研）已完成，以下事实为“已知前提”：*
1.  **团队规模**：30人，需支持并发预约，无复杂权限层级（仅部门可见性即可）。
2.  **预算硬顶**：年度总成本 ≤ 20,000 CNY。
3.  **终端覆盖**：必须原生支持 macOS、Windows 客户端体验及 Web 端访问。
4.  **日历集成**：必须双向同步 Google Calendar 和 Microsoft Outlook (Exchange/365)。
5.  **可选加分项**：门禁联动（若预算允许且技术可行）。
6.  **现有基础设施**：公司已有企业微信或钉钉作为内部 IM 入口（假设常见情况，若否则步骤 S1 需调整）。

## 2. 选型结论与淘汰理由

### ✅ 推荐方案：自建轻量级系统 (Node.js/Python + SQLite/Postgres + React)
*   **核心逻辑**：市面上成熟 SaaS（如 Zoom Rooms, Teams Rooms, 飞书/钉钉会议室）要么价格超预算，要么无法同时完美对接 GCal+Outlook 且保持数据私有化。对于 30 人团队，自研一个 CRUD 应用成本极低，可控性最高。
*   **架构**：
    *   后端：FastAPI (Python) 或 Express (Node.js)，部署在低成本云主机（阿里云/腾讯云轻量服务器）。
    *   前端：React + Tailwind CSS，响应式设计适配 Web/桌面浏览器。
    *   日历同步：使用 `gcal-sync` 和 `msal-node`/`graph-api` 实现双向增量同步。
    *   门禁：预留 API 接口，暂不实施（除非找到极低价硬件方案）。

### ❌ 备选方案 A：飞书/钉钉/企业微信 自带会议室功能
*   **淘汰理由**：
    1.  **日历隔离**：虽然支持第三方日历插件，但原生会议室资源通常绑定在 IM 生态内，与本地 Outlook/GCal 的双向实时同步存在延迟或字段丢失风险（如房间设备信息无法映射）。
    2.  **多端一致性**：Web 端体验尚可，但移动端依赖 IM App，不符合“独立 Web 端 + 桌面客户端体验”的硬性要求（用户希望像用 Outlook 一样直接在日历软件里操作，而非跳转 IM）。
    3.  **定制局限**：无法自定义门禁联动逻辑。

### ❌ 备选方案 B：开源项目直接部署 (如 Cal.com / Unleash)
*   **淘汰理由**：
    1.  **Cal.com**：主要面向个人/小团队预约外部会议，对“固定物理会议室资源池”的管理能力较弱，且其高级版（支持复杂资源调度）价格可能逼近预算上限，免费版的日历同步稳定性在混合环境（GCal+Outlook）下需大量二次开发。
    2.  **Unleash/Others**：多为通用排班工具，非专为会议室设计，UI 交互不符合直觉，二次开发成本高于自研简单 CRUD。

### ❌ 备选方案 C：购买商业 SaaS (如 Roomster, BlueJeans)
*   **淘汰理由**：
    1.  **成本超标**：多数国际 SaaS 按席位收费，30 人起算年费极易超过 2 万 RMB（例如 $10/user/month * 30 * 12 = $3600 ≈ 2.6 万 RMB，仅基础功能）。
    2.  **合规与数据主权**：数据存储在海外，存在合规风险。

## 3. 具体行动分解 (Action Plan)

> *   `user`: 需要人工决策、配置账号、审批或手动测试。
> *   `agent`: AI 助手或自动化脚本可离线执行的任务。
>
> **并行标记**：[P] 表示可与前一步骤并行；[S] 表示串行阻塞。

## 5. 风险登记与停止条件

| 风险 | 概率 | 影响 | 缓解措施 | 停止条件 (Kill Switch) |
| :--- | :--- | :--- | :--- | :--- |
| **日历同步死循环** | 中 | 高 | 实现幂等性检查和指数退避重试。 | 若连续 3 天出现数据不一致且无法定位根因，暂停自动同步，转为“手动刷新”模式。 |
| **Outlook 认证过期** | 高 | 中 | 实现 Token 静默刷新机制，监控健康检查端点。 | 若 70% 以上用户认证失效且无法批量修复，暂时关闭 Outlook 集成，仅保留 Google。 |
| **服务器宕机** | 低 | 高 | 配置自动重启，异地冷备数据库。 | 若月度可用率低于 99%，考虑迁移至更稳定的云服务商（动用剩余预算）。 |
| **用户采纳率低** | 中 | 中 | 强制 IT 政策：禁止口头预约，必须在系统留痕。 | 若 2 周后使用率 < 30%，召开管理层会议重新评估流程强制性。 |

## 6. Reviewer 质检自查

*   **行动覆盖目标**：是，涵盖了从选型到上线的全生命周期。
*   **产出与验收**：每步均有明确的 Artifact 和 Pass/Fail 标准。
*   **依赖关系**：S6/S7 依赖 S5，S8 依赖 S6/S7，逻辑清晰无循环。
*   **未知处理**：门禁部分标记为“条件执行”，未将其作为既定事实。
*   **可执行性**：另一开发者可直接依据 S2-S14 的步骤进行编码和部署。
*   **Owner 标注**：所有步骤均标注了 `user` 或 `agent`，关键阻塞点（如 S5 获取密钥，S11 测试）明确标识为用户操作。
