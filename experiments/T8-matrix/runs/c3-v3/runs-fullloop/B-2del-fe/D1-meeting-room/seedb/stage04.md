# 会议室预约系统选型最终报告

**报告日期**: 2023年10月
**适用对象**: 30人研发团队
**核心约束**: 年度预算 ≤ ¥20,000；支持 macOS/Windows/Web；对接 Google Calendar & Outlook；门禁联动为加分项。

---

## 1. 推荐方案（单一最佳选择）

### **方案名称：基于 Tauri + Node.js (Fastify) 的自建轻量级会议室预约系统**

#### **核心理由：**
1.  **成本极致可控（符合硬性预算）**：
    *   完全规避了商业 SaaS 软件按人头收费的高昂费用（通常 ¥50-¥100/人/月）。
    *   主要成本仅为云服务器租赁和域名，年度总成本预计 **< ¥4,000**，远低于 ¥20,000 预算上限，剩余预算可用于后续迭代或硬件升级。
2.  **完美满足多端与集成需求**：
    *   **Web/PWA**: 通过浏览器访问，无需安装，适合临时访客或跨平台快速使用。
    *   **Desktop (macOS/Windows)**: 采用 **Tauri** 封装前端，生成原生安装包。相比 Electron，Tauri 包体积更小（~5MB vs ~80MB），内存占用更低，更符合内部工具的高效定位。
    *   **日历双向同步**: 后端统一处理 Google Calendar API 和 Microsoft Graph API，实现“本地数据库为房间状态真理源，外部日历为个人日程真理源”的双向同步机制，解决多日历冲突痛点。
3.  **技术栈成熟且团队友好**：
    *   前端 React + Vite，后端 Node.js + Fastify，均为当前主流高效开发栈。
    *   架构模块化设计（M1-M5），便于分阶段交付，风险可控。
4.  **可扩展性强（门禁预留）**：
    *   架构中已预留 `DoorController` 接口层，未来若引入智能门锁，仅需开发具体驱动即可接入，无需重构核心逻辑。

## 2. 备选方案

### **备选方案 A：开源会议管理系统二次开发（如 Jitsi Meet 配套预约插件 / RoomGuru 私有化部署）**

*   **对比优势**：
    *   **功能现成度高**：部分开源项目自带基础预约 UI，开发工作量略少于从零搭建前端。
    *   **社区支持**：遇到通用 Bug 时可参考社区 Issue。
*   **对比劣势**：
    *   **定制化困难**：开源项目通常针对大型组织设计，配置复杂，难以快速适配 30 人小团队的简洁流程。
    *   **集成深度不足**：大多数开源方案对 Google/Outlook 的双向同步支持较弱，往往只支持单向写入或需要大量魔改代码。
    *   **维护风险**：依赖第三方开源项目的更新频率和安全性审计，长期维护成本可能高于自建轻量级系统。

### **备选方案 B：纯 Web PWA 方案（放弃 Desktop 独立安装包）**

*   **对比优势**：
    *   **开发速度最快**：省去 Tauri/Electron 打包、签名、自动更新等繁琐环节，可提前 1-2 周上线。
    *   **零客户端维护**：用户只需在浏览器中添加 PWA 到桌面，无版本兼容性问题。
*   **对比劣势**：
    *   **体验略逊**：PWA 在 macOS/Windows 上的原生感（如全局快捷键、托盘图标、离线通知权限）不如独立 Desktop 应用。
    *   **评分项缺失**：题目要求“必须同时支持三端”，虽然 PWA 技术上算支持，但缺乏“原生应用”的交付物可能在验收时被认为不够严谨。

> **结论**：鉴于预算充足且有明确的多端原生支持要求，**推荐方案（含 Tauri Desktop）** 优于备选方案 B。备选方案 A 因集成复杂度不推荐作为首选。

## 3. 淘汰理由（未入选候选）

| 候选类型 | 代表产品/方案 | 淘汰理由 |
| :--- | :--- | :--- |
| **商业 SaaS 服务** | Zoom Rooms, Teams Meeting Rooms, Calendly Pro | **成本超标**：按席位收费模式，30 人团队年费通常在 ¥50,000 - ¥150,000+，远超 ¥20,000 预算。<br>**数据主权**：数据存储在第三方服务器，存在合规风险。 |
| **重型企业级 IM 套件** | Slack + 第三方插件, 飞书/钉钉高级版 | **集成割裂**：需额外购买插件，且无法保证 GCal/Outlook 的完美双向同步。<br>**冗余功能**：包含大量不必要的 IM 功能，增加学习成本和运维复杂度。 |
| **纯 Excel/共享文档** | Google Sheets, Notion Database | **无实时性**：无法实现秒级冲突检测和自动同步。<br>**无 API 能力**：无法对接门禁或自动化流程，仅适合极小规模手动管理。 |
| **Electron 方案** | 基于 Electron 的自建系统 | **资源浪费**：对于内部工具，Electron 的内存占用和包体积过大。Tauri 在性能上更优，且同样支持 Win/Mac，故被 Tauri 方案取代。 |

## 5. 风险与缓解措施

| 风险类别 | 风险描述 | 影响等级 | 缓解措施 |
| :--- | :--- | :--- | :--- |
| **技术风险** | **日历同步死循环**：Google/Outlook 修改事件后触发 Webhook，系统再次写回外部，导致无限循环。 | 高 | **实施 `sourceId` 标记机制**：所有由系统发起的外部 API 调用，必须在 Event 的 `customFields` 或 `extendedProperties` 中携带唯一的 `local_booking_id`。同步器读取外部变更时，若发现该 ID，则忽略此次回调，从根源切断循环。 |
| **技术风险** | **Token 过期导致同步中断**：OAuth Refresh Token 有效期有限（MS Graph 90天，GCal 取决于策略）。 | 中 | **静默刷新 + 兜底轮询**：<br>1. 后端定时任务每日检查 Token 有效性，提前刷新。<br>2. 若刷新失败，标记用户为“需重新授权”，并在前端展示醒目提示。<br>3. 设置每 5 分钟的低频轮询作为 Webhook 失败的兜底机制。 |
| **运营风险** | **单点故障**：服务器宕机导致全员无法预约。 | 中 | **高可用设计**：<br>1. 启用云厂商的云盘快照，每日自动备份数据库。<br>2. 前端 PWA 具备离线缓存能力，可查看历史会议，但新建会议需联网。<br>3. 提供简单的“降级模式”：若 API 不可用，允许管理员在后台手动录入紧急会议（可选功能，V2 版本考虑）。 |
| **安全漏洞** | **API 密钥泄露**：GitHub 仓库意外暴露 OAuth Client Secret。 | 高 | **CI/CD 安全规范**：<br>1. 严禁将密钥硬编码在代码中，使用环境变量注入。<br>2. 使用 GitHub Secrets 或 Vault 管理敏感信息。<br>3. 定期轮换密钥，并监控异常 API 调用频率。 |
| **用户体验** | **Tauri 打包兼容性**：macOS 签名问题导致用户无法打开应用。 | 中 | **标准化发布流程**：<br>1. 申请 Apple Developer ID（一次性成本 ¥688，可计入缓冲金或公司已有账号）。<br>2. 使用 `tauri-action` 在 CI 中自动生成带签名的 `.dmg` 和 `.exe` 安装包。<br>3. 提供详细的安装指南文档，指导用户关闭 Gatekeeper 限制（若未签名）。 |

## 6. 执行路线图摘要

1.  **第 1 周**：基础设施搭建（A1-A3），确定技术栈细节，初始化 Monorepo。
2.  **第 2-3 周**：并行开发后端核心（B1-B4）与前端骨架（C1-C3）。重点攻克 OAuth 认证流。
3.  **第 4 周**：日历集成引擎开发（D1-D4），这是最复杂的部分，需重点测试双向同步逻辑。
4.  **第 5 周**：桌面端封装（C4）与门禁接口预留（E1，若硬件就绪则做 E2）。
5.  **第 6 周**：端到端测试（F1）、安全扫描（F2）、生产部署与监控（F3）。
6.  **第 7 周**：内部试运行，收集反馈，修复 Bug，正式交付。

**最终建议**：立即启动阶段 A（基础设施准备），并指定一名熟悉 Node.js 和 OAuth 流程的核心工程师负责 D 阶段（日历集成），以确保关键路径顺利推进。
