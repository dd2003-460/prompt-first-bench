# 阶段 03：具体行动分解（无 owner 组件）

## 1. 执行摘要与策略概览

基于阶段 02 的证据，本阶段将“选定会议室预约系统”这一目标拆解为 **5 个核心可执行步骤**。

**核心策略**：
1.  **主路径 (Primary Path)**：验证首选方案 **Roomle** 的落地可行性（合规、本地化、API 对接）。
2.  **并行路径 (Parallel Path)**：同步获取内部基线数据（会议室确切数量、现有门禁型号），以消除 G6 和 G3 的假设风险。
3.  **备选触发机制**：若主路径在关键验收点（如发票/合规）失败，立即切换至备选方案评估流程。

---

## 2. 详细行动步骤分解

### 步骤 1：内部基线数据确认与需求冻结
*   **输入**: 阶段 02 中的假设（5间会议室）、团队规模（30人）、现有IT基础设施清单。
*   **动作**:
    1.  向行政/设施管理部门发出正式询问，确认真实会议室数量（N_rooms）。
    2.  向 IT 部门索取当前使用的门禁控制系统品牌及型号（例如：海康威视 DS-K系列、大华、或传统继电器控制）。
    3.  确认团队中 Google Calendar 与 Outlook 用户的具体比例（用于测试覆盖范围）。
    4.  确认财务对“海外SaaS服务采购”的合规要求（是否必须开具国内增值税专票，或接受形式发票 Proforma Invoice + 代扣代缴流程）。
*   **依赖**: 无（这是所有后续技术验证的基础）。
*   **预期产出**: 《内部基线数据确认单》，包含：确切房间数、门禁型号、日历分布比例、财务合规红线。
*   **验收方式**: 获得行政和IT负责人的书面邮件或工单确认。
*   **并行性**: **可与步骤 2 并行执行**。

### 步骤 2：Roomle 深度功能与合规验证（POC 准备）
*   **输入**: 步骤 1 产出的基线数据（特别是房间数和财务要求）、阶段 02 识别的风险点（中文支持、数据出境）。
*   **动作**:
    1.  **注册试用账号**: 使用公司邮箱注册 Roomle Free/Trial 版本。
    2.  **UI 本地化检查**: 检查 Web 端界面是否有简体中文选项；若无，评估英文界面的学习成本是否可接受。
    3.  **日历集成实测**:
        *   创建一个测试会议室。
        *   分别用 Google Calendar 和 Outlook 账户进行双向同步配置。
        *   模拟冲突场景：在 A 日历预订，检查 B 日历是否即时锁定该时间段。
    4.  **API 文档审查**: 下载 Roomle API 文档，重点查找 `POST /bookings` 和 `Webhooks` 部分，确认能否通过 HTTP Request 触发外部设备（为门禁联动做理论验证）。
    5.  **销售/客服咨询**: 发送一封英文邮件给 Roomle 销售，明确询问：
        *   "Do you support issuing invoices for Chinese entities?" (发票问题)
        *   "What is the data residency policy for EU servers regarding PIPL compliance?" (合规问题)
        *   "Is there a discount for 5+ rooms?" (价格谈判)
*   **依赖**: 步骤 1 中的财务合规红线（决定是否需要发票）。
*   **预期产出**: 《Roomle POC 验证报告》，包含：截图证明日历双向同步成功、API 能力评估结论、销售关于发票和合规的官方回复。
*   **验收方式**: 日历同步测试通过（冲突检测无误）；收到销售关于发票可行性的明确答复。
*   **并行性**: **可与步骤 1 并行执行**（若步骤1未出结果，先按默认假设执行，后续修正）。

### 步骤 3：门禁联动技术方案预研（条件触发）
*   **输入**: 步骤 1 确认的门禁品牌型号、步骤 2 确认的 Roomle API 能力。
*   **动作**:
    1.  **方案 A (原生插件)**: 搜索 Roomle 市场或社区，确认是否存在针对该门禁品牌的现成连接器。（概率低，但需确认）
    2.  **方案 B (中间件开发)**:
        *   若门禁支持 TCP/IP 串口通信或提供 REST API：设计一个简单的 Node.js/Python 微服务。
        *   逻辑：监听 Roomle Webhook -> 解析 JSON -> 调用门禁 API 开门/关门。
        *   估算开发工作量（人天）。
    3.  **方案 C (硬件替代)**: 评估是否购买一个通用的 IoT 网关（如 ESP32 模组或商业智能插座/门锁控制器），将其接入门禁信号线，并让该网关接收来自 Roomle API 的指令。
    4.  **成本估算**: 计算中间件服务器资源（极低）或硬件采购成本。
*   **依赖**: 步骤 1（门禁型号）、步骤 2（API 可用性）。
*   **预期产出**: 《门禁联动实施草案》，包含推荐的技术路径（A/B/C）、预估开发时间、额外硬件成本。
*   **验收方式**: 确定一条可行的技术路径，且总成本（含硬件）不超过预算剩余空间（约 15,000 RMB）。
*   **并行性**: **必须在步骤 1 和 2 完成后执行**（因为需要知道门禁型号和API细节）。

### 步骤 4：备选方案快速复核（Risk Mitigation）
*   **输入**: 步骤 2 的结果。如果 Roomle 在“发票”或“中文支持”上存在致命缺陷（即无法在国内合规报销或团队完全无法使用英文界面）。
*   **动作**:
    1.  **触发条件判断**:
        *   若 Roomle 无法满足财务合规（必须开国内发票） -> 启动此步骤。
        *   若 Roomle 满足 -> 跳过此步骤，直接进入步骤 5。
    2.  **备选 1 评估 (Frontdesk)**: 重新核算 Frontdesk Starter 计划的价格。尝试联系销售，询问对于 5 间小会议室是否有初创/小团队折扣，争取降至 20,000 RMB 以内。
    3.  **备选 2 评估 (国内 SaaS 变通)**: 调研飞书/钉钉是否支持通过第三方插件（如 Zapier 或自建脚本）实现 Google Calendar 单向同步 + 手动处理冲突。评估这种“半自动”方案的维护成本和用户体验损失。
*   **依赖**: 步骤 2 的结论。
*   **预期产出**: 《备选方案可行性简报》（仅在触发时生成）。
*   **验收方式**: 找到一个能同时满足“预算 ≤ 2万”、“双日历支持（至少单向）”、“合规”的方案。
*   **并行性**: **串行执行**（仅在主路径受阻时执行）。

### 步骤 5：选型报告撰写与决策定稿
*   **输入**: 步骤 1-4 的所有产出物（基线数据、POC 报告、门禁草案、备选分析）。
*   **动作**:
    1.  **成本明细表制作**:
        *   列出推荐方案（Roomle）的年费、潜在门禁硬件/开发成本、汇率波动预留金。
        *   对比备选方案的成本。
    2.  **风险披露**:
        *   明确列出数据出境风险及缓解措施（如签署 DPA 数据处理协议）。
        *   明确列出语言障碍及缓解措施（如提供内部简易操作手册）。
    3.  **淘汰理由归档**: 引用阶段 02 的证据，清晰说明为何淘汰 Resource Guru、飞书等。
    4.  **最终推荐**: 给出明确的“Go/No-Go”建议。
    5.  **审批流提交**: 将报告提交给 CTO 和 CFO 审批。
*   **依赖**: 步骤 1, 2, 3 (及可能的 4)。
*   **预期产出**: **《会议室预约系统选型报告 v1.0》**。
*   **验收方式**: 报告包含所有必要章节（背景、候选对比、推荐方案、成本、风险、下一步计划），并获得管理层签字批准。
*   **并行性**: **最后一步，串行执行**。

## 3. 关键失败情况与替代路径 (Fallbacks)

| 失败场景 | 触发条件 | 替代路径 (Alternative Path) | 预期影响 |
| :--- | :--- | :--- | :--- |
| **F1: 财务合规阻断** | Roomle 明确表示无法提供中国增值税发票，且公司财务政策禁止无票采购。 | **路径 A**: 转向 **Frontdesk**，极力谈判折扣至预算内。<br>**路径 B**: 转向 **国内 SaaS (飞书/钉钉)**，放弃 Google Calendar 双向同步，改用“iCal 单向订阅 + 人工核对”的低配方案，并在报告中注明体验降级风险。 | 项目延期 1-2 周；或功能妥协（失去自动冲突检测）。 |
| **F2: 门禁对接不可行** | 现有门禁为老旧模拟信号，不支持数字接口，且改造成本超过 1 万元。 | **路径 A**: 放弃门禁联动，仅使用软件预约。在会议室门口张贴二维码，员工扫码签到（利用 Roomle 的 Check-in 功能，若有）。<br>**路径 B**: 采购独立的智能门锁（如小米/凯迪仕智能锁），替换原有机械锁，实现独立控制，不与旧门禁系统打通。 | 增加一次性硬件成本 (~2k-5k RMB)，但简化了系统架构。 |
| **F3: 日历同步不稳定** | POC 测试中发现 Google/Outlook 同步延迟超过 5 分钟，或频繁出现双向冲突漏检。 | **路径 A**: 更换为 **Resource Guru** 的低配版（若能找到仅管理员付费的模式，虽然阶段02判定超预算，但需再次确认是否有“只读用户免费”政策）。<br>**路径 B**: 采用 **开源方案自托管**，利用 CalDAV 协议直接对接 Google/Outlook，稳定性由自己代码保证，但需投入开发资源。 | 若选 B，需额外投入 2-3 人周的开发时间。 |
| **F4: 会议室数量激增** | 步骤 1 确认实际会议室数量为 15 间以上。 | **路径 A**: Roomle Premium 计划成本上升至 ~$5,400/年 (~38k RMB)，严重超预算。<br>**路径 B**: 启用 **开源自托管方案**，此时边际成本趋近于零，仅需服务器费用。 | 推荐方案从 SaaS 变更为 Self-Hosted。 |
