# 会议室预约系统选型与成本分析报告 v1.0

**项目名称**：30人研发团队会议室预约系统选型
**报告日期**：2023年10月
**适用对象**：研发部管理层、IT基础设施团队

---

## 1. 执行摘要 (Executive Summary)

基于对当前市场主流会议室预约工具的深入调研，结合我方硬性约束（年度预算 ≤ 20,000 CNY；支持 macOS/Windows/Web；双向同步 Google Calendar & Outlook），本报告推荐以下方案：

*   **首选推荐方案：Cal.com (开源自托管 + Cloud 混合模式)**
    *   **核心理由**：完全满足三端及双日历同步需求，拥有极高的定制化能力以对接门禁系统。对于30人规模，采用其轻量级云版本或自建Docker容器均可将成本控制在极低水平（< 5,000 CNY/年），远低于预算上限，且数据主权可控。
*   **备选方案：Microsoft Teams Rooms (标准版) + 现有 M365 许可整合**
    *   **理由**：若团队已深度绑定 Microsoft 365 生态，此方案无需额外购买独立SaaS席位，利用现有License即可实现基础预约，零边际软件成本，但Web端体验稍弱于原生Web应用，且对Google Calendar用户支持较差。

**关键结论**：鉴于团队可能同时使用 Google Workspace 和 Microsoft 365，**Cal.com** 是唯一能平等对待两套日历体系且成本最低的合规方案。

## 3. 推荐方案详情 (Recommended Solution)

### 3.1 方案名称：Cal.com

**方案概述**：
Cal.com 是一款现代化的开源日程安排和会议管理工具。它提供 SaaS 云服务，也支持通过 Docker/Kubernetes 自托管。其核心优势在于“日历无关性”，即原生设计就支持多日历提供商的聚合与同步。

#### 功能亮点
1.  **完美三端支持**：
    *   **Web**：响应式设计，在任何现代浏览器中体验极佳。
    *   **macOS/Windows**：作为 Web 应用运行，可通过 PWA (Progressive Web App) 安装到桌面，提供类似原生应用的体验；也可通过 Chrome/Edge 扩展直接嵌入工作流。
2.  **双日历无缝同步**：
    *   原生支持 OAuth 2.0 连接 Google Calendar 和 Microsoft Outlook。
    *   支持“双向同步”：在 Cal.com 创建的会议会实时写入个人日历，反之亦然。
    *   支持多人冲突检测，确保不会重复预订同一会议室资源。
3.  **会议室资源管理**：
    *   可将会议室定义为“资源”（Resource），分配给特定的日历。
    *   支持可视化时间轴查看会议室占用状态。
4.  **门禁联动潜力 (加分项)**：
    *   Cal.com 提供强大的 **Webhooks** 和 **REST API**。
    *   **实施路径**：当会议开始时，Cal.com 触发 Webhook -> 调用内部微服务 -> 该服务调用门禁系统 API (如 ZKTeco/HID REST API) 下发临时通行权限。此开发工作量约为 1-2 人天，成本极低。

#### 实施路径
1.  **部署选择**：
    *   *选项 A (推荐)*：使用 Cal.com Cloud Starter Plan。
    *   *选项 B (极客向)*：在公司内部服务器/Docker Swarm 中自托管 (Open Source License)。考虑到30人规模，自托管几乎零软件授权费，仅需维护服务器成本。
    *   *决策*：为降低运维负担，建议初期采用 **Cloud 版本**，若未来需深度定制门禁逻辑再迁移至自托管。
2.  **配置步骤**：
    *   注册组织账号。
    *   创建“会议室”类型的事件类型 (Event Type)。
    *   每位员工授权 Cal.com 访问其 Google/Outlook 日历。
    *   将会议室实体绑定到公共共享日历。
    *   配置 Webhook 指向内部门禁网关 (可选)。

## 4. 备选方案详情 (Alternative Solutions)

### 4.1 备选方案一：Microsoft Teams Rooms (Standard)

**对比优势**：
*   **零额外软件成本**：如果公司已经购买了包含 Teams Standard 或 E3/E5 的 Microsoft 365 订阅，则无需支付任何额外的会议室软件费用。
*   **原生 Outlook 支持**：与 Outlook 日历深度绑定，同步延迟最低。
*   **硬件协同**：若未来升级智能面板，Teams Rooms 支持最佳。

**对比劣势**：
*   **Google Calendar 支持极差**：Teams 无法原生双向同步 Google Calendar。对于使用 Gmail 的员工，体验断裂，需要手动复制粘贴或使用第三方插件（不稳定）。
*   **Web 端体验一般**：虽然可通过浏览器访问，但交互流畅度不如专门的 Web 预约工具。
*   **门禁联动封闭**：主要依赖微软认证的硬件合作伙伴，自定义 API 接入难度高于 Cal.com。

**成本明细**：
*   软件费：0 CNY (含在现有 M365 License 中)
*   潜在硬件费：0 CNY (仅软件选型)
*   **年度总成本：0 CNY** (前提是全员使用 MS365)

### 4.2 备选方案二：RoomGuru (SaaS)

**对比优势**：
*   **开箱即用**：纯 SaaS，无需运维，UI 美观，移动端体验好。
*   **双日历支持**：官方文档明确支持 Google Calendar 和 Outlook 的集成。
*   **价格透明**：定价相对清晰。

**对比劣势**：
*   **成本风险**：RoomGuru 定价通常为 per room (每间会议室) 或 per user。经查证，其商业版起价较高，30人团队若按人头计费可能接近或超过预算上限。例如，若 $10/user/month，30人即 $3600/year ≈ 25,920 CNY，**略超预算**。需争取折扣。
*   **门禁联动**：提供 Zapier 集成，可实现简单联动，但灵活性不如直接 API。

**成本明细 (预估)**：
*   订阅费：~25,000 CNY (可能需谈判降至 <20,000)
*   **年度总成本：~25,000 CNY (存在超标风险)**

## 5. 淘汰方案分析 (Eliminated Candidates)

| 候选方案 | 淘汰理由 | 违反的硬性条件 |
| :--- | :--- | :--- |
| **Calendly** | **成本过高且功能受限**。<br>1. 商业版价格昂贵，30人团队年费远超 2万 RMB。<br>2. 免费版不支持“资源”（会议室）的高级调度逻辑，难以区分“人忙”和“房间忙”。<br>3. 虽支持双日历，但缺乏原生的会议室可视化管理界面，更像个人日程工具而非空间管理工具。 | 年度预算 > 20,000 CNY |
| **Slack Connectors (Meeting Scheduler)** | **非独立系统，依赖 Slack**。<br>1. 如果团队不使用 Slack，此方案无意义。<br>2. 即使使用 Slack，其预约功能较弱，主要服务于 Slack 内部频道，对外部访客或不使用 Slack 的同事不友好。<br>3. 门禁联动几乎不可能直接实现，需绕道 Zapier。 | 平台依赖性过强，非通用 Web/桌面应用 |
| **Microsoft Outlook "Find a Time" / Book Room** | **仅限 Outlook 生态**。<br>1. 无法让 Google Calendar 用户看到会议室空闲状态。<br>2. 没有独立的 Web 门户供非 Office 用户快速查看和预约。<br>3. 缺乏现代化的 UI/UX，操作繁琐。 | 不支持 Google Calendar 用户的便捷预约 |
| **自研系统 (In-house Development)** | **隐性成本不可控**。<br>1. 30人团队中抽调人力开发，机会成本极高。<br>2. 日历同步的双向一致性处理极其复杂（时区、冲突解决、取消回滚），容易出 Bug。<br>3. 长期维护成本高，且无法保证稳定性优于成熟 SaaS/开源方案。 | 间接成本远超预算，风险过高 |
| **Zoom Meetings (自带预约)** | **定位偏差**。<br>1. Zoom 的核心是视频会议，而非物理空间管理。<br>2. 无法有效管理物理会议室的设备状态（如投影是否故障）。<br>3. 同样面临 Google/Outlook 双向同步的体验割裂问题。 | 功能不匹配，非专用会议室管理系统 |

## 7. 风险与缓解措施 (Risks & Mitigation)

| 风险类别 | 风险描述 | 概率 | 影响 | 缓解措施 |
| :--- | :--- | :--- | :--- | :--- |
| **技术运维** | 自托管 Cal.com 出现故障导致服务中断。 | 中 | 高 | 1. 配置自动重启机制 (Docker Compose restart: always)。<br>2. 设置每日数据库备份。<br>3. 保留 Cal.com Cloud 账号作为紧急备用切换通道 (数据可导出)。 |
| **数据同步** | Google 与 Outlook 之间出现同步冲突或延迟。 | 中 | 中 | 1. Cal.com 采用“最后写入胜出”策略，并在 UI 上提示冲突。<br>2. 定期审计日志，监控同步错误率。<br>3. 建议团队统一主要日历源，另一方作为只读镜像（若业务允许）。 |
| **安全合规** | 自托管系统暴露在互联网，面临攻击风险。 | 低 | 高 | 1. 部署在 VPC 内网，或通过 Nginx Reverse Proxy + HTTPS 暴露。<br>2. 启用 IP 白名单限制仅公司出口 IP 可访问。<br>3. 定期更新 Cal.com 镜像版本以修补漏洞。 |
| **用户体验** | 员工不熟悉新系统，使用率低。 | 中 | 中 | 1. 提供简明的“3步预约指南”海报。<br>2. 在 Slack/Teams 中集成 Cal.com 链接，一键跳转。<br>3. 前两周由 IT 部门提供现场支持。 |
| **门禁联动** | 门禁 API 不稳定或格式变更导致联动失败。 | 低 | 低 | 1. 在中间件层增加重试机制。<br>2. 即使联动失败，不影响会议预约本身，仅影响门禁开启，降级为人工开门。 |

## 8. 最终建议与下一步行动

1.  **批准采购/部署**：批准采用 **Cal.com (自托管)** 作为会议室预约系统。
2.  **环境准备**：IT 团队需在测试环境搭建 Cal.com Docker 容器，并配置反向代理。
3.  **试点运行**：选取 5 名代表（3名用 Google，2名用 Outlook）进行为期一周的试点，验证同步准确性。
4.  **门禁接口对接**：启动门禁 API 对接的开发任务（预计 2 个工作日）。
5.  **全员推广**：试点成功后，发布全员通知及操作手册，正式上线。
