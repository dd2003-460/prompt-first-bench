# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**最终交付物**：一份可执行的会议室预约系统选型报告。
**报告必须包含以下组件**：
1. **推荐方案**：1 个最佳匹配的系统，含核心理由。
2. **备选方案**：1-2 个次优但可行的系统。
3. **淘汰理由**：针对主要候选池中未入选系统的明确排除依据（基于约束违反）。
4. **成本明细**：推荐方案的年度总拥有成本（TCO）拆解，确保 ≤2 万元/年。
5. **实施路径简述**：部署方式（SaaS vs 私有化）、日历集成配置步骤概要、门禁联动可行性结论。

---

## 2. 顶层影响因素分解（正交性检查）

将“选出一套满足约束的系统”这一目标分解为四个互相正交的维度：

| 因素 ID | 因素名称 | 定义与边界 | 优先级 | 正交性说明 |
| :--- | :--- | :--- | :--- | :--- |
| **F1** | **功能合规性** | 系统是否具备核心功能：多端支持、日历双向同步、门禁接口能力。 | P0 (硬性) | 决定“能不能用”。不满足则直接淘汰。 |
| **F2** | **经济可行性** | 系统年度总成本（License + 实施费 + 维护费）是否在预算内。 | P0 (硬性) | 决定“买不买得起”。不满足则直接淘汰。 |
| **F3** | **技术集成复杂度** | 日历对接和门禁联动的开发/配置工作量、稳定性风险。 | P1 (软性) | 决定“好不好用/难不难装”。影响运维成本和上线周期。 |
| **F4** | **用户体验与管理效能** | 界面易用性、移动端体验、管理后台效率、数据安全性。 | P2 (参考) | 决定“员工愿不愿用”。在 F1/F2 满足后作为 tie-breaker。 |

> **覆盖性检查**：
> - “三端支持” → F1
> - “日历集成” → F1 (功能存在) + F3 (集成难度)
> - “门禁联动可选” → F1 (接口能力) + F3 (实施复杂度)
> - “预算 ≤2万” → F2
> - “30人团队” → F2 (规模定价) + F4 (并发/容量)
> - “产出报告” → 依赖上述所有因素的评估结果。
> *结论：四个因素完整覆盖任务要求，且彼此独立（一个系统可能功能强但贵，或便宜但集成难），无重叠。*

## 3. 递归分解与条件区分

### 3.1 F1: 功能合规性 (P0)

#### 子因素 F1.1: 多终端支持
- **定义**：系统必须原生支持 macOS, Windows, Web 浏览器访问。
- **条件区分**：
    - **已知条件**：用户明确要求 macOS/Windows/Web。
    - **可推导条件**：若系统仅提供 iOS/Android App 而无 Web 端，则不满足；若仅有桌面客户端而无 Web，则不满足。
    - **待研究条件（空缺）**：主流候选系统的具体终端支持列表。例如，某些企业级 IM 内置的会议模块可能不支持独立的 Web 门户。
- **叶子原子**：
    - `A1.1.1`: 是否存在独立 Web 门户？(Yes/No)
    - `A1.1.2`: 是否有官方 macOS 客户端？(Yes/No)
    - `A1.1.3`: 是否有官方 Windows 客户端？(Yes/No)
    - *注：若 A1.1.1=Yes，通常可通过 Chrome/Edge 访问，满足 Web 需求。若 A1.1.2/3=No，需确认是否提供通用 Electron 应用或仅依赖 Web。*

#### 子因素 F1.2: 日历集成能力
- **定义**：支持与 Google Calendar 和 Outlook (Exchange/OWA) 进行双向同步（预约占用时间、取消释放时间）。
- **条件区分**：
    - **已知条件**：需同时支持 GCal 和 Outlook。
    - **可推导条件**：若系统仅支持单向推送（只读），则无法防止双订，视为不合格。若仅支持其中一种，视为部分合格（需人工干预或第三方中转）。
    - **待研究条件（空缺）**：各候选系统对 GCal 和 Outlook 的同步方向（单向/双向）、同步延迟、冲突处理机制。
- **叶子原子**：
    - `A1.2.1`: 是否原生支持 Google Calendar API 双向同步？
    - `A1.2.2`: 是否原生支持 Microsoft Exchange/Outlook API 双向同步？
    - `A1.2.3`: 是否支持 OAuth 2.0 授权流（避免硬编码 Token）？

#### 子因素 F1.3: 门禁联动接口
- **定义**：系统能否输出信号给门禁控制器（如 HTTP/MQTT/SDK），或在预约成功后自动下发开门权限。
- **条件区分**：
    - **已知条件**：此为“可选”功能，非硬性门槛，但若支持则加分。
    - **可推导条件**：若系统无任何 API 或 Webhook 出口，则无法实现联动。
    - **待研究条件（空缺）**：各候选系统是否开放 API/Webhook；是否有现成的门禁厂商插件。
- **叶子原子**：
    - `A1.3.1`: 是否提供公开 RESTful API 或 Webhook？
    - `A1.3.2`: API 是否包含“房间状态变更”事件？

### 3.2 F2: 经济可行性 (P0)

#### 子因素 F2.1: 许可费用模型
- **定义**：按年支付的软件订阅费或一次性买断费摊销。
- **条件区分**：
    - **已知条件**：总预算 ≤ 20,000 RMB / 年。团队规模 30 人。
    - **可推导条件**：人均成本上限 ≈ 666 RMB / 人 / 年。
    - **待研究条件（空缺）**：具体 SaaS 产品的阶梯定价（Per user/month vs Per room/year）。许多会议室系统是“按房间数”收费而非“按人数”，这会导致成本结构不同。
- **叶子原子**：
    - `A2.1.1`: 计费单位是“用户数”还是“会议室数量”？
    - `A2.1.2`: 30 人团队对应的最小会议室数量假设是多少？（*注：此为业务假设，需根据实际办公环境确定，见空缺清单*）
    - `A2.1.3`: 首年是否有实施费/设置费？

#### 子因素 F2.2: 隐性成本
- **定义**：硬件、服务器、开发人力、第三方中间件费用。
- **条件区分**：
    - **已知条件**：Web 端通常免硬件。门禁联动可能需要额外网关。
    - **可推导条件**：若选择私有化部署，需考虑服务器成本（通常超出预算）。故优先考察 SaaS。
    - **待研究条件（空缺）**：实现门禁联动所需的中间件/网关硬件成本。
- **叶子原子**：
    - `A2.2.1`: 是否需要购买额外的 IoT 网关以连接门禁？
    - `A2.2.2`: 该网关的一次性成本是多少？

### 3.3 F3: 技术集成复杂度 (P1)

#### 子因素 F3.1: 日历对接实施难度
- **定义**：从开通账号到完成双向同步所需的时间和技术技能要求。
- **条件区分**：
    - **已知条件**：IT 团队通常具备基本 API 知识。
    - **可推导条件**：若提供可视化配置向导，复杂度低；若需手写代码解析 API，复杂度高。
    - **待研究条件（空缺）**：各系统的文档完善度、社区活跃度、是否有现成连接器（如 Zapier/Make 模板）。
- **叶子原子**：
    - `A3.1.1`: 是否提供“一键连接”GCal/Outlook 的配置界面？
    - `A3.1.2`: 是否支持通过 iCalendar (.ics) 共享链接作为降级方案？

#### 子因素 F3.2: 门禁联动实施难度
- **定义**：将预约系统与物理门禁打通的工作量。
- **条件区分**：
    - **已知条件**：门禁品牌未知（可能是海康、大华、中控等）。
    - **可推导条件**：若系统无标准 API，需使用 RPA 或屏幕抓取，极不稳定，应视为高复杂度/高风险。
    - **待研究条件（空缺）**：常见门禁厂商（Hikvision/Dahua/ZKTeco）是否有与候选系统的官方对接案例或 SDK 兼容性。
- **叶子原子**：
    - `A3.2.1`: 候选系统是否有针对主流门禁品牌的官方适配器？
    - `A3.2.2`: 若无官方适配器，API 速率限制是否允许实时触发开门指令？

### 3.4 F4: 用户体验与管理效能 (P2)

#### 子因素 F4.1: 易用性与推广阻力
- **定义**：员工学习成本和管理员配置效率。
- **条件区分**：
    - **已知条件**：30 人团队，沟通成本低，但对工具挑剔。
    - **可推导条件**：UI 现代程度、移动端体验会影响采纳率。
    - **待研究条件（空缺）**：各系统的 UI 截图评价、用户口碑（G2/Capterra/知乎/掘金上的评价）。
- **叶子原子**：
    - `A4.1.1`: 是否有简体中文界面？
    - `A4.1.2`: 移动端是否支持扫码签到/快速预约？

#### 子因素 F4.2: 数据安全与合规
- **定义**：数据存储位置、隐私政策。
- **条件区分**：
    - **已知条件**：国内团队，数据出境敏感。
    - **可推导条件**：若数据存储在境外服务器且无境内节点，可能存在合规风险（虽非硬性法律禁止，但增加审计麻烦）。
    - **待研究条件（空缺）**：候选系统的服务器地理位置、是否通过等保认证。
- **叶子原子**：
    - `A4.2.1`: 数据主存储地是否在中国大陆？

| **G4** | **API 开放程度**：各候选系统是否提供公开 API 用于门禁联动？ | 事实缺失 | 影响 F1.3 及 F3.2 | 查阅 Developer Portal 或 API Docs。若无，检查是否有 Webhook 设置。 |
| **G5** | **门禁兼容性案例**：是否有海康/大华等门禁厂商与某预约系统的成功对接案例？ | 事实缺失 | 影响 F3.2 风险评估 | 搜索 "Hikvision API meeting room", "Dahua access control calendar integration". 查看 GitHub 开源项目或技术论坛帖子。 |
| **G6** | **地域合规性**：主要国际竞品（如 Roomle, MyRoom）的数据存储地及中国区可用性。 | 事实缺失 | 影响 F4.2 及 F1.1 (网络可达性) | 查看 Terms of Service 中的 Data Center location。测试网站在国内访问速度（备用路径）。 |
| **G7** | **隐性硬件成本**：若需门禁联动，通用的 IoT 网关（如 ESP32 + MQTT Broker 自建）的成本估算。 | 估算缺失 | 影响 F2.2 总成本 | 参考淘宝/京东上工业级 IoT 网关价格，或评估自建 MQTT Server 的人力成本（若 IT 资源充足，此项可能为 0）。 |

## 5. 已知与可推导条件汇总

1.  **团队规模**：30 人。（*推导*：并发用户峰值预计 < 10，任何正规 SaaS 均可承载，无需担心性能瓶颈。）
2.  **预算上限**：20,000 RMB / 年。（*推导*：若按房间计费，每房间年成本上限约为 4,000-6,000 RMB（假设 3-5 间房）。）
3.  **终端要求**：macOS, Windows, Web。（*推导*：Web 端通常指响应式网页，兼容 Chrome/Edge/Safari。若系统无专用桌面客户端，Web 端即满足“多端”要求，除非用户强制要求离线桌面应用——*此点需确认，暂按 Web 可用即可推导为满足*）。
4.  **日历生态**：Google Calendar + Outlook。（*推导*：这是两大主流生态，绝大多数现代 SaaS 均支持，但“双向同步”是关键差异点。）
5.  **门禁联动**：可选。（*推导*：若首选方案无此功能，但不影响核心预约流程，则可接受，只需在报告中注明“需额外开发/硬件才能实现门禁联动”。）

## 6. 阶段 02 研究入口与行动指南

基于上述分解，阶段 02 应按以下步骤执行：

### 第一步：构建候选池 (解决 G1)
*   **动作**：广泛搜索国内外主流的会议室预约 SaaS。
*   **搜索策略**：
    *   英文关键词：`best meeting room booking software 2024`, `room scheduling app with google calendar sync`.
    *   中文关键词：`会议室预约系统 云`, `智能会议室 解决方案`, `工位预约 会议室`.
    *   平台：G2, Capterra, Product Hunt, 阿里云云市场, 腾讯云云市场, 华为云市场.
*   **初筛标准**：
    1.  必须有 Web 端。
    2.  必须声称支持 GCal 或 Outlook。
    3.  必须有免费试用或清晰的价格表。
*   **预期输出**：5-8 个初步候选名单（例如：Roomle, MyRoom, Calendly [需确认房间功能], 钉钉/飞书/企微内置模块, 专门的垂直 SaaS 如“慧空间”、“智慧办公”等）。

### 第二步：功能与集成核验 (解决 G3, G4, G6)
*   **动作**：逐一访问候选系统官网，阅读 Help Center 和 Pricing Page。
*   **核查字段**：
    *   **日历**：查找 "Integrations", "Calendar Sync". 确认是 "Two-way" 还是 "One-way". 记录支持的平台。
    *   **API**：查找 "API", "Developer", "Webhooks". 记录是否有文档链接。
    *   **终端**：下载/试用客户端，确认 Mac/Win 兼容性。
    *   **地域**：查看 Footer 或 ToS 中的公司主体和数据中心位置。
*   **失败备用路径**：若官网信息模糊，注册 Free Trial 账号实测，或联系 Sales 询问 "Do you support two-way sync with Outlook?"。

### 第三步：成本建模 (解决 G2, G7)
*   **动作**：建立 Excel 成本模型。
*   **输入变量**：
    *   会议室数量：设定基准值 N_rooms = 4（30 人团队的典型配置，需在报告中声明此假设）。
    *   单价：从定价页获取 Per Room/Year 或 Per User/Year。
    *   门禁硬件：若选定系统无原生门禁接口，估算一个简易 IoT 网关成本（约 500-2000 RMB 一次性）或忽略（如果门禁联动非强制）。
*   **计算**：Total Annual Cost = (N_rooms * Unit_Price) + Setup_Fee + Hardware_Amortization.
*   **判定**：若 Total > 20,000，标记为“超预算”，进入备选或淘汰区。

### 第四步：综合评分与报告撰写
*   **动作**：使用加权评分法。
    *   F1 (功能): 40%
    *   F2 (成本): 30%
    *   F3 (集成): 20%
    *   F4 (体验): 10%
*   **输出**：
    1.  **推荐方案
