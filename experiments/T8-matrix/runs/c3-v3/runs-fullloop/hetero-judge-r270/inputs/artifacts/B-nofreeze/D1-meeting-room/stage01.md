# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义

**核心交付物**：一份可执行的会议室预约系统选型报告。

**报告必须包含的组成部分**：
1. **推荐方案**：单一首选系统，含理由。
2. **备选方案**：至少 1-2 个次优选项，含适用场景说明。
3. **淘汰理由**：对未入选主流候选的明确排除依据（需对应具体约束违反）。
4. **成本明细**：推荐及备选方案的年度总拥有成本（TCO）拆解（许可费、实施费、硬件联动费等），总和需 ≤ 2 万元/年。

---

## 2. 顶层影响因素分解（正交覆盖）

将“选出一套满足约束的系统”这一目标，分解为以下 5 个互相正交的顶层因素。只有当所有因素均被评估并满足时，目标才达成。

| 因素 ID | 因素名称 | 定义与边界 | 优先级 |
| :--- | :--- | :--- | :--- |
| F1 | **功能合规性** | 系统是否具备任务规定的必备功能（三端支持、双日历集成、门禁联动能力）。 | P0 (阻塞) |
| F2 | **经济可行性** | 系统的年度总成本（TCO）是否 ≤ 2 万元人民币，且成本结构透明。 | P0 (阻塞) |
| F3 | **技术兼容性** | 系统与现有 IT 环境（OS 版本、网络协议、身份认证体系）的适配程度。 | P1 (高) |
| F4 | **运维与管理效率** | 部署复杂度、管理员权限配置、故障恢复能力及对 30 人规模的适配度。 | P2 (中) |
| F5 | **扩展性与稳定性** | 未来 1-2 年内用户增长或功能需求变化的承载能力，以及 SLA 保障。 | P3 (低) |

*注：F1 和 F2 是硬性门槛（Gate），若不满足直接淘汰；F3-F5 用于在通过门槛的候选中排序。*

---

## 3. 递归分解与条件状态判定

### 3.1 F1: 功能合规性

#### 子因素 F1.1: 多端支持 (macOS / Windows / Web)
- **人类已提供条件**：必须同时支持 macOS、Windows 客户端及 Web 端。
- **可推导条件**：Web 端通常基于浏览器标准，兼容性风险较低；桌面端需确认是否有原生 App 或 Electron/PWA 方案。
- **仍需研究条件 (空缺)**：
    - [待验证] 各候选系统在 macOS 和 Windows 上的最新版本号及最低 OS 要求。
    - [待验证] 移动端支持情况（虽非强制，但常作为加分项，需确认是否影响评分）。
    - [待验证] Web 端是否需要独立域名部署，还是 SaaS 托管。

#### 子因素 F1.2: 日历集成 (Google Calendar + Outlook)
- **人类已提供条件**：必须同时集成 Google Calendar 和 Outlook (Microsoft 365)。
- **可推导条件**：主流商业 SaaS 系统通常通过 OAuth 2.0 API 实现双向同步。
- **仍需研究条件 (空缺)**：
    - [待验证] 集成方式：是原生内置、插件形式还是第三方桥接？
    - [待验证] 同步延迟与冲突处理机制（如双方同时预订同一房间）。
    - [待验证] 是否需要额外付费才能解锁高级日历同步功能（部分系统基础版仅单向同步）。

#### 子因素 F1.3: 门禁联动 (可选)
- **人类已提供条件**：门禁联动为“可选”，非强制。
- **可推导条件**：若系统不支持，需在报告中注明“无此功能”，但不构成淘汰理由，除非其他维度严重劣势。
- **仍需研究条件 (空缺)**：
    - [待验证] 支持的门禁品牌列表（如 HID, ZKTeco, 海康威视等）。
    - [待验证] 联动逻辑：是“预约成功即开门”还是“扫码/刷卡+预约校验”？
    - [待验证] 是否需要额外购买硬件网关或中间件软件及其成本。

### 3.2 F2: 经济可行性

#### 子因素 F2.1: 许可费用 (License Cost)
- **人类已提供条件**：总预算 ≤ 20,000 CNY / 年。
- **可推导条件**：按 30 人计算，人均年成本上限约为 666 CNY/人/年。
- **仍需研究条件 (空缺)**：
    - [待验证] 计费模式：按席位 (Per Seat)、按房间数 (Per Room) 还是按企业打包 (Flat Rate)？
    - [待验证] 免费试用额度及试用期长度。
    - [待验证] 汇率波动对美元计价 SaaS 的影响（需锁定当前汇率假设或查询实时汇率）。

#### 子因素 F2.2: 实施与初始费用 (Onboarding Cost)
- **人类已提供条件**：无单独列出的实施费预算，隐含在 2 万总额内。
- **可推导条件**：SaaS 系统通常零实施费或低实施费；私有化部署可能有高昂的一次性费用。
- **仍需研究条件 (空缺)**：
    - [待验证] 是否存在一次性 Setup Fee。
    - [待验证] 数据迁移服务是否收费。

#### 子因素 F2.3: 隐性成本 (Hidden Costs)
- **人类已提供条件**：无。
- **可推导条件**：可能包括存储超额费、API 调用超额费、客服升级费。
- **仍需研究条件 (空缺)**：
    - [待验证] 超出基础包后的单价。
    - [待验证] 取消订阅时的数据处理费用。

### 3.3 F3: 技术兼容性

#### 子因素 F3.1: 身份认证 (SSO/LDAP)
- **人类已提供条件**：未明确指定公司现有 IDP。
- **可推导条件**：30 人研发团队大概率使用 Microsoft 365 或 Google Workspace 作为主邮箱，因此 SSO 应优先支持这两家。
- **仍需研究条件 (空缺)**：
    - [待验证] 候选系统支持的 SSO 协议（SAML 2.0, OIDC）。
    - [待验证] 是否支持 LDAP/AD 直接对接。
    - [假设] 默认假设团队主要使用 M365 或 GWS，若实际使用自建 AD 或其他 IDP，需调整权重。

#### 子因素 F3.2: 网络与安全
- **人类已提供条件**：无特殊网络安全要求。
- **可推导条件**：SaaS 需符合基本的数据隐私法规（如 GDPR 或中国个人信息保护法 PIPL，取决于服务器位置）。
- **仍需研究条件 (空缺)**：
    - [待验证] 数据存储地点（中国大陆节点 vs 海外节点）。
    - [待验证] 是否提供 SOC 2 Type II 或 ISO 27001 认证。
    - [关键决策点] 数据主权要求：如果公司要求数据必须存于境内，则排除纯海外 SaaS。此为重大未知条件，需向用户确认或列为高优先级调研项。

### 3.4 F4: 运维与管理效率

#### 子因素 F4.1: 部署模式
- **人类已提供条件**：无。
- **可推导条件**：30 人规模，SaaS (Public Cloud) 是最优解，降低运维负担。Private Cloud 或 On-Premise 维护成本过高，大概率超出预算或人力限制。
- **仍需研究条件 (空缺)**：
    - [待验证] 候选系统是否仅提供 SaaS？若有 Hybrid 选项，其成本如何？

#### 子因素 F4.2: 管理后台易用性
- **人类已提供条件**：无。
- **可推导条件**：IT 管理员需要能批量添加房间、设置规则、查看报表。
- **仍需研究条件 (空缺)**：
    - [待验证] 管理界面是否支持中文。
    - [待验证] 是否提供 API 供内部系统集成。

### 3.5 F5: 扩展性与稳定性

#### 子因素 F5.1: SLA 与可用性
- **人类已提供条件**：无。
- **可推导条件**：会议室预约属非核心业务中断型应用，99.5% 可用性即可接受。
- **仍需研究条件 (空缺)**：
    - [待验证] 官方 SLA 承诺值。
    - [待验证] 历史宕机记录（可通过 Status Page 或社区反馈获取）。

## 4. 空缺条件清单 (Gap List)

以下条件无法在当前阶段假定，必须进入阶段 02 进行研究或向用户澄清。**任何未列入此处的条件不得在后续阶段中被默认为真。**

| ID | 空缺描述 | 关联因素 | 阻塞判断 | 优先级 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| G1 | **数据驻留要求**：公司是否强制要求用户数据存储在中华人民共和国境内？ | F3.2 | 决定候选池范围（排除纯海外 SaaS 或强制选择国内厂商） | P0 | **关键决策点**，若未确认，阶段 02 需并行调研国内外两类方案 |
| G2 | **现有身份认证体系**：团队目前使用什么邮箱/IDP？(M365 / GWS / 自建 AD / 其他) | F3.1 | 影响 SSO 配置难度及兼容性评分 | P1 | 默认假设为 M365 或 GWS，需验证 |
| G3 | **候选系统的具体定价表**：各主流候选（如 Roomle, Calendly, Zoom Rooms, 钉钉/企微自带功能, 专业会议系统如 BookRoom 等）的最新年度价格。 | F2.1 | 无法生成成本明细，无法进行预算筛选 | P0 | 需实时抓取官网或联系销售 |
| G4 | **门禁联动具体需求**：虽然标记为“可选”，但如果有此需求，具体的门禁硬件品牌是什么？ | F1.3 | 影响是否将“支持特定品牌门禁”作为加分项或扣分项 | P2 | 若无具体品牌，仅评估“是否具备通用 API 接口” |
| G5 | **候选系统的日历同步细节**：是否支持双向实时同步？冲突解决策略？ | F1.2 | 影响功能合规性评分 | P1 | 需查阅文档或试用 |
| G6 | **免费试用政策**：哪些候选提供足够长的试用期以进行 PoC (Proof of Concept)？ | F4.1 | 影响验证路径 | P2 | 有助于降低选型风险 |
| G7 | **汇率基准**：计算 USD 计价产品时需使用的固定汇率。 | F2.1 | 成本计算精度 | P3 | 建议使用近期平均汇率或当前央行中间价 |

## 5. 阶段 02 研究入口与行动指南

基于上述分解，阶段 02 的研究工作应按以下路径执行：

### 5.1 第一批行动：确定候选池 (Candidate Pooling)

**目标**：列出 5-8 个潜在候选系统，覆盖不同价位和功能侧重。

**搜索策略**：
1.  **关键词组合**：
    *   "Meeting room booking system for small teams"
    *   "会议室预约系统 中小企业 价格"
    *   "Calendar integration meeting room scheduler"
    *   "SaaS meeting room management under $10/user/month"
2.  **来源类型**：
    *   G2 Crowd / Capterra / TrustRadius (国际评测)
    *   36氪 / 知乎 / 阿里云市场 (国内生态)
    *   各大厂商官网 Pricing 页面
3.  **初步筛选标准 (Pre-filter)**：
    *   排除仅支持单端的系统。
    *   排除明确不支持 GCal/Outlook 集成的系统。
    *   排除明显超过预算上限（如 >$50/user/month）的企业级重型系统。

**预期候选类别 (待验证假设)**：
*   **轻量级 SaaS**：例如 Roomle, BookRoom, Meetingroom.io (待验证价格和功能)。
*   **办公套件内置**：例如 Microsoft Teams Rooms (需结合 M365 许可), Google Meet/Workspace Add-ons (待验证是否独立售卖或捆绑)。
*   **国内协同平台**：例如 钉钉/企业微信 的会议室插件 (待验证是否满足独立预约需求及 API 开放度)。
*   **开源/自托管**：例如 Unify (Rust-based), Nextcloud (若考虑自托管，需评估运维成本是否超支)。

### 5.2 第二批行动：深度验证 (Deep Dive Validation)

针对初筛后的 3-5 个候选，逐一核验以下字段：

| 核验维度 | 具体字段/问题 | 数据来源建议 | 失败备用路径 |
| :--- | :--- | :--- | :--- |
| **价格** | 30 席位的年费是多少？是否有隐藏费用？货币单位？ | 官网 Pricing 页; 邮件咨询销售; 第三方比价网站 | 若官网不公开，记录为“需询价”，并在报告中注明估算区间 |
| **功能** | 是否支持 macOS/Win/Web? 是否支持 GCal+Outlook 双向同步? | 官方 Feature Matrix; 帮助文档; YouTube 演示视频 | 若无明确文档，尝试申请免费试用账号实测 |
| **兼容性** | 支持哪种 SSO? 数据存储在哪里? | 安全白皮书; 信任中心 (Trust Center); 隐私政策 | 若信息缺失，视为高风险，降级处理 |
| **门禁** | 是否有 Door Access 模块? 支持哪些协议? | 开发者文档; 集成列表 | 若无，标记为“不支持”，不影响基本入围，但影响排名 |

### 5.3 第三批行动：成本建模与对比

1.  **建立 TCO 模型**：
    *   `Total Annual Cost = (Seat Price × 30) + Implementation Fee + Hardware Cost (if any) + Support Plan`
    *   将所有货币转换为 CNY (使用 G7 确定的汇率)。
2.  **矩阵评分**：
    *   构建 Excel 表格，行=候选系统，列=F1-F5 各子因素。
    *   对每个单元格打分 (1-5) 或标记 Pass/Fail。
    *   F1, F2 为否决项 (Veto)，其余为加权项。
3.  **产出草稿**：
    *   根据评分结果，确定 Top 1 (推荐), Top 2 (备选), Rest (淘汰)。
    *   撰写淘汰理由：必须引用具体违反的约束（如：“因不支持 Outlook 集成，违反 F1.2” 或 “因年费 25,000 CNY，违反 F2.1”）。

### 5.4 风险与备用路径

*   **若所有国际 SaaS 均因数据驻留 (G1) 被排除**：
    *   备用路径：转向国内 SaaS (如钉钉/企微生态内的专业会议室插件) 或评估开源自托管方案 (Unify/Nextcloud)，并重新评估运维人力成本是否计入 2 万预算。
*   **若所有候选均无免费试用**：
    *   备用路径：依赖详细的功能文档和视频演示进行静态评估，并在报告中增加“建议先小额采购单月套餐进行测试”的建议。
*   **若价格信息不透明**：
    *   备用路径：使用同类竞品的公开价格作为基准线进行估算，并在报告中明确标注“价格为估算值，需最终合同确认”。

---

## 6. 阶段 01 完成判定

*   **因素正交性**：F1-F5 分别覆盖功能、成本、技术、运维、扩展，无重叠。
*   **覆盖完整性**：任务中的所有显性约束（预算、端、日历、门禁）均已映射到具体子因素。
*   **已知/未知区分**：所有未验证的价格、兼容性、政策均列入 Gap List (G1-G7)，未伪装成事实。
*   **可操作性**：阶段 02 可直接依据 5.1-5.3 的路径开始搜索和验证，无需再回头询问阶段 01 关于“该查什么”的问题。
*   **阻塞分析**：明确指出 G1 (数据驻留) 是关键分叉点，需在阶段 02 初期尽快确认或并行处理。

**结论**：本工件已满足启动阶段 02 的条件。
