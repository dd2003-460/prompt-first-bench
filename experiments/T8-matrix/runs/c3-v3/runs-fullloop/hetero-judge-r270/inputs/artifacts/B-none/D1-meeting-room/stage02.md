## 2. 关键主张核验与证据记录

### 2.1 飞书 (Feishu/Lark) - 会议室模块

*   **主张 1: 支持 macOS/Windows/Web 三端。**
    *   **观察**：飞书提供完整的桌面客户端 (Mac/Win) 和 Web 端。会议室预约通常在“日历”或“工作台”中嵌入。
    *   **来源**：模型知识 (飞书官网及产品文档)。
    *   **不确定性**：低。这是飞书的基础能力。
    *   **独立来源佐证**：飞书帮助中心关于“会议室预订”的教程；用户社区讨论。

*   **主张 2: 支持 Google Calendar 和 Outlook 双向同步。**
    *   **观察**：飞书日历本身支持导入/导出 ICS。对于第三方日历，飞书提供“日历集成”功能，允许连接外部日历。
        *   **Outlook**: 飞书企业版通常通过 Microsoft Graph API 或 Exchange 连接器实现双向同步（需管理员配置）。
        *   **Google Calendar**: 支持通过 OAuth 连接 GCal，实现事件同步。
        *   **关键点**：如果是“会议室资源”，需要在飞书中创建“会议室”实体，然后将其忙碌状态同步到员工日历，或将员工在 GCal/Outlook 中的会议占用同步回飞书会议室状态。这通常是**单向或半双向**的复杂配置，取决于版本。
    *   **来源**：模型知识 (飞书开放平台文档)。
    *   **不确定性**：**高**。双向同步的具体深度（是同步“忙/闲”还是同步“会议详情”）取决于订阅等级。基础版可能仅支持 ICS 单向读取。
    *   **行动项**：需确认 30 人团队所需的版本是否包含高级日历集成 API 权限。

*   **主张 3: API 开放程度 (门禁联动)。**
    *   **观察**：飞书拥有强大的 Open Platform。提供 RESTful API 和 Webhook。
        *   `A1.3.1`: Yes, 提供公开 API。
        *   `A1.3.2`: Yes, 可以订阅“日程变更”事件，从而触发 Webhook 给门禁系统。
    *   **来源**：模型知识 (飞书开放平台开发者文档)。
    *   **不确定性**：低。API 成熟度较高。

*   **主张 4: 成本 (F2)。**
    *   **观察**：飞书采用“免费 + 增值”模式。
        *   基础版：免费，支持基本日历和会议室显示（限制会议室数量或功能）。
        *   商业版/旗舰版：按年付费，解锁高级集成、更多存储和管理功能。
        *   **估算**：30 人团队，若仅使用基础会议室功能，可能在免费额度内（通常免费额度支持少量会议室）。若需高级双向同步和 API 高频调用，可能需要购买商业版。
        *   **价格参考**：飞书商业版人均约 ¥300-¥500/年（估算值，需核实）。30 人 × ¥400 = ¥12,000/年。
    *   **来源**：模型知识 (飞书定价页历史数据)。
    *   **不确定性**：**高**。具体套餐价格随政策调整。需登录后台查看实际报价。

### 2.2 钉钉 (DingTalk) - 会议室模块

*   **主张 1: 支持 macOS/Windows/Web 三端。**
    *   **观察**：同飞书，全平台支持。
    *   **来源**：模型知识。
    *   **不确定性**：低。

*   **主张 2: 支持 Google Calendar 和 Outlook 双向同步。**
    *   **观察**：钉钉日历支持绑定外部日历。
        *   **Outlook**: 钉钉与 Microsoft 365 有战略合作，企业版通常提供较好的 O365 集成，支持双向同步。
        *   **Google Calendar**: 支持 ICS 订阅（单向为主），双向同步可能需要通过“宜搭”或第三方连接器实现，配置复杂度高于 Outlook。
    *   **来源**：模型知识 (钉钉开发者文档)。
    *   **不确定性**：**中高**。GCal 的双向同步稳定性不如 Outlook。

*   **主张 3: API 开放程度 (门禁联动)。**
    *   **观察**：钉钉开放平台 API 完善。
        *   支持获取日程列表、监听日程变更事件。
        *   钉钉自身生态内有大量智能硬件（包括门禁、投影仪等），若使用钉钉推荐的硬件，联动最简便。
    *   **来源**：模型知识。
    *   **不确定性**：低。

*   **主张 4: 成本 (F2)。**
    *   **观察**：钉钉也有免费版和商业版。
        *   基础会议室功能通常在免费范围内。
        *   高级 API 调用量或专属域名等功能可能涉及费用。
        *   **估算**：30 人团队，若仅用基础功能，成本可能接近 0 元。若需定制开发门禁联动，主要成本在于开发人力或中间件。
    *   **来源**：模型知识。
    *   **不确定性**：**高**。需确认 API 调用频率限制是否在免费额度内。

### 2.3 Roomle / MyRoom (国际垂直 SaaS)

*   **主张 1: 支持 Web/Mobile。**
    *   **观察**：纯 Web 应用，响应式设计，兼容 Mac/Win 浏览器。无专用桌面客户端（Electron 包装少见）。
    *   **来源**：模型知识 (Roomle 官网)。
    *   **不确定性**：低。

*   **主张 2: 日历集成。**
    *   **观察**：核心卖点即日历集成。
        *   **GCal/Outlook**: 原生支持双向同步。配置简单，扫码即可绑定。
        *   **优势**：比 IM 平台更专注于“房间”资源，冲突处理逻辑更优。
    *   **来源**：模型知识 (Roomle Help Center)。
    *   **不确定性**：低。

*   **主张 3: API 开放程度。**
    *   **观察**：提供 REST API 和 Webhooks。
    *   **来源**：模型知识。
    *   **不确定性**：低。

*   **主张 4: 成本 (F2)。**
    *   **观察**：按房间数收费。
        *   **定价参考**：Roomle 大约 $9-$15/room/month。
        *   **计算**：假设 4 间会议室。
            *   低端: 4 rooms × $9 × 12 months = $432/year ≈ ¥3,100 RMB。
            *   高端: 4 rooms × $15 × 12 months = $720/year ≈ ¥5,200 RMB。
        *   **结论**：远低于 2 万元预算。
    *   **来源**：模型知识 (Roomle Pricing Page 历史数据)。
    *   **不确定性**：**高**。汇率波动及最新定价策略需核实。

*   **主张 5: 地域合规与网络 (G6)。**
    *   **观察**：服务器位于海外（美国/欧洲）。
        *   **风险**：国内访问速度不稳定，可能存在延迟或偶尔无法访问。
        *   **合规**：数据出境问题。对于一般研发团队，若无严格的数据驻留法律要求，风险可控，但体验可能打折。
    *   **来源**：模型知识 (ToS 分析)。
    *   **不确定性**：**高**。实际网络体验因地而异。

## 4. 暂定结论与风险评估

### 4.1 推荐方案倾向：飞书 (Feishu) 或 钉钉 (DingTalk)

**理由**：
1.  **合规性与稳定性**：作为国内团队，使用境内服务避免了网络抖动和数据出境的法律灰色地带。
2.  **生态整合**：团队很可能已经在使用飞书或钉钉进行沟通。将会议室预约集成在现有 IM 中，无需增加新的账号体系，推广阻力最小 (F4.1)。
3.  **门禁联动**：国内门禁厂商对钉钉/飞书的适配更好，可能存在“开箱即用”的解决方案，降低 F3.2 复杂度。
4.  **成本**：30 人规模在两者中都属于中小客户，基础功能免费或低成本，即使升级到商业版也在预算内。

### 4.2 备选方案倾向：Roomle

**理由**：
1.  **专业度**：专为房间预约设计，UI 交互优于 IM 内的嵌入式模块。
2.  **日历同步**：对 GCal/Outlook 的支持最为原生和稳健。
3.  **成本极低**：按房间收费，绝对金额低。
**风险**：网络访问稳定性需实测。若公司网络环境良好（有代理或直连畅通），则是极佳选择。

### 4.3 淘汰理由

*   **Calendly**：核心逻辑不匹配，不适合物理资源管理。
*   **传统 OA 系统 (如泛微、致远)**：虽然功能强大，但部署重、成本高（远超 2 万预算）、实施周期长，不符合敏捷需求。
*   **开源自建 (如 Nextcloud Rooms)**：需要自购服务器和维护，隐性人力成本高，且 UI 现代化程度不足，30 人团队维护负担过重。
