# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**核心交付物**：一份可交付的选型报告，包含以下具体组件：
1.  **推荐方案**：单一最佳选项，附带理由。
2.  **备选方案**：至少一个次优但可行的选项。
3.  **淘汰理由**：对主要竞品或不符合约束方案的明确排除说明。
4.  **成本明细**：基于30人团队规模的年度总花费测算（上限3万元人民币）。
5.  **合规性检查表**：验证Web/macOS/Windows覆盖、版本管理、细粒度权限、离线支持情况。

**非交付物**：实施计划、迁移脚本、培训材料（除非作为加分项简要提及）。

## 2. 因素分解（递归结构）

### 顶层影响因素 (Level 1)
*   **F1: 功能性合规性 (Functional Compliance)** - *硬性约束*
    *   F1.1: 平台兼容性 (Platform Compatibility)
        *   F1.1.1: Web端可用性
        *   F1.1.2: macOS客户端存在性与稳定性
        *   F1.1.3: Windows客户端存在性与稳定性
    *   F1.2: 文档版本管理 (Document Versioning)
        *   F1.2.1: 自动保存/快照机制
        *   F1.2.2: 历史版本回溯与恢复能力
        *   F1.2.3: 并发编辑冲突处理（若适用）
    *   F1.3: 细粒度权限控制 (Granular Permission Control)
        *   F1.3.1: 文件夹/文件级读写执行权限分离
        *   F1.3.2: 基于角色/组的权限继承
        *   F1.3.3: 外部协作者权限隔离（可选，但研发常需）
    *   F1.4: 离线使用支持 (Offline Support) - *加分项*
        *   F1.4.1: 本地缓存机制
        *   F1.4.2: 离线编辑与在线同步冲突解决策略

*   **F2: 经济可行性 (Economic Feasibility)** - *硬性约束*
    *   F2.1: 年度总成本 (Total Annual Cost, TAC)
        *   F2.1.1: 许可费用 (Licensing Fees)
            *   F2.1.1.1: 按用户数计费模型 (Per User)
            *   F2.1.1.2: 按存储量计费模型 (Per Storage)
            *   F2.1.1.3: 混合计费模型
        *   F2.1.2: 隐性成本 (Hidden Costs)
            *   F2.1.2.1: 部署/维护人力成本 (SaaS vs On-prem)
            *   F2.1.2.2: 额外插件或高级功能费用
    *   F2.2: 预算约束校验
        *   F2.2.1: 30人规模下的单价敏感性分析
        *   F2.2.2: 汇率波动风险（若涉及海外服务）

*   **F3: 技术适配性与生态 (Technical Fit & Ecosystem)** - *推导条件/中优先级*
    *   F3.1: 数据安全性与合规
        *   F3.1.1: 数据传输加密 (TLS)
        *   F3.1.2: 静态数据存储加密 (AES-256等)
        *   F3.1.3: 数据驻留地 (Data Residency) - *关键空缺，取决于团队所在地*
    *   F3.2: 集成能力
        *   F3.2.1: API开放性
        *   F3.2.2: 与现有研发工具链（Git, Jira, Slack等）的集成潜力
    *   F3.3: 性能与稳定性
        *   F3.3.1: 大文件上传/下载速度
        *   F3.3.2: 高并发访问稳定性

*   **F4: 运维与支持 (Operations & Support)** - *低优先级/参考*
    *   F4.1: 技术支持响应速度
    *   F4.2: 服务商SLA承诺

### 正交性检查
*   F1 (功能) 与 F2 (成本) 正交：功能好不代表成本低，反之亦然。
*   F1 (功能) 与 F3 (技术/安全) 部分重叠但边界清晰：F1关注“能否做”，F3关注“做得是否安全/稳定/易集成”。
*   F2 (成本) 与 F4 (运维) 正交：运维好可能成本高，也可能降低长期隐性成本，但直接财务支出归F2，服务体验归F4。

## 3. 条件状态分类

### A. 人类已提供的条件 (Knowns)
1.  **团队规模**：30人。
2.  **年度预算上限**：30,000 RMB / 年。
3.  **必需平台**：Web, macOS, Windows。
4.  **核心功能要求**：
    *   文档版本管理。
    *   细粒度权限控制。
5.  **加分项**：支持离线使用。
6.  **使用场景**：研发团队（隐含需求：代码片段共享、设计稿、需求文档、会议纪要等混合文件类型；可能对大文件或二进制文件有需求）。

### B. 从项目可推导的条件 (Derived Assumptions)
1.  **协作频率**：研发团队通常高频协作，实时同步或快速同步是重要考量。
2.  **文件类型多样性**：不仅限于Office文档，可能包含PDF、图片、代码压缩包、甚至小型二进制文件。因此“网盘”属性比纯“在线文档编辑器”更重要，或者需要两者兼备。
3.  **数据安全敏感度**：研发代码和架构文档属于公司机密，对权限控制和审计日志有潜在高要求（虽未明说，但属行业常识推导，需在研究中验证候选方案是否满足基本企业级安全标准）。
4.  **地域限制假设**：*待验证*。假设团队位于中国大陆，因此对中国大陆访问速度和数据合规性（如GDPR不适用于中国境内主体，但需注意国内法规）有要求。若团队在海外，此假设失效。**[注意：此为推导，需用户在阶段02前确认或作为默认假设进行筛选]**

## 4. 候选对象类别冻结 (Candidate Set Freeze)

根据“团队文件协作/网盘”定义，结合30人研发场景，冻结以下**四大类**候选对象供阶段02研究。任何新增类别需在阶段02显式声明理由。

1.  **C1: 国际主流协同办公套件 (International Collaborative Suites)**
    *   *特征*：文档编辑+网盘+版本管理一体化，全球知名，通常按用户收费。
    *   *典型代表 (待验证)*: Microsoft 365 (OneDrive + SharePoint), Google Workspace (Drive + Docs).
    *   *研究重点*: 中国区可用性、价格、离线同步稳定性。

2.  **C2: 国际专业云存储/网盘服务 (International Cloud Storage Services)**
    *   *特征*：以文件同步为主，版本管理和权限为辅，强调大容量和跨平台。
    *   *典型代表 (待验证)*: Dropbox Business, Box.
    *   *研究重点*: 权限粒度是否足够细、价格是否在预算内、国内访问速度。

3.  **C3: 中国本土协同办公/网盘平台 (Domestic Chinese Collaboration Platforms)**
    *   *特征*：针对中国市场优化，访问速度快，合规性好，价格通常较低，集成微信/钉钉等。
    *   *典型代表 (待验证)*: 飞书 (Feishu/Lark), 钉钉 (DingTalk), 腾讯企业微信 (WeCom), 坚果云 (Jianguoyun), 亿方云 (Yifangyun).
    *   *研究重点*: 细粒度权限能力（特别是文件级）、版本管理深度、30人套餐价格、离线能力。

4.  **C4: 自托管/开源解决方案 (Self-Hosted/Open Source Solutions)**
    *   *特征*：软件免费或低成本，需自行维护服务器，完全掌控数据。
    *   *典型代表 (待验证)*: Nextcloud, Seafile, Synology Drive (硬件捆绑).
    *   *研究重点*: 运维人力成本折算后是否超过30k RMB？30人团队是否有IT人员维护？(注：若无人力，此类通常因隐性成本过高而被淘汰，但仍需列出以完成对比)。

**排除说明**：
*   排除纯个人网盘（如百度网盘个人版）：缺乏企业级细粒度权限和管理后台。
*   排除纯代码托管平台（如GitHub/GitLab）：虽然版本管理极强，但不具备通用“文件协作/网盘”属性（如Office文档实时协作、非代码文件的大容量存储），不符合“团队文件协作”的广义定义，除非任务特指代码仓库，但题目强调“文档版本管理”且包含Web/mac/Win客户端，暗示通用文件协作。

## 5. 阶段 02 研究路径 (Research Roadmap for Stage 02)

阶段02应依据上述空缺(G1-G9)和候选集(C1-C4)执行以下行动：

### 第一批行动：初筛与价格核验 (对应 G1, G6, G7)
1.  **动作**：访问各候选代表的官方网站或官方代理商页面。
2.  **搜索词示例**：
    *   "Microsoft 365 Business Basic price 30 users China"
    *   "Dropbox Business pricing annual cost"
    *   "飞书 商业版 价格 30人"
    *   "坚果云 企业版 报价"
3.  **字段采集**：
    *   最低起步人数（是否支持30人定制或最小包）。
    *   每人每月/每年单价。
    *   是否包含Web/mac/Win客户端。
    *   服务器节点位置（是否在中国大陆）。
4.  **失败备用路径**：若官网无明确价格，需记录“需联系销售”，并尝试查找第三方评测网站（如Gartner Peer Insights, 知乎, 少数派）中的近期用户反馈价格。

### 第二批行动：功能深度验证 (对应 G2, G3, G4, G5)
1.  **动作**：查阅产品帮助文档(Help Center)或试用账号。
2.  **关键验证点**：
    *   **权限**：找到“Permission”或“Access Control”文档，确认是否支持“File-level”而非仅“Folder-level”。确认是否支持“External Guest”链接及其过期时间设置。
    *   **版本**：找到“Version History”文档，确认最大保留版本数、保留时长、是否支持命名版本。
    *   **离线**：确认客户端是否支持“Sync specific folders offline”以及冲突解决策略（Last-write-wins vs Manual merge）。
3.  **来源类型**：官方知识库、产品发布博客、权威科技媒体评测（The Verge, TechCrunch, 36Kr, InfoQ）。

### 第三批行动：综合评分与成本建模 (对应 F2, F3)
1.  **动作**：建立Excel评分矩阵。
2.  **权重建议**（待阶段02根据研究发现微调）：
    *   预算合规 (30%)
    *   权限细粒度 (25%)
    *   版本管理 (20%)
    *   平台覆盖与离线 (15%)
    *   国内访问速度/合规 (10%)
3.  **输出**：生成初步排名，标记出Top 2进入详细POC或深入访谈环节。

## 6. 缺失条件对后续判断的阻塞分析

*   **G1 (价格)** 阻塞：最终推荐方案的选择。若所有国际大牌均超预算，则必须转向国产或自托管。
*   **G6 (国内访问速度)** 阻塞：若首选的国际方案在国内访问极慢，即使功能完美也需降级为备选，因为会严重影响30人团队的日常效率。
*   **G3 (权限粒度)** 阻塞：若某方案仅支持文件夹级权限，而研发团队要求对单个代码文件进行不同权限控制，则该方案不满足核心需求，需淘汰。
