# 阶段 03：具体行动分解（无 owner 组件）

**执行说明**：
本阶段基于阶段 02 的选型结论，将“为 30 人研发团队部署飞书专业版”这一目标拆解为可执行的落地步骤。
**核心策略**：采用 **“POC 验证 + 数据迁移 + 权限配置 + 全员推广”** 的四步走策略。
**关键假设**：团队目前可能分散使用本地硬盘、个人网盘或旧版企业微信/钉钉文档，需进行数据清洗和迁移。

---

## 1. 行动计划概览 (Action Plan Overview)

## 2. 详细步骤分解 (Detailed Step Breakdown)

### Step 1: 环境准备与账号初始化

*   **输入 (Inputs)**:
    *   公司主体营业执照信息（用于企业认证）。
    *   公司官方邮箱域名（如 `@company.com`，用于绑定飞书并实现 SSO 单点登录基础）。
    *   30 名员工的姓名、手机号、部门归属列表（Excel/CSV 格式）。
    *   IT 管理员的手机号（作为超级管理员）。
*   **动作 (Actions)**:
    1.  注册飞书企业账号，完成企业认证（通常 1-3 个工作日审核，若已有认证可跳过）。
    2.  在后台导入员工名单，建立基础组织架构（研发部、产品部、测试部等）。
    3.  设置管理员角色：指定 1 名超级管理员，2-3 名普通管理员（负责日常维护）。
    4.  购买“飞书专业版”订阅，确保 30 个席位生效。
    5.  配置基础安全策略：强制密码复杂度、启用两步验证（2FA）。
*   **依赖 (Dependencies)**:
    *   需要财务流程审批采购付款（若尚未完成）。
    *   需要 HR 提供准确的最新员工通讯录。
*   **预期产出 (Expected Outputs)**:
    *   一个可用的飞书企业租户 URL。
    *   所有 30 名员工收到邀请链接并能成功登录。
    *   组织架构在后台正确显示。
*   **验收方式 (Acceptance Criteria)**:
    *   [ ] 随机抽取 3 名员工，确认可正常登录且看到正确的部门标签。
    *   [ ] 确认后台“成员管理”中人数为 30，且状态均为“已激活”。
    *   [ ] 确认套餐状态为“专业版”，有效期至次年今日。

### Step 2: POC 试点验证 (Pilot Test)

*   **输入 (Inputs)**:
    *   选取 3-5 名核心种子用户（建议包含 1 名后端开发、1 名前端开发、1 名产品经理、1 名测试工程师）。
    *   定义 3 个典型业务场景：
        1.  **需求文档协同**：PM 编写 PRD，研发评论并提出修改意见，查看版本历史。
        2.  **技术资产存储**：上传一个 500MB 的设计源文件或编译包，设置仅项目组可见。
        3.  **离线/弱网测试**：在地铁或飞行模式下打开最近编辑的文档，尝试简单修改，恢复网络后检查同步状态。
*   **动作 (Actions)**:
    1.  创建专门的“POC 测试空间”，仅对种子用户开放。
    2.  引导种子用户按照上述 3 个场景进行操作。
    3.  记录痛点：例如“Markdown 渲染是否支持代码高亮”、“大文件上传速度”、“外部访客分享链接的安全性”。
    4.  收集反馈，调整内部使用规范（如：统一使用飞书云文档而非 Word 附件，以发挥协同优势）。
*   **依赖 (Dependencies)**:
    *   种子用户需预留约 4 小时的时间进行测试。
    *   需准备真实的脱敏测试数据。
*   **预期产出 (Expected Outputs)**:
    *   《POC 测试反馈表》：列出功能满足情况、Bug 列表、体验评分。
    *   《团队使用规范草案 v1.0》：明确哪些内容用在线文档，哪些用文件存储，命名规范是什么。
*   **验收方式 (Acceptance Criteria)**:
    *   [ ] 种子用户确认核心工作流（写文档、存文件、查版本）均可顺畅完成。
    *   [ ] 发现并记录至少 3 个潜在风险点或优化建议（如：某些插件不兼容、特定格式转换失败等），并制定应对方案。
    *   [ ] 团队负责人签字确认《使用规范草案》。

### Step 3: 历史数据迁移与清洗

*   **输入 (Inputs)**:
    *   现有的共享文件夹路径（如 NAS、FTP、百度网盘企业版导出包）。
    *   数据分类标准：
        *   A 类：活跃项目文档（近 6 个月）→ 迁移至飞书对应项目空间。
        *   B 类：归档资料（半年前）→ 打包压缩后存入飞书“归档区”文件夹。
        *   C 类：垃圾/重复文件 → 删除或不迁移。
*   **动作 (Actions)**:
    1.  **清理**：IT 人员遍历旧文件系统，删除明显过期、损坏或重复的文件，减少迁移体积。
    2.  **映射**：建立旧目录与新飞书空间的映射关系表（Mapping Table）。
    3.  **批量迁移**：
        *   对于文档类（Word/PDF/MD）：建议使用飞书官方的“导入工具”或直接拖拽，以便自动转换为在线文档（可选）。
        *   对于二进制文件（图片/视频/代码包）：直接拖拽至飞书云盘对应文件夹。
    4.  **校验**：抽样检查迁移后的文件完整性（MD5 对比或手动打开）。
*   **依赖 (Dependencies)**:
    *   需要足够的带宽时间窗口（建议在非工作时间执行大文件传输）。
    *   需要明确的数据保留策略（是否迁移 3 年前的冷数据？建议只迁移近 2 年，更早的留作本地备份）。
*   **预期产出 (Expected Outputs)**:
    *   飞书云盘中结构清晰的历史文件库。
    *   《数据迁移完成报告》：包含迁移总量、成功数、失败数及原因。
*   **验收方式 (Acceptance Criteria)**:
    *   [ ] 核心活跃项目（Top 5 项目）的所有文档在飞书中可检索、可编辑。
    *   [ ] 随机抽取 10 个不同大小的文件，确认可正常下载且内容无误。
    *   [ ] 旧系统中标记为“废弃”的文件未出现在新系统中。

### Step 4: 细粒度权限与安全配置

*   **输入 (Inputs)**:
    *   部门职能说明书。
    *   敏感数据分级标准（公开、内部、机密）。
    *   外部协作需求清单（哪些供应商/客户需要访问特定文件夹？）。
*   **动作 (Actions)**:
    1.  **目录重构**：根据“项目制”或“职能制”重组根目录结构。建议采用 `01_项目管理` / `02_技术架构` / `03_产品需求` / `04_人事行政` / `99_归档` 的一级结构。
    2.  **权限分配**：
        *   **默认私有**：新建文件夹默认为“仅创建者可见”。
        *   **项目级隔离**：每个项目创建一个独立空间，仅该项目成员拥有“可编辑”或“可阅读”权限。其他部门成员无权查看。
        *   **公共知识区**：设立“全员可见”的 Wiki 区域，存放规章制度、通用技术规范。
    3.  **外部协作配置**：
        *   关闭默认的“任何人可通过链接查看”选项。
        *   对外部协作者，使用“指定成员”方式添加，并设置有效期（如 30 天）。
    4.  **审计开启**：在后台开启“操作审计日志”，重点关注“下载”、“删除”、“权限变更”事件。
*   **依赖 (Dependencies)**:
    *   各部门负责人需确认本部门可见范围。
    *   法务/合规部门需审核外部分享策略。
*   **预期产出 (Expected Outputs)**:
    *   配置完毕的权限矩阵表。
    *   开启审计功能的后台截图证明。
*   **验收方式 (Acceptance Criteria)**:
    *   [ ] **负向测试**：A 部门员工尝试访问 B 部门的私有项目文件夹，提示“无权限”。
    *   [ ] **正向测试**：B 部门员工能正常读写自己项目的文档。
    *   [ ] **外部测试**：模拟外部用户通过链接访问受保护文件夹，无法获取内容；通过指定邀请可访问，但无法下载（若设置为禁止下载）。
    *   [ ] 审计日志中能看到上述测试的操作记录。

### Step 5: 全员培训与正式上线

*   **输入 (Inputs)**:
    *   《飞书团队使用手册》（含常见问题 FAQ）。
    *   30 分钟线上培训会排期。
    *   “新手引导”任务卡（每人需完成的 3 个小任务）。
*   **动作 (Actions)**:
    1.  **宣导**：发送全员邮件/公告，说明切换背景、时间节点（如：下周一正式停用旧系统写入权限）、联系方式。
    2.  **培训**：
        *   演示核心功能：如何搜索文档、如何发起版本回溯、如何分享文件给同事。
        *   强调红线：禁止使用个人网盘传输涉密代码。
    3.  **赋能**：发放“新手引导”任务卡，要求每位员工在上线首周内完成：
        *   Task 1: 登录并完善个人资料。
        *   Task 2: 在自己的个人空间中创建一篇测试文档。
        *   Task 3: 找到所在项目的入口并浏览一篇历史文档。
    4.  **监控与支持**：IT 管理员在群内值守，实时解答问题。每日下班前汇总 Top 3 高频问题并更新 FAQ。
*   **依赖 (Dependencies)**:
    *   管理层的支持（确保员工有时间参与培训和迁移）。
    *   旧系统的只读保留期（建议保留 1 个月，以防遗漏）。
*   **预期产出 (Expected Outputs)**:
    *   全员激活率报告。
    *   更新后的《FAQ 知识库》。
    *   正式停止旧系统写入的公告。
*   **验收方式 (Acceptance Criteria)**:
    *   [ ] 30 名员工中，至少 28 人（>90%）完成了“新手引导”任务卡。
    *   [ ] 连续 3 天，旧系统中无新增文件写入。
    *   [ ] 团队满意度调查（可选）：NPS 分数或主观评价达到“满意”以上。

## 3. 风险管理与应急预案 (Risk Management)

| 风险描述 | 概率 | 影响 | 缓解措施 (Mitigation) |
| :--- | :--- | :--- | :--- |
| **数据丢失**：迁移过程中文件损坏或遗漏 | 低 | 高 | 1. 迁移前对旧数据进行完整快照备份。<br>2. 迁移后执行 MD5 校验。<br>3. 保留旧系统只读权限 1 个月作为回滚兜底。 |
| **用户抵触**：员工习惯旧工具，不愿切换 | 中 | 中 | 1. 强调飞书在“版本管理”和“协同效率”上的具体收益（如：不再发多个版本的 Excel）。<br>2. 提供便捷的 Markdown 支持，降低研发门槛。<br>3. 管理层带头使用。 |
| **性能瓶颈**：大量并发下载导致网络拥堵 | 低 | 中 | 1. 错峰安排大型二进制文件的集中下载。<br>2. 利用飞书的 CDN 加速特性。<br>3. 若持续卡顿，联系飞书技术支持扩容带宽。 |
| **权限泄露**：误设权限导致敏感数据外泄 | 低 | 高 | 1. 严格执行“最小权限原则”，默认私有。<br>2. 开启审计日志，每周抽查一次异常访问记录。<br>3. 对外部分享必须经过二级审批。 |
