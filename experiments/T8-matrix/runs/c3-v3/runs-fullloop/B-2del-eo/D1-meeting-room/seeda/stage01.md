# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**最终产出**：一份《30人研发团队会议室预约系统选型报告》。
**核心约束**：
- 预算上限：2万元/年（硬性）。
- 用户规模：30人（中型团队，需考虑并发和权限管理）。
- 功能底线：支持 macOS/Windows/Web 三端；集成 Google Calendar + Outlook；门禁联动为可选加分项。
**报告结构要求**：推荐方案（含成本明细）、备选方案、淘汰理由。

---

## 2. 因素分解树（递归分解）

### 顶层影响因素（正交覆盖）
1. **功能兼容性因素 (Functionality & Compatibility)**
2. **成本与商业模式因素 (Cost & Business Model)**
3. **技术集成与部署因素 (Integration & Deployment)**
4. **用户体验与运维因素 (UX & Operations)**
5. **安全与合规因素 (Security & Compliance)** *(注：虽未明确提及，但企业级软件隐含要求，作为低优先级参考)*

#### 2.1 功能兼容性因素 (F)
*   **F1: 终端支持完整性**
    *   F1.1: Web 端可用性（浏览器兼容性，Chrome/Safari/Edge）。
    *   F1.2: 桌面端支持（macOS 原生/App Store, Windows 原生/MS Store）。
        *   *子因素*: 是否存在独立客户端或仅为 PWA？
    *   F1.3: 移动端支持（iOS/Android）—— *推导条件：虽然任务只提了三端，但研发人员常用手机查看日程，通常视为隐性需求，若不支持需标注为缺点。*
*   **F2: 日历双向同步能力**
    *   F2.1: Google Calendar API 集成深度（仅读取 vs 双向写入）。
    *   F2.2: Microsoft Outlook/Exchange API 集成深度。
    *   F2.3: 冲突检测机制（跨日历源的实时性）。
*   **F3: 会议室硬件联动能力**
    *   F3.1: 基础状态显示（空闲/占用）。
    *   F3.2: 门禁联动（可选）：是否支持 API 对接主流门禁系统（如 HID, ZKTeco, 海康威视等）？是否需要中间件？
    *   F3.3: 室内导航/指引（非必需，但影响体验）。

#### 2.2 成本与商业模式因素 (C)
*   **C1: 年度总拥有成本 (TCO)**
    *   C1.1: 软件订阅费（按席位/按会议室/固定包年）。
        *   *关键判断点*: 30人团队是买30个License还是按会议室数量计费？
    *   C1.2: 实施/部署费用（一次性）。
    *   C1.3: 硬件额外成本（如需专用面板/传感器，是否包含在预算内？任务说预算≤2万，通常指软件服务费，硬件若需另购可能超预算，需界定边界）。
*   **C2: 免费/开源选项可行性**
    *   C2.1: 是否有满足需求的开源 SaaS 或 Self-hosted 方案？
    *   C2.2: 自托管的服务器/维护人力成本折算是否超过2万？

#### 2.3 技术集成与部署因素 (T)
*   **T1: 部署模式**
    *   T1.1: SaaS (公有云)。
    *   T1.2: Private Cloud / On-premise (私有化部署)。
        *   *推导*: 30人团队通常倾向于 SaaS 以降低运维负担，除非有严格数据合规要求。
*   **T2: API 开放性与扩展性**
    *   T2.1: 是否有公开 RESTful API 供内部工具调用？
    *   T2.2: 门禁联动的实现难度（Low-code/High-code/预置连接器）。

#### 2.4 用户体验与运维因素 (U)
*   **U1: 易用性 (Adoption Rate)**
    *   U1.1: 学习曲线（员工无需培训即可上手）。
    *   U1.2: 界面直观性（拖拽预订、快速筛选）。
*   **U2: 管理后台功能**
    *   U2.1: 权限管理（谁能预订、谁可取消他人预订）。
    *   U2.2: 报表统计（利用率分析，用于后续优化）。
    *   U2.3: 异常处理（无脑占座、迟到释放策略）。

#### 2.5 安全与合规因素 (S)
*   **S1: 数据安全**
    *   S1.1: 数据存储位置（中国大陆节点 vs 海外节点，影响访问速度和合规性）。
    *   S1.2: 认证方式（SSO/OIDC 支持）。

## 3. 条件分类清单

### A. 人类已提供的条件 (Known Constraints)
1.  **用户规模**: 30人研发团队。
2.  **预算上限**: ≤ 20,000 RMB / 年。
3.  **必选平台**: macOS, Windows, Web。
4.  **必选集成**: Google Calendar, Outlook。
5.  **可选功能**: 门禁联动。
6.  **交付物**: 选型报告（推荐+备选+淘汰+成本）。

### B. 从项目推导的条件 (Derived Assumptions)
1.  **部署偏好倾向**: 鉴于30人规模和预算限制，**SaaS 模式**为首选考量对象，私有化部署因服务器和维护人力成本极高，大概率超出2万预算（除非使用极低成本云服务且忽略人力，但这不符合常理）。*标注：此为高概率假设，需在阶段02验证是否存在极低成本的私有化轻量方案。*
2.  **计费模型推测**: 多数此类软件按“会议室数量”或“活跃用户数”收费。若按30人全量购买License，单价需控制在 ~666 RMB/人/年以内才符合预算。若按会议室（假设5-10间），单价空间更大。*标注：具体计费逻辑待研究。*
3.  **地域属性**: 用户提及中文语境及人民币预算，推断主要面向**中国市场**或使用全球通用SaaS在中国可用。需区分“国内SaaS”和“国际SaaS（需翻墙/支付外币）”。*标注：支付渠道和网络可达性是潜在阻塞点。*

## 4. 候选对象类别冻结 (Candidate Set Freeze)

为防止阶段02漂移，本阶段冻结以下**候选类别**。阶段02必须在此范围内进行检索和核验，不得随意引入全新类别（除非发现原类别完全失效并记录理由）。

1.  **国内协同办公套件内置模块**
    *   *代表假设*: 飞书会议室、钉钉智能会议室、企业微信关联插件。
    *   *特点*: 通常与IM深度绑定，价格可能随套件套餐浮动，集成日历方便，但灵活性可能受限。
2.  **国际通用SaaS预约平台**
    *   *代表假设*: Calendly (Team/Enterprise), Acuity Scheduling, Snagajob, Eventbrite (Room booking).
    *   *特点*: 功能强大，UI现代，但存在网络/支付门槛，价格通常以美元计。
3.  **垂直领域会议室管理系统 (Vertical VMS)**
    *   *代表假设*: RoomRes, Opus2, Spacewell, Smart Meeting Room Solutions.
    *   *特点*: 专为会议室设计，功能最全（含门禁、访客、资产），价格较高，可能有起售门槛。
4.  **开源/自托管轻量级方案**
    *   *代表假设*: Unify, OpenBooking, Nextcloud Rooms.
    *   *特点*: 软件免费，但需服务器成本和IT维护人力。对于30人团队，除非有专职IT，否则“隐形成本”极高。
5.  **定制化/白标解决方案**
    *   *排除理由预判*: 通常起步价远超2万，且开发周期长。*暂列为观察项，若前四类均无法满足，再深入调研。*

*(注：以上具体产品名称均为“待验证的研究目标”，不代表其一定符合所有约束，例如Calendly可能不直接支持Outlook双向同步，需阶段02核实。)*

## 5. 阶段 02 研究入口与行动指南

阶段02应基于上述空缺和候选类别执行以下动作：

### 第一批优先研究动作 (P0)
1.  **构建候选短名单 (对应 G1)**:
    *   **搜索词策略**:
        *   国内: "会议室预约系统 SaaS", "飞书会议室定价", "钉钉会议室功能", "中小企业会议室管理软件".
        *   国际: "Meeting room booking software comparison", "Calendly vs Acuity for meeting rooms", "Room reservation software pricing".
    *   **筛选标准**: 必须有Web端，必须声称支持Google/Outlook集成。
    *   **输出**: 一个包含5-8个候选产品的表格，列出初步印象。

2.  **价格核验 (对应 G2, G5)**:
    *   **动作**: 访问官网 Pricing 页面。
    *   **字段提取**:
        *   最低套餐价格。
        *   计费单位（Per user / Per room / Flat rate）。
        *   货币及支付方式。
        *   是否有免费层。
    *   **计算**: 将价格换算为 RMB/年，判断是否 ≤ 20,000。
    *   **失败备用路径**: 若官网价格模糊，需发送邮件/联系销售获取Quote。记录响应时间。

3.  **功能矩阵验证 (对应 G3, G4)**:
    *   **动作**: 查阅 Help Center 或 FAQ，重点搜索 "Outlook integration", "Google Calendar sync", "Access control", "API documentation"。
    *   **关键判定**:
        *   是否支持**双向**同步？(很多工具只支持单向创建事件)。
        *   门禁联动是“原生支持”还是“通过API自行开发”？若是后者，评估30人团队是否有能力/预算做二次开发。

### 第二批次要研究动作 (P1)
4.  **用户体验评测 (对应 U1, U2)**:
    *   **来源**: G2 Crowd, Capterra, Trustpilot, 知乎/小红书用户评价。
    *   **关注点**: 员工抱怨最多的点是什么？（如：同步不同步、界面复杂、客服慢）。

5.  **合规与网络测试 (对应 G5, G7)**:
    *   **动作**: 尝试在国内网络环境下访问国际SaaS官网（不使用VPN），记录是否可访问。
    *   **检查**: 隐私政策中的数据存储地。

### 失败备用路径 (Fallback)
*   若所有国际SaaS因网络/支付原因被排除 -> 聚焦国内SaaS。
*   若国内SaaS均无法同时满足“Google+Outlook”双集成（常见痛点，国内软件多侧重钉钉/企微日历）-> 考虑**混合方案**：使用开源日历服务器（如Nextcloud）+ 简易前端，或寻找支持ICS文件导入导出的轻量级工具，手动同步（体验差，作为最后备选）。
*   若所有商用SaaS均超预算 -> 重新评估“自建”成本，或降低功能要求（如放弃Outlook，仅用Google，因为研发常用Git/GitHub，可能更偏Google生态？需确认用户实际日历主力）。

## 6. 判定原则自查

*   **因素正交**: 功能、成本、技术、体验、安全五个维度基本互斥，覆盖了选型的主要决策面。
*   **覆盖目标**: 预算、三端、日历、门禁均有对应因素。
*   **边界清晰**: 明确了SaaS为主流，私有化为高风险备选；明确了2万预算为硬约束。
*   **空缺完整**: 价格、集成深度、网络可达性、门禁实现路径均未假定，列入空缺。
*   **研究路径具体**: 提供了具体的搜索词、网站类型、字段提取要求和失败路径。
*   **未伪装事实**: 所有具体产品名均标记为“假设/待验证”，未断言某产品一定符合预算。

**结论**: 本工件已将任务分解为可执行的研究单元，阶段02可立即依据“第一批优先研究动作”开始工作。
