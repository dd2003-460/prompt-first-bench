# 阶段 01：目标分解、已知与空缺条件

## 1. 目标交付物定义
**核心交付物**：一份可交付的《会议室预约系统选型报告》。
**报告必须包含的内容**：
1. **推荐方案**：单一最佳选择，需满足所有硬性条件。
2. **备选方案**：至少一个次优但可行的选择。
3. **淘汰理由**：针对每个未入选候选（含被排除类别）的具体理由。
4. **完整成本明细**：年度总成本拆解，必须 $\le$ 20,000 CNY。
5. **合规性验证表**：证明所选方案满足 macOS/Windows/Web 三端支持及 Google/Outlook 双日历对接。
6. **加分项评估**：门禁联动能力的存在性及实现难度评估。

## 2. 影响因素递归分解

### 顶层因素 (L1)

#### L1-1: 功能兼容性 (Functional Compatibility)
*边界：软件是否能运行在指定硬件/OS上，以及能否集成指定第三方服务。*
*   **L1-1-a: 客户端平台支持**
    *   *子因素*: macOS 原生或兼容支持。
    *   *子因素*: Windows 原生或兼容支持。
    *   *子因素*: Web 浏览器访问能力（无需安装客户端即可用）。
    *   *约束*: 三者必须同时满足。若仅支持移动端 App 而无桌面/Web 版本，则淘汰。
*   **L1-1-b: 日历双向同步能力**
    *   *子因素*: Google Calendar API/插件集成状态（只读 vs 双向读写）。
    *   *子因素*: Microsoft Outlook (Exchange/Office 365) API/插件集成状态。
    *   *约束*: 必须同时支持两套生态。通常通过 CalDAV 标准接口或官方 OAuth 插件实现。

#### L1-2: 经济可行性 (Economic Feasibility)
*边界：总拥有成本 (TCO) 是否在预算内。*
*   **L1-2-a: 软件许可费 (License Cost)**
    *   *子因素*: SaaS 订阅模式下的 per-user/month 价格。
    *   *子因素*: 是否提供免费版/社区版且功能受限？
    *   *子因素*: 一次性买断制软件的价格及后续维护费。
    *   *计算逻辑*: $Cost_{annual} = Price_{per\_user} \times 30 \times 12$。
*   **L1-2-b: 基础设施与实施成本**
    *   *子因素*: 私有部署服务器成本（若选自托管方案）。
    *   *子因素*: IT 人员配置/调试时间成本（折算为机会成本或直接人力成本）。
    *   *子因素*: 门禁硬件改造费用（若启用加分项）。
*   **L1-2-c: 预算红线**
    *   *约束*: $Total Annual Cost \le 20,000$ CNY。
    *   *推导*: 人均年预算上限 $\approx 666$ CNY/人/年 ($\approx 55$ CNY/人/月)。这是一个非常紧的预算约束，直接限制了高端商业 SaaS 的选择范围。

#### L1-3: 运维与管理复杂度 (Operational Complexity)
*边界：系统上线后的维护负担对 30 人小团队的影响。*
*   **L1-3-a: 部署模式**
    *   *子因素*: SaaS (云端托管) vs Self-hosted (本地/私有云部署)。
    *   *影响*: SaaS 降低运维负担但增加持续订阅费；Self-hosted 可能免费但增加服务器管理和安全维护负担。
*   **L1-3-b: 用户上手难度**
    *   *子因素*: 界面直观性。
    *   *子因素*: 培训需求。
*   **L1-3-c: 稳定性与可靠性**
    *   *子因素*: SLA 保障（SaaS 通常有，自建取决于运维水平）。

#### L1-4: 扩展性与加分项 (Extensibility & Bonus)
*边界：超出基本需求的额外价值。*
*   **L1-4-a: 门禁联动 (Access Control Integration)**
    *   *子因素*: 是否提供 API 或与主流门禁品牌（如 HID, ZKTeco, 海康威视等）的原生连接器。
    *   *子因素*: 若无可原生集成，开发中间件的成本和时间。
    *   *性质*: 可选。若无此功能，不导致淘汰，但会降低评分。

#### L1-5: 数据安全与隐私 (Security & Privacy)
*边界：员工会议数据的安全存储位置。*
*   **L1-5-a: 数据存储地**
    *   *子因素*: 数据是否存储在境外（部分国内企业可能有合规顾虑，虽任务书未强制要求境内存储，但需作为风险点记录）。
*   **L1-5-b: 权限管理**
    *   *子因素*: 是否支持基于角色或部门的会议室可见性控制。

## 3. 候选对象类别冻结 (Candidate Set Freeze)

基于上述因素，阶段 02 应聚焦于以下三类候选对象。任何新增类别需在阶段 02 显式记录。

1.  **商业 SaaS 平台 (Commercial SaaS)**
    *   *特征*: 按人头订阅，开箱即用，无服务器维护。
    *   *典型代表 (待验证)*: Calendly, Acuity Scheduling, SimplyBook.me, YouCanBookMe, MeetingBar, RoomGuru (可能偏贵), 国内产品如“腾讯会议会议室模块”、“钉钉会议室”、“飞书会议室”（需注意是否独立计费或包含在套件中）。
    *   *关注点*: 单价是否低于 55 RMB/人/月；是否支持多会议室视图；API 开放性。

2.  **开源/自托管解决方案 (Open Source / Self-Hosted)**
    *   *特征*: 软件免费，需自行部署服务器和维护。
    *   *典型代表 (待验证)*:
        *   `Nextcloud` + `Rooms` App (如果可用)
        *   `Roomster` (GitHub 项目，需验证活跃度)
        *   `FreeScout`? (No, that's email) -> 寻找专门的小众 GitHub 项目，如 `room-reservation-system`。
        *   *替代思路*: 使用通用的日程管理软件（如 `Radicale` for CalDAV server）配合前端定制？(复杂度高，可能不适合 30 人团队快速落地)。
    *   *关注点*: 部署难度、社区活跃度、安全性、隐性人力成本。

3.  **混合/轻量化方案 (Hybrid/Lightweight)**
    *   *特征*: 利用现有办公套件的高级功能或简单脚本。
    *   *典型代表 (待验证)*:
        *   **Google Workspace 高级版**: 本身不包含独立的“物理会议室锁定”功能，但可以通过共享日历 + 简单的自动化脚本（Apps Script）实现预约逻辑。
        *   **Microsoft 365 Teams/Outlook**: 利用 Outlook 共享日历 + 会议室资源账号。这是最“原生”的方案，但缺乏可视化的大屏显示和门禁联动。
        *   **低代码平台**: 使用 Airtable, Notion, 或国内的宜搭/简道云搭建简单的预约表单 + 日历视图。
    *   *关注点*: 功能完整性（是否有实时占用显示）、用户体验、长期维护性。

**排除类别说明**：
*   *纯硬件一体机*: 排除。通常单台设备成本远超 2 万预算，且不满足软件层面的多端支持灵活性。
*   *大型 ERP 模块*: 排除。实施周期长，成本高，杀鸡用牛刀。

## 4. 阶段 02 研究行动指南 (Stage 02 Action Plan)

### 第一批优先行动 (High Priority)

1.  **筛选 SaaS 短名单 (针对 U1, U2, U3)**
    *   *动作*: 访问以下网站获取最新价格和功能矩阵：
        *   Calendly.com/Pricing
        *   Acuityscheduling.com/pricing
        *   Simplybook.me/pricing
        *   Trello/Asana (检查是否有会议室插件，通常较贵或不适用)
        *   国内: 钉钉开放平台/飞书开放平台 (查询会议室管理组件价格)。
    *   *字段提取*: 最低套餐名、每用户月费 (USD/CNY)、最大用户数限制、是否支持 Web、是否支持 GCal/Outlook 双向同步。
    *   *判定规则*: 若 $Price \times 30 \times 12 > 20,000$，标记为“超预算”，除非有显著加分项且预算可弹性微调（任务书说“不超过”，故严格超标即淘汰，除非能找到团购价）。

2.  **评估原生 Office/Google 方案 (针对 L1-3, U7)**
    *   *动作*: 研究 Microsoft 365 Business Standard/Premium 中会议室资源的使用方式。
    *   *关键问题*: 是否需要额外付费？体验如何？能否生成简单的 Web 链接供访客查看空闲状态？
    *   *预期*: 这可能是成本最低（如果公司已订阅 M365/GWS）且最稳定的方案，但缺乏“酷炫”的门禁联动和可视化大屏。

3.  **调研开源选项可行性 (针对 U4)**
    *   *动作*: 在 GitHub 搜索 `meeting room reservation system`, `room booking web app`。
    *   *重点考察*: 星数 > 100，最近一年有 Commit 的项目。
    *   *成本估算*: 假设租用一台 2核4G 云服务器 (约 100-200 RMB/月)，加上域名和证书。主要成本在于 IT 人员的配置时间。

### 第二批行动 (Medium Priority)

4.  **门禁联动技术预研 (针对 U5)**
    *   *动作*: 选定 2-3 个潜在入围方案后，查阅其 API 文档。
    *   *关键词*: "Webhook", "API documentation", "Integration with access control".
    *   *若无可直接集成*: 评估编写一个简单的 Python Node.js 中间件监听预约成功事件并调用门禁 API 的工作量（预计 1-3 天开发）。

### 失败备用路径 (Fallback)

*   *若所有商业 SaaS 均超预算*: 转向“混合方案”，即使用免费的 Google/Outlook 共享日历作为核心，配合一个极低成本的开源看板或简单的 HTML 页面展示状态，放弃复杂的自动门禁联动，改为人工扫码或手动授权。
*   *若开源方案过于陈旧*: 考虑使用 No-Code 工具（如 Airtable + Make/Zapier）构建简易工作流，虽然美观度差，但成本低且灵活。
