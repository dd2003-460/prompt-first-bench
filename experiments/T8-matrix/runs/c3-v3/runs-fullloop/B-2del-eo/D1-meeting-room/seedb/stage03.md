# 阶段 03：具体行动分解（无 owner 组件）

基于阶段 02 的调研结论，**推荐方案**为“飞书标准版 + 自定义门禁中间件”，**备选方案**为“自建轻量级 Web 应用”。

考虑到任务要求产出“可交付报告”且包含“完整成本明细”，本阶段将执行路径锁定为 **主推荐方案（飞书）**，因为其在预算、合规性和运维复杂度上得分最高，且无需承担自建的长期技术债风险。同时，我们将把“自建方案”作为 Plan B 保留在应急流程中，但主要执行步骤围绕飞书展开。

以下是具体的可执行步骤分解：

---

## 执行目标
在 **5 个工作日** 内完成选型确认、配置部署、集成测试及最终报告撰写，确保系统满足 30 人团队需求，总年度成本控制在 2 万元人民币以内。

## 前置条件 (Pre-conditions)
1. 已获取公司 IT 管理员权限或能联系到 IT 部门协助开通企业账号。
2. 已知晓当前使用的门禁品牌型号（如海康威视、ZKTeco 等），以便评估 API 接口可用性。
3. 已确认团队成员日常主要使用的日历客户端分布（GCal vs Outlook 比例）。

---

### Step 1: 商务采购与账号初始化
*   **输入**:
    *   员工名单（30 人邮箱/手机号）。
    *   年度预算上限：20,000 CNY。
    *   飞书官网定价页数据（参考阶段 02：标准版约 30 CNY/人/月）。
*   **动作**:
    1. 登录飞书开放平台或企业版购买页面，申请试用或正式购买“飞书标准版”30 席位。
    2. 核对报价单，确认是否包含“会议室资源管理”功能模块（通常基础版即含，若不含需升级至专业版并重新核算成本）。
    3. 完成支付（预计支出：$30 \times 30 \times 12 = 10,800$ CNY）。
    4. 创建企业管理员账号，导入 30 名员工信息，建立组织架构。
*   **依赖**:
    *   财务审批流程。
    *   飞书官方销售支持（如需议价或确认功能包）。
*   **预期产出**:
    *   激活的飞书企业租户。
    *   30 个已绑定的用户账号。
    *   发票/合同存档。
*   **验收方式**:
    *   所有 30 名员工收到邀请邮件并可正常登录。
    *   后台显示席位状态均为“已激活”。
    *   实际支付金额 $\le$ 12,000 CNY（预留缓冲）。

### Step 2: 核心功能配置（会议室与多端适配）
*   **输入**:
    *   物理会议室列表（名称、容量、设备配置，如投影仪、白板）。
    *   工作时间规则（如 9:00-18:00，周末不可预约）。
*   **动作**:
    1. 进入飞书管理后台 -> 日历设置 -> 会议室管理。
    2. 创建所有物理会议室资源，设置属性（容纳人数、可用时间段）。
    3. 配置默认提醒策略：会议开始前 15 分钟通知参会人和房间。
    4. 验证三端体验：
        *   macOS/Windows 客户端安装最新版飞书。
        *   浏览器访问 `calendar.feishu.cn`。
        *   移动端（iOS/Android）测试查看空闲时段和预约操作。
    5. 进行冲突检测测试：两人同时预约同一房间同一时间，确认系统拦截并提示冲突。
*   **依赖**:
    *   行政人员提供准确的会议室清单和设备状态。
*   **预期产出**:
    *   配置完成的会议室资源池。
    *   三端可用的日历界面。
*   **验收方式**:
    *   在 macOS、Windows、Web 端均能看到相同的会议室列表。
    *   成功创建一个包含会议室的会议，并在各端同步显示。
    *   尝试重叠预约被系统拒绝。

### Step 3: 日历对接实施（Google Calendar & Outlook）
*   **输入**:
    *   员工的 Google Workspace 或 Microsoft 365 账号信息。
    *   飞书 CalDAV 文档说明。
*   **动作**:
    1. **策略确定**：鉴于阶段 02 分析，采用 **“飞书为主，外部日历为辅”** 的策略，或 **“双向单向同步”** 策略。
        *   *场景 A (全员用 GCal/Outlook)*: 指导员工在 GCal/Outlook 中订阅飞书生成的 ICS 链接（只读视图，用于看占用情况），或在飞书中添加外部日历（只读，用于看个人日程）。
        *   *场景 B (混合使用)*: 对于重度 GCal 用户，使用第三方连接器（如 Zapier 免费层或飞书官方连接器若可用）实现关键事件的双向同步。若无法实现完美双向，需在报告中明确“以飞书为准”的操作规范。
    2. **批量配置**：
        *   生成飞书会议室共享日历链接（ICS URL）。
        *   编写简短的操作指南（SOP），教员工如何在 Outlook/GCal 中添加该 ICS 链接以查看房间占用。
        *   （可选进阶）若团队中有 1-2 名工程师，编写一个简单的 Python 脚本，定期从飞书 API 拉取未来 7 天的会议室占用数据，并推送到 GCal/Outlook 的公共日历中（模拟双向写回，降低实时性要求，提高稳定性）。
    3. **测试同步延迟**：在飞书创建会议，检查 GCal/Outlook 中是否在 5 分钟内出现该事件（取决于轮询频率或 Webhook 触发）。
*   **依赖**:
    *   员工的日历账号权限。
    *   （若开发脚本）Python 环境及飞书 App ID/Secret。
*   **预期产出**:
    *   《会议室预约操作手册》v1.0（含 GCal/Outlook 对接教程）。
    *   （若有脚本）自动同步服务运行日志。
*   **验收方式**:
    *   随机抽取 3 名分别使用 GCal、Outlook 和飞书的员工。
    *   员工 A 在飞书预约房间，员工 B 在 GCal 中能立即/短时间内看到该房间忙碌。
    *   员工 C 在 Outlook 中查看房间状态正确。
    *   无重大数据冲突导致的双重预订事故。

### Step 4: 门禁联动开发与测试（加分项）
*   **输入**:
    *   门禁厂商 API 文档（假设现有门禁支持 HTTP API）。
    *   飞书开放平台 “事件订阅” 文档。
    *   一台内网服务器或云函数计算实例（Serverless）。
*   **动作**:
    1. **架构设计**：
        *   监听源：飞书开放平台 -> 事件 `calendar.event.created` 和 `calendar.event.deleted`。
        *   处理逻辑：解析事件 JSON，提取 `start_time`, `end_time`, `attendees`, `room_id`。
        *   执行动作：调用门禁 API `open_door(room_id, duration=30s)`。
    2. **代码开发**：
        *   使用 Python (Flask/FastAPI) 搭建轻量级 Webhook 接收器。
        *   实现签名校验（防止伪造请求）。
        *   实现重试机制（网络超时重试 3 次）。
        *   实现日志记录（谁在什么时候开了门，用于审计）。
    3. **安全加固**：
        *   仅允许来自飞书 IP 段或特定 Token 的请求。
        *   限制开门时长，防止门常开。
    4. **联调测试**：
        *   模拟发送飞书事件 JSON 到本地服务。
        *   观察门禁控制器是否收到开门指令。
        *   测试异常场景：会议取消时，不发送开门指令；网络断开时，服务重启后恢复。
*   **依赖**:
    *   门禁硬件的网络可达性（需 IT 开放防火墙端口）。
    *   开发人员工时（预估 8-16 小时）。
*   **预期产出**:
    *   门禁联动微服务代码仓库。
    *   部署好的自动化开门服务。
    *   测试报告（成功/失败用例统计）。
*   **验收方式**:
    *   在飞书中创建一个 10 分钟后的会议室会议。
    *   会议开始前 30 秒，对应会议室的门自动解锁 30 秒。
    *   会议结束后，门锁恢复常态。
    *   若会议取消，门不开启。

### Step 5: 成本核算与最终报告撰写
*   **输入**:
    *   Step 1 的实际采购发票。
    *   Step 4 的服务器/云函数费用账单（若有）。
    *   Step 3 & 4 的人力工时估算（内部折算）。
    *   阶段 02 的淘汰理由表。
*   **动作**:
    1. **成本明细汇总**：
        *   **软件许可费**：飞书标准版年费 (10,800 CNY)。
        *   **基础设施费**：门禁联动 Serverless 函数或轻量服务器 (预估 500-1,500 CNY/年，若使用公司闲置资源则为 0)。
        *   **人力成本 (机会成本)**：
            *   配置与培训：20 小时 × 100 CNY/h = 2,000 CNY。
            *   门禁开发：16 小时 × 150 CNY/h (高级工程师) = 2,400 CNY。
            *   *注：若不计入内部人力现金支出，则直接现金成本仅为 ~12,300 CNY。若计入全口径 TCO，约为 16,700 CNY。两者均低于 20,000 CNY 预算。*
        *   **总计**：直接现金支出 ~12,300 CNY < 20,000 CNY 预算。✅ 达标。
    2. **撰写《会议室预约系统选型与实施报告》**：
        *   **摘要**：推荐飞书方案，满足所有硬性指标，具备门禁联动能力，成本低。
        *   **推荐方案详情**：架构图、操作流程、成本明细表。
        *   **备选方案对比**：简述自建方案的优缺点，解释为何未选择（维护成本高、初始投入大）。
        *   **淘汰方案清单**：引用阶段 02 表格，列出 Calendly, Acuity, Nextcloud 等被淘汰的具体原因（超预算、功能缺失、体验差）。
        *   **风险评估与缓解**：
            *   风险：CalDAV 同步延迟。缓解：制定“以飞书为准”的 SOP。
            *   风险：门禁 API 不稳定。缓解：增加心跳检测和告警。
        *   **后续建议**：每季度审查一次 SaaS 价格变动；每年更新一次门禁联动脚本兼容性。
*   **依赖**:
    *   各部门反馈的使用体验（可选，用于完善报告）。
*   **预期产出**:
    *   PDF 格式的最终交付报告。
    *   Excel 格式的成本明细表。
*   **验收方式**:
    *   报告包含所有必需章节（推荐、备选、淘汰、成本）。
    *   成本数字经过复核，准确无误。
    *   管理层签字确认批准该方案。

## 风险与应急预案 (Contingency)

| 风险点 | 概率 | 影响 | 应对措施 |
| :--- | :---: | :---: | :--- |
| **飞书标准版不含高级会议室功能** | 低 | 高 | 立即切换至 **备选方案：自建轻量级 Web 应用**。利用剩余预算购买服务器，启动 Django 项目，周期延长 2 周。 |
| **门禁品牌不支持开放 API** | 中 | 中 | 降级为 **“人工+短信通知”** 模式。飞书预约成功后，通过钉钉/飞书机器人推送消息给前台，由前台手动刷卡开门。虽失去自动化加分项，但核心功能不受影响。 |
| **Outlook/GCal 同步冲突频发** | 中 | 中 | 强制推行 **“单一事实来源”** 政策：所有会议室预约必须在飞书发起。外部日历仅作为只读视图展示，禁止在外部日历直接修改会议室状态。 |
| **汇率波动导致超预算** | 低 | 低 | 当前主要为人民币结算，风险极低。若涉及外币支付，锁定汇率或使用信用卡分期免息。 |
