# 30人研发团队会议室预约系统选型最终报告

## 1. 执行摘要 (Executive Summary)

基于对预算（<2万 RMB/年）、多端兼容性（macOS/Windows/Web）及日历集成能力（Google Calendar & Outlook）的严格筛选，本报告推荐采用 **“飞书（Feishu/Lark）免费版 + 轻量级自研同步脚本”** 作为核心方案。该方案以零软件许可成本、原生支持全平台及双日历生态对接的优势，完美契合硬性指标，并通过极低的开发投入实现门禁联动等加分项。

## 2. 推荐方案：飞书（Feishu）会议室模块 + 自定义同步服务

### 2.1 方案架构
*   **核心载体**：使用飞书企业版（或标准版，视团队规模而定，30人通常免费额度充足）内置的“会议室”功能。
*   **日历对接策略**：
    *   **Outlook 用户**：通过 Microsoft Graph API 将 Outlook 日历与飞书日程进行双向同步（利用开源库 `msgraph-sdk` 或 Zapier 低代码连接）。
    *   **Google Calendar 用户**：通过 Google Calendar API 实现双向同步。
    *   **统一入口**：所有预约最终落地在飞书日程中，确保状态一致性。
*   **三端支持**：飞书客户端原生支持 macOS、Windows 桌面端及 Web 端，无需额外开发 UI。
*   **门禁联动（加分项）**：若现有门禁系统支持 HTTP API 或 MQTT，可编写一个轻量级 Node.js/Python 监听器，当检测到飞书会议室被占用时，推送信号至门禁控制器锁定/解锁对应区域（或仅用于数据展示）。

### 2.2 核心理由
1.  **成本优势极大**：飞书基础协作功能免费，30人团队远低于付费阈值。主要成本仅为潜在的 API 调用费（极低）和少量内部人力开发时间。
2.  **全平台原生覆盖**：无需维护三个独立的客户端，UI/UX 一致性好，降低用户学习成本。
3.  **双日历生态兼容**：虽然飞书不与 GCal/Outlook 直接原生互通，但通过成熟的 API 中间件可实现稳定同步。对于混合日历环境的团队，这是最稳妥的低成本路径。
4.  **扩展性强**：飞书开放平台允许轻松接入第三方硬件（如门禁、投影仪），满足未来需求。

## 3. 备选方案

### 备选方案 A：Notion + Calendly + Zapier (SaaS 组合拳)

*   **描述**：使用 Notion 作为会议室资源看板，Calendly 处理具体时段预约逻辑，Zapier 负责将 Calendly 的事件同步到 Google Calendar 和 Outlook。
*   **对比优势**：
    *   **零代码配置**：无需开发人员介入，业务人员即可自行搭建和维护。
    *   **高灵活性**：Notion 页面可高度自定义，适合喜欢可视化看板的团队。
*   **对比劣势**：
    *   **成本高**：Calendly 团队版约 $25-30/月，Zapier 任务量较大时需订阅 Pro 计划（~$20/月），Notion 高级版可选。年成本估算约 ¥1.8 - 2.5 万，逼近或超出预算上限。
    *   **同步延迟与稳定性**：依赖第三方 Zapier 中转，存在同步延迟和失败风险，需额外监控。
    *   **移动端体验割裂**：Web 端体验好，但 Mac/Win 桌面端缺乏原生应用，依赖浏览器，体验略逊于原生客户端。

### 备选方案 B：自建轻量级系统 (Node.js/React + PostgreSQL)

*   **描述**：完全自主开发一个基于 React 的前端（适配 Web/Mac/Win via Electron 或 PWA）和 Node.js 后端，直接调用 GCal/Outlook API。
*   **对比优势**：
    *   **完全定制化**：可完美贴合团队工作流，无功能限制。
    *   **数据主权**：所有数据存储在自有服务器，隐私性最高。
*   **对比劣势**：
    *   **隐性成本极高**：虽然软件 License 为 0，但需要至少 1 名全栈工程师投入 2-4 周进行开发、测试及后续维护。按 30 人团队平均人力成本折算，开发+首年维护成本极易超过 2 万元预算。
    *   **维护负担**：API 变更、Bug 修复、安全补丁均需内部团队承担，长期运维压力大。

## 4. 淘汰理由

| 候选方案 | 淘汰原因 | 详细依据 |
| :--- | :--- | :--- |
| **Zoom Rooms / Teams Rooms** | **超预算且封闭** | 这两款产品主要服务于音视频会议，其房间管理模块通常绑定昂贵的许可证（Teams Rooms 需额外购买，Zoom Rooms 需硬件或高级订阅）。此外，它们难以低成本地同时深度对接 GCal 和 Outlook 进行纯日程预约，且 30 人规模下采购专用硬件或软件授权远超 2 万预算。 |
| **Microsoft Bookings** | **单日历生态局限** | 虽然与 Outlook 无缝集成，但对 Google Calendar 的支持极其有限（基本不支持双向同步）。对于混用 GCal 的团队，会导致大量手动操作，无法满足“同时对接两套日历”的硬性条件。 |
| **通用 SaaS 如 Acuity Scheduling** | **功能不匹配** | 这类工具侧重于个人/小团队的客户预约，缺乏针对企业内部“会议室资源池”的管理功能（如设备列表、容量限制、多人协同编辑），且中文本地化及国内网络访问速度可能成为痛点。 |
| **钉钉会议室** | **同飞书竞争，但生态稍弱** | 钉钉同样符合大部分条件。但在全球化和 Google Calendar 集成的社区插件丰富度上，飞书（Lark）在国际开发者社区中的 API 文档友好度和第三方集成案例略多于钉钉，尤其在跨国或混合日历环境下，飞书的国际化背景使其在 GCal 对接上更自然。*(注：若团队已重度使用钉钉，此方案可作为并列推荐)* |

## 6. 风险与缓解措施

| 风险类别 | 风险描述 | 概率 | 影响 | 缓解措施 |
| :--- | :--- | :--- | :--- | :--- |
| **技术风险** | Google/Outlook API 密钥过期或配额限制导致同步中断 | 中 | 高 | 1. 设置 API 调用监控告警。<br>2. 在同步脚本中加入指数退避重试机制。<br>3. 预留备用 API 密钥并定期轮换。 |
| **数据一致性** | 双向同步过程中出现冲突（如用户在两端同时修改同一时间段） | 中 | 中 | 1. 采用“最后写入胜出”（Last Write Wins）策略，并在飞书端标记冲突记录供人工审核。<br>2. 禁止在飞书端直接创建与外部日历重叠的会议，强制通过外部日历发起后同步。 |
| **用户习惯** | 部分用户不愿切换新系统，继续手动操作 | 低 | 中 | 1. 提供简洁的操作手册。<br>2. 前两周由 IT 支持人员驻场指导。<br>3. 强调“一键预约”带来的效率提升，而非强制命令。 |
| **门禁联动失效** | 门禁系统老旧，无法提供 API 接口 | 高 | 低 | 1. 将此功能定义为“Nice-to-have”，不作为核心验收标准。<br>2. 若无法联动，仅通过飞书机器人发送通知给安保人员，实现“软联动”。 |

## 7. 下一步行动建议

1.  **第 1 天**：申请飞书企业管理员权限，开通会议室功能，配置 3-5 个典型会议室信息。
2.  **第 2-3 天**：开发/部署简单的 Node.js 同步脚本，打通 1 个 Google Calendar 和 1 个 Outlook 账号的测试环境。
3.  **第 4-5 天**：选取 5 名不同操作系统（Mac/Win）和不同日历（GCal/Outlook）的员工进行内部 Beta 测试。
4.  **第 6 天**：根据反馈调整同步频率和冲突处理逻辑，全员推广。
5.  **第 7 天**：评估门禁联动可行性，若有现成 API 则集成，否则归档需求。
