## 2. 反驳角度逐条 verdict

verdict 取值：**成立**（该角度确实构成有效威胁/限制）/ **不成立**（被本轮数据否定）/ **无法判定**（现有数据不足）。

### 角度 1 · n 太小（每格仅 2 reps）

- 证据：逐 run M1 的 rep 极差 S8E-Q1 0.500、S8E-Q4 0.400、S7-Q4 0.333、S7V-Q1 0.162、S7V-Q4 0.133（`scores.json`）；而组间 Δ(S8E−S7V) 仅 0.102（Q1 M1）/ −0.333（Q4 M1）。噪声 ≥ 信号。
- 能否推翻结论：能。Q1 的 +0.1139 total 优势完全落在 rep 噪声范围内，不能当成"提升"。
- **Verdict：成立**。这也是 `03-iteration.md` 不扩展的核心理由。

### 角度 2 · 同族 judge 自评偏置

- 证据：本轮 judge 是 `qwen3.8-27b ×1, non-IRR`（`sop/arena-loop-pipeline.md` §3.1：同底座两遍都只算"上下文独立"，不算"家族独立"，本轮连两遍都没有）；`score.py:5` 自述 "judge 非独立模型"。paper §4.5 用异族 judge 估过同族偏置 ≈0.15（保守方向），但**本轮没有异族复核**，无法量化本次偏置。
- 能否推翻结论：偏置确实存在，影响所有绝对分数；但三臂共用同一 judge，偏置在相对比较上大致抵消，所以主要威胁是"绝对分数不可外推"，而非"三臂排序一定错"。
- **Verdict：成立**（偏置存在且未量化，属硬限制）；其对"三臂相对排序"的具体影响 **无法判定**（缺异族 judge，本轮按任务书不派 arena、不联网）。

### 角度 3 · Q1 源缺失导致的天花板

- 证据：paper §5.1 finding (4) 已写明 Q1 源里真缺 PCIe-vs-SXM 吞吐数据；本轮 `02-experiment.md` §2.2 的注入来源里第 3 条 `thundercompute.com` 的 snippet 只是网页导航文本（Products/Resources/TABLE OF CONTENTS…），不含规格数字。Q1 的 M1 三臂均不高（S7V 0.4813、S8E 0.5833），且明显低于 Q4 的 S7V 0.9333。
- 能否推翻结论：能。Q1 上 S8E 的"优势"很可能只是"被约束少写数字 → 少犯 source-anchoring 错误"，而不是验证规则真的提升了事实覆盖；验证只能防幻觉、不能补缺失（§5.1 原话）。
- **Verdict：成立**。因此 Q1 结果不能解读为"嵌入式验证优于两遍验证"。

### 角度 4 · token 预算变化是否让 S8E 占便宜

- 证据：S8E `max_tokens=2000`，4 跑 `tok_out` = 1807/1856/2000/2000，其中 **Q4 两跑撞上限被截断**（`runs/S8E-Q4-r*.json`）；S7V 两遍累计 `tok_out` = 4944/5277/8093/9634（`runs/S7V-*.json`，L3 对账）。S8E 的生成预算**更小**，且信息条件与 S7V 相同（同来源）。
- 能否推翻结论：这个角度原本是担心 S8E 靠更大预算取胜；数据显示恰恰相反——若说占便宜，是 S7V 靠两遍调用有更多 token 重构答案（Q4 M1 0.9333 高）。S8E 没占便宜，反而吃亏。
- **Verdict：不成立**（"S8E 因 token 预算占便宜"被数据否定）。但反向限制成立：Q4 截断可能压低 S8E 的 M1，使 −0.3333 的退化幅度被高估，属无法完全剥离的混杂因素。

### 角度 5 · 本轮口径与 paper 表格不是同一批次（额外）

- 证据：本轮重算 S7-Q1 M1=0.8708 > S7V-Q1 M1=0.4813，与 paper §5.1「S7V M1≈S7(0.771)」方向相反；`01-research.md` §1.2-D11 已证仓库内并存 ≥4 套 total 口径（§4.1 / §5.1 / §4.5 / `t23v2_arm_summary`）。本轮用 `gold/Q*.md`，T30–T32 当时的 gold/judge 批次可能不同。
- 能否推翻结论：能推翻"把本轮数字与 paper 表格并列解读"的做法，但不推翻本轮三臂间的相对比较（三者同批次）。
- **Verdict：成立**（限制）。所有本轮结论必须标注"仅限本轮 score.py 同口径重算，不与 paper 表格对齐"。

### 角度 6 · "保持 M6 引用能力"其实没被真正检验（额外）

- 证据：S8E 与 S7V 的 M6 完全相同（Q1 0.6667、Q4 1.0000，Δ=0），因为 S8E **离线复用了 S7V 同一 rep 的 `sources`**（`run_s8e.py`），`score.py:check_urls` 的 URL 缓存跨 run 命中。M6 相等是受控设计的必然结果。
- 能否推翻结论：能。H 里"在保持 M6 引用能力的同时"这一子目标**未被检验**——我们只证明了"单次生成没把来源丢掉"，没证明"验证规则本身能保住引用"。
- **Verdict：成立**。FINAL 的结论里不得把 M6 相等写成 S8E 的能力证据。

## 4. 诚实条款

**负面结果也是成果。** 本轮最可靠的产出不是"某个臂更好"，而是：
1. 一份带文件+行号+新旧值的数字一致性修正清单（`FINAL.md`）；
2. 一个明确的否定/混合结论：嵌入式单次验证在 Q4 明显不如两遍验证，且 n=2 噪声过大，按判据不扩展；
3. 一套可复核的工件（`audit.json`、`scores.json`、`verify-out.txt`、4 份完整 prompt、4 个 run JSON）。

不把 Q1 的 +0.1139 包装成提升，不把 M6 相等包装成能力，不把不显著改善写成方向性胜利。
