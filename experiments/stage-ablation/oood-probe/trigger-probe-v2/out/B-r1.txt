### 思考自检（内部执行）

**(a) 质疑方向：**
*   **可行性**：10^9 条日志 * 1KB = 1TB 数据量。16GB 内存远小于数据总量，因此**不可能**将原始日志全部加载到内存进行精确哈希去重。必须采用“近似去重”策略，即只保留指纹（Fingerprint）或摘要，而非全文。
*   **价值**：日志去重是大数据清洗的核心环节，能显著降低存储和计算成本。这是一个典型的工程挑战，值得设计。
*   **风险**：<1% 漏重率（False Negative）意味着允许极少量的重复通过，或者更准确地说，通常“漏重”指本应去重的没去掉（False Negative in dedup context? 不，通常去重关注的是 False Positive: 把不同的当成相同的导致误删，或者 False Negative: 把相同的当成不同的导致保留重复。题目说“允许 <1% 漏重”，在去重语境下，通常指**允许保留 <1% 的重复项**（即去重召回率 >99%），或者**允许误删 <1% 的不同项**？
    *   *澄清语义*：“漏重”通常指“遗漏了重复”，即重复项没有被合并，而是作为新条目保留了。这对应的是 **False Negative**（在检测重复的任务中）。如果允许 <1% 漏重，意味着我们可以接受 99% 的重复被正确识别并去除。这是一个非常宽松的约束，对算法精度要求不高，主要瓶颈在于**吞吐量**和**内存管理**。
    *   *另一种解读*：如果是指“误去重”（False Positive），通常会说“允许 <1% 误杀”。鉴于“漏重”字面意思，我按**允许 <1% 的重复未被去除**来设计。这意味着我们可以使用低成本的指纹算法，甚至不需要高精度的 SimHash，简单的 MinHash 或 Count-Min Sketch 即可。

**(b) 查前人：**
*   **经典方案**：
    *   **HyperLogLog (HLL)**：用于基数估计，不适合去重具体元素。
    *   **Bloom Filter**：适合判断“是否存在”，但无法区分“当前批次的重复”与“历史批次的重复”。且存在 False Positive（误判存在），会导致误删（如果逻辑是“存在则跳过”）。对于日志去重，我们通常希望保留第一个，丢弃后续的。Bloom Filter 可以配合时间窗口使用。
    *   **Count-Min Sketch (CMS)**：用于频率估计，内存小，但同样有误报。
    *   **SimHash / MinHash**：用于近似相似性检测。日志通常是文本，SimHash 适合检测“近似重复”（如只有几个词不同）。但如果日志是结构化或完全相同的字符串，直接用 Hash 指纹即可。
    *   **Roaring Bitmap / IntSet**：如果 ID 是整数，可以用位图。但日志是 1KB 文本，ID 不是自然数，需先 Hash。
    *   **工业界实践**：Spark/Flink 中的 Deduplicate 算子通常基于 Key。对于海量文本，通常先提取特征（如 MD5/SHA1 的前 N 位，或 SimHash），存入内存中的布隆过滤器或 LRU Cache。

**(c) 找更快：**
*   **压缩路径**：
    *   不需要全文比对。
    *   不需要高精度哈希（如 SHA256），64-bit 哈希足够（碰撞概率极低）。
    *   不需要全局去重（除非业务要求跨天去重），通常日志去重在**滑动窗口**或**会话**级别更有意义。假设题目隐含的是**流式去重**或**批量去重**。鉴于 10^9 条总量，若是离线批处理，可分片并行；若是实时流，需状态管理。
    *   **核心简化**：将 1KB 日志压缩为一个 8-byte 的 Hash 指纹。10^9 * 8 bytes = 8 GB。刚好在 16GB 预算内！
    *   **关键洞察**：如果我们将每条日志映射为 64-bit 哈希，存储所有哈希值只需 8GB。加上索引结构开销，16GB 内存**足以容纳全量指纹集合**。
    *   **结论**：既然内存够存全量指纹（8GB < 16GB），我们可以构建一个**基于内存哈希集合（HashSet）或布隆过滤器的全量去重系统**，而不必依赖复杂的近似相似度算法（如 SimHash），因为“漏重 <1%”的约束非常宽松，即使有哈希碰撞导致的误判，或者由于哈希冲突导致的极少量重复保留，都远低于 1%。
    *   **修正**：等等，10^9 * 1KB = 1TB。如果我们要去重，我们需要知道哪些是重复的。如果我们只存 Hash，遇到相同 Hash 认为重复。
        *   存储 10^9 个 64-bit Hash = 8GB。
        *   使用 HashSet<64-bit>，Java/Go 的开销较大。每个 entry 可能有对象头、指针等。
        *   优化：使用**紧凑数据结构**，如 `RoaringBitmap`（如果 Hash 分布均匀，可用 64-bit 空间，Roaring 对稀疏集合有效，但这里是稠密的 10^9/2^64 ≈ 极稀疏？不，10^9 相对于 2^64 是稀疏的，但对于 16GB 内存，直接存 8GB 原始字节数组 + 排序/二分查找？太慢。
        *   更好方案：**Bloom Filter** 或 **Cuckoo Filter**。
            *   Bloom Filter: 空间效率极高，误判率可控。若误判率为 1%，则可能将 1% 的新日志误判为旧日志而丢弃（False Positive -> 误删）。题目允许“漏重”（False Negative -> 保留重复），不允许误删吗？
            *   重新审视“漏重”：如果系统把 A 和 B 都输出了，而 A==B，这叫漏重。如果系统只输出了 A，而 A!=B 但 Hash(A)==Hash(B)，这叫误删。
            *   通常去重系统更怕误删（数据丢失）。所以我们应该设计一个**无 False Positive** 或 **极低 False Positive** 的系统，允许少量 False Negative（即偶尔保留重复）。
            *   **完美匹配方案**：**Exact Set Membership with Limited Memory**.
            *   由于 10^9 个 64-bit hash 占 8GB，我们有 8GB 剩余空间。
            *   方案 A：**Sorted Array of 64-bit Hashes**. 输入 10^9 条，计算 Hash，写入磁盘临时文件或内存缓冲，最后排序去重。但题目要求吞吐 10^4/s，如果是流式，不能等最后排序。
            *   方案 B：**In-Memory HashSet**. 使用高效的 C++/Rust 实现，或者 Java 的 `LongOpenHashSet` (Eclipse Collections)。10^9 个 long 值，负载因子 0.75，需要约 1.33 * 10^9 * 8 bytes ≈ 10.6 GB。加上元数据，16GB 有点紧，但可行。
            *   方案 C：**Two-Level Design**.
                1.  **L1 Cache (LRU)**: 高速缓存最近出现的 Hash。
                2.  **L2 Storage (Bloom/CMS)**: 记录历史。
            *   考虑到“漏重 <1%”，最简单的其实是：**直接存 Hash 集合**。如果内存不够，就丢弃最老的（滑动窗口）。
            *   但题目没说时间窗口。假设是全量去重。
            *   **最终策略**：利用 **64-bit Hash** 将 1KB 日志降维为 8 Bytes。10^9 * 8B = 8GB。使用 **紧凑型哈希表** 或 **BitVector**（如果哈希空间可压缩）？不，64-bit 空间太大，BitVector 不可行。
            *   使用 **Cuckoo Filter** 或 **Bloom Filter** 来节省内存？
                *   Bloom Filter 有 FP (False Positive)。如果 FP=1%，则 1% 的不同日志会被误判为重复而丢弃。题目只说了“允许 <1% 漏重”（FN），没说允许误删（FP）。通常数据系统中 FP 比 FN 更严重。
                *   但是，如果“漏重”指的是“重复项没被去掉”，那 FN 是允许的。如果 FP 发生，是“不同项被去掉了”，这是数据错误。
                *   为了安全，应尽量避免 FP。
                *   **折中**：由于内存 16GB 足够存 8GB 的精确 Hash 集（使用紧凑结构），我们**优先选择精确匹配**，仅在极端情况或为了加速使用近似。
                *   实际上，10^9 个 64-bit 整数，如果用 `std::unordered_set<uint64_t>`，内存开销约为 1.3-1.5x。10^9 * 8 * 1.5 = 12GB。加上其他开销，16GB 够用。
                *   **决策**：采用**精确哈希去重**，而非近似。因为内存预算（16GB）覆盖了全量指纹存储（~12-13GB）。这使得“近似”变得不必要，直接满足 <1% 漏重（实际上是 0% 漏重，除非哈希碰撞，概率极低）。
                *   **备选**：如果担心哈希表开销过大，可使用 **Sort-Based External Merge**（如果允许非实时）或 **Distributed Sharding**。但题目未提及分布式，假设为单机或逻辑单元。

**分解树设计思路：**
1.  **数据接入层**：高吞吐读取。
2.  **预处理层**：日志清洗与标准化。
3.  **特征提取层**：1KB -> 64-bit Hash。
4.  **核心去重引擎**：内存管理策略（HashSet vs Bloom）。
5.  **冲突处理**：哈希碰撞与边界情况。
6.  **输出层**：结果写入。
7.  **监控与调优**：性能指标。
8.  **故障恢复**：状态持久化。
9.  **扩展性**：未来数据增长。
10. **测试验证**：准确性与压力测试。

### 分解树：大规模日志去重系统设计

#### 节点 1: 数据接入与缓冲模块 (Ingestion & Buffering)
*   **关键设计决策**：采用**异步批量读取**机制。使用内存环形缓冲区（Ring Buffer）暂存原始日志，批次大小设为 10,000 - 100,000 条。
*   **理由**：避免每条日志都触发一次 I/O 或 CPU 密集操作。批量处理可提高 CPU 缓存命中率，满足 10^4 条/秒 的吞吐要求（实际可轻松达到 10^5+）。

#### 节点 2: 日志标准化与清洗 (Normalization)
*   **关键设计决策**：在执行哈希前，对日志进行**规范化处理**（去除时间戳、TraceID、动态 IP 等非确定性字段，或将其替换为固定占位符）。
*   **理由**：日志去重通常针对“内容模板”而非“具体实例”。例如，`User 101 login success` 和 `User 102 login success` 可能被视为同一类重复日志。如果不清洗，它们哈希不同，去重失效。此步骤决定了去重的粒度（精确字符串去重 vs 语义/模板去重）。

#### 节点 3: 指纹生成器 (Fingerprint Generation)
*   **关键设计决策**：选用**64-bit 非加密哈希算法**（如 MurmurHash3 或 xxHash3），而非 SHA-256。
*   **理由**：
    1.  **速度**：xxHash3 吞吐量可达 GB/s 级别，远超 SHA-256。
    2.  **内存**：64-bit 指纹占 8 字节，10^9 条仅需 8GB 理论空间。
    3.  **安全性**：日志去重非安全敏感场景，无需抗碰撞加密强度。MurmurHash 分布均匀，碰撞概率在 10^9 规模下极低（生日悖论估算碰撞对数极少，且即使碰撞，也仅影响极个别条目，符合 <1% 漏重/误判容忍度）。

#### 节点 4: 核心去重数据结构选型 (Core Data Structure)
*   **关键设计决策**：使用**紧凑型哈希集合（Compact Hash Set）**或 **Cuckoo Filter**，而非标准语言库的 `HashSet`。
*   **理由**：
    1.  **内存效率**：标准 `HashSet` 每个元素有对象头、指针开销，10^9 个 Long 可能占用 >20GB，超出预算。
    2.  **Cuckoo Filter**：支持 O(1) 查找，空间效率极高（接近 Bloom Filter 但支持删除），误判率（False Positive）可控制在 1% 以下。若使用 Cuckoo Filter，可能产生少量 FP（误删不同日志），但题目允许的是“漏重”（FN）。若严格禁止误删，则需使用精确的 Open Addressing Hash Table（如 SwissTable 或 Rust's HashMap），其空间开销约为 1.3x 数据大小，即 ~10.4GB，仍在 16GB 预算内。**决策：首选精确 Open Addressing Hash Table 以保证零误删，若内存紧张则降级为 Cuckoo Filter。**

#### 节点 5: 内存管理与溢出策略 (Memory Management & Overflow)
*   **关键设计决策**：实施**滑动窗口去重（Sliding Window Deduplication）** 或 **LRU 淘汰策略**。设定最大保留指纹数为 1.2 * 10^9。当哈希表满载时，淘汰最久未访问的条目（LRU）或最旧的条目（FIFO）。
*   **理由**：
    1.  **防止 OOM**：虽然 10^9 * 8B = 8GB，但哈希表负载因子和元数据会使其膨胀至 12-14GB。预留 2-4GB 给 OS 和其他组件。
    2.  **业务合理性**：日志去重通常只关心短时间内（如最近 1 小时或 1 天）的重复。无限期保留所有历史日志的指纹不仅浪费内存，且随着时间推移，旧日志重复的概率降低。LRU 确保内存始终用于存储“活跃”日志的指纹。

#### 节点 6: 并发与锁竞争优化 (Concurrency Control)
*   **关键设计决策**：采用**分片哈希表（Sharded Hash Table）**架构。将 64-bit Hash 的高位作为分片键，划分为 32 或 64 个独立的子哈希表。
*   **理由**：多线程并发插入/查询时，全局锁会成为瓶颈。分片后，不同线程操作不同分片，锁粒度细化，可充分利用多核 CPU，轻松支撑 10^4+ 条/秒 的写入吞吐。

#### 节点 7: 重复判定与输出逻辑 (Decision & Output Logic)
*   **关键设计决策**：遵循**“首次出现保留，后续丢弃”**原则。查询哈希表，若指纹不存在，则插入指纹并将原始日志写入输出队列；若指纹已存在，则丢弃原始日志（或计入重复计数器）。
*   **理由**：这是标准去重行为。输出队列应与去重引擎解耦，通过无锁队列（Lock-free Queue）传递，避免阻塞去重主循环。

#### 节点 8: 持久化与故障恢复 (Persistence & Recovery)
*   **关键设计决策**：启用**周期性快照（Checkpointing）**。每隔 N 秒或 M 条日志，将当前哈希表的状态序列化并写入本地 SSD。
*   **理由**：进程崩溃后，若无持久化，重启时需从头开始或丢失去重状态，导致大量重复日志输出。通过快照恢复，可将去重状态回滚到最近检查点，保证系统可用性（HA）。

#### 节点 9: 监控与自适应调优 (Monitoring & Adaptive Tuning)
*   **关键设计决策**：实时监控**去重率（Dedup Ratio）**、**哈希表负载因子**和**内存使用率**。若去重率异常升高或内存逼近阈值，动态调整 LRU 窗口大小或触发告警。
*   **理由**：日志模式可能随时间变化（如大促期间流量激增）。自适应调整可防止内存溢出，并确保系统在资源受限下仍能维持 <1% 的错误率。

#### 节点 10: 边界情况与哈希碰撞处理 (Edge Cases & Collision Handling)
*   **关键设计决策**：引入**二级校验（Secondary Check）**机制（可选，仅在内存允许时）。对于哈希命中的条目，若内存中有缓存，可对比原始日志的前 16 字节或完整哈希的高 32 位+低 32 位（使用 128-bit 哈希）以消除碰撞。
*   **理由**：虽然 64-bit 哈希碰撞概率极低，但在 10^9 规模下，理论上可能存在极少量碰撞。若业务对“误删”极其敏感，可使用 128-bit 哈希（16 字节/条，总 16GB，刚好打满内存，风险高）或仅在碰撞时进行二次全文比对（需额外存储部分原文，成本高）。鉴于题目允许 <1% 误差，**决策：默认忽略碰撞，或仅记录碰撞日志供事后审计，不做在线二次比对，以保持高吞吐。**

### 总结
该设计通过将 1KB 日志压缩为 64-bit 指纹，利用 16GB 内存构建精确或近似的哈希集合，结合分片并发和 LRU 淘汰策略，在满足内存和吞吐约束的前提下，实现了高效的大规模日志去重。核心在于**指纹降维**和**内存紧凑结构**的选择。
