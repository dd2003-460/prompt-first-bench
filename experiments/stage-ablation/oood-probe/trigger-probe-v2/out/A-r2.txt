这是一个典型的**海量数据流处理与近似计算**问题。
**核心矛盾分析**：
1. **数据量 vs 内存**：$10^9 \times 1\text{KB} = 1\text{TB}$，远超 $16\text{GB}$ 内存。必须采用“指纹化”或“哈希压缩”策略，不能存原文。
2. **精确性 vs 性能**：允许 $<1\%$ 漏重（False Positive 可接受，但 False Negative 即漏掉重复项需严格控制，或者定义“漏重”为将不同日志误判为相同？通常去重场景中，“漏重”指该去重的没去掉，即 False Negative in Deduplication context? 不，通常去重系统关注的是 **Duplicate Missed (FN)** 和 **False Duplicate (FP)**。题目说“允许 <1% 漏重”，结合语境，通常指 **False Positive Rate < 1%** (把不同的当成相同的，导致数据丢失) 或者 **Recall > 99%** (重复的没被识别出来)。
   *   *澄清*：在日志去重中，如果漏掉了重复项（即保留了本该删除的重复日志），后果通常是存储浪费，可容忍度高；如果把唯一日志误判为重复并删除，后果是数据丢失，不可容忍。
   *   *重新解读约束*：“允许 <1% 漏重”。在中文语境下，“漏重”通常指 **Missed Duplicates**（该合并的没合并）。但如果是指 **False Positives**（误删唯一数据），那对系统安全性要求极高。
   *   *假设*：通常工程上“去重”最坏情况是误删。但题目说“允许<1%”，暗示这是一个**近似去重**系统，可能允许极少量的误判或遗漏。为了安全起见，我们设计目标为：**高召回率（Recall > 99%，即漏掉的重复 < 1%）**，同时控制误报率（False Positive）在合理范围（如 < 0.1%），或者根据具体业务定义。这里我们将“漏重”定义为 **Duplicate Miss Rate (DMR) < 1%**。
   *   *吞吐量*：$10^4$/s 对于现代硬件来说非常低（单核即可处理百万级哈希），瓶颈不在计算速度，而在**I/O 和 状态管理**。

**前置检查 (b) 查前人**：
*   **HyperLogLog / Count-Min Sketch**: 用于计数，不适合直接去重（无法区分“见过”还是“没见”）。
*   **Bloom Filter**: 经典方案。空间复杂度 $O(n)$，支持动态扩容，误报率可控。
*   **Cuckoo Filter**: 比 Bloom Filter 空间效率高，支持删除（如果日志有TTL），但插入失败需处理。
*   **LSH (Locality Sensitive Hashing)**: 用于近似相似性检测，而非完全相同去重。日志去重通常指完全相同或归一化后相同。若指“近似日志”（如时间戳不同但内容相同），需先归一化再哈希。本题假设“去重”指**内容哈希后的精确匹配**（经过去噪处理后）。

**设计思路**：
由于数据量巨大且内存有限，必须使用**概率数据结构**存储日志特征（指纹），而非日志本身。
1.  **预处理**：日志清洗、归一化（去除时间戳、IP等易变字段）、分块/哈希。
2.  **核心结构**：分布式/分层 Bloom Filter 或 Cuckoo Filter。
3.  **持久化**：内存中的过滤器需要定期落盘或构建快照，以应对进程重启或数据增长超过内存上限。

以下是分解树：

### 大规模日志去重系统设计分解树

#### 1. 日志预处理与标准化模块
*   **1.1 日志解析与清洗**
    *   *关键决策*：使用轻量级解析器（如正则表达式预编译或状态机）提取日志模板（Template）和变量部分。**决策理由**：原始日志包含时间戳、ID等动态信息，直接哈希会导致同一事件的不同实例被视为不同日志。需提取不变部分作为去重键的基础。
*   **1.2 动态字段掩码 (Masking)**
    *   *关键决策*：识别并掩码高频变化字段（如 `timestamp`, `request_id`, `ip_address`）。**决策理由**：提高去重命中率。通过统计或规则引擎确定哪些字段是“噪声”。
*   **1.3 内容分片与指纹生成**
    *   *关键决策*：对清洗后的日志文本计算 **MurmurHash3** 或 **xxHash** 生成 64-bit 或 128-bit 指纹。**决策理由**：64-bit 碰撞概率在 $10^9$ 规模下约为 $10^{-5}$，可接受；128-bit 更安全但内存占用翻倍。鉴于内存紧张，选 64-bit 配合多重哈希或使用 Cuckoo Filter 的特性。

#### 2. 核心去重数据结构层
*   **2.1 概率过滤器选型**
    *   *关键决策*：选用 **Cuckoo Filter** 而非传统 Bloom Filter。**决策理由**：Cuckoo Filter 空间利用率更高（约为 Bloom Filter 的 1/7 ~ 1/10），且支持元素删除（若日志有过期机制）。在 16GB 内存下，可容纳更多的唯一指纹，从而降低误报率（False Positive Rate, FPR）。
*   **2.2 内存布局优化**
    *   *关键决策*：使用 **数组对齐** 和 **位操作** 优化 Cuckoo Filter 的桶存储。每个桶存储 4 个 64-bit 指纹及对应的计数器（或仅指纹，依赖外部计数）。**决策理由**：CPU 缓存友好，减少内存带宽压力。
*   **2.3 分层过滤策略 (Two-Stage Filtering)**
    *   *关键决策*：第一阶段使用小容量的 **L1 Filter**（内存驻留）快速拦截绝大多数新日志；第二阶段对 L1 未命中或疑似重复的日志查询大容量的 **L2 Filter**（内存+磁盘混合或更大内存池）。**决策理由**：利用局部性原理，热数据在 L1，冷数据在 L2，降低平均访问延迟和内存峰值。

#### 3. 状态管理与持久化模块
*   **3.1 增量快照机制**
    *   *关键决策*：采用 **WAL (Write-Ahead Log)** + **Checkpoint** 模式。实时写入 WAL 记录新增指纹，每隔 N 分钟或 M 万条触发 Checkpoint，将当前 Cuckoo Filter 序列化压缩后写入磁盘。**决策理由**：保证故障恢复时的数据一致性，避免重启后去重状态丢失导致大量重复日志流入下游。
*   **3.2 过滤器重建与合并**
    *   *关键决策*：启动时加载最新的 Checkpoint 文件，重放 WAL 中未持久化的变更。**决策理由**：确保系统从崩溃中恢复后，去重状态准确。
*   **3.3 过期与清理策略 (TTL)**
    *   *关键决策*：引入 **Time-To-Live** 机制。若日志去重窗口为 24 小时，则指纹在 24 小时后失效。**决策理由**：防止内存无限增长。Cuckoo Filter 支持删除，可定期扫描或基于时间戳标记进行惰性删除。若无 TTL，需设计**滚动窗口 (Rolling Window)** 或 **分层淘汰**。

#### 4. 高并发与扩展性架构
*   **4.1 无锁并发设计**
    *   *关键决策*：Cuckoo Filter 内部采用 **细粒度锁 (Per-Bucket Locking)** 或 **CAS (Compare-And-Swap)** 操作实现无锁更新。**决策理由**：$10^4$/s 的吞吐量下，全局锁会成为瓶颈。细粒度锁允许多线程并行处理不同哈希桶，最大化 CPU 利用率。
*   **4.2 批量处理 (Batching)**
    *   *关键决策*：输入端使用 **Ring Buffer** 收集日志，每积累 100~1000 条或每 10ms 触发一次批量去重检查。**决策理由**：减少系统调用开销（如果是异步 I/O），提高缓存命中率，平滑瞬时流量尖峰。
*   **4.3 水平扩展预留接口**
    *   *关键决策*：虽然单机 16GB 足够处理 $10^9$ 条指纹（约需 1-4GB 内存），但设计时需将 Filter 抽象为 **Stateful Service**，支持未来通过 **Consistent Hashing** 将不同指纹路由到不同节点。**决策理由**：为应对日志量增长至 $10^{11}$+ 或更高吞吐需求提供扩展路径。

#### 5. 监控与容错模块
*   **5.1 误报率估算与校准**
    *   *关键决策*：在线采样 0.1% 的“判定为重复”的日志，回溯验证其是否真正重复（例如比对原文摘要）。**决策理由**：Cuckoo/Bloom Filter 的理论 FPR 可能随负载波动，实时监控实际 FPR 以确保满足 <1% 的约束。
*   **5.2 背压控制 (Backpressure)**
    *   *关键决策*：当内存使用率超过阈值（如 80%）或队列积压超过水位线时，触发 **慢消费** 或 **丢弃低优先级日志** 策略。**决策理由**：保护系统稳定性，防止 OOM (Out Of Memory) 导致服务崩溃。
*   **5.3 异常日志隔离**
    *   *关键决策*：对无法解析或哈希冲突异常的日志，写入独立的 **Dead Letter Queue (DLQ)**，由人工或离线任务处理。**决策理由**：避免异常数据污染主去重流程或导致死循环。

### 总结关键指标验证
*   **内存估算**：
    *   唯一日志数估计：假设 10% 重复率，唯一日志约 $9 \times 10^8$ 条。
    *   Cuckoo Filter (64-bit fingerprint, 4 items/bucket):
        *   每条目开销 $\approx 10 \sim 12$ bits (含计数器和指纹)。
        *   $9 \times 10^8 \times 12 \text{ bits} \approx 1.35 \times 10^9 \text{ bits} \approx 168 \text{ MB}$。
        *   即使考虑 2x 冗余和元数据，总内存占用 < 1GB，远低于 16GB 预算。**结论：内存充足，甚至可以使用 128-bit 指纹以提高精度，或增加更复杂的归一化逻辑。**
*   **吞吐验证**：
    *   单次 xxHash 计算耗时 ~10ns。$10^4$/s 仅需 0.1ms/s 的 CPU 时间。
    *   瓶颈在于内存访问和锁竞争，通过 Batching 和无锁设计轻松满足。
*   **精度验证**：
    *   Cuckoo Filter 在填充率 < 75% 时，FPR 极低（< 0.1%）。
    *   “漏重”（False Negative）在 Bloom/Cuckoo Filter 中理论为 0（只要内存不溢出且未发生极端哈希冲突导致插入失败）。若发生插入失败（Load Factor > 100%），需扩容或降级。本设计中内存充裕，不会发生。

此设计在满足所有约束条件下，具有极高的鲁棒性和可扩展性。
