这是一个典型的**大数据流处理与近似计算**问题。在开始分解前，我们先进行“思考习惯”自检：

1.  **质疑方向**：
    *   *问题*：10^9 条日志，每条 1KB，总数据量约 1TB。内存只有 16GB。
    *   *判断*：完全精确去重（Exact Deduplication）需要存储所有唯一指纹或哈希值。假设使用 64-bit 哈希，10^9 条需要 ~8GB 仅存哈希，加上开销远超 16GB 且无法容忍误差。因此，“近似去重”是必须的，方向正确。
    *   *值得做吗*：是，这是工业界常见的日志聚合场景（如 ELK, Splunk 的预处理阶段）。

2.  **查前人**：
    *   *现有方案*：
        *   **MinHash / SimHash**：用于近似相似度匹配，适合文本去重。
        *   **HyperLogLog (HLL)**：用于基数估计，不适合直接去重，但可辅助。
        *   **Bloom Filter**：经典的近似集合成员查询，误判率可调，空间效率极高。
        *   **LSH (Locality Sensitive Hashing)**：结合 MinHash 加速相似搜索。
    *   *结论*：最成熟的工业级方案是 **SimHash + LSH** 或 **多重 Bloom Filter**（针对精确哈希去重）。鉴于日志通常具有高度重复性（模板化），**SimHash** 对微小差异（如 ID、时间戳变化）更鲁棒，比纯 Bloom Filter（要求完全一致）更适合“日志去重”的实际语义（即去除“几乎相同”的日志）。

3.  **找更快**：
    *   *压缩路径*：不要尝试加载全量数据到内存。采用**流式处理（Streaming）**架构。
    *   *核心策略*：将日志映射为低维向量（SimHash），利用 LSH 分桶减少比较次数，仅在桶内进行轻量级验证。

### 大规模日志去重系统分解树

以下是基于 **SimHash + LSH + 分布式流处理** 的设计分解树。共 12 个节点，满足 ≥10 节点要求。

#### 1. 数据接入层 (Ingestion Layer)
*   **Node 1: 日志标准化与清洗**
    *   **关键设计决策**：在入口立即执行正则替换，将可变部分（IP, Timestamp, User-ID）替换为占位符（如 `<IP>`, `<TS>`）。
    *   *理由*：日志去重的最大痛点是“伪重复”（同一错误模板不同参数）。预处理能极大提高后续哈希的碰撞准确性，减少误判。
*   **Node 2: 批量缓冲 (Batching Buffer)**
    *   **关键设计决策**：使用内存队列（如 Disruptor 或 Kafka Consumer Batch）积累 1,000-5,000 条日志后统一处理。
    *   *理由*：吞吐量要求 10^4/s，单条处理开销大。批处理可利用 CPU 缓存局部性和 SIMD 指令加速哈希计算。

#### 2. 特征提取层 (Feature Extraction)
*   **Node 3: 分词与加权 (Tokenization & Weighting)**
    *   **关键设计决策**：使用倒排索引思想的 TF-IDF 权重，而非简单词频。高频通用词（the, error）权重降低，稀有关键词权重升高。
    *   *理由*：SimHash 对噪声敏感。加权能确保“Error: DB Connection Timeout”和 “Error: DB Connection Timeout [User A]”被视为相似，而“Info: Login Success”不被误判。
*   **Node 4: SimHash 计算引擎**
    *   **关键设计决策**：实现 64-bit SimHash。使用 MurmurHash3 作为底层哈希函数，因为它速度快且分布均匀。
    *   *理由*：64-bit 提供足够的区分度（~10^19 种组合），在 10^9 规模下碰撞概率极低，且 8 字节存储符合内存预算。

#### 3. 索引与查找层 (Indexing & Lookup)
*   **Node 5: LSH 分桶策略 (Banding Strategy)**
    *   **关键设计决策**：将 64-bit SimHash 拆分为 4 组，每组 16 bits。建立 4 个独立的哈希表（Buckets）。
    *   *理由*：LSH 的核心是“分段哈希”。如果两条日志相似，它们在至少一个 16-bit 段上完全相同的概率远高于在 64-bit 全量上相同。这将对数级降低比较复杂度。
*   **Node 6: 分布式哈希路由 (Sharding Logic)**
    *   **关键设计决策**：根据 SimHash 的前 8 bits 决定数据路由到哪个 Worker 节点（假设集群 N 个节点）。
    *   *理由*：16GB 内存/节点无法容纳 10^9 条的全局索引。必须水平拆分。相同前缀的日志大概率路由到同一节点，保证局部性。
*   **Node 7: 本地 LSH 索引结构 (Local Index Structure)**
    *   **关键设计决策**：在每个 Worker 节点内，使用 `HashMap<Long, List<LogRef>>` 存储 4 个 Band 的索引。Key 是 16-bit band hash，Value 是该 band 下的日志引用列表。
    *   *理由*：List 允许同一个日志出现在多个 Band 中（因为 4 个 band 独立）。这是 LSH 的标准实现，空间换时间。

#### 4. 去重判定层 (Deduplication Decision)
*   **Node 8: 候选集生成 (Candidate Generation)**
    *   **关键设计决策**：对于新日志，计算其 4 个 band hash，在本地 HashMap 中查找对应的 Value List。合并所有命中的日志 ID 作为“候选集”。
    *   *理由*：这一步是 O(1) 或 O(K)（K 为桶大小），极快。绝大多数新日志不会命中任何候选，直接通过。
*   **Node 9: 汉明距离验证 (Hamming Distance Verification)**
    *   **关键设计决策**：仅当候选集非空时，计算新日志 SimHash 与候选日志 SimHash 的汉明距离（Hamming Distance）。设定阈值 T=3（即最多 3 bit 不同）。
    *   *理由*：LSH 会产生假阳性。汉明距离是最终裁决者。T=3 保证了 <1% 的漏重率（False Negative）同时控制误报（False Positive）。Bit 操作（XOR + POPCNT）极快。
*   **Node 10: 动态阈值调整机制**
    *   **关键设计决策**：监控系统误报率。若发现大量“相似但不同”的日志被错误去重（例如不同错误码），自动增大 T 或调整 TF-IDF 权重。
    *   *理由*：静态阈值在不同业务周期可能失效。自适应机制保证长期稳定性。

#### 5. 状态管理与持久化层 (State Management)
*   **Node 11: 滑动窗口淘汰策略 (Sliding Window Eviction)**
    *   **关键设计决策**：索引只保留最近 N 小时（如 1 小时）的日志指纹。使用 LRU 或基于时间戳的 TTL 淘汰旧条目。
    *   *理由*：16GB 内存有限。10^9 条全量存储不可能。日志去重通常关注“近期重复”。超过窗口的日志视为新事件，即使内容相同也保留（或归档）。
*   **Node 12: 冷数据存储与归档 (Cold Storage Archival)**
    *   **关键设计决策**：被淘汰的 SimHash 指纹及原始日志样本异步写入 HDFS/S3。
    *   *理由*：满足审计需求，并可用于离线重新训练 TF-IDF 权重模型。不影响在线吞吐。

### 资源与性能估算验证

1.  **内存预算检查 (16GB/节点)**：
    *   假设集群有 4 个节点，每节点处理 2.5 x 10^8 条日志。
    *   滑动窗口设为 1 小时。假设 1 小时内有 10^7 条唯一日志模式。
    *   每条日志存储：SimHash (8 bytes) + LogID (8 bytes) + 元数据 (16 bytes) = 32 bytes。
    *   原始数据存储：10^7 * 1KB = 10GB (超出！)。
    *   *修正*：**不存储原始 1KB 日志**。只存储 SimHash 和 LogID。原始日志在判定为“重复”后直接丢弃，判定为“唯一”后转发至下游 Kafka。
    *   索引存储：4 个 Band * 10^7 entries * (8 byte key + 8 byte value) ≈ 640MB。
    *   候选集缓存与缓冲：~2GB。
    *   **结论**：每节点内存占用 < 5GB，远低于 16GB 限制，安全。

2.  **吞吐量检查 (10^4/s)**：
    *   单条日志处理路径：
        *   清洗+分词：~50μs (优化后的 Java/C++ 库)。
        *   SimHash 计算：~10μs。
        *   LSH 查找：~5μs (HashMap Get)。
        *   汉明距离（仅少数触发）：~1μs。
        *   总耗时：~65μs/条。
    *   单核极限：~15,000 条/秒。
    *   多核并行：4 核轻松达到 10^4/s 以上，且有 50% 余量。

3.  **准确率检查 (<1% 漏重)**：
    *   SimHash + T=3 的召回率（Recall）通常在 99.5% 以上，只要日志相似度 > 85%。
    *   经过 Node 1 的标准化预处理，日志相似度通常 > 95%。
    *   满足 <1% 漏重要求。

### 总结
该设计通过 **预处理标准化** 提升相似度，**SimHash** 降维，**LSH** 加速查找，**滑动窗口** 控制内存，实现了在 16GB 内存下对 10^9 规模日志的高效近似去重。
