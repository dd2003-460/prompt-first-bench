

## 逐层质疑：T53b 消融实验设计

### (1) 目标层：目标本身站得住吗？几个目标是不是正交的？
**质疑点：**  
- **目标耦合导致归因污染**：目标(1)（prompt 格式效果）与目标(2)（SSL 修复有效性）**非正交**。若 SSL 卡死在 `formula` 组高频触发（如新格式触发更多长文本处理），则 `coverage/depth` 下降可能源于系统故障而非 prompt 缺陷；反之，若 `text` 组因 watchdog 重启丢失中间状态，其"低分"实为执行失败伪影。**两目标共享同一批 run 数据，无法解耦"格式效应"与"稳定性效应"**。  
- **目标定义模糊**："分解质量高"仅由 `coverage` 和 `depth` 代理，但二者可能**负相关**（例：`formula` 生成浅层但全覆盖的树 vs `text` 生成深层但遗漏要点的树）。未定义"质量"的优先级（如 `coverage > depth`？），导致判据自相矛盾。  
- **目标(2)缺乏独立验证**：SSL 修复有效性应通过**故障注入测试**（如人为模拟卡死）验证，而非依赖自然发生的 run 中"无复发"。当前设计将稳定性验证寄生于主实验，若 62 run 中 SSL 故障率为 0%，无法区分"修复有效"与"故障未触发"。

---

### (2) 分组/对照层：分组能归因吗？
**质疑点：**  
- **题目作为混杂变量未控制**：3 道题（`nat/soc/gpu`）难度/领域差异极大（如 `gpu` 可能需硬件知识，`soc` 偏抽象）。若 `formula` 恰在 `gpu` 上优势显著，而 `text` 在 `soc` 上占优，**聚合比较会掩盖题目特异性效应**。未将题目设为随机效应或分层分析，导致归因失效。  
- **重复次数不均等**：62 runs ÷ (3 题 × 2 格式) = **10.33 次/格**，非整数。若部分格仅 10 次、部分 11 次，方差估计偏差；且未说明重复是否**独立同分布**（如是否固定随机种子？若每次 run 输入微扰不同，则"重复"实为不同实验条件）。  
- **无时间/顺序随机化**：62 runs 按固定顺序执行（如先 `nat-formula` 全跑完再 `soc-text`），则**服务器负载、模型缓存状态、时间漂移**成为混杂变量。未采用拉丁方或随机块设计，无法排除时序效应。  
- **对照组缺失**：`text` 格式是否为**当前生产环境基线**？若 `text` 是已废弃的旧版本，其"低分"可能源于过时而非格式劣势，结论外推无效。

---

### (3) 指标层：指标真的可比吗？
**质疑点：**  
- **`coverage` 分母不可比**：`coverage = 覆盖 GOLD 要点数 / GOLD 要点总数`。若 `nat` 题 GOLD 有 8 个要点、`soc` 仅 3 个，则 `soc` 的 `coverage` 天然更易接近 1.0（分母小）。**跨题目直接比较 `coverage` 均值是统计谬误**，需标准化（如按题目难度加权）或改用绝对覆盖数。  
- **`depth` 的 judge 信度存疑**：`depth` 由 LLM judge 打分，但未提供：  
  - Judge 模型版本及提示词（是否含题目上下文？）  
  - 人工标注一致性（Cohen's κ ≥ 0.7？若 judge 对"深度"理解不一，噪声淹没信号）  
  - **深度与题目结构的混淆**：`gpu` 题可能天然需更深分解（如硬件→驱动→API），`soc` 题较浅。未控制题目复杂度，`depth` 差异可能反映题目属性而非 prompt 效果。  
- **指标未覆盖关键维度**：  
  - **准确性**：`coverage` 仅衡量"是否提及"，未验证要点**正确性**（如错误覆盖 GOLD 要点是否扣分？）  
  - **一致性**：同一题目多次 run 的 `coverage` 方差未报告，若 `formula` 组方差更大，均值高但可靠性低。  
  - **效率**：`formula` 是否导致 token 消耗激增？未纳入成本指标，结论缺乏工程实用性。

---

### (4) 判据层：判据定了吗、预注册了吗？
**质疑点：**  
- **无预注册判据**：仅描述"formula 分数更高即有效"，但未指定：  
  - **统计检验方法**（配对 t 检验？Wilcoxon 符号秩？混合效应模型？）  
  - **显著性阈值**（α=0.05？是否校正多重比较？3 题 × 2 指标 = 6 次比较，Bonferroni 后 α=0.0083？）  
  - **效应量门槛**（如 `coverage` 提升 <5% 视为无实际意义，即使 p<0.05）  
  → **事后选择有利判据的风险极高**（例如仅报告 `soc` 题的显著结果）。  
- **判据未处理缺失数据**：若某 run 因 SSL 故障中断，`coverage/depth` 缺失。未定义：  
  - 缺失 run 是否剔除？（若 `formula` 组缺失率更高，剔除后样本偏差）  
  - 是否用插补法？（若无，直接删除导致两组 n 不等，破坏配对设计）  
- **无阴性结果预案**：若 `formula` 在 `nat` 题显著更优、`soc` 题显著更差，如何判定整体"有效"？未预设交互效应分析框架。

---

### (5) 样本层：样本量够吗？
**质疑点：**  
- **功效分析缺失**：62 runs 未基于**最小可检测效应（MDE）** 计算。假设 `coverage` 标准差 σ=0.15，要检测 Δ=0.1 的提升（中等效应），双尾 α=0.05、power=0.8 需 **n≈16/组**（配对设计）。当前每格仅 ~10 次，**功效不足**，易犯 II 型错误（漏检真实效应）。  
- **题目间异质性未建模**：3 道题的效应方向/大小可能不同（如 `formula` 在 `gpu` 上 +0.2，`soc` 上 -0.1）。若用固定效应模型忽略题目随机效应，**标准误低估**，假阳性率上升。应使用混合效应模型（题目为随机截距），但 n=3 题目时随机效应估计极不稳定。  
- **重复非独立**：若同一题目多次 run 共享缓存/上下文，观测值相关。未报告**组内相关系数（ICC）**，若 ICC>0.3，有效样本量远低于 62，统计推断失效。

---

### (6) 执行层：可复现吗？
**质疑点：**  
- **SSL 修复的执行细节不透明**：  
  - Watchdog 触发后是否**完整重跑**该 run？还是从断点恢复？（后者可能引入状态污染）  
  - 故障 run 是否标记为"有效数据"？若 watchdog 静默修复，研究者无法区分"成功 run"与"修复后 run"，**混淆稳定性与性能**。  
- **Prompt 版本未锁定**：`formula/text` 的 prompt 模板是否固定？若实验期间微调过 prompt（如调整示例），则"格式差异"混入"内容差异"。未提供 prompt 哈希值或版本控制记录。  
- **Judge 评分不可复现**：  
  - LLM judge 的温度参数（temperature=0？）、采样策略未说明  
  - 若 judge 模型在实验期间升级（如 GPT-4 → GPT-4o），`depth` 分数漂移  
  - **无人工校验流程**：judge 错误（如对 `depth` 误判）无纠错机制  
- **数据管道黑箱**：  
  - `coverage` 计算依赖 GOLD 要点匹配算法（精确匹配？语义相似度？阈值多少？）  
  - 未开源原始 run 日志（prompt、response、judge 输入/输出），第三方无法验证指标计算  
  - **无随机种子记录**：若 LLM 调用含随机性，重复实验结果不可复现  

---

### 总结：核心风险矩阵
| 层次       | 最致命缺陷                          | 后果                     |
|------------|-------------------------------------|--------------------------|
| 目标层     | 两目标耦合，稳定性污染格式效应      | 归因错误                 |
| 分组层     | 题目未随机化 + 重复次数不均         | 混杂变量主导结果         |
| 指标层     | `coverage` 分母不可比 + `depth` 信度低 | 指标失真                 |
| 判据层     | 无预注册统计方案                    | P-hacking 风险           |
| 样本层     | 功效不足 + 题目异质性未建模         | 假阴性/假阳性            |
| 执行层     | SSL 修复与数据完整性未解耦          | 数据污染                 |

**建议优先修复项**：  
1. **解耦目标**：SSL 稳定性用独立故障注入实验验证，主实验仅保留 prompt 格式对比。  
2. **预注册判据**：明确混合效应模型、Bonferroni 校正、效应量门槛，并公开分析代码。  
3. **指标标准化**：`coverage` 改为绝对覆盖数 + 题目难度加权；`depth` 增加人工标注一致性检验。  
4. **执行透明化**：记录所有 run 的 SSL 事件日志，故障 run 单独标记并敏感性分析（含/不含故障 run 的结果对比）。
