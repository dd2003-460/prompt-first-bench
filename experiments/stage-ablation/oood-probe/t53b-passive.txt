

经过审查，该实验设计存在以下**关键问题**需确认或修正（仅列出实质性缺陷，非吹毛求疵）：

---

### **1. SSL 卡死修复的有效性无法通过当前设计验证**
- **问题**：实验目标 (2) 要求验证 "SSL 卡死修复 + watchdog 有效、无复发"，但 **62 个 run 中未定义任何 SSL 相关的测量指标**（如卡死次数、watchdog 触发日志、连接超时事件等）。  
- **风险**：若仅依赖 "run 成功完成" 作为隐含证据，则：  
  - 无法区分 "SSL 问题未发生" 与 "问题发生但被掩盖"（如 watchdog 静默重启后未记录）；  
  - 若某 run 因 SSL 卡死失败，该数据点会被排除，但 **失败率本身才是关键指标**（当前设计未统计）。  
- **必须补充**：  
  - 明确记录每个 run 的 SSL 事件日志（卡死时间戳、watchdog 动作、重试次数）；  
  - 将 **SSL 故障率**（故障 run 数 / 总 run 数）作为核心指标，并与历史基线对比。

---

### **2. `depth` 指标与 "分解质量" 的逻辑关联不成立**
- **问题**：`depth`（节点树深度）被用作质量指标，但 **深度 ≠ 质量**：  
  - 过深分解可能导致冗余/错误分支（如将无关细节纳入树结构），反而降低实用性；  
  - 高质量分解可能追求 **精准且适度深度**，而非盲目加深。  
- **风险**：若 formula 格式生成更深的树但 coverage 更低，按当前判据会误判为 "更有效"。  
- **必须修正**：  
  - 替换或补充更合理的指标（如 **节点准确率**：分解节点中正确子问题的比例）；  
  - 若保留 `depth`，需论证其与业务目标的关联性（例如：下游任务是否依赖深度？）。

---

### **3. 统计推断缺失，判据不严谨**
- **问题**：判据仅描述 "formula 分数更高就说明更有效"，但 **未指定统计检验方法**：  
  - 62 个 run 中，每组（3 题 × 2 格式）仅约 10 次重复，小样本下均值差异易受噪声干扰；  
  - 未说明是否进行显著性检验（如 t 检验/Mann-Whitney U）、效应量计算或置信区间。  
- **风险**：可能将随机波动误判为格式优势。  
- **必须补充**：  
  - 明确统计方法（例如：对 coverage/depth 分别做配对检验，校正多重比较）；  
  - 报告 p 值 + 效应量（如 Cohen's d），避免仅依赖均值比较。

---

### **4. 实验变量未控制，混杂因素干扰结论**
- **关键漏洞**：  
  - **LLM 随机性**：未说明是否固定随机种子/温度参数。若每次 run 输出随机，则 "格式差异" 可能被模型自身方差淹没；  
  - **题目难度不均**：nat/soc/gpu 三题的 GOLD 要点数量、复杂度若差异大，coverage 分数不可直接跨题比较（例如：5 个要点的题 vs 10 个要点的题）；  
  - **SSL 问题与格式实验耦合**：若某 run 因 SSL 卡死失败，其数据被排除后，**剩余 run 的格式分组可能失衡**（如 formula 组损失 2 个 run，text 组损失 0 个），破坏可比性。  
- **必须确认**：  
  - 是否设置 `temperature=0` 或多次采样取平均以消除随机性；  
  - 三题的 GOLD 要点数量是否均衡？若不均衡，需对 coverage 做归一化处理；  
  - SSL 故障 run 是否从格式比较中剔除？若剔除，需检查两组剩余样本量是否仍满足统计检验前提。

---

### **5. `GOLD` 要点的定义与标注可靠性未说明**
- **问题**：`coverage` 依赖 "GOLD 要点"，但未说明：  
  - 要点如何定义（人工标注？自动提取？）；  
  - 标注者间一致性（如 Cohen's κ）是否达标；  
  - 不同题目的要点粒度是否统一（例如：soc 题的 "安全策略" 要点 vs gpu 题的 "显存分配" 要点，抽象层级是否可比？）。  
- **风险**：若 GOLD 标注存在主观偏差，coverage 分数失真。  
- **必须补充**：  
  - 提供 GOLD 要点的标注协议及信度检验结果；  
  - 确认三题的要点粒度一致（建议由同一团队按统一标准标注）。
