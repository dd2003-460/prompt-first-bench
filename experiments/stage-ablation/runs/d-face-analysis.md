## 根因确认（v3 最终）

**三轮实验排除搜索源假设：**

| 版本 | 修改 | Coverage | Δ vs v1 |
|------|------|----------|---------|
| v1 | 无直访源（全 arXiv） | 0.446 | — |
| v2 | +KNOWN_SITES（AWS/Aliyun 定价页），但 snippet 是导航垃圾 | 0.457 | +0.011 |
| v3 | snippet 修复为定价正文（标准/低频/归档/¥/GB） | 0.441 | -0.005 |

v2→v3 的 snippet 质量有本质提升（从"问办公天猫全球速卖通..."变成"标准类型/低频访问类型/归档类型/冷归档类型"），但 coverage 纹丝不动。

**真正根因：模型能力上限。** 即使 prompt 里注入了真实的阿里云 OSS 分层定价表和 AWS S3 存储类别说明，27b 仍然：
1. 没有把 gold tree 里的换算系数（EC 冗余 1.375、元数据开销 1.05、预留水位 1.25）独立识别为叶子节点——它做了因素分解框架（F1-F10），但停在"阶段 01"不往下填数字
2. 没有探索边缘场景（分流比、双跑最低消费、海外单价上浮）
3. 没有覆盖运维隐性成本（监控/DDoS/备件/巡检）和 RTO 维度

**输出结构诊断（Q7-r1, 13778 chars）：** 模型输出了完整的"阶段 01 — 目标分解"（10 个正交因素 + 已知条件 + 可推导条件 + 空缺清单），但没有继续执行阶段 02（用注入的定价数据填充具体数值）。Gold tree 要的叶子节点（N-1.1 EC 8+3=1.375、N-2.1 HDD $28/TB、N-4.1 OSS 0.12 ¥/GB·月）全部在"空缺条件清单"里被标记为 G1-G10，但没有被实际求解。

**结论：D 面 FAIL 是 27b 模型在跨域成本计算任务上的能力天花板。** 模型能建框架但不能填数字——这是 prompt 工程修不了的问题。要过 D3 gate (≥0.70)，需要：(a) 更强模型（70B+），或 (b) 多轮迭代（R1 建框架 → R2 填数字 → R3 验证），或 (c) 限定 pfb 适用范围为 AI/ML 域并在论文中声明。

## 决策：采用 (c) 限定适用范围（2026-11-07）

**理由：**
- (a) 换 70B+ 模型：成本高，且当前本地只有 27b，短期内不可行。
- (b) 多轮迭代：可能把 coverage 从 0.44 提到 0.55-0.60，但很难到 0.70，且每轮都要重新跑 harness，时间成本中等。
- (c) 限定范围：零成本，立刻可做。pfb 的核心卖点是"prompt engineering 提升 LLM 研究质量"，不是"通用知识代理"。在 AI/ML 域内 S5 确实显著打赢开源竞品（C 面 Δ+0.147, p=0.031），这个结论是站得住的。

**具体做法：**
1. 论文中明确声明 pfb 的适用域为 AI/ML（Q1-Q5 覆盖的子领域：模型架构、训练优化、推理加速、数据工程、评估方法）。
2. D 面的跨域结果作为"局限性讨论"保留，不删除——它定义了 pfb 的能力边界，这对论文是有价值的信息。
3. B 面（真实泛化）改为在 AI/ML 域内验证泛化性（不同子领域之间），而不是跨到 networking/storage。
4. A 面（可应用）同样限定在 AI/ML 域内的实际任务场景。
