# 标准答案 · 数据处理方案（RAG vs 长上下文 vs 混合）

**题面**：企业知识库问答（文档总量约 50 万页，用户问题需引用文档内容回答且不能编造，
周更），选一个数据处理方案使**每千次正确回答的成本最低**，且答案需**可引用出处**、端到端 p95 < 15s。

**候选**：纯 RAG（切块→嵌入→检索 top-k→生成）· 纯长上下文（全文/近全文塞入 128K 模型）·
混合（RAG 粗筛 + 长上下文精读 top 片段）。

**与 27B 硬件 gold 的结构差异**：硬件题候选是 GPU、叶子是物理量；本题候选是**管道架构**，
叶子是**信息流属性**（检索召回/上下文定位/幻觉 grounding/token 成本结构）。
根节点仍是「单位正确产出的成本」，但**分子里第一次出现「建设成本 vs 边际成本」的分裂**
（RAG 有 upfront 索引成本、长上下文没有；长上下文边际 token 成本高、RAG 低）——
这是管道选型独有的结构，硬件题里没有。

---

## 0. 根节点（L0)

**N-0 每千次正确回答的成本 `c_correct` [¢/1k_correct]**

```
c_correct = 1000 × ( c_retrieval + c_gen + c_build_amortized ) / P(correct)
```

- `P(correct)`：回答正确且可引用的概率——**本题主导项**，由检索/定位/幻觉决定。
- `c_retrieval + c_gen`：每次问答的边际成本。
- `c_build_amortized`：一次性建设成本摊到每次问答（RAG 有，长上下文 ≈ 0）。

**为什么用这个标量**：
1. 「哪个方案最划算」= 单位正确回答成本最低，无歧义。
2. **把「建设成本」和「边际成本」都放进分子**——只看边际成本会无条件选 RAG（每次 token 少），
   漏掉 RAG 的 upfront 索引/调参成本；只看建设成本会无条件选长上下文（零建设），漏掉它的 token 账单。
3. 「正确」进分母，把**召回率/幻觉**拉进来——不正确的回答再便宜也是 0 价值。

**口径声明**：
| 项 | 口径 |
|---|---|
| `SHARE` | 弹性绝对值归一化 |
| `BOUND` | 叶子区间内 `c_correct` 的 max/min |
| 正确判定 | 答案事实正确 **且** 给出可核验出处（题面要求可引用）。判定标准未给细则 → 黑盒 B3 |
| 文档规模 | 约 50 万页（题面给定）；单次问题相关文档约 1–3 篇 |

## 1. 正交维度定义（L1)

```
c_correct = 1000 × 总成本 / P(correct)
总成本     = 建设摊销 + 检索边际 + 生成边际        （加法，三者份额和为 1）
P(correct) = P(拿到相关上下文) × P(上下文内答对) × (1 − halluc)
```

| 维度 | 节点 | KIND | 说明 |
|---|---|---|---|
| **正确率侧** | N-1 回答正确率 `P(correct)` | signal | 检索召回 × 上下文定位 × 抗幻觉 |
| **成本侧** | N-2 单次总成本 `c_total` | signal | 建设摊销 + 检索 + 生成 |
| **延迟侧** | N-3 端到端延迟 `latency` | constraint | 检索 + 生成（prefill 随输入涨） |
| **可行域** | N-4 规模/更新/合规 `feasible` | constraint | 文档装不装得下、更新多快、数据出不出域 |
| **质量修正** | N-5 可引用/时效 `quality` | nuisance | 出处可核验性、答案新鲜度 |

**正交性检验**：

| 这一对 | 前者独占 | 后者独占 |
|---|---|---|
| 正确率 ↔ 成本 | 检索召回率 | 输入 token 数 |
| 正确率 ↔ 延迟 | 幻觉率 | 检索延迟 |
| 成本 ↔ 延迟 | 建设摊销 | 生成 p95 |
| 可行域 ↔ 质量 | 文档规模 | 可引用性 |

全过。**SHARED 必须现在记**：`文档规模 doc_scale` 同时进
N-4.1（长上下文装不装得下→约束）和 N-1.1（RAG 检索难度→召回率）和 N-2.2（长上下文输入 token 成本）——
三条路径，见 §5。

## 3. 叶子卡片（执行动作 + 完成判据 + 数据来源）

### N-1.1.1 切块质量 `chunk_quality` ■B1
- **执行动作**：对 50 万页文档中抽样 200 篇用候选切块策略（固定 512/1024/语义切块）建索引，抽 200 个问题测「相关段落是否被完整切在同一个 chunk」。
- **完成判据**：chunk 级召回率（相关段落完整率）+ 最优 chunk size。
- **数据来源**：自测（黄金问题集标注相关段落）。
- **为什么黑盒**：切块破坏段落完整性是 RAG 头号失效模式，最优 chunk size 依文档结构而异，无闭式。

### N-1.1.2 嵌入相关性 `embed_quality` ■B1
- **执行动作**：用候选嵌入模型建索引，测 top-k（k=5/10/20）的问题-相关段落召回率。
- **完成判据**：recall@k 曲线；选拐点 k。
- **数据来源**：自测（同黄金问题集）。

### N-1.1.3 重排效果 `rerank_gain` ■B1
- **执行动作**：在 top-k 粗检后加 cross-encoder 重排，测「相关段落进 top-3」的提升。
- **完成判据**：rerank 前后 recall@3 差值；是否值得其延迟/成本。
- **数据来源**：自测。

### N-1.1.4 上下文内定位 `in_ctx_localization` ■B2
- **执行动作**：长上下文方案下，把相关文档放进不同位置（首/中/尾）× 不同总量（50/200/500 万 token），测「大海捞针」准确率衰减。
- **完成判据**：定位准确率 vs 上下文档/位置的衰减曲线。
- **数据来源**：自测（needle 基准 + 真实文档）。
- **为什么黑盒**：**标称 128K 上下文 ≠ 128K 都有效**。模型在长上下文中段定位能力显著衰减（U 型/首尾偏差），衰减曲线无解析式，且随模型而异。**这是长上下文方案最常被高估的能力。**

### N-1.2 上下文内作答正确率 `answer_given_ctx`
- **执行动作**：给定正确上下文，测模型作答正确率——引用 `model-selection` gold 的基准→任务迁移（transfer）。
- **完成判据**：一个条件正确率标量。
- **数据来源**：model-selection gold 的 B1 实测（S-c，不重复分解）。

### N-1.3 幻觉率 `halluc_rate` ■B3
- **执行动作**：200 个问题上统计「答案含上下文外编造事实 / 出处不可核验」的比例，分方案测。
- **完成判据**：每方案一个幻觉率 + CI。
- **数据来源**：自测人工判定。
- **为什么黑盒**：RAG 因 grounding 在检索片段上幻觉通常更低，但「检索到相关但不够的片段」时会强行作答产生幻觉；长上下文因信息全幻觉低但受定位衰减影响。**两方案幻觉率无先验公式，必须测。**

### N-2.1.1 索引构建成本 `index_build` ■B4
- **执行动作**：实测 50 万页全量切块+嵌入+建库的机时与人力。
- **完成判据**：人天 + GPU 时 + 存储量。
- **数据来源**：实测（首次构建）。

### N-2.1.2 调参成本 `tune_cost` ■B4
- **执行动作**：估 chunk size / top-k / 提示模板 / 重排阈值的调优人天（达到目标召回的迭代轮数）。
- **完成判据**：人天估值 + 依据（类似项目经验）。
- **数据来源**：经验估（S-b）。

### N-2.1.3 摊销问答数 `Q_amortize` ■B4
- **执行动作**：估系统生命周期内总问答数（决定建设成本摊薄程度）。
- **完成判据**：Q 的区间（如 1 万–50 万次）。
- **数据来源**：业务预估（S-b）。**关键**：Q 小（低频问答）时建设摊销占主导→长上下文赢；Q 大时边际成本占主导→RAG 赢。

### N-2.2.1–2.2.3 检索边际成本
- **执行动作**：查嵌入模型 API 价 / 自建嵌入 GPU 时；向量库（Qdrant/Milvus/pgvector）查询成本；重排模型调用成本。
- **完成判据**：每次问答的检索成本 ¢/q（通常 << 生成成本）。
- **数据来源**：官方定价 / 自部署算力账（S-a）。

### N-2.3.1 输入 token 数 `in_tok` · SHARED:doc_scale
- **执行动作**：RAG = top-k 片段 token 数（k×chunk_size）；长上下文 = 全文/近全文 token 数（受 doc_scale 与有效 ctx 限制）。
- **完成判据**：每方案 in_tok 中位数。
- **数据来源**：切块配置 + 文档统计（S-a）。**这是两方案成本结构分裂的核心**：长上下文 in_tok 是 RAG 的 10–100 倍。

### N-2.3.2 输出 token 数 `out_tok`
- **执行动作**：统计答案长度分布（两方案通常相近，都受「简洁作答」提示约束）。
- **完成判据**：out_tok 中位数。
- **数据来源**：自测/业务日志（S-a）。

### N-2.3.3 每 token 单价 `price`
- **执行动作**：引用 `model-selection` gold 选定模型的单价（或自部署摊销）。
- **完成判据**：(p_in, p_out) 一组。
- **数据来源**：model-selection gold（S-c）。

### N-3.1 检索延迟 `t_retrieval` ■B5
- **执行动作**：测嵌入+向量检索+重排的 p50/p95（含网络/库开销）。
- **完成判据**：t_retrieval p95；典型 100–500ms。
- **数据来源**：自测压测。

### N-3.2 生成延迟 `t_gen`
- **执行动作**：`t_gen ≈ in_tok / prefill速率 + out_tok / decode速率`，引用硬件 gold 的速率公式。
- **完成判据**：每方案 t_gen；长上下文因 in_tok 大，prefill 延迟显著更高。
- **数据来源**：硬件 gold 公式 + in_tok（S-a 可算）。

### N-3.3 端到端 p95 `e2e_p95` ■B5
- **执行动作**：全链路压测 200 请求，记录 p95。
- **完成判据**：是否达 SLO（< 15s）；长上下文方案常在此触顶。
- **数据来源**：自测。**p95 由最慢的 prefill 决定，无闭式**（受并发/缓存影响）。

### N-4.1 文档规模门槛 · SHARED:doc_scale
- **执行动作**：对比文档总量（500 万 token）与模型**有效**上下文（不是标称 128K，是 B2 测出的有效定位长度）。
- **完成判据**：长上下文方案 pass/fail。500 万 >> 128K → **纯长上下文直接不可行**，只剩「混合」（RAG 粗筛后精读）。
- **数据来源**：doc_scale + B2 有效 ctx（S-a 判定，但依赖 B2 黑盒）。

### N-4.2 更新频率 `update_freq`
- **执行动作**：周更文档→评估 RAG 增量索引成本 vs 长上下文「每次重新嵌入/重排」成本。
- **完成判据**：增量更新可行性 + 成本。
- **数据来源**：业务给出更新频率（S-a）。

### N-4.3 数据合规 `privacy`
- **执行动作**：查数据能否出域（用云端嵌入/向量库 API）还是必须本地驻留。
- **完成判据**：可用组件清单（合规约束下）。
- **数据来源**：合规要求（S-a）。**可能一票否决**某些云嵌入服务。

### N-5.1 可引用性 `citability`
- **执行动作**：评估两方案给出「可核验出处」的能力——RAG 天然带 chunk 来源；长上下文需模型自行标注引用（易错）。
- **完成判据**：出处准确率（抽 50 答案核出处）。
- **数据来源**：自测（题面硬性要求可引用，此项权重高）。

### N-5.2 时效性 `freshness`
- **执行动作**：周更文档下，测「更新后多快能反映到新答案」（RAG 增量索引后即时；长上下文取决于重新嵌入周期）。
- **完成判据**：更新生效延迟。
- **数据来源**：自测（S-a）。

## 4. 关键黑盒（S-b 收口）

| 黑盒 | 为什么没有闭式 | 区间（估） | 一天内能做完的测法 | 弹性 |
|---|---|---|---|---|
| **B1 检索召回（切块/嵌入/重排）** | 依文档结构与查询分布，无解析解 | recall@5 ∈ [0.5, 0.85] | 200 黄金问题测召回 | **高（RAG 方案主导）** |
| **B2 上下文内定位衰减** | 长上下文有效长度随位置/总量衰减，无公式 | 有效 ctx ∈ [0.3, 0.8]×标称 | needle 基准 + 真实文档 | **高（长ctx 方案主导）** |
| **B3 幻觉率** | 任务相关，两方案失效模式不同 | [0.05, 0.30] | 200 问题人工判定 | 中高 |
| **B4 建设/摊销** | 依业务量 Q，前瞻性 | Q ∈ [1e4, 5e5] | 业务预估 + 试点 | **高（决定 RAG vs 长ctx 翻转）** |
| **B5 检索/端到端延迟** | 并发与缓存影响 p95 | t_retrieval p95 [0.1, 1]s | 压测 200 请求 | 中（SLO 约束） |

**B1 和 B2 是「镜像黑盒」**：B1 决定 RAG 能不能用（检索召回），B2 决定长上下文能不能用（定位衰减）。
**两个都必须自测，且都要在选型前测**——只测 B1 会高估长上下文（以为 128K 全能用），
只测 B2 会高估 RAG（以为切块检索总能召回）。这是管道选型特有的「双向验证」结构。

**B4 是翻转项**：对应硬件 gold 的「利用率 u」——它是业务侧量，却决定技术选型方向。
Q 小（低频）→ 建设摊销主导 → 长上下文/混合赢；Q 大（高频)→ 边际 token 成本主导 → RAG 赢。
**没估清问答量之前，「RAG 更省」和「长上下文更省」都可能对。**

## 5. SHARED 参数：`文档规模 doc_scale` 的三条路径

```
doc_scale ──┬──▶ N-4.1  长上下文装不装得下        （500万 >> 128K → 纯长ctx 不可行)  约束
            ├──▶ N-1.1  RAG 检索难度              （文档越多召回越难，B1 越差）        降正确率
            └──▶ N-2.3.1 长ctx 输入 token 成本     （塞越多文档 in_tok 越大越贵）        升成本
```

三条路径方向一致（文档规模增大会同时「逼你用 RAG」+「让 RAG 更难」+「让长ctx 更贵」），
但**作用的方案不同**：前两条推高 RAG 的相对吸引力，第三条推高长上下文的成本。
**不标 SHARED 的树会分别得出「文档大→用 RAG」（只看约束）和「RAG 召回差→用长ctx」（只看 B1），
得出互相矛盾的结论。** 正解是**混合**：RAG 粗筛把 500 万压到 top 片段，长上下文精读保证定位质量。

---

## 6. 推荐方案

**结论形状**（条件化，不是「RAG 永远对」）：

1. **先判可行域**（N-4.1）：文档总量 500 万 token >> 任何模型有效上下文 →
   **纯长上下文方案直接排除**，不在排名里。（对应硬件题「M2 Ultra 带宽不够直接划掉」。)
2. **测 B1（检索召回）和 B2（定位衰减）**——各 1 天。这是双向验证，缺一不可。
3. **估 B4（问答量 Q）**——决定建设摊销权重。
4. **决策规则**：
   - **Q 大（高频问答）+ 需可引用 + 周更** → **RAG**（边际 token 成本低、天然带出处、增量更新）。
     前提是 B1 召回调到位（chunk + 重排），否则正确率崩。
   - **Q 小（低频）+ 文档总量 < 有效 ctx** → **长上下文**（零建设、召回=1、定位质量高）。
   - **Q 中 + 文档超 ctx 但单问题相关文档集中** → **混合**（RAG 粗筛 top 片段 → 长 ctx 精读），
     用长上下文补 RAG 的召回碎片化，用 RAG 补长ctx 的规模不可行。**本题（500 万 token、周更、需引用）落在混合区。**
5. **可引用性（N-5.1）是题面硬要求**：长上下文方案需额外验证模型自标引用的准确率，不达标则只能 RAG/混合。

**最有用的产出**（对应硬件 gold 的「u<0.35 别买卡」）：
**「RAG vs 长上下文的第一变量不是技术，是文档规模 × 问答量的组合」**——
文档装得下且问答少 → 长上下文；文档装不下或问答多 → RAG/混合。
**在测清 B1/B2/B4 之前，「RAG 比长上下文先进」这句话没有决策意义**，
因为两个方案各自的致命黑盒（召回 vs 定位衰减）都没量化。

## 常见误读（= 本实验要测的"隐藏矛盾"）
1. **「纯 RAG 召回 top-k 足够覆盖答案」** —— 错。50 万页规模下跨段落/跨文档推理的答案无法被固定 k 个 chunk 覆盖，召回率瓶颈直接压低"正确回答"概率，而题面要求不能编造。
2. **「长上下文塞入全文 = 准确率随长度提升」** —— 错。Lost in the Middle 效应使中段信息利用率下降，且 O(N²) 注意力让单位 token 成本非线性增长，"装得下"不等于"用得上"。
3. **「检索质量只取决于 embedding 模型」** —— 错。Chunking 策略（固定字数 vs 语义分段）、文档格式分布（表格/图片占比）、重排序层都显著影响召回，embedding 只是链路一环。
4. **「p95 < 15s 只约束生成延迟」** —— 错。端到端含检索+重排+生成，周更语料的索引重建窗口也计入运维成本，单看生成延迟会漏掉系统级瓶颈。
