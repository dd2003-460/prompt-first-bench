# 标准答案 · 推理基础设施（vLLM vs TGI vs 原生 transformers 怎么选）

**题面**：已有 27B 模型权重 + 固定 GPU（RTX 3090×4，96GB 总显存），选一个推理服务框架，
使**每千输出 token 的服务成本最低**，且满足在线 SLO（TTFT p99 < 2s，TPOT p99 < 60ms，并发 ≥ 8）。

**候选**：vLLM · TGI（Text Generation Inference）· 原生 transformers（`generate()`/`pipeline`）·
（对照：SGLang，作为国内/长上下文备选）。

**与 27B 硬件 gold 的结构差异**：硬件题里 GPU 是**变量**、模型固定，叶子是物理规格；
本题 GPU 和模型都**固定**，变量是**软件框架**，叶子是**框架工程属性**（调度/KV 管理/批量/运维）。
根节点仍是「单位产出的成本」，但成本侧 `c_hour` 是**常数**（硬件已定），
**整棵树的重心从「钱怎么花」移到「吞吐怎么榨」**——这是和硬件题最本质的结构不同。

---

## 0. 根节点（L0)

**N-0 每千输出 token 的服务成本 `c_serve` [¢/1k_out_tok]**

```
c_serve = c_hour / ( λ_out × u )        λ_out = 输出 token 速率 [tok/h]
```

- `c_hour`：每小时持有成本——**硬件已定，是常数**（引用 `gold/` 硬件树算好，不重复分解）。
- `λ_out`：框架实际输出的 token 速率——**本题唯一的优化主战场**。
- `u`：服务利用率（有请求的小时占比）——业务侧黑盒，与框架无关。

**为什么用这个标量**：
1. 「哪个框架最划算」= 单位输出 token 成本最低，无歧义。
2. 标量，可排序可弹性。
3. **SLO 作为约束**（不是成本项）：不达 SLO 的框架无论多快都划掉——和硬件题「带宽不够直接划掉 M2 Ultra」同构。

**口径声明**：
| 项 | 口径 |
|---|---|
| `SHARE` | 弹性绝对值归一化 |
| `BOUND` | 叶子区间内 `c_serve` 的 max/min |
| 负载画像 | 混合负载：in≈1500 / out≈500 token，并发 8–32（题面给定） |
| 成本口径 | 只算框架带来的**增量**成本差异；`c_hour` 常数项在排名中抵消，但绝对值仍要报 |

## 1. 正交维度定义（L1)

```
c_serve = c_hour / ( λ_out × u )
λ_out   = 调度效率 × KV管理效率 × 批量效率 × 算力利用率 × 硬件峰值   （后者是常数）
```

| 维度 | 节点 | KIND | 说明 |
|---|---|---|---|
| **吞吐侧** | N-1 输出吞吐 `λ_out` | signal | 框架榨干硬件的能力，本题主导 |
| **延迟侧** | N-2 延迟可行性 `latency_ok` | constraint | TTFT/TPOT/p99 是否达 SLO |
| **显存侧** | N-3 显存效率 `mem_eff` | signal | KV 管理决定并发上限 n_max |
| **运维侧** | N-4 运维成本 `ops_cost` | signal（次要） | 部署/升级/排障的人天 |
| **功能侧** | N-5 功能完备 `feature` | nuisance | 量化/投机解码/长上下文支持 |
| **可行域** | N-6 兼容性 `feasible` | constraint | 硬件/模型是否被支持 |

**正交性检验**：

| 这一对 | 前者独占 | 后者独占 |
|---|---|---|
| 吞吐 ↔ 延迟 | 批量策略 | 尾延迟 p99 |
| 吞吐 ↔ 显存 | 调度效率 | KV 碎片率 |
| 延迟 ↔ 显存 | TPOT | 最大并发 n_max |
| 运维 ↔ 功能 | 部署复杂度 | 量化支持 |

全过。**SHARED 必须现在记**：`并发数 n` 同时由 N-3（显存装得下多少）和 N-2（延迟允许多少）决定，
`n = min(n_mem, n_slo)`——和硬件 gold 的 `n = min(n_speed, n_cap)` 完全同构，是框架题的标志性耦合。

## 3. 叶子卡片（执行动作 + 完成判据 + 数据来源）

### N-1.1 调度效率 `sched_eff` ■B1
- **执行动作**：在目标负载（in1500/out500，并发 8–32）下压测，测「请求从进到开始出的排队延迟」占比；对比 continuous batching（vLLM/TGI）vs 静态 batch（原生）的差异。
- **完成判据**：每个框架一个 sched_eff ∈ (0,1] + 实测吞吐/理论吞吐比。
- **数据来源**：自测压测（ Serve 基准如 `genai-perf` / `vllm bench`）。
- **为什么黑盒**：调度效率取决于负载到达模式（泊松 vs 突发），benchmark 常用合成负载，与真实业务差 20–40%。

### N-1.2 KV 缓存管理 `kv_mgmt` ■B1
- **执行动作**：测「同样显存下能维持的最大有效并发」，对比 PagedAttention（vLLM）/ 块分配（TGI）/ 预分配（原生，易 OOM 或浪费）。
- **完成判据**：每个框架一个「有效 KV 利用率」= 实际用于生成 token 的 KV / 总 KV 显存。
- **数据来源**：自测 + 框架文档的内存模型说明。

### N-1.3 批量策略 `batch_eff` ■B1
- **执行动作**：测 dynamic batching 下不同 batch _size 的吞吐曲线，找拐点；对比 static batch 的 padded 浪费。
- **完成判据**：最优 batch_size + 对应吞吐；padded token 占比。
- **数据来源**：自测扫 batch。

### N-1.4 算子/kernel 效率 `kernel_eff` ■B1
- **执行动作**：同模型同硬件，测各框架 decode 阶段实测带宽利用率（对比硬件峰值 936GB/s×4）。
- **完成判据**：每个框架一个 η_kernel = 实测吞吐 / (硬件峰值 × 理论)。
- **数据来源**：自测 + `nsight`/`rocprof` /profile 输出。

### N-2.1 / N-2.2 延迟 TTFT / TPOT ■B3
- **执行动作**：压测 1000 请求，记录 TTFT、TPOT 的 p50/p90/p99。
- **完成判据**：p99 值 + 是否达 SLO（TTFT<2s, TPOT<60ms）。
- **数据来源**：自测。**厂商只公布平均/理想值，p99 必须自测**——尾延迟由调度抢占、批内最长序列决定，无闭式。

### N-2.3 并发允许上限 `n_slo`
- **执行动作**：递增并发，找到「TPOT p99 刚达 60ms」的并发数。
- **完成判据**：一个 n_slo 整数。
- **数据来源**：自测扫并发（S-c，由 SLO 约束决定）。

### N-3.1 KV 碎片率 `frag_rate` ■B2
- **执行动作**：混合序列长负载下跑 1 小时，测 KV 显存的碎片率（已分配但不可用的比例）。
- **完成判据**：frag_rate ∈ [0,1]；PagedAttention 类应 < 5%，预分配类可能 20–40%。
- **数据来源**：自测 + 框架内存指标。

### N-3.2 最大并发 `n_mem`
- **执行动作**：`n_mem = floor((总显存 − 权重占用 − 预留) / 每流KV@目标ctx)`，引用硬件 gold 的 KV 公式。
- **完成判据**：每个框架一个 n_mem（KV 管理方式不同→每流实际占用不同）。
- **数据来源**：config.json + 硬件规格（S-a 可算，但「每流 KV」受 frag_rate 影响）。

### N-3.3 前缀缓存 `prefix_cache`
- **执行动作**：测系统提示（system prompt）复用时 prefill 算力节省比例。
- **完成判据**：命中率 × 节省比；vLLM/SGLang 支持自动前缀缓存，原生不支持。
- **数据来源**：框架文档 + 自测（S-a）。

### N-4.1 部署复杂度 `setup` ■B4
- **执行动作**：从零装机到首个可用服务，计时（含依赖/CUDA 版本/模型加载调通）。
- **完成判据**：人时数 + 踩坑清单。
- **数据来源**：实测部署（原生 transformers 最快，vLLM 中等，TGI 需 Docker Compose）。

### N-4.2 升级排障成本 `maint` ■B4
- **执行动作**：模拟一次版本升级 + 一次典型故障（OOM/死锁/精度异常）的定位耗时。
- **完成判据**：人时数 + 难度定性。
- **数据来源**：实测 + 社区 issue 频率（GitHub issue 搜索）。

### N-4.3 可观测性 `observability`
- **执行动作**：查框架内置 metrics（Prometheus 端点）、日志、请求 trace 的完备度。
- **完成判据**：三项各有/无 + 质量定性。
- **数据来源**：框架文档（S-a）。

### N-5.1 量化支持 `quant`
- **执行动作**：查目标量化格式（GPTQ/AWQ/GGUF）在该框架的加载与推理支持状态。
- **完成判据**：支持矩阵（框架 × 量化格式）。
- **数据来源**：框架文档 + 模型仓库（S-a）。

### N-5.2 投机解码 `spec_decode`
- **执行动作**：查是否支持 draft-model 投机解码，实测加速比。
- **完成判据**：支持与否 + 加速比（27B 自投机通常 1.3–1.8×）。
- **数据来源**：框架文档 + 自测（S-a 为主）。

### N-5.3 长上下文/多模态 `long_ctx`
- **执行动作**：查 32K+ 上下文稳定性、是否支持多模态输入。
- **完成判据**：最大稳定 ctx + 多模态布尔。
- **数据来源**：框架文档（S-a）。

### N-6.1 硬件兼容 `hw_ok`
- **执行动作**：查框架对消费级卡（3090，SM 8.6）/ 未来国产卡的支持状态。
- **完成判据**：pass/fail + 已知问题。
- **数据来源**：框架 CI 支持矩阵（S-a）。**一票否决**：不支持目标硬件直接划掉。

### N-6.2 模型支持 `model_ok`
- **执行动作**：查目标 27B 模型是否在框架的官方支持列表 + 是否有社区成功部署记录。
- **完成判据**：官方支持/社区支持/未支持 三级。
- **数据来源**：框架 model support 页 + GitHub（S-a）。

## 4. 关键黑盒（S-b 收口）

| 黑盒 | 为什么没有闭式 | 区间（估） | 一天内能做完的测法 | 弹性 |
|---|---|---|---|---|
| **B1 调度/KV/批量/kernel** | 取决于真实负载到达模式，benchmark 合成负载不代表业务 | 框架间吞吐差 [1.3×, 2.5×] | 目标负载压测 4 框架 | **高（主导排序）** |
| **B2 KV 碎片率** | 混合序列长下的动态分配，无解析解 | [0.03, 0.40] | 混合负载跑 1h 看内存指标 | 中（定 n_mem） |
| **B3 尾延迟 p99** | 调度抢占+批内最长序列，厂商不给 | TTFT p99 [1, 8]s | 1000 请求压测 | 中（SLO 约束） |
| **B4 运维成本** | 依赖团队经验，无闭式 | setup [0.5, 3] 人天 | 实测部署 | 低（次要项） |

**B1 是本题的核心黑盒**，对应硬件 gold 的 B2/B3（MFU/η_bw）——都是「厂商标称 vs 实测」的差距。
但性质不同：硬件的 MFU 是**物理噪声**（kernel/batch 影响），框架的调度效率是**工程设计差异**，
** Framework 之间差 1.3–2.5 倍是真实的、可复现的**，不是噪声。所以框架题的 B1 区间更窄、更可靠，
**结论比硬件题更「硬」**——这是泛化测试的一个正面发现：方法论在「工程选型」上比「物理选型」给出的排名更稳。

## 5. SHARED 参数：`并发数 n` 的双约束决定

```
n = min( n_mem [N-3.2 显存装得下],  n_slo [N-2.3 延迟允许] )
```

- `n_mem` 由 KV 管理方式决定（PagedAttention 碎片少→n_mem 大）。
- `n_slo` 由调度决定（continuous batching 下高并发不显著拉高 TPOT→n_slo 大）。
- **两个框架可能在 n_mem 和 n_slo 上各有优劣**，`min` 让最终 n 由短板决定。

**不标 SHARED 的后果**：会分别得出「vLLM 显存效率高→并发大」（只看 N-3）和「原生 transformers 单请求延迟低」（只看 N-2），
拼不出「在线高并发场景 vLLM 赢、单请求低延迟场景原生够用」这个正确的条件化结论。

## 6. 推荐方案

**结论形状**（条件化决策规则，不是「无脑 vLLM」）：

1. **先过可行域**（N-6）：目标硬件 + 目标模型不被框架支持 → 直接划掉。
   （例：某国产卡只有 TGI 适配 → vLLM 再好也不可选。）
2. **在线高并发服务（并发 ≥ 8，吞吐优先）**→ **vLLM**（PagedAttention + continuous batching，
   吞吐通常比原生高 2–4×，比 TGI 略高或相当）。SGLang 在长上下文/前缀复用多时可能更优。
3. **已有 HF 生态、需要最简单部署 + 中等并发** → **TGI**（Docker Compose 一键起，运维成本最低）。
4. **离线批处理 / 研究原型 / 单请求低延迟、并发=1** → **原生 transformers** 足够
   （没有调度开销，单请求 TTFT 最低；但并发一上来吞吐断崖）。
5. **运维成本（N-4）是次级 tie-breaker**：吞吐差 < 10% 时，选团队更熟、可观测性更好的。

**最有用的产出**（对应硬件 gold 的「u<0.35 别买卡」）：
**「框架选型的第一变量不是框架，是负载画像（并发数 + 序列长分布）」**——
并发 < 4 且离线时，原生 transformers 的「低吞吐」根本不是问题，选它运维最省；
并发 ≥ 8 在线时，调度效率（B1）主导，vLLM 类才体现价值。
**没测自己的负载并发分布之前，「vLLM 比 transformers 快 3 倍」这句话没有决策意义。**

## 常见误读（= 本实验要测的"隐藏矛盾"）
1. **「官方 benchmark 吞吐排名 = 我的 workload 下的排名」** —— 错。benchmark 的 batch/seq len/量化配置与真实 SLO 约束不同，同口径对比缺失时排名不可迁移（尤其 vLLM vs SGLang 各自宣传数据不同源）。
2. **「TTFT 和 TPOT 可以独立优化」** —— 错。两者共享同一调度器和显存预算：压 TTFT（prefill 并行）会挤占 decode 带宽推高 TPOT，SLO 是耦合约束不是两个独立指标。
3. **「原生 transformers 只是慢，不会错」** —— 错。缺少连续 batching/PagedAttention 时高并发下显存碎片化和 OOM 风险上升，正确性边界随并发数移动。
4. **「多卡线性加速」** —— 错。张量并行的通信开销使 4×3090 的有效加速远低于 4x，PCIe 互联（非 NVLink）场景尤甚。
