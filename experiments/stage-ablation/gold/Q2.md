# 标准答案 · 模型选型（27B 级开源模型该选哪个）

**题面**：为私有化部署选一个 24–33B 级开源 LLM，主要做**函数级代码补全（Python/JS）+ 通用指令跟随**，
单台双卡 24GB（或等效 API），使**每千次合格回答的总成本最低**。

**候选**（2026-10 时点，open-weight，参数 24–33B 为主，含 70B 量化作上界对照）：
Qwen3-32B · Qwen2.5-Coder-32B-Instruct · Mistral-Small-2501-24B · GLM-4-32B-0414 ·
DeepSeek-Coder-V2-33B · Llama-3.3-70B-Instruct(W4) 。

**与 27B 硬件 gold 的结构差异**：硬件题的候选是 GPU，叶子是物理量（带宽/算力/卡价）；
本题候选是**模型**，叶子是**模型属性**（基准分/单价/上下文/许可证/生态）。
根节点同为「单位合格产出的成本」，但**树下面的维度完全不同**——这正是泛化测试要看的：
方法论（正交拆解+原子化+交叉检验）能否长出一棵**形状不同但同样可验算**的树。

---

## 0. 根节点（L0）

**N-0 每千次合格回答的成本 `c_acc` [¢/1k_acc]**

```
c_acc = 1000 × c_call / acc_rate
```

- `c_call`：生成一次回答的花费（¥ 或 ¢），取决于走 API 还是自部署。
- `acc_rate`：一次回答「合格」的概率（代码能跑通 / 指令被正确跟随）。

**为什么用这个标量**（而不是「哪个模型最好」）：
1. 「最划算」在模型选型里只有这一种无歧义读法：**单位合格产出的成本**。
2. 它是标量，可排序、可做弹性、可做区间。
3. 「合格」二字把**能力**拉进分母——不看能力只看价格的选型，会选出便宜但答不对的模型。

**口径声明**：
| 项 | 口径 |
|---|---|
| `SHARE` | 弹性绝对值归一化，`SHARE_i = |ε_i|/Σ|ε_j|` |
| `BOUND` | 叶子在区间内变动时 `c_acc` 的 max/min |
| 合格判定 | 代码补全：单测通过；指令跟随：人工判「可用」。判定标准题面未给 → 黑盒 B2 |
| 部署形态 | 自部署与 API 都在候选内，由 N-2.3 breakeven 决定走哪条 |

## 1. 正交维度定义（L1）

第一刀按**模型选型的五个正交维度**切，不是按推理物理切：

```
c_acc = c_call / acc_rate
      =  [成本侧 N-2]  /  [能力侧 N-1]
约束侧 N-4 与 生态侧 N-5 不进 SHARE 池（约束先筛候选，生态是次要修正项）
速度侧 N-3 是 SLO 可行性约束（不是成本项）
```

| 维度 | 节点 | KIND | 说明 |
|---|---|---|---|
| **能力侧** | N-1 合格回答率 `acc_rate` | signal | 基准分 → 任务接受率的转换 |
| **成本侧** | N-2 单次调用成本 `c_call` | signal | API 价格 或 自部署摊销 |
| **速度侧** | N-3 延迟可行性 `latency_ok` | constraint | TTFT/TPOT 是否达 SLO |
| **约束侧** | N-4 可行域 `feasible_set` | constraint | 上下文/许可证/微调 |
| **生态侧** | N-5 生态维护 `eco` | nuisance | 工具链/社区/长期风险 |

**正交性检验**（每对找一个独占参数）：

| 这一对 | 前者独占 | 后者独占 |
|---|---|---|
| 能力 ↔ 成本 | 基准分 bench_score | 单价 p_in/p_out |
| 能力 ↔ 速度 | 幻觉率 | TPOT |
| 成本 ↔ 速度 | 卡价/电价 | SLO 达标率 |
| 成本 ↔ 约束 | API 价格 | 许可证条款 |
| 约束 ↔ 生态 | 上下文窗口 | 更新频率 |

五对全过。**一处 SHARED 必须现在记下**：` params 参数量 ` 同时进
N-2.2.1（显存→GPU 数→成本）和 N-3（速度）和 N-4.1（上下文承载）——三条路径，
见 §5。

## 2. 全树（24 节点）

```
N-0  每千次合格回答成本  c_acc [¢/1k_acc]                     split
│
├─ N-1  合格回答率  acc_rate [—]                               split   ■能力侧
│  │    acc_rate = P(bench→task) × (1 − halluc_rate) × P license-clean
│  ├─ N-1.1  基准能力分  bench_score                           split
│  │  ├─ N-1.1.1  代码基准    HumanEval/MBPP pass@1            leaf S-a
│  │  └─ N-1.1.2  指令基准    IFEval/MMLU-Pro                  leaf S-a
│  ├─ N-1.2  基准→任务迁移系数  transfer                        leaf S-b  ■B1
│  └─ N-1.3  幻觉/拒答率    halluc_rate                         leaf S-b  ■B2
│
├─ N-2  单次调用成本  c_call [¢/call]                           split   ■成本侧
│  │    c_call = min( API 路径, 自部署路径 )
│  ├─ N-2.1  API 路径成本                                        split

│  │  ├─ N-2.1.2  输出单价    p_out [¢/1k tok]                   leaf S-a
│  │  └─ N-2.1.3  token 画像  (in, out per completion)           leaf S-a
│  ├─ N-2.2  自部署路径成本                                       split
│  │  ├─ N-2.2.1  所需 GPU 数  n_gpu = f(params, bits, KV)       leaf S-a  →硬件gold
│  │  ├─ N-2.2.2  每小时成本  c_hour                              leaf S-c  →硬件gold
│  │  └─ N-2.2.3  每小时合格产出  λ·acc                           leaf S-c  →硬件gold
│  └─ N-2.3  API/自部署 breakeven  u Break                       leaf S-b  ■B3  SHARED:u
│
├─ N-3  延迟可行性  latency_ok                                  split   ■速度侧
│  ├─ N-3.1  首 token 延迟  TTFT                                leaf S-b  ■B4
│  ├─ N-3.2  每 token 延迟  TPOT                                 leaf S-b  ■B4
│  └─ N-3.3  SLO 达标率    p99_ok                                leaf S-b  ■B4
│
├─ N-4  可行域  feasible_set                                    split   ■约束侧
│  ├─ N-4.1  上下文窗口    ctx_win vs 任务需求                    leaf S-a
│  ├─ N-4.2  许可证        license（商用/修改/分发）               leaf S-a
│  └─ N-4.3  微调可用性    finetune_avail（领域适配时）            leaf S-a
│
└─ N-5  生态维护  eco                                           split   ■nuisance
   ├─ N-5.1  工具链成熟度  tooling（vLLM/量化/推理框架支持）        leaf S-a
   ├─ N-5.2  社区与更新    community（issue 响应/发布频率）         leaf S-b  ■B5
   └─ N-5.3  长期维护风险  maint_risk（停更/改许可/模型下架）        leaf S-b  ■B5
```

**图例**：`S-a` 可直接查/算 · `S-b` 只能给区间（黑盒）· `S-c` 由约束/外部 gold 决定 · `■Bn` 黑盒编号。

## 3. 叶子卡片（执行动作 + 完成判据 + 数据来源）

> 每张卡片三行：**执行动作**（怎么拿到这个值）/ **完成判据**（什么时候算拿到）/ **数据来源**。

### N-1.1.1 代码基准分
- **执行动作**：跑 HumanEval（164 题）+ MBPP（约 400 题）pass@1，用统一评测脚本（evalplus / 官方 leaderboard 口径）。
- **完成判据**：每个候选模型出一个 pass@1 标量，误差棒 ±2%（多次采样平均）。
- **数据来源**：模型官方技术报告 + 第三方 OpenCompass/SuperCLUE 榜单交叉核对。

### N-1.1.2 指令基准分
- **执行动作**：跑 IFEval（指令遵循）+ MMLU-Pro 或 C-Eval（通用知识），记录加权分。
- **完成判据**：每个候选出一个 0–100 分数，与官方博客分差 < 3 分。
- **数据来源**：OpenCompass 公开榜 + 模型仓库 README 自称分（两者冲突时记冲突，取保守值）。

### N-1.2 基准→任务迁移系数 `transfer` ■B1
- **执行动作**：从真实业务抽 100 个代码补全 case + 50 个指令 case，人工标「合格/不合格」，算 `acc_rate实测 / bench_score归一` 的比值。
- **完成判据**：得到一个 transfer 标量 + 95% CI（二项比例）。
- **数据来源**：自有业务标注（无公开数据，必须自测）。
- **为什么是黑盒**：benchmark 分数**不能直接当任务接受率**——HumanEval 80 分的模型在内部老代码库上可能只有 55% 可用（风格/依赖/边界差异）。这个 gap 没有闭式，是模型选型**最核心也最常被忽略**的黑盒。

### N-1.3 幻觉/拒答率 `halluc_rate` ■B2
- **执行动作**：在 100 个指令 case 上统计「答非所问 / 编造 API / 拒绝回答」的比例。
- **完成判据**：一个比例 + CI；与 bench 分无关地单独记录。
- **数据来源**：自有标注。
- **为什么是黑盒**：榜单不测幻觉，而代码补全里「编造不存在的函数」是高频失效模式。

### N-2.1.1 / N-2.1.2 API 单价
- **执行动作**：查各模型官方 API 定价页，记录输入/输出每千 token 价（含缓存折扣与否分开记）。
- **完成判据**：每个候选一组 (p_in, p_out)，带生效日期。
- **数据来源**：官方定价页（OpenAI/Anthropic/通义/月之暗面/DeepSeek 等），截图存档。

### N-2.1.3 token 画像
- **执行动作**：统计真实任务的输入/输出 token 分布（代码补全通常 in≈800–2000, out≈200–600）。
- **完成判据**：(in_med, out_med) + P90。
- **数据来源**：自有任务日志；无日志则用领域公开统计（如 code completion 语料统计）。

### N-2.2.1 所需 GPU 数
- **执行动作**：`n_gpu = ceil((params×bits/8 + KV预留) / 单卡可用显存)`，引用 `gold/` 硬件树的显存公式。
- **完成判据**：每个候选 × 每种精度一个 n_gpu 整数。
- **数据来源**：模型 config.json（参数量）+ 硬件规格（显存）。**S-a 可算**。

### N-2.2.2 / N-2.2.3 自部署每小时成本与产出
- **执行动作**：直接引用 `bench/gold/`（27B 硬件金标准）的 `c_hour` 和 `λ_raw` 公式，代入本模型的 n_gpu 与精度。
- **完成判据**：每个候选一个自部署 `c_call_selfhost`。
- **数据来源**：硬件 gold 的 `calc.py`（S-c，由外部 gold 决定，不重复分解）。

### N-2.3 API/自部署 breakeven `u_break` ■B3 · SHARED:u
- **执行动作**：解 `c_call_api = c_call_selfhost(u)` 的 u，得到 breakeven 利用率。
- **完成判据**：一个 u_break 标量；u > u_break 走自部署，否则 API。
- **数据来源**：N-2.1 与 N-2.2 的结果联立。
- **为什么是黑盒**：`u`（业务利用率)是硬件 gold 的全题第一瓶颈（BOUND 8×），这里同样不可计算，只能测业务日志。
- **SHARED**：`u` 同时出现在 API/自部署决策和自部署成本里，两条路径**反向**（u 高→自部署省），是本题真正的决策变量。

### N-3.1 / N-3.2 / N-3.3 延迟三件套 ■B4
- **执行动作**：在目标硬件（或 API）上跑 100 次真实请求，记录 TTFT、TPOT 的 p50/p99，对照 SLO（如 TTFT<2s, TPOT<50ms）。
- **完成判据**：每个候选一个 p99 达标率。
- **数据来源**：自测压测（无公开 p99，厂商只给理想条件吞吐）。
- **为什么是黑盒**：延迟取决于并发/序列长/硬件，厂商标称值与实测差 2–3 倍。

### N-4.1 上下文窗口
- **执行动作**：读 config.json 的 `max_position_embeddings`，对照任务需求（代码补全需装下整个文件/多文件，通常 8K–32K）。
- **完成判据**：pass/fail + 余量。
- **数据来源**：config.json（S-a）。**注意**：标称 128K 的模型在 32K 以上有效注意力可能衰减，长上下文「能用」≠「好用」，衰减部分进 B1。

### N-4.2 许可证
- **执行动作**：读 LICENSE 文件，判三条：能否商用 / 能否修改 / 能否分发衍生权重。
- **完成判据**：三个布尔值。
- **数据来源**：模型仓库 LICENSE（S-a）。**一票否决项**：私有化商用部署遇限制性许可（如非商用研究许可）直接划掉候选。

### N-4.3 微调可用性
- **执行动作**：查是否有官方/社区 LoRA 或全参微调 recipe，适配成本估时。
- **完成判据**：可用/不可用 + 预估适配人天。
- **数据来源**：GitHub issues + 社区（S-a 为主，适配成本是估的）。

### N-5.1 工具链成熟度
- **执行动作**：查 vLLM/SGLang/TGI 是否已支持该模型（含量化格式），推理是否开箱即用。
- **完成判据**：支持的框架列表 + 已知 bug 数。
- **数据来源**：框架 GitHub 的 model support 列表（S-a）。

### N-5.2 / N-5.3 社区与长期风险 ■B5
- **执行动作**：查近 6 个月 release 频率、issue 响应中位时间、是否有停更/改许可信号。
- **完成判据**：一个定性风险等级（低/中/高）+ 依据。
- **数据来源**：GitHub activity + 官方博客（S-b，前瞻性无闭式）。

## 4. 关键黑盒（S-b 收口）

| 黑盒 | 为什么没有闭式 | 区间（估） | 一天内能做完的测法 | 弹性 |
|---|---|---|---|---|
| **B1 基准→任务迁移** | benchmark 与真实任务分布不同，gap 无公式 | transfer ∈ [0.55, 0.85] | 150 个真实 case 人工标注 | **高（决定排序）** |
| **B2 幻觉/拒答率** | 榜单不测，任务相关 | [0.05, 0.25] | 100 case 标注 | 中 |
| **B3 breakeven 利用率** | 取决于业务量，与硬件 gold 同源 | u ∈ [0.10, 0.80] | 看 3 个月任务日志 | **高（API/自部署翻转）** |
| **B4 延迟 p99** | 厂商不给真实并发下 p99 | TTFT p99 ∈ [1, 5]s | 压测 100 请求 | 中（SLO 约束） |
| **B5 社区/维护风险** | 前瞻性事件 | 定性 低/中/高 | 查 GitHub activity | 低（nuisance） |

**B1 是本题最值得看的一个黑盒**，性质和硬件 gold 的 B7（KV 头数歧义）类似但更普遍：
**「27B 级」这个模糊输入，会被每个评测者默默填上不同的 benchmark→任务换算**，
造成排序级分歧（一个模型 HumanEval 高 5 分，transfer 低 0.1，真实接受率就反过来）。
1 分钟能查的 config 造成 2 倍分歧（硬件 B7）；**1 天能测的 transfer 造成排名翻转（本题 B1）**。

## 5. SHARED 参数：`params 参数量` 的三条路径

```
params ──┬──▶ N-2.2.1 显存→GPU数→c_hour     （params 越大越贵）  升成本
         ├──▶ N-3     速度（params 越大 TPOT 越高）              降可行性
         └──▶ N-4.1   长上下文承载（params 大→KV 挤占→有效 ctx 短） 降可行性
```

三条路径**同号**（params 增大都变差），所以「选更大模型」不是无条件更好——
70B 量化(W4) 能力最强，但需要更多卡、TPOT 更高、有效上下文更短。
**不标 SHARED 的树会输出「参数量大=能力强=选它」，漏掉成本和可行性的反噬。**

**真正的决策变量是 `transfer × params` 的权衡**：能力增益能否覆盖成本/可行性损失，
取决于 B1（任务迁移），而 B1 只能自测。

## 6. 推荐方案

**结论形状**（不是「选 Qwen3-32B」，是「在什么前提下选谁」）：

1. **先测 B1（transfer）和 B2（幻觉）**——1 天，150 个真实 case。
   在 transfer 测清之前，任何基于榜单的排名都不可靠（榜单分差 5 分以内 ≈ transfer 噪声）。
2. **许可证一票否决先行**（N-4.2）——私有化商用部署，非商用许可的模型直接划掉，不进排名。
3. **API/自部署由 B3 决定**：u < u_break 走 API（按 N-2.1 单价选最便宜的合格模型），
   u > u_break 自部署（按硬件 gold 选卡）。**u 测不清之前，「选哪个模型」和「怎么部署」是同一个问题。**
4. **在 transfer 实测后**，对幸存者按 `c_acc = c_call / (transfer × bench × (1−halluc))` 排序。
   预期赢家画像：**代码任务 → 代码特化模型（Qwen2.5-Coder-32B / DeepSeek-Coder 系）；
   通用任务 → 综合旗舰（Qwen3-32B / GLM-4-32B）**。70B 量化只在「能力瓶颈且不在乎延迟」时赢。

**最有用的产出**（对应硬件 gold 的「u<0.35 就别买卡」）：
**「在测清 transfer 之前，榜单前两名之间的差距没有意义」**——
模型选型的第一瓶颈不是模型，是**你自己没测 benchmark→任务的迁移系数**。

## 常见误读（= 本实验要测的"隐藏矛盾"）
1. **「MoE 理论速度优势 = 实际部署速度优势」** —— 错。MoE 的速度优势依赖激活参数占比和 batch size；低并发（batch=1）时内存访问模式可能抵消甚至反转该优势，实测前不能当既成事实。
2. **「代码特化模型在混合负载下一定占优」** —— 错。若通用指令跟随占比高，代码特化模型的通用能力短板会拉低整体合格回答率，性价比结论随任务混合比翻转。
3. **「显存装得下 = 能跑得快」** —— 错。装得下只保证不 OOM；吞吐还受 KV cache 策略、量化精度损失、attention 实现影响，容量不是性能的第一变量。
4. **「每千次合格回答成本只看推理单价」** —— 错。合格率低导致重试/人工兜底的成本必须计入总成本，单价最低者未必总成本最低。
