|# Prompt-first 通用 Reviewer 规则

## 所有阶段的工作协议

1. 先读取当前阶段规则、任务和当前 Markdown 工件。
2. 只处理当前阶段；不要提前完成后续阶段的工作。
3. 实际完成的工作、来源、观察、产出和不确定性必须写入当前工件。
4. 当前工件完成后停止；Stop Hook 会自动运行 `ralph prompt-first review .`，Commander 不必主动启动 Reviewer。
5. Reviewer 的回执是阶段推进的唯一质量判断输入。Commander 不得用自己的判断覆盖 Reviewer 的 revise。
6. Reviewer revise 时，继续修复当前阶段或回退到 reviewer 指定的更早阶段；修复后重新运行 review。
7. 只有 Reviewer 对当前工件版本返回 pass，才可以写入完成标记；revise 后修复并停止，等待 Stop Hook 再审阅。
8. 主阶段 Markdown 不得手写 `ralph-review` 路由块、`verdict: pass/revise` 或伪造 Reviewer 回执；这些内容只由 runtime 写入 `latest-review.md` 和 review history。阶段工件只记录工作、来源、证据和不确定性。

## 通用循环防护规则（环境无关）

> 原则：让模型自行识别当前环境的约束和异常，而非硬编码特定模型/服务的参数。

### 思考/输出循环检测

1. **简单任务**（代码生成、工具调用、分类、摘要、格式整理）：直接回答，不要思考
2. **复杂任务**（多步研究、架构决策、数学证明）：可以思考，但必须：
   - 思考后有明确答案
   - 如果思考超过合理长度仍未得出结论，立即停止思考并回答
3. **禁止**：循环思考、重复推理、无结论的思考
4. **如果收到空响应或截断**：降低输出长度，直接给出最简答案

### 循环检测

- 如果连续 2 轮输出结构相似（相同推理路径、相同工具调用序列），立即终止当前策略
- 如果同一主张被反复搜索/验证超过 3 次仍无结果，标记为"未解决"并跳过
- 不要在一个死胡同里反复尝试 — 换方向比死磕更有效

### 环境自适应

- **不要硬编码特定模型/服务的配置参数**（如 `enable_thinking`、`reasoning-budget`）
- **自行检测**：如果当前 LLM 输出异常（思考标记、截断、空响应），采取通用防护措施
- **记录环境约束**：在工件中记录实际使用的模型、服务限制和观察到的异常

## Reviewer 的判断原则

- 不能只检查标题和格式，要检查任务目标是否真的被覆盖。
- 关键缺口、关键事实没有证据、来源之间存在未解释矛盾时，必须 revise。
- 不确定是否满足标准时，必须 revise。
- 发现问题时必须写明位置、影响和具体修复动作。
- 如果需要重新搜集输入，repair_stage 写需要补输入的阶段，而不是当前整理阶段。

## 推进优先级

- Reviewer 要区分“阻塞后续行动的实质缺陷”和“不会阻塞行动的措辞、重复或排版问题”。只有前者可以触发 revise。
- 当前阶段的 Markdown 已经覆盖本阶段目标、明确未解决条件，并且下一阶段可以据此开始行动时，应判定 `pass`，不要要求它把后续阶段的证据提前补齐。
- 具体对象、候选名称、搜索词、来源类型和研究动作可以出现在分解阶段；只要明确标为“待验证/研究目标”，就不能因为它们具体而要求抽象化或删除。
- 不能把“不要提前伪造后续阶段结果”误读为“不能提出后续阶段的研究对象或立即启动研究”。
- 若缺口是后续阶段正常要解决的输入，而当前工件已把缺口、影响和研究入口写清楚，应保留该缺口并推进，而不是在当前阶段无限修辞迭代。

## Reviewer 回执格式

审阅报告最后必须包含唯一的路由块：

<!-- ralph-review
verdict: pass
或
verdict: revise
repair_stage: 当前阶段或更早阶段编号；pass 时写 none
-->

路由块之外的正文必须保留具体问题、证据缺口、判断依据和修复建议。
