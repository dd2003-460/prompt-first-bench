# 阶段 03：具体行动分解

## 操作流程

1. 只使用已经通过 Reviewer 的证据，不把猜测写成行动前提。
2. 将目标拆成可执行步骤，每步写输入、动作、依赖、预期产出和验收方式。
3. 标注哪些步骤可以并行，哪些步骤必须等待前一步结果。
4. 为关键失败情况写替代路径和停止条件。

## Reviewer 质检标准

- 行动步骤是否覆盖目标，而不是只生成漂亮计划；
- 每步是否有明确产出和验收方式；
- 依赖关系是否完整且没有循环；
- 关键未知是否被错误地当成已知前提；
- 另一个执行者能否直接依据本工件行动。

如果行动计划依赖尚未核验的事实，repair_stage 写 02 或 02.5；否则写 03。

## 操作示例

### 示例 1：GPU 调研 — 执行计划

**阶段 02 证据：**
```
- RTX 4090：24GB GDDR6X，$1,599，CUDA 生态成熟
- RTX 4080：16GB GDDR6X，$1,199，CUDA 生态成熟
- AMD 7900 XTX：24GB GDDR6，$999，ROCm 生态发展中
- Apple M2 Max：192GB 统一内存，$3,199，Metal 生态成熟
```

**行动分解：**
```
步骤 1：搭建测试环境
- 输入：已核验的 GPU 列表
- 动作：准备 4 台测试机器（或云实例）
- 依赖：无
- 预期产出：4 台可运行的测试环境
- 验收方式：`nvidia-smi` / `system_profiler SPDisplaysDataType` 正常输出
- 并行：是（4 台可并行准备）
- 失败替代：云实例（AWS p4d / GCP A3）

步骤 2：安装推理框架
- 输入：测试环境
- 动作：安装 PyTorch + vLLM / Ollama / llama.cpp
- 依赖：步骤 1 完成
- 预期产出：框架安装成功，`python -c "import torch; print(torch.cuda.is_available())"` 返回 True
- 验收方式：框架版本检查 + 简单推理测试
- 并行：是（4 台可并行安装）
- 失败替代：Docker 容器部署

步骤 3：基准测试
- 输入：安装好的框架
- 动作：运行标准基准测试（MLPerf / 自定义脚本）
- 依赖：步骤 2 完成
- 预期产出：各 GPU 的 tokens/sec、延迟、显存占用数据
- 验收方式：测试脚本输出日志 + 数据表
- 并行：是（4 台可并行测试）
- 失败替代：使用公开基准数据

步骤 4：成本效益分析
- 输入：基准测试数据 + 价格数据
- 动作：计算每美元性能比
- 依赖：步骤 3 完成
- 预期产出：性价比排名表
- 验收方式：数据表 + 结论
- 并行：否（必须等待步骤 3）
- 失败替代：使用估算值（标注不确定性）
```

### 示例 2：技术选型 — 执行计划

**阶段 02 证据：**
```
- Ollama：易用，支持 GGUF，速度中等
- vLLM：高性能，支持 AWQ/FP16，部署复杂
- llama.cpp：轻量，支持多种硬件，API 简单
- TensorRT-LLM：NVIDIA 专属，性能最高，学习曲线陡峭
```

**行动分解：**
```
步骤 1：部署测试环境
- 输入：已核验的框架列表
- 动作：在测试机器上安装 4 个框架
- 依赖：无
- 预期产出：4 个框架均可运行
- 验收方式：`ollama list` / `vllm --help` / `llama-server --help` / `trtllm --help`
- 并行：是
- 失败替代：Docker 容器

步骤 2：统一测试模型
- 输入：安装好的框架
- 动作：下载同一模型（如 Llama-3-8B）的多种格式
- 依赖：步骤 1 完成
- 预期产出：模型文件 + 加载成功日志
- 验收方式：模型加载无报错
- 并行：否（必须等待步骤 1）
- 失败替代：使用公开可用的模型

步骤 3：性能对比测试
- 输入：加载好的模型
- 动作：运行相同提示词，记录 tokens/sec、延迟、显存
- 依赖：步骤 2 完成
- 预期产出：性能对比数据表
- 验收方式：数据表 + 统计显著性检验
- 并行：是（不同框架可并行）
- 失败替代：使用公开基准数据

步骤 4：易用性评估
- 输入：性能数据
- 动作：评估部署复杂度、文档质量、社区支持
- 依赖：步骤 3 完成
- 预期产出：易用性评分表
- 验收方式：评分表 + 理由
- 并行：否（必须等待步骤 3）
- 失败替代：基于文档和社区数据的间接评估
```

## 通用原则

### 步骤设计原则

1. **原子性**：每步只做一个明确的事情
2. **可验证**：每步都有明确的验收方式
3. **可并行**：能并行的步骤明确标注
4. **有退路**：关键步骤有替代方案

### 依赖关系处理

1. **无依赖**：可以立即执行
2. **单依赖**：等待前一步完成后执行
3. **多依赖**：等待所有依赖完成后执行
4. **循环依赖**：重新分解步骤，消除循环

### 失败处理

1. **记录失败**：如实记录失败原因
2. **评估影响**：判断失败对后续步骤的影响
3. **执行替代**：使用替代方案或标记为未解决
4. **不掩盖问题**：不要把失败包装成成功
