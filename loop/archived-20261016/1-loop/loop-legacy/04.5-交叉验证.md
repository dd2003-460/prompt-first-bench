# 04.5 交叉验证（产出后）

<!-- origin: ai -->

## 输入
- 上一阶段交付物 `loop-artifacts/04-r1.md` 与 `.json`：关键 claim 与结论、事实账本。
- 本阶段若已存在 `verification_report`（上次被打断），直接在其基础上继续，**不要重头再来**。

## 本阶段要交付什么
对 04 的**最终产出**（关键 claim 与结论）逐条核验，检查不同来源间是否存在**矛盾与冲突**，给出最终置信度，并产出可交付的交叉验证摘要。目标是在交付 / 进入 exploration 之前，把结论矛盾暴露出来。

## 机制（主 agent 只派发 subagent，或直接用工具）
1. 先读 `loop-artifacts/04.5-r1.json` 里已有的 `verification_report`（若有），继续未完成的 claim，不要重做已 verified 的。
2. 对每条关键 claim，用下方「可用核验来源」去核验，判定 `status`（verified / uncertain / rejected）并填 `checked_by`。
3. 产出最终交叉验证摘要（一致点 / 冲突点 / 最终置信度）。

## 可用核验来源（务必用「能抓到」的来源，禁止死循环重试抓不到的站点）
- **首选 `WebSearch`**：论文（arXiv / Google Scholar）、官方规格、基准测试、厂商文档——自动化环境里最可靠的交叉印证方式。
- **可 WebFetch 的公开页（直接能抓到文本）**：
  - `https://arxiv.org/abs/<id>` — 论文原文。
  - 厂商规格页：`https://www.nvidia.com/en-us/data-center/h100/`、`https://www.amd.com/en/processors/instinct-mi300x`、`https://cloud.google.com/tpu/docs/...`、`https://www.sk-hynix.com/...`（datasheet PDF 可能抓不到，改用 WebSearch）。
- **禁止**对纯 JS 聊天页（`perplexity.ai` / `chatgpt.com` / `claude.ai` / `gemini.google.com` / `grok.com` / `copilot.microsoft.com` / `arena.ai/agent` / `poe.com` / `bigmodel.cn` / `aistudio.google.com`）做 WebFetch——这些页自动化抓取返回空，会无限空转。对于已经由人类以 `ralph web-llm-authorize <项目>` 授权、且受运行时支持的站点，字段 worker 反而应运行 `ralph web-llm-check . <当前 task/request.json>`：本地 Agent 会在新鲜的可见 Playwright 窗口中输入并提交同一问题，再把回复保存为回执；不读取浏览器 cookie/凭据，也不尝试登录。未授权时只能用 `WebSearch` 获取公开信息并记录 `llm_status=not_authorized`。

## 逐条核验要点
- 该 claim 是否被 ≥1 个独立权威来源支持？（不强求 ≥2 个 LLM；能用 WebSearch + 1 个权威来源确认即可标 verified）
- 不同来源是否冲突？冲突点具体在哪？
- 若实在无法独立验证（如未量产规格、需实测数据）：标 `uncertain`，在 rationale 注明「待实测 / 未量产」，不进入最终推荐即可——**不要为 uncertain 的 claim 反复重试抓取，也不得把训练记忆、搜索失败或站点首页包装为 verified。**

## 交付（关键，之前卡住的根因）
1. 把最终交叉验证摘要作为**一条字段**提交到 `attribute_matrix`（运行时只认 `attribute_matrix` 字段，不认 `verification_report` 顶层键）：
   写一份 field-apply 文件，例如 `loop-artifacts/04.5-r1.fields.json`：
   ```json
   { "fields": [
     { "concept": "cross_validation_out",
       "role": "交叉验证摘要",
       "attribute": "最终交叉验证：一致点 / 冲突点 / 最终置信度（verification_report 已落盘于 04.5-r1.json）",
       "disposition": "confirmed",
       "rationale": "30 条 claim 中已验证若干、其余 uncertain（多为需实测/未量产的规格），矛盾点已在 rationale 标注",
       "evidence_refs": ["loop-artifacts/stages/04.5/r1/web-llm/<receipt>.json", "https://example.org/specific-source"],
       "validation_records": [{"claim_ref": "<claim id>", "source_refs": ["https://source-a.example/path", "https://source-b.example/path"], "observed_at": "2026-07-29T00:00:00+08:00", "verdict": "supported"}],
       "confidence": 0.8, "impact": "material", "reversible": true }
   ]}
   ```
   运行：**`ralph field-apply . loop-artifacts/04.5-r1.fields.json`**（校验并原子落盘）。
2. **推进到下一阶段（关键）**：本阶段字段齐全后必须显式推进——**只有阶段 01 自动推进，02+ 不会**，且聊天里输出 advance 无效（运行时不会解析聊天 token）。写 action 文件 `loop-artifacts/04.5-r1.advance.json`：
   ```json
   { "action": "advance", "status": "completed", "stage_id": "04.5", "revision": "r1", "next_stage": "exploration", "message": "完成产出后交叉验证，推进到 exploration" }
   ```
   运行：**`ralph apply . loop-artifacts/04.5-r1.advance.json`**（或 `ralph validate --result loop-artifacts/04.5-r1.advance.json --apply`）即完成推进。
3. 禁止直接 Write/Edit `loop-state.json`（易损坏导致循环崩溃）；状态损坏用 `ralph recover-state .`。
