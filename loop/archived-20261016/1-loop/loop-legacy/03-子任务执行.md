# 03 子任务执行（执行任务分解：含调研 + 后续行动）

<!-- origin: ai -->

## 输入

- `02.5-交叉验证.md` 验证后的字段（`task_spec.attribute_matrix`）。
- 02 整理的「每个分解项的后续执行计划」雏形。

## 本阶段要交付什么

把已调研、已交叉验证的分解项，细化为**可执行的子任务图**，并执行：

1. **执行任务分解**：把每个分解项拆成具体的子任务（T1.1 / T1.2 …），
   每个子任务有明确输入、输出、验收条件、依赖、写入路径。
2. **含调研子任务**：对执行中仍需补的事实，派调研 subagent（继续填 attribute_matrix）。
3. **含后续行动**：把「调研完成后的动作」（实现、计算、实验、写作）也列为子任务。
4. **执行**：逐个派发已批准的子任务卡，汇总产物到 `execution_summary`。

## 执行要求

- [ ] 子任务图正交、可验证、DAG 无环。
- [ ] 并行节点显式标注 `execution_mode` / `parallel_group_id`；Join 声明 `join_policy`。
- [ ] 每个 MUST 类约束被至少一个子任务覆盖。
- [ ] 调研类子任务产出 `evidence_refs` 通过 `ralph field-apply` 写回 attribute_matrix（禁止直接改 loop-state.json）。
- [ ] 所有 DAG 节点完成后才进入门禁。

## Gold Case

- 每个子任务凭定义即可执行（执行者模拟通过）。
- 调研子任务与行动子任务都跑通，产物可追溯。

## Bad Case

- 只列任务不执行。
- 跨任务代替决策 / 裸派 Agent（应派已批准任务卡）。

## 输出

- 子任务 DAG（含调研 + 后续行动）。
- `execution_summary`：已完成任务、产物引用、未决 claim。
- 更新后的 attribute_matrix。

## 必须遵守

1. 阶段编号 `03`；重新执行用 `03-r2`、`03-r3`。
2. 只能派发当前 ready 任务的已批准任务卡；不得裸派 Agent。
3. 所有结论最终进入 04 的事实核验。
4. 完成前须派发 execution-join-auditor（DAG 全部完成才出现）。

## 分支

- 通过：返回 `advance`，进入 `04`。
- 信息不足：返回 `rollback`，回到 `02`/`03` 新 revision。
- 等待人类：返回 `blocked_human`。
- 无 ready 任务：返回 `explore`。

## 结构化结果

  "next_stage": "04",
