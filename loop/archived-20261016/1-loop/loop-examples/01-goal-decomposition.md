# 阶段 01：目标、因素与空缺条件

## 操作流程

1. 将任务拆成互相区分但合起来覆盖目标的影响因素。
2. 区分人类已经提供的条件、可以从项目推导的条件和仍需研究的条件。
3. 为每个关键因素写出边界、优先级和它对后续结论的影响。
4. 把无法假定的条件写入空缺清单，避免把未知内容伪装成默认值。

## 阶段边界

- 本阶段是因素分解，不是资料搜集；尚未核验的型号、日期、价格、性能或兼容性只能作为"待研究假设"出现，必须明确标注为未验证，并写入空缺条件。
- 不要求在本阶段给出阶段 02 才能取得的价格、性能或网页 AI 证据；但必须给出阶段 02 的具体研究路径、来源类型和失败备用路径。
- Reviewer 不应因为阶段 02 的事实证据尚未出现而拒绝阶段 01，只要这些事实没有被伪装成已知，且对应空缺、优先级和研究动作完整。

### 启动下一阶段的门槛

- 阶段 01 的目的，是把任务变成可以立刻执行的研究入口，不是把研究对象抽象到无法行动，也不是穷举全部候选型号。
- 可以写出具体产品类别、候选型号、目标网站、搜索词、字段和研究动作；它们必须标成"待验证的研究目标/假设"，不能写成已经核验的事实。
- 只要目标交付物、主要因素、已知条件、关键空缺、阻塞影响和阶段 02 的第一批行动已经清楚，Reviewer 应判定 `pass`，允许直接进入阶段 02。未解决的价格、性能、时效性和来源问题本来就是阶段 02 的工作。
- 不得因为术语具体、空缺之间有轻微重叠、研究路径较详细或措辞不够抽象而 revise；只有遗漏关键因素、把未验证内容写成确定事实，或下一阶段无法据此开始行动时才 revise。

### 本阶段的判定原则（通用框架）

- **因素正交**：每个因素应独立影响目标，不重叠。若因素 A 和 B 有重叠，合并或重新定义边界。
- **覆盖目标**：所有关键目标必须有至少一个因素覆盖。若目标未被覆盖，添加新因素。
- **边界清晰**：每个因素的边界条件应明确（如"最小 8GB"、"tokens/sec > 10"），避免模糊。
- **优先级合理**：高优先级因素应直接影响目标达成，中优先级影响体验，低优先级仅参考。
- **空缺完整**：所有未验证条件必须列入空缺清单，不得伪装成已知。
- **研究路径具体**：阶段 02 的研究路径应写明目标网站、搜索词、字段和备用来源，但不要求实际执行。
- **候选型号处理**：若工件主动列出候选型号，必须标明其规格/价格仍待验证（例如：RTX 4090 — 待验证价格 $1,599）。排除理由应明确（例如：排除 8GB 以下显存卡 — 无法运行 13B+ 模型）。
- **复合空缺处理**：若使用复合空缺名，必须在其条目中列出可分别核验的子问题（例如："[待研究] 各候选 GPU 的价格和性能 — 子问题：1) 价格 2) 推理速度 3) 显存带宽"）。
- **术语具体性**：术语具体、空缺之间有轻微重叠、研究路径较详细或措辞不够抽象，不构成 revise 理由。只有遗漏关键因素、把未验证内容写成确定事实，或下一阶段无法据此开始行动时才 revise。

## 当前工件必须回答

- 目标到底要交付什么；
- 目标受哪些因素影响；
- 哪些条件已经确定；
- 哪些条件仍然缺失；
- 缺失条件会阻塞哪个后续判断；
- 下一阶段应该优先研究什么。

## 操作示例

### 示例 1：GPU 调研任务

**任务**：调研适合本地大模型推理的 GPU

**因素分解：**
```
1. 显存容量 — 决定能加载的模型大小（例如：最小 8GB，推荐 24GB+）
   - 边界：最小 8GB，推荐 24GB+
   - 优先级：高（硬性约束）
   - 影响：显存不足 → 模型无法加载

2. 显存带宽 — 决定推理速度（例如：HBM > GDDR6X > GDDR6）
   - 边界：HBM > GDDR6X > GDDR6
   - 优先级：中（影响体验，不阻塞）
   - 影响：带宽低 → 推理速度慢

3. 软件生态 — 决定兼容性（例如：CUDA（NVIDIA）vs ROCm（AMD）vs Metal（Apple））
   - 边界：CUDA（NVIDIA）vs ROCm（AMD）vs Metal（Apple）
   - 优先级：高（生态不兼容 → 无法使用）
   - 影响：生态差 → 需要额外适配

4. 价格 — 决定可行性（例如：待阶段 02 调研）
   - 边界：待阶段 02 调研
   - 优先级：中（用户预算内可接受）
   - 影响：价格过高 → 超出预算

5. 功耗/散热 — 决定部署环境（例如：桌面级 vs 服务器级）
   - 边界：桌面级 vs 服务器级
   - 优先级：低（不影响功能，只影响部署）
   - 影响：功耗高 → 需要额外散热设备
```

**空缺清单：**
```
- [待研究] 各候选 GPU 的当前市场价格
- [待研究] 各候选 GPU 的显存带宽具体数值
- [待研究] Apple M 系列芯片的 Metal 对主流框架的支持程度
- [待研究] 用户现有电源/机箱的兼容性
```

### 示例 2：技术选型任务

**任务**：选择本地部署的 LLM 推理框架

**因素分解：**
```
1. 推理速度 — 决定用户体验（例如：tokens/sec > 10 为可用）
   - 边界：tokens/sec > 10 为可用
   - 优先级：高
   - 影响：速度慢 → 无法实时交互

2. 模型兼容性 — 决定可用模型范围（例如：支持 GGUF / AWQ / FP16 等格式）
   - 边界：支持 GGUF / AWQ / FP16 等格式
   - 优先级：高
   - 影响：兼容性差 → 可用模型少

3. 硬件利用率 — 决定性能发挥（例如：GPU 利用率 > 80%）
   - 边界：GPU 利用率 > 80%
   - 优先级：中
   - 影响：利用率低 → 浪费硬件

4. 部署复杂度 — 决定维护成本（例如：一键部署 vs 手动编译）
   - 边界：一键部署 vs 手动编译
   - 优先级：中
   - 影响：复杂度高 → 维护困难

5. 社区活跃度 — 决定问题解决速度（例如：GitHub stars > 1000, 近期有更新）
   - 边界：GitHub stars > 1000, 近期有更新
   - 优先级：低
   - 影响：社区小 → 问题难解决
```

## Reviewer 质检标准

- 是否覆盖了任务目标的主要影响因素；
- 是否区分已知、可推导和未知；
- 是否存在把关键未知条件直接假定掉的情况；
- 每个后续研究问题是否能追溯到一个具体空缺；
- 阶段 02 能否直接依据本工件开始搜集资料。
- 未验证事实是否都明确标注为假设/空缺，而不是无来源的确定性断言。
- 阶段 02 的研究路径是否足够具体，但没有把阶段 02 的实际证据伪装成阶段 01 结果。
- 预算应以用户给出的总预算为约束；若讨论 GPU 预算视角，必须明确它只是待验证的下游分配问题，不得把未经阶段 02 成本核验的 GPU 预算写成阶段 01 结论。

如果上述内容已经足够让阶段 02 立即开始研究，即使仍有待验证空缺，也应判定 `pass`，并把这些空缺交给阶段 02，而不是继续要求阶段 01 细化。

如果因素分解不完整，repair_stage 写 01。
