# Prompt-first 通用 Reviewer 规则

> **适用声明（通道无关 · 成璐 m00201 批准）**：1-loop（01→04.5）与 arena 通道可用性无关——arena 执行或回退本地自答，**6 阶段一个不少**，回退只降执行通道（见 `sop/arena-loop-pipeline.md` §0）。

## 工作协议

1. 先读当前阶段规则、任务、当前工件；**只做当前阶段**，不提前完成后续阶段。
2. 实际完成的工作、来源、观察、产出、不确定性必须写进当前工件；工件完成即停。审阅流程（独立审阅者，如 subagent）自动审阅，Commander 不必主动启动。
4. **Reviewer 回执是阶段推进的唯一质量输入**；Commander 不得用自己判断覆盖 revise。
5. revise 后修当前阶段或回退到 Reviewer 指定的更早阶段，修完重新 review；**只有当前版本返回 pass 才能写完成标记**。
6. **阶段 Markdown 不得手写 `stage-review` 块、`verdict: pass/revise` 或伪造回执**——这些只由审阅流程写入 `latest-review.md` 与 review history；阶段工件只记工作、来源、证据、不确定性。

## 循环防护（环境无关）

- **简单任务**（代码生成、工具调用、分类、摘要、格式整理）直接回答，不要思考；**复杂任务**（多步研究、架构决策、数学证明）可思考但必须有明确答案，超长仍无结论则停止并回答。
- **禁止**循环思考、重复推理、无结论的思考；**空响应/截断**时降低输出长度，直接给最简答案。
- **不得硬编码** `enable_thinking` / `reasoning-budget` 等特定模型参数；输出异常时自行采取通用防护，并把实际模型、服务限制、异常记进工件。

操作示例见 `examples/00-common-review-examples.md`。

## 判定原则（revise 触发条件）

- 不能只检查标题格式，要检查**任务目标是否真的被覆盖**。
- 关键缺口、关键事实无证据、来源间矛盾未解释、不确定是否达标 → **必须 revise**。
- 区分「阻塞后续行动的实质缺陷」与「不阻塞的措辞/重复/排版问题」；**只有前者触发 revise**；已覆盖本阶段目标、明确未解决条件、下一阶段可据此开始 → 判 `pass`。
- 具体对象、候选名称、搜索词、来源类型、研究动作**可以**出现在分解阶段，只要标为「待验证/研究目标」；不得因其具体而要求抽象化或删除，也不得把「不要提前伪造后续阶段结果」误读为「不能提出后续研究对象或启动研究」。
- 缺口本就是后续阶段的正常输入且工件已写清缺口/影响/研究入口 → 保留缺口并推进，不做无限修辞迭代。
- 发现问题必须写明**位置、影响、修复动作**；需重新搜集输入时，`repair_stage` 写需要补输入的阶段，不是当前整理阶段。

## Reviewer 回执格式

审阅报告最后必须包含唯一路由块：

<!-- stage-review
verdict: pass
或
verdict: revise
repair_stage: 当前阶段或更早阶段编号；pass 时写 none
-->

块外必须保留具体问题、证据缺口、判断依据、修复建议。
